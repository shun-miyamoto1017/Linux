## まずこれだけ

| 用語 | 何か |
|:--|:--|
| **SSD**（Solid State Drive） | **記憶装置そのもの**。実際にはフラッシュメモリに属する機器 |
| **AHCI** | **SATA を活かすためのインターフェース仕様**（インテルが策定） |
| **NVMe**（NVM Express） | **PCI Express バスから SSD に接続するための規格** |
| **Trim** | **消去されていない領域を事前に消しておき、速度低下を緩和する仕組み** |
| **`fstrim`** | **Linux で Trim を行うコマンド** |

**押さえる 3 点**

| 論点 | 結論 |
|:--|:--|
| **SSD の弱点は** | **書き込み消去による素子の劣化（寿命）**。衝撃には**むしろ強い** |
| **NVMe とは** | **PCI Express バスから SSD に接続するための規格**。SATA/AHCI がボトルネックになったから生まれた |
| **Trim を行うコマンド** | **`fstrim`**。`discard` や `ssdisk` というコマンドは**存在しない** |

**デバイスファイルの読み方**

```text
  /dev/nvme0n1p1
       │    │ │
       │    │ └─ p = パーティション番号（1 から）
       │    └─── n = ネームスペース ID（1 から）
       └──────── nvme の直後の数字 = デバイスの連番（0 から）
```

## SSDとは何か

**SSD（Solid State Drive）は、ディスク、という名前がついていますが、
実際にはフラッシュメモリに属する機器**です。
**ハードディスクのようなディスクドライブを模した動きをすることから、ディスク、という名称になっています。**

```text
  HDD   円盤が回り、ヘッドが動いて読み書きする    … 機械
  SSD   フラッシュメモリに電気的に読み書きする    … 半導体
        ↑ ディスクは回っていないが「ドライブ」と呼ぶ
```

**中身は半導体なのに、OS からは HDD と同じように見える**——これが SSD の要点です。
**だから `mkfs` も `mount` も `fstab` も、HDD とまったく同じ**に使えます。

## 長所と短所

**長所**

| 長所 | 内容 |
|:--|:--|
| **ランダムアクセス性能に優れる** | **ヘッドの移動が無い**ので、バラバラの位置を読んでも速い |
| **省電力・静音** | 機械的な駆動部分が無い |
| **非接触メディアであるため、耐振動・衝撃性が高い** | **落としても壊れにくい** |

**短所**

| 短所 | 内容 |
|:--|:--|
| **高価**（ただし、飛躍的に価格は下がってきている） | 容量あたりの単価は HDD より高い |
| **書き込み消去により素子が劣化するため、寿命がある**（ただし、現実的にはあまり大きな制約にはなっていない） | **書き換え回数に上限がある** |
| **故障時のデータ復旧の技術はハードディスクのようには確立されていない** | 壊れたら諦めることになりやすい |

**説明の正誤を切る**

| 説明 | 正誤 | 理由 |
|:--|:-:|:--|
| **NVMe という新しい接続規格がある** | **○** | **PCI Express バスを使う規格** |
| 衝撃に弱い | ✕ | **非接触メディアなので耐振動・衝撃性が高い**（弱いのは HDD） |
| ランダムアクセスは HDD より遅い | ✕ | **SSD の最大の長所がランダムアクセス性能** |
| AHCI 接続で実用十分な速度が得られる | ✕ | **次第にインターフェイスがボトルネックとなってきている**。だから NVMe が生まれた |

**「SSD の弱点」を問われたら書き換え寿命**、**「SSD の強み」を問われたらランダムアクセス**、
と押さえておけば取り違えません。

**寿命は SMART で見る**

```bash
$ sudo smartctl -A /dev/sda | grep -i -E "wear|percent"   # 消耗度を見る
```

詳しくは [ディスクの健全性監視_SMART](./ディスクの健全性監視_SMART.md) にあります。

## Trimと速度低下

### なぜ遅くなるのか

**SSD の性能を発揮するために必要な項目の一つに、Trim というものがあります。**

**SSD に使用されるフラッシュメモリの特徴として、書き込みできる領域は、
明示的に消去されないと使用する段階になって消去動作を行ってから書き込みになるため、
このことが、使用するにしたがって速度低下を引き起こす可能性を持っています。**

```text
  【新品のとき】
    空の領域に そのまま 書ける              → 速い

  【使い込んだあと】
    「削除済み」フラグは立っているが、実際には消えていない
        ▼
    書く前に まず消す 必要がある
        ▼
    消去 → 書き込み の 2 手間になる          → 遅い
```

**Trim は、この速度低下を引き起こす明示的に消去されていない領域に対し、
事前に消去を行い、速度低下を緩和するように働くものです。**

```text
  ファイルを削除しても、SSD は「その領域が不要になった」ことを知らない
        ▼
  OS が Trim で「この領域はもう使っていない」と SSD に伝える
        ▼
  SSD が空き時間に 先回りして 消しておく
        ▼
  次に書くとき、すぐ書ける                    → 速度が戻る
```

### fstrim で明示的に消す

**Linux では、Trim を行うコマンドとして `fstrim` があります。**

```text
fstrim [オプション] マウントポイント
```

```bash
$ sudo fstrim /                        # ルートに対して Trim を実行する
```

**引数はデバイスではなくマウントポイント**です。ここが `hdparm` などと違います。

| オプション | 意味 |
|:--|:--|
| **`-a`、`--all`** | **マウントされているファイルシステムすべてに実行する** |
| **`-v`、`--verbose`** | **解放したバイト数を表示する** |
| `-A`、`--fstab` | `/etc/fstab` に書かれたものに実行する |
| `-n`、`--dry-run` | 実際には Trim せず、動作だけ確認する |
| `-m`、`--minimum` | この大きさ未満の領域は対象にしない |

**`fstrim 2.39.3` の `--help` を実機で確認した抜粋**

```text
 -a, --all                trim mounted filesystems
 -A, --fstab              trim filesystems from /etc/fstab
 -v, --verbose            print number of discarded bytes
 -n, --dry-run            does everything, but trim
```

```bash
$ sudo fstrim -av                      # 全ファイルシステムを Trim して結果を表示する
/boot: 512 MiB (536870912 bytes) trimmed
/: 40 GiB (42949672960 bytes) trimmed
```

**存在しないコマンド**

| 見かける名前 | 実際は |
|:--|:--|
| **`discard`** | **そういうコマンドは無い**。`discard` は**マウントオプションの名前** |
| **`ssdisk`** | **存在しない** |
| `fdisk` | **領域確保、フォーマットを行うコマンド**。Trim とは無関係 |

**`discard` は「コマンド」ではなく「マウントオプション」**——ここが引っかけどころです。

### discard マウントオプション

**Trim には 2 つのやり方**があります。

| やり方 | 仕組み | 向き不向き |
|:--|:--|:--|
| **定期実行**（推奨） | **`fstrim` を cron や systemd タイマーで定期的に走らせる** | **まとめて処理するので負荷が読める** |
| **連続実行** | **`discard` マウントオプション**。**ファイルを消すたびに即 Trim** | **削除のたびに待ちが入る**ので、書き込みが多い環境では不利 |

```text
/dev/sda1  /data  ext4  defaults,discard  0 2      ← 削除のたびに Trim（非推奨のことが多い）
```

**現在の多くのディストリビューションは `fstrim.timer` で週 1 回実行する**のが既定です。

```bash
$ systemctl list-timers | grep fstrim    # 定期実行の設定を確認する
$ systemctl status fstrim.timer          # 有効になっているか見る
```

**`discard` を付けるより、タイマーに任せるほうが安全**——これが今の定石です。

マウントオプションの書き方は [fstabの書き方](./fstabの書き方.md) にあります。

## 接続規格の移り変わり

**ハードディスクの置き換えとしての側面が重視されたこともあって、
インターフェイスは SATA を使用する AHCI によるものが主流として普及しましたが、
次第にインターフェイスがボトルネックとなってきています。**

**こうした背景から、PCI Express バスを使った NVMe という新しい規格が生まれてくることになりました。**

```text
  SSD を HDD の置き換えとして使う
        ▼
  SATA ＋ AHCI で繋ぐ（既存の仕組みをそのまま使える）
        ▼
  SSD が速すぎて SATA(600MB/s) が足りない ← ボトルネック
        ▼
  PCI Express に直結する NVMe が登場
```

**NVM Express（NVMe）は PCI Express バスから SSD に接続するための規格**です。
**PCI Express Gen3 4x という条件下で、フラッシュメモリストレージに最適化されたバスとして、規格されています。**

**3 つの略語を取り違えない**

| 略語 | 何か | 何のためのものか |
|:--|:--|:--|
| **AHCI** | **SATA のためのインターフェース仕様** | **SATA 本来の性能を出すため**。インテルが策定 |
| **NVMe** | **PCI Express バスから SSD に接続するための規格** | **SATA では足りない速度を出すため** |
| **SSD** | **記憶装置そのもの** | **規格ではない** |
| **UEFI** | **旧来のファームウエアである BIOS に代わる新しいファームウエア** | **ストレージ規格ではない** |

**「PCI Express バスから SSD に接続するための規格は」と問われたら NVMe**、
**「SATA の仕様を定義したインテルの規格は」と問われたら AHCI** です。

**速度の目安**

| 接続 | 帯域の目安 |
|:--|:--|
| ATA（Ultra DMA） | 133MB/s |
| SATA III | 600MB/s |
| **NVMe（PCIe Gen3 x4）** | **約 4GB/s** |

AHCI と SATA の関係は
[接続規格とデバイスファイル](./接続規格とデバイスファイル.md) にもあります。

## NVMeのデバイスファイル

**nvme デバイスは複数のデバイス名があります。**

**nvme の直後の 0 から始まる数字がデバイスの連番であり、
その後の `n` は 1 から振られるネームスペース ID、
`p` がやはり 1 から振られるパーティション番号となります。**
**パーティションの特定などの際、注意が必要です。**

```bash
$ ls -l /dev/ | grep nvme*             # NVMe 関連のデバイスファイルを一覧する
crw-------. 1 root root  246, 0 5月 26 12:44 nvme0       ← キャラクタデバイス名
brw-rw----. 1 root disk  259, 0 5月 26 12:44 nvme0n1     ┐
brw-rw----. 1 root disk  259, 1 5月 26 12:44 nvme0n1p1   │ ブロックデバイス名
brw-rw----. 1 root disk  259, 2 5月 26 12:44 nvme0n1p2   │
brw-rw----. 1 root disk  259, 3 5月 26 12:44 nvme0n1p3   ┘
                              ↑ p がパーティション
```

| 名前 | 何を指すか | 種類 |
|:--|:--|:--|
| **`/dev/nvme0`** | **コントローラそのもの**（管理コマンド用） | **キャラクタデバイス**（`c`） |
| **`/dev/nvme0n1`** | **1 つ目のネームスペース**（ディスク全体に相当） | **ブロックデバイス**（`b`） |
| **`/dev/nvme0n1p1`** | **その中の 1 番目のパーティション** | ブロックデバイス |

**「NVMe デバイスとして正しいものをすべて選べ」という問いの答えは
`/dev/nvme0` と `/dev/nvme0n1p1` の 2 つ**です。

| 選択肢 | 正誤 |
|:--|:-:|
| **`/dev/nvme0`** | **○**（キャラクタデバイス名） |
| **`/dev/nvme0n1p1`** | **○**（ブロックデバイス名） |
| `/dev/sda` | ✕（**SATA 等のデバイス名**） |
| `/dev/hda` | ✕（**IDE 等のデバイス名**） |

**`sd` 系との対応**

```text
  SATA :   /dev/sda      /dev/sda1
             ディスク      パーティション

  NVMe :   /dev/nvme0n1  /dev/nvme0n1p1
             ネームスペース  パーティション
             ↑ ここが「ディスク全体」に相当する
```

**`nvme0n1` の次のディスクは `nvme1n1`** です（`nvme0n2` ではありません）。

```text
  1 台目の NVMe →  /dev/nvme0n1
  2 台目の NVMe →  /dev/nvme1n1
  3 台目の NVMe →  /dev/nvme2n1
```

**ネームスペースは 1 台の SSD を論理的に分割する仕組み**で、
**通常のサーバでは `n1` しか出てきません。**

## 手を動かして確かめる

**① Trim に対応しているか確認する**

```bash
$ sudo hdparm -I /dev/sda | grep -i trim    # ドライブから直接、TRIM 対応を調べる
   *    Data Set Management TRIM supported (limit 8 blocks)
   *    Deterministic read ZEROs after TRIM
```

**`-I`（大文字）はドライブから直接詳細情報を得るオプション**です。
**SSD は比較的新しい技術なので、古いフォーマットの `-i`（小文字）では全ての情報は取得できません。**
詳しくは [hdparmによるディスクパラメータ](./hdparmによるディスクパラメータ.md) にあります。

**② Trim を実行してみる**

```bash
$ sudo fstrim -v /                     # 解放されたバイト数が出る
/: 40 GiB (42949672960 bytes) trimmed
$ sudo fstrim -n -v /                  # 実際には実行せず動作だけ確認する
```

**`-n`（dry-run）で先に確認**してから実行するのが安全です。

**③ 定期実行の設定を見る**

```bash
$ systemctl list-timers --all | grep fstrim   # タイマーの有無と次回実行時刻
$ cat /usr/lib/systemd/system/fstrim.timer    # 既定の設定を見る
```

**④ NVMe の構造を見る**

```bash
$ lsblk -o NAME,TYPE,SIZE,TRAN         # TRAN に nvme と出るか確認する
$ sudo nvme list                       # NVMe デバイスの一覧（nvme-cli が要る）
```

**⑤ 回転するディスクかどうかを見る**

```bash
$ cat /sys/block/sda/queue/rotational  # 1 なら HDD、0 なら SSD
0
```

**`rotational` が `0` なら SSD**——カーネルがそう判定しています。

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| **使い込んだ SSD が遅くなった** | **Trim が行われていない** | **`fstrim -av`** を実行する。タイマーを有効にする |
| **`fstrim` が `the discard operation is not supported`** | **Trim 非対応か、仮想化層が通していない** | **`hdparm -I` で対応を確認**する |
| **`fstrim /dev/sda1` が失敗する** | **引数はマウントポイント** | **`fstrim /data`** のように書く |
| **`discard` というコマンドを探した** | **コマンドではなくマウントオプション** | **`fstrim`** を使う |
| **`hdparm -i` で Trim 対応が分からない** | **`-i` は古いフォーマット** | **`-I`（大文字）**を使う |
| **`/dev/nvme0n2` を探した** | **2 台目は `nvme1n1`** | ネームスペースではなくデバイス番号が増える |
| **`discard` を付けたら削除が遅くなった** | **削除のたびに Trim が走る** | **外して `fstrim.timer` に任せる** |
| **SSD は衝撃に弱いと思っていた** | **非接触なので逆に強い** | 弱いのは HDD |

## クラウド実務メモ

**① EBS では Trim をあまり気にしなくてよい**

**EBS はクラウド側で仮想化されたブロックストレージ**なので、
**物理的なフラッシュの消去動作は AWS 側が面倒を見ています。**

| ストレージ | Trim を気にするか |
|:--|:--|
| **EBS（gp3 / io2 など）** | **ほぼ不要**。ただし `fstrim` を実行すると**未使用領域が解放されてスナップショットが小さくなる**ことがある |
| **インスタンスストア（NVMe SSD）** | **効く**。長時間動かすインスタンスでは定期 Trim が有効 |
| **ローカルの物理 SSD**（オンプレ） | **効く**。`fstrim.timer` を必ず有効にする |

```bash
$ sudo fstrim -av                      # スナップショット取得前に実行すると容量が減ることがある
```

**② Nitro 世代では EBS も NVMe として見える**

**コンソールで `/dev/sdf` としてアタッチしても、OS からは `/dev/nvme1n1`** です。

```bash
$ lsblk -o NAME,SIZE,MODEL             # MODEL に Amazon Elastic Block Store と出る
NAME        SIZE MODEL
nvme0n1       8G Amazon Elastic Block Store
nvme1n1     100G Amazon Elastic Block Store
```

**どの EBS ボリュームがどの `nvme` かを対応付ける**には、シリアル番号を見ます。

```bash
$ sudo nvme id-ctrl -v /dev/nvme1n1 | grep -i sn   # vol-xxxx がそのまま入っている
sn        : vol0123456789abcdef0
```

**AWS は `/sbin/ebsnvme-id` というツールも提供**しています（Amazon Linux に同梱）。

**③ インスタンスストアは停止で消える**

| ストレージ | 停止・起動で |
|:--|:--|
| **EBS** | **残る** |
| **インスタンスストア（NVMe）** | **消える**。デバイス名も変わり得る |

**`/etc/fstab` に書くなら `nofail` 必須**です。書かないと起動が止まります。

```text
/dev/nvme1n1  /scratch  ext4  defaults,nofail,discard  0 0
```

**インスタンスストアは消えて当然の領域**なので、`discard` を付けても実害が小さい場所です。

**④ 性能が出ないときの切り分け順**

```text
  ① EBS のボリュームタイプと IOPS/スループットの設定を見る   ← まずここ
  ② インスタンスタイプの EBS 帯域上限に当たっていないか見る
  ③ ファイルシステムのマウントオプション（noatime など）を見る
  ④ それでも足りなければ複数ボリュームを RAID0 で束ねる
```

**物理 SSD の Trim を疑うのは、オンプレかインスタンスストアのとき**です。
**EBS で「SSD だから遅くなった」はまず起きません。**

RAID0 で束ねる話は
[RAIDの基礎とレベル](./RAIDの基礎とレベル.md) にあります。
