## ファイルシステムという仕組み

**ファイルシステムとは、記録デバイス上に構築される、
ファイルやディレクトリを単位としてデータを管理するための仕組み**です。

**用語を取り違えない**

Ping-t は**この 5 つを並べて出題**します。**どれが「区画」でどれが「仕組み」か**で切り分けます。

| 用語 | 何を指すか |
|:--|:--|
| **パーティション** | **ハードディスクの記録領域を複数に分けた、それぞれの領域**。「切り分けられた領域そのもの」 |
| **ファイルシステム** | **各パーティションの上に作られ、その領域をファイルやディレクトリという単位で扱うための論理的な仕組み**。領域そのものの名前ではない |
| **i ノード** | **ファイルシステムにおいて、記録デバイス上の物理的なデータ位置と各ファイルを対応づける情報** |
| **ディレクトリ** | **ファイルシステムにおいて、内部にファイルやディレクトリを含むことができる階層構造の単位**。Windows の「フォルダ」に相当する |
| **MBR** | **ハードディスクの先頭部分にあり、システムのブートのために利用される特別な記録領域**。ここにブートローダがインストールされる |

```text
  ハードディスク
   ├─ MBR（先頭 512 バイト。ブートローダが入る特別な領域）
   ├─ パーティション1 ─→ その上に ファイルシステム(ext4) を作る
   │                          └─ ディレクトリ / ファイル / i ノード
   └─ パーティション2 ─→ その上に ファイルシステム(xfs) を作る
```

**「各パーティション上に、ファイルシステムが作られる」**——この上下関係が要点です。
MBR については [BIOSとUEFI](../05_起動プロセスとカーネル/BIOSとUEFI.md) を参照してください。

### ルートファイルシステムと複数マウント

**Linux ではディレクトリのルート（`/`）とするファイルシステムを「ルートファイルシステム」といい、
この中の指定の位置に他のファイルシステムをマウントすることで、
複数のファイルシステムからなるディレクトリ構造を作り、統一的にアクセスすることを可能にしています。**

```text
  /            ← ルートファイルシステム（ext4）
  ├─ /boot     ← 別のファイルシステム（ext4）をマウント
  ├─ /home     ← 別のファイルシステム（xfs）をマウント
  ├─ /tmp      ← tmpfs をマウント
  ├─ /proc     ← proc をマウント
  └─ /media/cdrom ← CD-ROM（iso9660）をマウント
```

**押さえておく 3 点**

| 言われ方 | 正しいか |
|:--|:--|
| **ルートファイルシステム内に複数のファイルシステムをマウントできる** | **○** |
| ひとつの標準のファイルシステムに統一されている | **✕**。`ext2` / `ext3` は標準的だが**統一されてはいない**。`xfs` なども使える |
| ハードディスクによって、利用できるファイルシステムが決まっている | **✕**。**通常のファイルシステムは記録デバイスに依存せず利用できる**（ただし CD-ROM 用の `iso9660` のように、**デバイスと密接な関わりを持つものは存在する**） |

マウントの操作そのものは [マウントとアンマウント](./マウントとアンマウント.md) にあります。

### VFS 仮想ファイルシステム

**VFS（Virtual File System ／ 仮想ファイルシステム）は、
Linux で異なるファイルシステムの違いを吸収するために用いられる仕組み**です。

```text
  ユーザプログラム
        │  システムコール（open / read / write …）
        ▼
      VFS        ← ここで違いを吸収する
        │
   ┌────┼────┬────────┐
   ▼    ▼    ▼        ▼
  ext4  xfs  btrfs   nfs
```

| 論点 | 内容 |
|:--|:--|
| **名前の由来** | **実際のファイルシステムではなく、統一されたインタフェースで扱える仮想的な仕組み**なので Virtual File System |
| **主たる目的** | **複数の異なるファイルシステムの違いを吸収する** |
| **どう呼び出されるか** | **ユーザプログラムはシステムコールを使って VFS に指示を出す** |
| **何ではないか** | **Linux で利用できるファイルシステムのひとつではない**。**固有のファイルシステムの名前ではない** |

**`VFS` を `ext4` や `xfs` と同じ並びのものだと思うのが典型的な誤り**です。
**VFS はそれらの「上」にいる仲介役**で、`mkfs -t vfs` のようなものは存在しません。

**システムコールは OS の機能を呼び出すための仕組み**です。
実際のプログラムでは、用意されているライブラリがシステムコールを使う部分を代行してくれるため、
**システムコールを意識することは少ない**のですが、**内部的にはファイル操作の際にこれが行われています。**

**VFS があるおかげで、`cat` も `cp` も、相手が ext4 でも XFS でも NFS でも同じように動きます。**

### 利用できるファイルシステムを調べる

**現在のシステムがサポートしているファイルシステムの種類の一覧は `/proc/filesystems`** で分かります。

```bash
$ cat /proc/filesystems                              # サポートしている種類の一覧を見る
nodev   devpts
        ext2
        ext3
        ext4
nodev   ramfs
nodev   tmpfs
nodev   binfmt_misc
        reiserfs
        xfs
```

| 見るところ | 意味 |
|:--|:--|
| **右側の名前** | **`/etc/fstab` や `mount -t` に書ける名前**がそのまま並んでいる |
| **`nodev`** | **実体のブロックデバイスを必要としない**ファイルシステム（`tmpfs` / `proc` など） |
| （何も無い） | ブロックデバイスの上に作るファイルシステム |

**まぎらわしい 4 つのファイルを整理する**

| ファイル | 何が書かれているか |
|:--|:--|
| **`/proc/filesystems`** | **システムで利用可能なファイルシステムの種類の一覧** |
| **`/etc/fstab`** | **マウントの設定**（これから、どうマウントするか） |
| **`/etc/mtab`** | **現在マウントされているファイルシステムの一覧** |
| **`/proc/mounts`** | 同上（`/etc/mtab` と同等の情報） |
| `/etc/mount.conf` | **存在しない** |

**「利用可能な種類」と「いまマウントされているもの」は別物**です。
`/etc/fstab` と `/etc/mtab` の違いは [fstabの書き方](./fstabの書き方.md) も参照してください。

## Linux で主に使われるファイルシステム

| ファイルシステム | 説明 |
|:--|:--|
| **ext2** | **以前の Linux で標準的に使用されていた規格**。ジャーナリング機能を持たない |
| **ext3** | **ext2 の後継**／**ジャーナリングファイルシステム** |
| **ext4** | **ext3 の後継**／**ジャーナリングファイルシステム** |
| **XFS** | **シリコングラフィクス社（SGI）が開発した高性能なファイルシステム**／**ジャーナリングファイルシステム**／**動的 inode**／元々は **IRIX** という UNIX 系 OS のためのものだったが、移植が進んだ結果、今では Linux でもほとんどすべてのディストリビューションで利用できる |
| **JFS** | **IBM が開発**／**ジャーナリングファイルシステム**／**動的 inode** |
| **Btrfs** | 比較的新しく高機能。マルチデバイス・サブボリューム・スナップショット・圧縮。**ZFS を参考として開発された** |
| **ZFS** | **Sun Microsystems が Solaris の `UFS` の後継として開発を開始**し、**現在は Oracle が管理**。ソフトウェア RAID やスナップショットを比較的簡単に扱える。**btrfs が参考としたファイルシステム** |
| **tmpfs** | **メモリ上に作成できる一時ファイルシステム**（RAM ディスク） |
| **iso9660** | CD-ROM / DVD-ROM 用の標準規格 |
| **FAT / vfat** | FAT の拡張仕様。**フラッシュメモリ等で使われる**／Windows では古いファイルシステム／**UEFI の ESP や ISOLINUX のイメージでも使われている** |
| **NTFS** | **近年の Windows で使われる**ファイルシステム |
| **nfs** | **ネットワークファイルシステム**。物理的な記憶装置上に構成するものではないが、便宜上ファイルシステムの一種として扱われる |
| **swap** | **物理メモリのスワップ先**。厳密にはファイルシステムではない（[スワップ領域](./スワップ領域.md)） |

**開発元をセットで覚える**

```text
XFS … シリコングラフィクス社（SGI）
JFS … IBM
ZFS … Sun Microsystems（Solaris 用）→ 現在は Oracle が管理
ext系 … Linux コミュニティ（ext2 → ext3 → ext4 と代を重ねている）
```

「**X**FS は SGI」「**J**FS は IBM」と、頭文字と社名を並べて覚えると混同しません。
**`ZFS` は「Oracle が使うファイルシステム」**として問われます。
**`XFS` と 1 文字違い**なので、**社名とセット**で覚えておくと取り違えません。

### 世代と継承の関係

**「何の後継か」「何を参考にしたか」がそのまま問われます。**

```text
  UFS（Solaris）
     └─▶ ZFS（Sun → Oracle）
              └─▶ btrfs（ZFS を参考として開発。スナップショットを持つ）

  ext2（ジャーナリング無し）
     └─▶ ext3（ext2 にジャーナリング機能を加えたもの）
              └─▶ ext4（ext3 の後継。大容量 1EiB をサポート）
```

| 問われ方 | 答え |
|:--|:--|
| **Oracle が使用するファイルシステムで、btrfs が参考としたもの** | **ZFS** |
| **ZFS を参考として開発され、スナップショット機能を持つもの** | **btrfs** |
| **Linux で最も標準的なファイルシステムの後継で、大容量（1EiB）をサポートするもの** | **ext4** |
| **ext2 にジャーナリング機能を加えたもの** | **ext3** |
| **Linux で標準的に使われ、ジャーナリング機能を持つもの** | **ext3**（`ext2` は持たない／`xfs` は「標準的」とは言わない） |
| **メモリ上に配置できる特殊なファイルシステム** | **tmpfs** |
| **近年の Windows OS で使われているもの** | **ntfs** |
| **CD-ROM に使われているもの** | **iso9660** |

**`ext2` は `ext3` より数字が小さい分、機能が少ない（ジャーナリングが無い）**と覚えると迷いません。

> **`xfs` にスナップショット機能はありません。**
> **`ntfs` にスナップショット機能はありますが、開発中のファイルシステムではありません。**
> **`nfs` はネットワーク越しにディレクトリをマウントする仕組み**なので、
> **`nfs` 自体がスナップショット機能を持つことはありません。**

### ジャーナリングとは

**ジャーナリングとは、更新履歴をジャーナル（ログ）に記録しておく機能**です。

```text
① これから書く内容をジャーナルに記録する
        ↓
② 実際にファイルシステムへ書き込む
        ↓
③ ジャーナルの記録を消す
```

停電やクラッシュで ② の途中で止まっても、**ジャーナルを見れば「何をしようとしていたか」が分かる**ので、
再起動時に整合性を素早く回復できます。

| | ジャーナリングなし（ext2） | ジャーナリングあり（ext3 以降） |
|:--|:--|:--|
| 障害後の復旧 | **全体を検査**するため非常に時間がかかる | **ジャーナルを見るだけ**なので速い |
| データ破損のリスク | 高い | 低い |
| 書き込みの手間 | 少ない | ジャーナルの分だけ増える |

**ext2 が現在ほとんど使われない理由がこれです。**
ジャーナリング機能がないため、障害時の復旧に時間がかかり、破損のリスクも高くなります。

### 動的 inode とは

**inode** は、ファイル 1 つにつき 1 つ割り当てられる**管理情報の入れ物**です。
権限・所有者・サイズ・タイムスタンプ・データの位置などを持っています。

| | 静的 inode（ext2/3/4） | **動的 inode（XFS / JFS / Btrfs）** |
|:--|:--|:--|
| いつ確保するか | **ファイルシステム作成時に総数が決まる** | **必要になったときに作られる** |
| 上限 | **決まった数を超えるとファイルを作れない** | **実質的に上限がない** |
| 空き容量があるのに作れない現象 | **起きる** | 起きない |

**ext 系で起きる「容量は空いているのにファイルが作れない」**

```bash
$ df -h /data                       # 容量には余裕がある
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       100G   30G   70G  31% /data

$ touch /data/newfile               # なのに作れない
touch: cannot touch '/data/newfile': No space left on device

$ df -i /data                       # -i を付けると inode の使用率が見える
Filesystem      Inodes  IUsed IFree IUse% Mounted on
/dev/sdb1      6553600 6553600     0  100% /data     ← inode を使い切っている
```

小さいファイルを大量に作るワークロード（メールスプール、セッションファイル、
キャッシュ）で起きます。**`df -h` だけ見ていると原因にたどり着けません。**

**XFS は動的 inode なのでこの問題が起きません。** RHEL 系が既定を XFS にしている理由のひとつです。

**Btrfs も動的 inode です。** そのため「inode の数が制限される」というのは Btrfs の特徴として誤りです。

## ルートファイルシステムに使えるもの

**最上位のルートディレクトリ（`/`）を格納するルートファイルシステムに使用できるのは、
Linux でサポートされており、ブート時にカーネルが認識できるファイルシステム**です。

| ファイルシステム | ルートに使えるか | 理由 |
|:--|:-:|:--|
| **ext3** | **○** | Linux 標準のジャーナリングファイルシステム |
| **ext4** | **○** | 同上。現在の Debian / Ubuntu 系の既定 |
| **XFS** | **○** | 同上。現在の RHEL 系の既定 |
| **Btrfs** | ○ | openSUSE などが既定に採用 |
| **NTFS** | **✕** | **Windows のファイルシステム**。Linux から読み書きはできるが、ルートには使えない |
| **iso9660** | **✕** | **CD-ROM 用で読み取り専用**。書き込みができないためルートにできない |
| **vfat** | ✕ | **パーミッションや所有者の概念がない**ため、Linux のルートには使えない |
| **tmpfs** | ✕ | **メモリ上なので再起動で消える** |

**判断の軸は 3 つです**

```text
① 書き込めるか            … iso9660 は読み取り専用なので不可
② パーミッションを保持できるか … vfat は権限も所有者も持てないので不可
③ カーネルが起動時に読めるか   … NTFS は標準では起動対象にならない
```

### 実際に推奨されるのは ext4 と XFS

**「使える」ものの中でも、実際に推奨されるのはさらに絞られます。**

**Linux の起動に必要なファイルやディレクトリを持つルートファイルシステムについては、
何を使用してもいいというわけにはいきません。
起動時のファイルシステムチェックや、適切なアクセス権が付与されていることなど、
重要な機能をサポートするファイルシステムを使うことが推奨されます。**

**現在、多くのディストリビューションが既定のルートファイルシステムに使っているもの**

| ファイルシステム | 採用しているディストリビューション |
|:--|:--|
| **`ext4`** | **Red Hat Enterprise Linux 6、Ubuntu など** |
| **`XFS`** | **Red Hat Enterprise Linux 7 およびその派生 OS**（CentOS、Oracle Linux など） |

**他の OS 向けに開発されたものは推奨されません。**

| ファイルシステム | どの OS のものか |
|:--|:--|
| **`HFS`** | **macOS** |
| **`NTFS`** | **Windows NT、およびその後の NT 系 Windows**（2000 / XP / 7 / 8 / 10 など） |
| **`HPFS`** | **IBM が開発した OS/2**（現在はほぼ使われていない） |

**`ext3` や `Btrfs` もルートファイルシステムとして使用できます。**
**ただし、古いファイルシステムを採用する場合はデメリットにも留意が必要**です。

> **`ext3` は基本的に、2038年1月19日3時14分7秒以降のタイムスタンプをサポートしていません。**
> これは**日付時刻を32ビットで管理するシステム全てに存在する「2038年問題」**の影響です。
> **`ext4` は 2038 年以降も扱えます。**

**まとめると**

```text
  推奨            ext4 / XFS
  使えるが注意    ext3（2038年問題）／ Btrfs（用途次第）
  使えない        NTFS / HFS / HPFS / iso9660 / vfat / tmpfs
```

**補足 … 「読み書きできる」と「ルートにできる」は別です**

Linux は NTFS も vfat も**マウントして読み書きできます**。
しかしルートファイルシステムには、
**ユーザ・グループ・パーミッション・シンボリックリンク**といった Unix の仕組みが必要です。
vfat にはこれらが無いため、`/etc/shadow` のような権限に依存するファイルを置けません。

## Btrfs は別ノートにある

**Btrfs（B-tree File System）は比較的新しく高機能な Linux のファイルシステム**で、
**マルチデバイス対応・サブボリューム・スナップショット・圧縮**を持ちます。

**`btrfs` コマンドの操作と、ext からの変換**は分量があるため、
[Btrfsとサブボリューム](./Btrfsとサブボリューム.md) にまとめました。

| 知りたいこと | どちらのノートか |
|:--|:--|

## tmpfs メモリ上のファイルシステム

**`tmpfs` はメモリ上に作成できる一時ファイルシステムです。**

**ファイルを HDD ではなくメモリ上に置くことで高速にアクセスすることができ、
システム再起動時にファイルは消去されます。一時的な記憶領域として利用します。**

```text
通常のファイルシステム        tmpfs
  ┌──────────┐            ┌──────────┐
  │ ディスク  │            │  メモリ   │
  │（永続）   │            │（揮発）   │
  └──────────┘            └──────────┘
   再起動しても残る          再起動で消える
   遅い                     速い
```

**名前に注意** … 正しくは **`tmpfs`** です。
`tempfs` / `memfs` / `ramfs` という選択肢が並ぶことがありますが、
`tempfs` と `memfs` は**存在しません**（`ramfs` は別物として実在します）。

### RAM ディスクとの違い

**`tmpfs` のサイズは最初にメモリ上に確保されるわけではなく、使用した分に応じて動的に変化するので、
メモリを効率的に使用できます。**

**RAM の一部をストレージとして利用する RAM ディスクと似ていますが、
RAM ディスクはファイルシステムを作成する必要があり固定サイズです。
`tmpfs` はファイルシステムとしてディレクトリにマウントして利用できます。**

| | **tmpfs** | RAM ディスク |
|:--|:--|:--|
| メモリの確保 | **使った分だけ動的に増減** | **最初に固定サイズで確保** |
| `mkfs` が必要か | **不要**（マウントするだけ） | **必要** |
| メモリの効率 | **良い**（使わない分は他に回せる） | 悪い（使わなくても占有し続ける） |
| スワップ | **できる**（使われていないページはスワップへ退避される） | できない |

**補足 … `size=` は「上限」であって「予約」ではありません**

```bash
$ sudo mount -t tmpfs -o size=64M tmpfs /mnt/mytmp   # 上限 64M で作る
$ df -h /mnt/mytmp                                   # 64M と表示される
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            64M     0   64M   0% /mnt/mytmp
```

`df` は 64M と表示しますが、**この時点で消費しているメモリはほぼゼロ**です。
ファイルを置いた分だけ実際のメモリを使います。

**補足 … `size=` を省略すると物理メモリの半分**

カーネル公式ドキュメントによると、`size=` も `nr_blocks=` も指定しない場合、
上限は**物理メモリの半分**になります（`size=50%` と同じ）。

**補足 … スワップへ退避されます**

`tmpfs` の内容は、使われていなければ**スワップ領域へ追い出される**ことがあります
（`noswap` オプションで禁止できます）。
「メモリ上」といっても、常に物理メモリを占有し続けるわけではありません。

### 使い方

```text
mount -t tmpfs [マウントオプション] tmpfs マウントポイント
```

デバイス名の位置に書く `tmpfs` は、**実体のあるデバイスではなく単なるラベル**です。
`none` と書いても動きますが、`df` の表示が分かりにくくなるので `tmpfs` と書くのが慣例です。

**例文** … `/mnt/mytmp` ディレクトリを最大 64M の tmpfs としてマウントする

```bash
$ sudo mkdir /mnt/mytmp                              # マウントポイントを作る
$ sudo mount -t tmpfs -o size=64M tmpfs /mnt/mytmp   # 64M 上限の tmpfs をマウントする
$ df -h                                              # マウントされたことを確認する
Filesystem                Size  Used Avail Use% Mounted on
/dev/mapper/centos-root    14G  6.3G  7.7G  45% /
devtmpfs                  904M     0  904M   0% /dev
tmpfs                     920M  156K  919M   1% /dev/shm
tmpfs                     920M  940K  919M   1% /run
tmpfs                     920M     0  920M   0% /sys/fs/cgroup
/dev/sda1                 497M  204M  293M  42% /boot
tmpfs                     184M   12K  184M   1% /run/user/1000
tmpfs                      64M     0   64M   0% /mnt/mytmp    ← メモリ上で利用できる
```

**主なマウントオプション**

| オプション | 意味 |
|:--|:--|
| `size=値` | 上限サイズ。`64M` のような単位のほか、`50%` のように**物理メモリに対する割合**でも書ける |
| `nr_inodes=値` | 作れるファイル数（inode 数）の上限 |
| `mode=値` | マウントポイントのパーミッション |
| `uid=` / `gid=` | 所有者・グループ |
| `noswap` | スワップへ退避させない |

**`/etc/fstab` に書く場合**

```text
tmpfs  /mnt/mytmp  tmpfs  defaults,size=64M  0 0
```

1 つ目（デバイス名）に `tmpfs` と書きます。実体が無いので UUID はありません。

### 既定でマウントされている tmpfs

**上記の実行例のように、CentOS 7 など一部のディストリビューションでは
`/dev/shm` や `run（/var/run）` などのディレクトリがデフォルトで tmpfs ファイルシステムとして
マウントされています。**

| マウント先 | 用途 |
|:--|:--|
| `/dev/shm` | **共有メモリ**。プロセス間でデータをやり取りするための領域 |
| `/run`（`/var/run`） | **起動中のプロセスの情報**。PID ファイル、ソケットなど。**再起動で消えるべきもの** |
| `/sys/fs/cgroup` | cgroup（リソース制御）のインターフェース |
| `/run/user/<UID>` | ログイン中のユーザごとの一時領域 |

**なぜ tmpfs なのか**

`/run` にある PID ファイルは「**いま動いているプロセスの情報**」です。
再起動したら無効になるので、**むしろ消えてくれたほうが正しい**のです。
ディスクに残っていると、前回起動時の古い PID ファイルが残って起動に失敗する原因になります。

```bash
$ df -h -t tmpfs                     # tmpfs だけを絞り込んで表示する
Filesystem      Size  Used Avail Use% Mounted on
tmpfs           7.9G     0  7.9G   0% /dev/shm
tmpfs           4.0G     0  4.0G   0% /sys/fs/cgroup
```
