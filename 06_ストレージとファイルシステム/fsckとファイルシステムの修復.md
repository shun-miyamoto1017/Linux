## fsck とは何か

**`fsck`（file system check）は、ファイルシステムの整合性を検査し、必要なら修復するコマンド**です。

**ファイルシステムに異常が起こると、ファイルやディレクトリを正常に参照できなくなります。**
たとえば `/home/staff/workfile` というテキストファイルを `cat` で読み出そうとしても、
**ファイルシステムのどの位置に実データが存在するかの情報が不正になると、
`workfile` の中身が参照できなくなります。**

```text
  正常な状態
    ディレクトリエントリ「workfile」 ──▶ i ノード 12 ──▶ 実データ

  壊れた状態（①ディレクトリエントリが消えた）
    （どこからも指されていない） ×      i ノード 12 ──▶ 実データ
        ▲
        └─ このファイルが lost+found 行きになる

  壊れた状態（②i ノードの位置情報が不正）
    ディレクトリエントリ「workfile」 ──▶ i ノード 12 ──▶ ？？？
```

**`fsck` はこの食い違いを見つけて、つじつまを合わせます。**

---

### SMART との違い

**名前が似ていますが、見ている対象がまったく違います。**

| | **`fsck`** | **S.M.A.R.T（`smartctl`）** |
|:--|:--|:--|
| 対象 | **ファイルシステムの中の論理的な辻褄** | **ディスク装置そのものの劣化** |
| いつ見るか | **電源断のあと、起動が止まったとき** | **平常時から継続して** |
| 直せるか | **直せる**（データは失われることがある） | **直せない**（交換するしかない） |
| 仮想ディスクで | **使える** | **物理情報が返ってこない** |

**両方を順に見るのが切り分けの定石**です。

```text
  ① dmesg に I/O error が出ていないか   → 出ていたら装置の問題を疑う
  ② smartctl -H で装置の健全性を見る    → FAILED なら交換が先
  ③ fsck でファイルシステムを直す        → 装置が無事なら、ここで直る
```

**装置が壊れているのに `fsck` をかけると、傷を広げるだけ**になります。
[ディスクの健全性監視 SMART](./ディスクの健全性監視_SMART.md) も参照してください。

---

### 実行前に必ずアンマウントする

**マウント中のファイルシステムに `fsck` をかけてはいけません。**

**検査している最中にも OS が書き込みを続ける**ため、
**直したそばから食い違いが生まれ、かえって壊れます。**

```bash
$ sudo umount /data                     # ① 必ず先にアンマウントする
$ sudo fsck -f /dev/sdb1                # ② それから検査する
$ sudo mount /dev/sdb1 /data            # ③ 終わったらマウントし直す
```

**ルートファイルシステムはアンマウントできない**ので、次のどちらかを取ります。

| 方法 | やり方 |
|:--|:--|
| **起動時に検査させる** | **`touch /forcefcheck`** を作って再起動（古い方式）／`fsck.mode=force` をカーネルパラメータに渡す |
| **別の環境から検査する** | **レスキューメディアや別インスタンスから**そのディスクを繋いで検査する |

**クラウドでは後者が現実的**です。

**読むだけなら安全です**

```bash
$ sudo fsck -n /dev/sdb1                # -n はすべての質問に no と答える＝変更しない
```

**`-n` は何も書き換えません。** 状況を知りたいだけのときはこれを使います。

### 気をつけるべき点は「書き込みが行われないこと」

**ファイルシステムの検査・修復を行う際は、
その最中に対象ファイルシステムに書き込みが行われることがないように注意する必要があります。**
**検査・修復と書き込みがバッティングしてしまうと、
それによりさらにファイルシステムの整合性が取れなくなり、状態が悪化してしまう可能性があります。**

**書き込みが行われないようにする方法は 3 つ**あります。

| # | 方法 | やり方 |
|:-:|:--|:--|
| **①** | **アンマウントしておく** | **`umount` してから検査する**（いちばん確実） |
| **②** | **読み込み専用でマウントしておく** | **マウント時に `ro` マウントオプションを指定する** |
| **③** | **起動時にチェックさせる** | **`/etc/fstab` の `fsck` フラグが 1 以上であることを確認のうえ、`shutdown -F`** |

**③ の書き方**

```bash
$ sudo shutdown -r -F now               # 今すぐ再起動し、次回起動時の fsck を強制する
```

| オプション | 意味 |
|:--|:--|
| `-r` | 再起動する |
| **`-F`** | **次回起動時にファイルシステムチェックを強制する** |

**①②のどちらの方法も採用できない場合**——
つまり**ルートファイルシステムのように外せないもの**——に③を使います。

**注意点として「誤り」になるもの**

| 言われ方 | なぜ誤りか |
|:--|:--|
| `/etc/fstab` に対象ファイルシステムの記述があることを確かめる | **手動で `fsck` を実行する場合は `/etc/fstab` の設定は関係ない**。記述が無いファイルシステムでもチェックできる |
| マウントオプション **`exec`** 付きでマウントされていることを確かめる | **`exec` はバイナリ実行の許可**でチェックとは無関係。**`ro` なら正しい注意点** |
| 対象ファイルシステムが ext2 / ext3 / ext4 であることを確かめる | **XFS などにもチェックコマンドは存在する**。ただし**利用するコマンドが `e2fsck` に限定されているなら正しい注意点**になる |

## fsck の使い方

```text
fsck [オプション] デバイス
```

### よく使うオプション

| オプション | 意味 |
|:--|:--|
| **`-n`** | **すべての質問に「no」と答える。修復せず検査だけ** |
| **`-y`** | **すべての質問に「yes」と答える。確認なしで修復する** |
| **`-f`** | **強制的に検査する**（`clean` と記録されていても飛ばさない） |
| `-p` | 安全に直せるものだけ自動で直す（preen） |
| **`-A`** | **`/etc/fstab` に書かれたものをすべて検査する** |
| **`-t 種類`** | **検査するファイルシステムの種類を指定する** |
| `-r` | 進捗を表示する |
| `-v` | 詳細を表示する |
| `-C` | 進捗バーを表示する |

```bash
$ sudo fsck -f -y /dev/sdb1             # 強制的に検査し、確認なしで直す
```

**`-y` は「何を直したか後から確認できない」**ので、
**まず `-n` で状況を見てから `-y` に進む**のが安全な順番です。

**`-A` と `-t` の組み合わせ**

```bash
$ sudo fsck -A -t ext4                  # fstab に書かれた ext4 をすべて検査する
```

**`-A` は `/etc/fstab` の 6 番目（`fsck` フラグ）の順序に従って検査**します。

---

### 種類ごとの実体

**`fsck` 自体は「窓口」で、実際の処理はファイルシステムごとの専用コマンドが行います。**

| ファイルシステム | 実体のコマンド |
|:--|:--|
| **ext2 / ext3 / ext4** | **`e2fsck`**（`fsck.ext4` は `e2fsck` へのリンク） |
| **XFS** | **`xfs_repair`**（`fsck.xfs` は何もしない） |
| Btrfs | `btrfs check` |
| vfat | `fsck.vfat`（`dosfsck`） |

```bash
$ sudo e2fsck -f -y /dev/sdb1           # ext系を直接指定して検査する
$ sudo xfs_repair /dev/sdb1             # XFS を修復する
```

**`e2fsck` がチェックできるのは ext2 / ext3 / ext4 だけ**です。**XFS はチェックできません。**

| オプション | 説明 |
|:--|:--|
| **`-b`** | **指定のスーパーブロックを使い復元を行う** |
| **`-c`** | **不良ブロックのチェックを行う** |
| **`-p`** | **自動的に不良ブロックを修復する** |

```bash
$ sudo e2fsck -b 32768 /dev/sdb1        # 予備のスーパーブロックを使って復元する
$ sudo e2fsck -c /dev/sdb1               # 不良ブロックを調べる
```

**`-b` は先頭のスーパーブロックが壊れたときの切り札**です。
**ext 系はスーパーブロックの複製を複数持っている**ので、そこから復元できます。

```bash
$ sudo dumpe2fs /dev/sdb1 | grep -i superblock   # 予備スーパーブロックの位置を調べる
```

ファイルシステムごとのコマンド対応は
[ファイルシステム別ユーティリティ](./ファイルシステム別ユーティリティ.md) にまとめてあります。

**`fsck.xfs` は「何もしないで正常終了する」だけ**の特殊な作りです。
**XFS はマウント時にジャーナルを再生するので、起動時の `fsck` が不要**という設計になっています。
**XFS を本当に直すときは `xfs_repair` を明示的に実行**します。

```bash
$ sudo xfs_repair -n /dev/sdb1          # XFS を検査だけする（-n は修復しない）
```

### 知らないオプションは呼び出し先に渡される

**`fsck` は窓口なので、`fsck` 自身が解釈しないオプションは
そのまま呼び出し先のコマンドに渡されます。**

> man 8 fsck:
> **Options which are not understood by fsck are passed to the filesystem-specific checker!**
> （`fsck` が理解しないオプションは、ファイルシステム固有のチェッカに渡される）

**この仕組みがあるので、次の 2 つはまったく同じ動きになります。**

```bash
$ sudo fsck -t ext3 -opt1 -opt2 /dev/sda1      # fsck 経由で呼ぶ
$ sudo fsck.ext3   -opt1 -opt2 /dev/sda1       # 直接呼ぶ（fsck.ext3 は e2fsck へのリンク）
```

```text
  fsck -t ext3 -b 32768 -p /dev/sdb1
        │      │        │
        │      └────────┴─ fsck は解釈しない → 呼び出し先へそのまま渡る
        └─ -t ext3 で fsck.ext3（＝ e2fsck）を呼ぶと決まる

  結果として実行されるのは   e2fsck -b 32768 -p /dev/sdb1
```

**「スーパーブロックが壊れたので、予備から直しつつ全体を自動修復したい」**という要求は、
**`-b`（予備スーパーブロックの指定）と `-p`（自動修復）の 2 つ**で満たせます。

| 書き方 | 要求を満たすか | 理由 |
|:--|:-:|:--|
| **`fsck -t ext3 -b 32768 -p /dev/sdb1`** | **○** | **`-b` で予備を指定し、`-p` で自動修復している** |
| `fsck -t ext3 -b 32768 -c /dev/sdb1` | ✕ | **`-c` は不良ブロックの検査**。自動修復にならない |
| `e2fsck -b -p /dev/sdb1` | ✕ | **`-b` の後ろにブロック番号が無い**。不正なオプション指定 |
| `e2fsck -p -c /dev/sdb1` | ✕ | **`-b` が無い**ので、予備から直す指定が含まれない |

**`-b` には必ずブロック番号が続く**という点が、選択肢を切る決め手になります。

### 不良ブロックの検査は badblocks が担当する

**`e2fsck -c` は、内部で `badblocks` コマンドを呼び出すことで実現されています。**

```bash
$ sudo e2fsck -f -p -c /dev/sdb1        # 不良ブロックを調べて記録する
/dev/sdb1: Updating bad block inode.
/dev/sdb1: 11/16384 files (0.0% non-contiguous), 9525/65536 blocks
```

**`Updating bad block inode` は、見つかった不良ブロックを
「不良ブロック専用の i ノード」に記録したという意味**です。
**以後そのブロックは使われなくなります。**

| コマンド | 何をするか |
|:--|:--|
| **`badblocks デバイス`** | **不良ブロックを探して一覧を出す**（記録はしない） |
| **`e2fsck -c デバイス`** | **`badblocks` を呼んで検査し、結果をファイルシステムに記録する** |
| **`mke2fs -c デバイス`** | **作成前に不良ブロックを検査する** |

```bash
$ sudo badblocks -sv /dev/sdb1                 # 読み取りテストだけ（非破壊）
$ sudo badblocks -wsv /dev/sdb1                # 書き込みテスト（データは全部消える）
```

**`-w` はデータを破壊します。** 新品のディスクの受け入れ検査以外では使いません。

**似ている 3 つを取り違えないこと**

| 指定 | 意味 |
|:--|:--|
| **`e2fsck -b 番号`** | **予備のスーパーブロックを使って復元する** |
| **`e2fsck -c`** | **不良ブロックのチェックを行う** |
| **`e2fsck -p`** | **自動的に修復する** |

**`-b` は backup、`-c` は check（bad blocks）、`-p` は preen**と結びつけます。

**なお、不良ブロックが増え続けるならディスク自体の寿命**です。
検査だけでなく [ディスクの健全性監視_SMART](./ディスクの健全性監視_SMART.md) も見ます。

## 検査は5つのパスで進む

**`e2fsck` は 5 段階に分けて検査します。** 出力を読むときの目印になります。

```bash
$ sudo e2fsck -f -n /dev/sdb1           # 強制的に検査する（修復はしない）
e2fsck 1.47.0 (5-Feb-2023)
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Pass 5: Checking group summary information
d.img: 11/5120 files (9.1% non-contiguous), 1356/5120 blocks
```

| パス | 何を調べるか |
|:--|:--|
| **Pass 1** | **i ノード・ブロック・サイズ**。壊れた i ノードを見つける |
| **Pass 2** | **ディレクトリ構造**。エントリが正しい i ノードを指しているか |
| **Pass 3** | **ディレクトリの接続**。`/` からたどり着けるか |
| **Pass 4** | **参照カウント**。**ここで「どこからも参照されていない i ノード」が見つかる** |
| **Pass 5** | **グループの集計情報**。空き領域の数え方が合っているか |

**最後の行の読み方**

```text
d.img: 11/5120 files (9.1% non-contiguous), 1356/5120 blocks
        │     │            │                    │
        │     │            │                    └─ 使用ブロック / 全ブロック
        │     │            └─ 断片化しているファイルの割合
        │     └─ i ノードの総数
        └─ 使用中の i ノード数
```

**`***** FILE SYSTEM WAS MODIFIED *****` が出たら、何かを直した**という意味です。

## 参照されないファイルの保管場所

### 何が入るのか

**`lost+found` は、どこからも参照されていないファイルの保管場所**です。

**各ファイルシステムの最上位に 1 つずつ自動で作られます。**
`/` のファイルシステムなら `/lost+found`、`/home` が別なら `/home/lost+found` です。

```bash
$ sudo mke2fs -q -t ext4 -F d.img       # ファイルシステムを作ると
$ sudo debugfs -R "ls -l /" d.img       # 最初から lost+found がある
      2   40755 (2)      0      0    4096 15-Sep-2026 01:50 .
      2   40755 (2)      0      0    4096 15-Sep-2026 01:50 ..
     11   40700 (2)      0      0   16384 15-Sep-2026 01:50 lost+found
```

| 見るところ | 意味 |
|:--|:--|
| **`11`** | **i ノード番号。`lost+found` は常に 11 番**（`/` は 2 番） |
| **`40700`** | **`drwx------`。root だけが読める** |
| **`16384`** | **あらかじめ領域が確保されている**（壊れたときに作れないと困るため） |

**あらかじめ作ってあるのが要点**です。
**ファイルシステムが壊れてから新しくディレクトリを作るのは危ないので、最初から用意しておきます。**

**入るタイミング**

**参照できなくなったファイルが `lost+found` ディレクトリに保管されるタイミングは、
`fsck` やそのファイルシステム用のチェックツールを使って修復作業を行ったとき**です。

**普段は空**です。中に何かあれば、**過去に修復が走った証拠**になります。

---

### 名前は i ノード番号になる

**実際に再現してみます。** ディレクトリエントリだけを消して、i ノードを孤立させます。

```bash
$ sudo debugfs -w -R "unlink /workfile" d2.img   # エントリだけ消す（iノードは残る）
$ sudo e2fsck -f -y d2.img                        # 検査して直す
e2fsck 1.47.0 (5-Feb-2023)
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Unattached inode 12
Connect to /lost+found? yes

Inode 12 ref count is 2, should be 1.  Fix? yes

Pass 5: Checking group summary information

d2.img: ***** FILE SYSTEM WAS MODIFIED *****
```

**`Pass 4` で `Unattached inode 12`（どこからも参照されていない i ノード）が見つかり、
`Connect to /lost+found?` と聞かれている**のが分かります。

**中を見ると、こうなっています。**

```bash
$ sudo debugfs -R "ls -l /lost+found" d2.img     # lost+found の中身を見る
     11   40700 (2)      0      0   16384 15-Sep-2026 01:51 .
      2   40755 (2)      0      0    4096 15-Sep-2026 01:51 ..
     12  100644 (1)      0      0       3 15-Sep-2026 01:51 #12
```

**元は `workfile` だったファイルが `#12` という名前になっています。**

**`lost+found` ディレクトリに保管されるファイルには i ノードを基に仮の名前が付けられます。**
**仮の名前は元のデータを類推することができるものではないため、
復元時には個々のファイルの中身を確認する必要があります。**

```text
  workfile  ──▶  #12
      │            │
   元の名前      i ノード番号がそのまま名前になる
      │
      └─ ディレクトリエントリが壊れた＝名前を持っていた場所が消えた
         だから名前は復元できない
```

**「名前はディレクトリが持ち、中身は i ノードが持つ」**という Linux の構造がそのまま表れています。

---

### 中身を確かめて戻す

**復旧の手順は「見る → 判別する → 戻す」**です。

```bash
$ sudo ls -l /lost+found                # ① 何が入っているか見る
$ sudo file /lost+found/*               # ② 種類を判別する
$ sudo head /lost+found/#12             # ③ 中身を覗いて正体を確かめる
$ sudo mv /lost+found/#12 /home/staff/workfile   # ④ 分かったら元の場所へ戻す
```

**`file` で種類、`head` で中身**——この 2 つでだいたい見当が付きます。
`file` については
[ファイルの種類とタイムスタンプ](../01_シェルとコマンドライン/ファイルの種類とタイムスタンプ.md) を参照してください。

**`lost+found` を消してはいけません。**
**消すとファイルシステムが壊れたときに救済先が無くなります。**
中のファイルを片付けるのは構いませんが、**ディレクトリ自体は残します。**

**まぎらわしい説明の整理**

| よくある誤解 | 正しくは |
|:--|:--|
| 検索によって発見したファイルへのシンボリックリンクが自動作成される | **そういう役割のディレクトリは存在しない** |
| 格納したファイルを自動でバックアップする | **バックアップ機能ではない** |
| 一定期間経過後に中のファイルを自動削除するゴミ箱 | **自動削除はされない**。手で片付ける |
| **どこからも参照されていないファイルの保管場所** | **これが正しい** |

## 自動チェックの条件

### fstab の6番目で決まる

**`/etc/fstab` の 6 番目（`fsck` フラグ）が、起動時に検査するかどうかを決めます。**

| 値 | 意味 |
|:--|:--|
| **`0`** | **検査しない** |
| **`1`** | **最初に検査する**（ルートファイルシステム） |
| `2` | `1` のあとに検査する |

詳しくは [fstabの書き方](./fstabの書き方.md) にあります。

---

### tune2fs で回数と間隔を変える

**ext 系には「何回マウントしたら検査する」「何日経ったら検査する」という設定**があります。

```bash
$ sudo dumpe2fs -h /dev/sdb1            # 現在の設定と状態を見る
Filesystem state:         clean
Mount count:              0
Maximum mount count:      -1
Last checked:             Tue Sep 15 01:50:59 2026
Check interval:           0 (<none>)
```

| 欄 | 意味 |
|:--|:--|
| **`Filesystem state`** | **`clean` なら正常に外された。`not clean` なら異常終了している** |
| **`Mount count`** | **前回の検査からマウントした回数** |
| **`Maximum mount count`** | **この回数に達したら検査する。`-1` は「回数では検査しない」** |
| `Last checked` | 前回検査した日時 |
| **`Check interval`** | **この間隔で検査する。`0` は「期間では検査しない」** |

```bash
$ sudo tune2fs -c 30 -i 90d /dev/sdb1   # 30回マウント または 90日 で検査する
tune2fs 1.47.0 (5-Feb-2023)
Setting maximal mount count to 30
Setting interval between checks to 7776000 seconds
```

| オプション | 意味 |
|:--|:--|
| **`-c 回数`** | **最大マウント回数**（`-c 0` または `-c -1` で無効） |
| **`-i 間隔`** | **検査間隔**（`d` 日 / `w` 週 / `m` 月。`-i 0` で無効） |
| `-l` | スーパーブロックの情報を表示する |
| `-L ラベル` | ラベルを設定する |
| `-j` | ジャーナルを追加する（ext2 → ext3） |

**最近のディストリビューションでは既定で無効（`-1` と `0`）**になっています。
**ジャーナリングがあるので毎回の全面検査が要らなくなった**ためです。

> **無効になっている理由**：数 TB のディスクで全面検査が走ると、
> **起動に何十分もかかって「止まったように見える」**ためです。
> **サーバでは有効にしないのが普通**で、代わりに S.M.A.R.T の継続監視で予兆を掴みます。

---

### 再起動のときに必ず検査させる

**ルートファイルシステムはアンマウントできないので、`fsck` をかける方法が限られます。**

**対象ファイルシステムに書き込みが行われないようにするには、以下の方法があります。**

| 方法 | どんなときに使えるか |
|:--|:--|
| **アンマウントしておく** | **データ用のファイルシステム** |
| **`ro` マウントオプションで読み込み専用にしておく** | アンマウントできないが止められるとき |
| **起動時に検査させる** | **ルートファイルシステムなど、上のどちらも採用できない場合** |

**「起動時に検査させる」を選ぶときは、`shutdown` コマンドにオプションを与えます。**

| オプション | 意味 |
|:--|:--|
| **`-r`** | **再起動を行う** |
| **`-F`** | **起動時の `fsck` を必ず行う**（Force） |
| **`-f`** | **`-F` とは逆で、起動時の `fsck` を必ずスキップする**（fast） |
| `-h` | シャットダウン後システムを停止する（halt 状態にする） |

```bash
$ sudo shutdown -r -F now               # 今すぐ再起動し、次回起動時の fsck を強制する
```

**前提として、`/etc/fstab` で対象ファイルシステムの `fsck` フラグが 1 以上**でなければ
起動時の検査対象になりません。**`0` のままでは `-F` を付けても検査されません。**

```text
  ① /etc/fstab の6番目が 1 以上であることを確認する
  ② shutdown -r -F now を実行する
  ③ 起動時に fsck が走る
```

**`-F` と `-f` は 1 文字違いで正反対**です。

```text
  -F  Force     … 必ず検査する
  -f  fast      … 必ず飛ばす（速く起動する）
```

> **実機で確認した注意**
> **`-F` / `-f` は SysVinit 時代の `shutdown` のオプション**です。
> **systemd の `shutdown`（systemd 255 で確認）の `--help` には `-F` も `-f` もありません。**
> 現在の同等の指定は**カーネルパラメータ `fsck.mode=force` / `fsck.mode=skip`** です。
> **試験では `-r` と `-F` が正解**ですが、実機で効かなくても異常ではありません。

```bash
$ shutdown --help | grep -E '^\s+-'     # systemd 版にあるオプションを確認する
     --help      Show this help
  -H --halt      Halt the machine
  -P --poweroff  Power-off the machine
  -r --reboot    Reboot the machine
  -h             Equivalent to --poweroff, overridden by --halt
  -k             Don't halt/power-off/reboot, just send warnings
     --no-wall   Don't send wall message before halt/power-off/reboot
  -c             Cancel a pending shutdown
     --show      Show pending shutdown
```

**systemd 環境で次回起動時に強制検査させる 2 つの方法**

| 方法 | 書き方 |
|:--|:--|
| **カーネルパラメータ**（推奨） | **ブートローダの起動オプションに `fsck.mode=force` を足す** |
| **目印ファイル**（互換のため残っている） | **`touch /forcefsck`**（スキップは `/fastboot`） |

**`systemd-fsck` は互換のため `/forcefsck` と `/fastboot` をまだ見ますが、
非推奨の警告を出します。**

```bash
$ strings /usr/lib/systemd/systemd-fsck | grep forcefsck   # まだ見ているか確かめる
/forcefsck
Please pass 'fsck.mode=force' rather than 'forcefsck' on the kernel command line.
```

`fsck` フラグそのものは [fstabの書き方](./fstabの書き方.md)、
カーネルパラメータの渡し方は
[ブートプロセスの全体像](../05_起動プロセスとカーネル/ブートプロセスの全体像.md) にあります。

## 結果画面の見方

**正常なとき**

```text
e2fsck 1.47.0 (5-Feb-2023)
d.img: clean, 11/5120 files, 1356/5120 blocks
```

**`clean` と出たら、検査自体が省略されています。**
**中身まで見たいときは `-f` を付けます。**

**直したとき**

```text
Unattached inode 12
Connect to /lost+found? yes

Inode 12 ref count is 2, should be 1.  Fix? yes

d2.img: ***** FILE SYSTEM WAS MODIFIED *****
```

| 出力 | 意味 | どうなるか |
|:--|:--|:--|
| **`Unattached inode N`** | **どこからも参照されていない i ノード** | **`lost+found` へ繋がれる** |
| `Inode N ref count is X, should be Y` | 参照カウントの食い違い | 正しい値に直る |
| `Duplicate blocks found` | 複数のファイルが同じブロックを指している | 片方が壊れる可能性がある |
| `Inode N is in use but has dtime set` | 削除済みなのに使われている | 修復される |
| **`FILE SYSTEM WAS MODIFIED`** | **何かを書き換えた** | **`lost+found` を必ず確認する** |

**終了ステータスも意味を持ちます**

| 値 | 意味 |
|:--|:--|
| **`0`** | **エラーなし** |
| **`1`** | **エラーを修復した** |
| `2` | 修復したが、再起動が必要 |
| `4` | **修復されなかったエラーが残っている** |
| `8` | 操作エラー |

```bash
$ sudo fsck -y /dev/sdb1 ; echo "終了ステータス: $?"   # 直したかどうかを数値で確認する
```

**スクリプトから呼ぶときは `1` と `4` の区別が重要**です。
`4` が返ったら**自動では直せていない**ので、人が見る必要があります。

## 起動できなくなったときの復旧

**電源断のあと、起動が緊急モード（emergency mode）で止まることがあります。**

```text
  Welcome to emergency mode!
  Give root password for maintenance
  (or press Control-D to continue):
```

**このときの手順**

```bash
$ journalctl -xb | grep -i -E "fsck|mount|error"   # ① どこで失敗したかを確認する
$ mount | grep sdb1                                 # ② マウントされていないことを確認する
$ fsck -n /dev/sdb1                                 # ③ 検査だけ先に実行して状況を見る
$ fsck -y /dev/sdb1                                 # ④ 直せそうなら修復する
$ reboot                                            # ⑤ 再起動する
```

**`/etc/fstab` の書き間違いでも緊急モードに落ちます。**
**まず `fsck` の問題なのか `fstab` の問題なのかを切り分ける**のが先です。

| 症状 | 疑うもの |
|:--|:--|
| `Failed to mount ...` で特定のデバイス名が出る | **`fstab` の書き間違い**か、そのデバイスが無い |
| `fsck failed with error code ...` | **ファイルシステムの破損** |
| `Dependency failed for ...` | 上のどちらかの巻き添え |

**`nofail` を書いておくと、そのデバイスが無くても起動が止まりません。**
[fstabの書き方](./fstabの書き方.md) と
[ブートプロセスの全体像](../05_起動プロセスとカーネル/ブートプロセスの全体像.md) も参照してください。
