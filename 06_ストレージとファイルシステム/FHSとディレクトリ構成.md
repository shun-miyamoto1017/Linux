## まずこれだけ

| ディレクトリ | 何が入るか |
|:--|:--|
| **`/usr/bin`** | **システムの起動には必須ではない、一般ユーザ用のコマンド** |
| **`/usr/sbin`** | **システムの起動には必須ではない、システム管理用のコマンド** |
| **`/usr/lib`** | **`/usr/bin`、`/usr/sbin` に格納されるコマンドが必要とする共有ライブラリ** |
| **`/usr/local`** | **ホスト固有で使用するプログラムや設定ファイル**（個人作成など）。配下に `bin` / `etc` などがある |
| **`/usr/share/man`** | **マニュアル** |

**押さえる 3 点**

| 論点 | 結論 |
|:--|:--|
| **共有ライブラリはどこか** | **`/usr/lib`**（`/usr/local` でも `/usr/share/man` でもない） |
| `/usr` に入るものの性格 | **起動には不要なプログラムなど** |
| **自分で入れたものはどこか** | **`/usr/local` 配下**。パッケージ管理が触らない領域 |

## FHS とは何か

**FHS（Filesystem Hierarchy Standard ／ ファイルシステム階層標準）は、
Linux をはじめとする UNIX 系 OS で、どのディレクトリに何を置くかを定めた標準**です。

**なぜ決まりが要るのか**

```text
  決まりが無いと
    ディストリビューションごとに置き場所がバラバラになる
        ▼
    同じスクリプトが別のディストリビューションで動かない
        ▼
    パッケージも作れない

  FHS があると
    「設定は /etc」「可変データは /var」と決まっている
        ▼
    どのディストリビューションでも同じ場所を見ればよい
```

**実務では「バックアップ設計」と「パーティション設計」に直結**します。
**`/var` だけ別パーティションにする**といった判断は、
**「どこに何が増えるか」が FHS で決まっている**から成り立ちます。

---

### FHSが定めていること定めていないこと

**以前は各ディストリビューションが、それぞれに定めたディレクトリ構造を使用していました。**
**そのため、インストールしたプログラムの配置場所がそれぞれのディストリビューションで違う
などの問題がありました。**
**このような問題をなくすために、どのディレクトリにどのようなファイルを格納するべきかを
標準化したのが FHS** です。

**試験では「FHS の説明として正しいものをすべて選べ」という形で問われます。**
**正しいものと誤りのものを、表で切り分けておきます。**

| 説明 | 正誤 | 理由 |
|:--|:-:|:--|
| **ディストリビューションに依存しない、Linux の標準的なディレクトリの構造を定めた規格のこと** | **○** | **これが定義そのもの** |
| **ユーザがインストールしたプログラムの配置場所などを推測しやすくするためのもの** | **○** | **標準化の目的がこれ** |
| **Linux の各ディストリビューションが FHS に完全に従う必要がある** | **✕** | **あくまでも標準。完全に従う必要はない** |
| **ファイルのフォーマットを定めた規格** | **✕** | **FHS が定めるのはディレクトリ構造**。ファイルの形式は範囲外 |
| **各ディストリビューションを区別するため、それぞれ違ったディレクトリ構造の使用を推奨する文書** | **✕** | **逆**。違いをなくすための標準化 |

**「標準であって強制ではない」**

**FHS ではディレクトリ構造を詳細に規定しているわけではありません。**
**また、あくまでもディレクトリ構造の標準ですので、
各ディストリビューションが FHS に完全に従う必要はありません。**

**そのため、ユーザ自身がファイルの保管場所を検索、把握しなければならない場合がある**
ことに注意してください。

**だから「探すコマンド」が要る**わけです。
`which` / `type` / `whereis` / `locate` / `find` の使い分けは
[コマンドの場所を探す](./コマンドの場所を探す.md) にあります。

**まぎらわしい 2 つの規格**

| 規格 | 何を定めるか |
|:--|:--|
| **FHS**（Filesystem Hierarchy Standard） | **どのディレクトリに何を置くか**（ディレクトリ構造） |
| **LSB**（Linux Standard Base） | ディストリビューション間でバイナリ互換を保つための、より広い仕様。**FHS を内包する** |

## ルート直下のディレクトリ

| ディレクトリ | 用途 |
|:--|:--|
| **`/bin`** | **起動に必須の、一般ユーザ用コマンド**（`ls` / `cp` など） |
| **`/sbin`** | **起動に必須の、システム管理用コマンド**（`fsck` / `mount` など） |
| **`/lib`** | **`/bin` と `/sbin` のコマンドが必要とする共有ライブラリ**とカーネルモジュール |
| **`/etc`** | **設定ファイル**（**実行ファイルは置かない**） |
| **`/var`** | **運用中に増減する可変データ**（ログ・メール・スプール・DB） |
| **`/usr`** | **起動には必須ではないプログラムなど** |
| **`/opt`** | **アドオンのアプリケーションパッケージ** |
| `/srv` | そのホストが提供するサービスのデータ |
| `/home` | 一般ユーザのホームディレクトリ |
| `/root` | root のホームディレクトリ |
| `/tmp` | 一時ファイル（**再起動で消える前提**） |
| `/boot` | カーネルとブートローダ |
| `/dev` | デバイスファイル |
| `/proc` | プロセスとカーネルの情報（**仮想**） |
| `/sys` | デバイスとドライバの情報（**仮想**） |
| **`/lost+found`** | **どこからも参照されていないファイルの保管場所**（[fsckとファイルシステムの修復](./fsckとファイルシステムの修復.md)） |
| `/media` | リムーバブルメディアの自動マウント先 |
| `/mnt` | 一時的に手でマウントする場所 |

**`/proc` と `/sys` はディスク上に実体がありません。**
詳しくは
[カーネルの実行時管理 dmesgとsysctl](../05_起動プロセスとカーネル/カーネルの実行時管理_dmesgとsysctl.md) を参照してください。

## usr 配下の配置

**`/usr` ディレクトリには起動には不要なプログラムなどが格納されています。**

| ディレクトリ | 格納物 |
|:--|:--|
| **`/usr/bin`** | **システムの起動には必須ではない、一般ユーザ用のコマンド** |
| **`/usr/sbin`** | **システムの起動には必須ではない、システム管理用のコマンド** |
| **`/usr/lib`** | **`/usr/bin`、`/usr/sbin` に格納されるコマンドが必要とする共有ライブラリ** |
| **`/usr/local`** | **ホスト固有で使用するプログラムや設定ファイル**（個人作成など）。配下に、プログラムを格納する `bin`、設定ファイルを格納する `etc` などのディレクトリがある |
| **`/usr/share/man`** | **マニュアル** |
| `/usr/share` | アーキテクチャに依存しないデータ（アイコン・ドキュメント・ロケール） |
| `/usr/include` | C 言語のヘッダファイル |
| `/usr/src` | ソースコード（カーネルソースなど） |

```bash
$ ls /usr/                             # /usr 配下を見る
bin  games  include  lib  lib64  libexec  local  sbin  share  src
```

### bin と sbin の違い

**`bin` と `sbin` の違いは「誰が使うか」**です。

| | **`bin`** | **`sbin`** |
|:--|:--|:--|
| 誰向けか | **一般ユーザ** | **システム管理者** |
| 例 | `ls` / `cp` / `find` | `fdisk` / `mkfs` / `useradd` |
| 一般ユーザの PATH | **通常は入っている** | **通常は入っていない** |

**`sbin` のコマンドが「見つからない」と言われたら、PATH の問題**であることが多いです。

```bash
$ fdisk -l                             # 一般ユーザでは見つからないことがある
-bash: fdisk: command not found
$ sudo fdisk -l                        # sudo なら PATH が通っている
```

**`sbin` に置いてあっても、実行できないわけではありません。**
**置き場所の分類と、実行権限は別の話**です。

---

### usr-lib に入るもの

**`/usr/lib` には、`/usr/bin` と `/usr/sbin` のコマンドが必要とする共有ライブラリが入ります。**

**共有ライブラリとは、複数のプログラムが共通して使う機能をまとめた部品**です。
**各プログラムが同じ機能を自前で持たずに済む**ので、容量も更新の手間も減ります。

```bash
$ ldd /usr/bin/find                    # find が使っている共有ライブラリを見る
        linux-vdso.so.1 (0x00007fd92265e000)
        libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x00007fd9225e9000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fd922200000)
        libpcre2-8.so.0 => /lib/x86_64-linux-gnu/libpcre2-8.so.0 (0x00007fd92254f000)
```

| 出力の欄 | 意味 |
|:--|:--|
| **左側（`libc.so.6`）** | **必要としているライブラリの名前** |
| **`=>` の右側** | **実際に見つかった場所** |
| `not found` | **そのライブラリが無い**。プログラムは起動できない |
| `linux-vdso.so.1` | カーネルが提供する特別なもの。ファイルとして存在しない |

**`/usr/lib` の下は、アーキテクチャごとのディレクトリに分かれていることがあります。**

```bash
$ ls -l /usr/lib/x86_64-linux-gnu/libc.so.6   # 64ビット版の C ライブラリ
-rwxr-xr-x 1 root root 2125328 Jan 30  2026 /usr/lib/x86_64-linux-gnu/libc.so.6
```

**64 ビット環境では `/usr/lib64` を使うディストリビューションもあります**（RHEL 系など）。

---

### usr-local はホスト固有

**`/usr/local` は「そのホストだけで使うもの」を置く場所**です。

| | **`/usr`** | **`/usr/local`** |
|:--|:--|:--|
| 誰が置くか | **ディストリビューションのパッケージ** | **そのホストの管理者** |
| **パッケージ更新で** | **上書きされる** | **触られない** |
| 例 | `dnf` や `apt` で入れたもの | **自分でビルドしたツール、自作スクリプト** |

```bash
$ ls /usr/local/                       # /usr/local の中も /usr と同じ構成になっている
bin  etc  games  include  lib  man  sbin  share  src
```

**`/usr/local` の下に `bin` / `etc` / `lib` と、同じ形が繰り返されている**のが分かります。
**「ミニチュアの `/usr`」**だと考えると覚えやすくなります。

**自作スクリプトの置き場所**

```bash
$ sudo install -m 755 mytool.sh /usr/local/bin/mytool   # 自作ツールを配置する
$ which mytool                                           # PATH が通っていることを確認する
/usr/local/bin/mytool
```

**`/usr/bin` に置いてはいけません。**
**パッケージ更新時に消えたり、パッケージ管理システムと衝突したりします。**

## 起動に必須かどうかで分かれる

**FHS の分け方の背骨は「システムの起動に必須かどうか」**です。

```text
  起動に必須          →  /bin   /sbin   /lib      （ルートファイルシステムに置く）
  起動には必須でない  →  /usr/bin  /usr/sbin  /usr/lib
  そのホスト固有      →  /usr/local/bin  /usr/local/etc  …
```

**なぜこう分かれていたのか**

**昔は `/usr` を別のディスクやネットワーク越しに置くことがありました。**
**`/usr` がまだマウントされていない段階でも起動できるように、
最低限必要なコマンドを `/bin` と `/sbin` に置いていた**のです。

| 段階 | 使えるもの |
|:--|:--|
| 起動直後（`/usr` 未マウント） | **`/bin` `/sbin` `/lib` だけ** |
| `/usr` をマウント後 | **すべて** |

---

### いまは統合されつつある

**近年の多くのディストリビューションでは、`/bin` は `/usr/bin` へのシンボリックリンク**になっています。
**usr merge（/usr 統合）**と呼ばれる変更です。

```bash
$ ls -ld /bin /sbin /lib /lib64        # 実体がどこを指しているか確認する
lrwxrwxrwx 1 root root 7 Apr 22  2024 /bin -> usr/bin
lrwxrwxrwx 1 root root 7 Apr 22  2024 /lib -> usr/lib
lrwxrwxrwx 1 root root 9 Apr 22  2024 /lib64 -> usr/lib64
lrwxrwxrwx 1 root root 8 Apr 22  2024 /sbin -> usr/sbin
```

**4 つとも `/usr` 配下へのシンボリックリンク**になっています。

| | **従来** | **usr merge 後** |
|:--|:--|:--|
| `/bin` | 実体のディレクトリ | **`/usr/bin` へのリンク** |
| 実際の置き場所 | `/bin` と `/usr/bin` に分散 | **`/usr/bin` に集約** |
| 初期起動 | `/usr` 未マウントでも動く | **`initramfs` が `/usr` も用意する** |

**試験では FHS の「本来の分類」で問われます。**
**実機でリンクになっていても、「`/usr/bin` は起動に必須でない一般ユーザ用コマンド」という分類は変わりません。**

`initramfs` については
[初期RAMディスク initrdとinitramfs](../05_起動プロセスとカーネル/初期RAMディスク_initrdとinitramfs.md) を参照してください。

## var と etc と opt

**`/var` … 運用中に増減するもの**

| ディレクトリ | 中身 |
|:--|:--|
| **`/var/log`** | **ログ**。いちばん増える |
| `/var/spool` | 印刷キュー、メールキュー、cron |
| `/var/lib` | アプリケーションが持つ状態（DB のデータなど） |
| `/var/cache` | キャッシュ（消えても再生成できる） |
| `/var/tmp` | 一時ファイル（**`/tmp` と違い再起動で消えない**） |

**`/tmp` と `/var/tmp` の違い**

| | **`/tmp`** | **`/var/tmp`** |
|:--|:--|:--|
| 再起動 | **消える前提** | **残る前提** |
| 用途 | ごく短期の作業 | 再起動をまたぐ作業 |

**`/etc` … 設定ファイル**

**`/etc` には設定ファイルだけを置き、実行ファイルは置かない**のが FHS の原則です。
**ホスト固有の設定**であり、**バックアップ対象の筆頭**でもあります。

**`/opt` … アドオンのパッケージ**

**ベンダーが配布する、自己完結型のソフトウェア**を置きます。

```text
  /opt/<製品名>/bin
  /opt/<製品名>/lib
  /opt/<製品名>/etc
```

**製品ごとに 1 つのディレクトリにまとまる**のが `/opt` の流儀です。
**`/usr/local` は「自分で作ったもの」、`/opt` は「ベンダーが配るもの」**と分けて覚えます。

## 結果画面の見方

**どこに何があるかを調べるコマンド**

```bash
$ which find                           # PATH の中から実行ファイルの場所を探す
/usr/bin/find
$ whereis find                         # 実行ファイル・ソース・マニュアルをまとめて探す
find: /usr/bin/find /usr/share/man/man1/find.1.gz
```

| 出力 | 意味 |
|:--|:--|
| **`/usr/bin/find`** | **実行ファイルの場所** |
| **`/usr/share/man/man1/find.1.gz`** | **マニュアルの場所**（`/usr/share/man` 配下） |

> **`which` / `type` / `whereis` / `locate` / `updatedb` / `find` の使い分け**は
> [コマンドの場所を探す](./コマンドの場所を探す.md) にまとめてあります。
> **`PATH` に依存するのは `which` と `type` だけ**、という切り分けもそちらです。

```bash
$ ls /                                 # ルート直下の構成を確認する
bin  boot  dev  etc  home  lib  lib64  media  mnt  opt  proc  root  run  sbin  srv  sys  tmp  usr  var
```

## まぎらわしい置き場所の整理

| 問われ方 | 答え |
|:--|:--|
| **共有ライブラリが格納されているディレクトリは** | **`/usr/lib`** |
| システムの起動には必須ではない、一般ユーザ用のコマンド | `/usr/bin` |
| システムの起動には必須ではない、システム管理用のコマンド | `/usr/sbin` |
| ホスト固有で使用するプログラムや設定ファイル | `/usr/local` |
| マニュアル | `/usr/share/man` |
| **起動に必須の**一般ユーザ用コマンド | **`/bin`**（`/usr/bin` ではない） |
| 設定ファイル | `/etc` |
| ログなどの可変データ | `/var` |

**取り違えの型**

```text
  /usr/lib        ← 共有ライブラリ          ○
  /usr/local      ← ホスト固有のプログラム  （ライブラリ「専用」ではない）
  /usr/share/man  ← マニュアル              （ライブラリではない）
  /usr/bin        ← 一般ユーザ用コマンド    （ライブラリではない）
  /usr/sbin       ← 管理用コマンド          （ライブラリではない）
```

**「lib」という綴りが入っているのは `/usr/lib` だけ**です。
**迷ったら綴りで判断できます。**

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| **自作ツールがパッケージ更新で消えた** | **`/usr/bin` に置いていた** | **`/usr/local/bin`** に置く |
| **`command not found`（管理コマンド）** | `sbin` が PATH に無い | `sudo` を使うか、フルパスで実行する |
| **`error while loading shared libraries`** | 共有ライブラリが見つからない | **`ldd` で `not found` を探す**。`ldconfig` を実行する |
| **`/var` が溢れてサービスが止まった** | ログが増え続けた | `logrotate` を設定する。`/var` を別パーティションにする |
| **`/tmp` に置いたファイルが消えた** | **`/tmp` は再起動で消える前提** | 残したいなら `/var/tmp` を使う |
| **`/bin` と `/usr/bin` の違いが分からない** | 実機ではリンクに統合されている | **試験では「起動に必須か」で分類する** |

## クラウド実務メモ

**パーティション設計に直結する**

| ディレクトリ | 分けるか | 理由 |
|:--|:--|:--|
| **`/var`** | **分けることが多い** | **ログで溢れてもルートが埋まらない** |
| `/home` | 分けることがある | ユーザデータを残したまま OS を入れ替えられる |
| `/tmp` | 分けるか tmpfs にする | 一時ファイルで溢れても影響を閉じ込める |
| `/boot` | 分けることがある | 暗号化や LVM を使う場合に必要 |

**EC2 の既定の AMI は 1 パーティションのことが多い**ので、
**ログの多いサーバでは `/var` 用に EBS を足してマウント**します。
手順は [ディスクを追加する手順](./ディスクを追加する手順.md) にあります。

**コンテナイメージでは `/usr/local` が主役**

```dockerfile
COPY mytool /usr/local/bin/mytool
```

**ベースイメージのパッケージ管理と衝突しない**ため、
**アプリのバイナリは `/usr/local/bin`、設定は `/etc/<アプリ名>`、データは `/var/lib/<アプリ名>`**
という置き方が定石です。

**設定とデータを分けておくと、ボリュームの設計が決まる**

```text
  /etc/myapp        設定      → ConfigMap / 起動時に配る
  /var/lib/myapp    データ    → 永続ボリューム（EBS / EFS）
  /var/log/myapp    ログ      → 標準出力に流して外へ送る
```

**FHS どおりに置いてあれば、どれを永続化すべきかが自動的に決まります。**
**置き場所がバラバラだと、この判断ができません。**

**Ansible や cloud-init で配るとき**

```bash
$ sudo install -D -m 644 myapp.conf /etc/myapp/myapp.conf   # 設定を配置する
$ sudo install -D -m 755 myapp      /usr/local/bin/myapp    # 実行ファイルを配置する
```

**`install` はディレクトリ作成・権限設定・配置をまとめてやってくれます。**
`cp` と `chmod` を並べるより、**手順書に書いたときに意図が伝わります。**
