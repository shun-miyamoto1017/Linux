## RAIDとは何か

**RAID とは複数のディスクをまとめて利用することでアクセスの高速化やデータの冗長化を行う技術**で、
**Redundant Arrays of Independent Disks（独立ディスク群の冗長配置）の頭文字**を取った名前です。

**RAID には RAID レベルと呼ばれるいくつかの種類があり、
RAID レベルによって複数のディスクの使い方や実現される内容が異なります。**

```text
  複数のディスク            まとめ方（RAID レベル）        得られるもの
  ┌───┐┌───┐┌───┐
  │ A ││ B ││ C │  ──▶  RAID0  直列化して1台に  ──▶  速度と容量
  └───┘└───┘└───┘  ──▶  RAID1  並列化して1台に  ──▶  安全性
                      ──▶  RAID5  パリティを分散  ──▶  容量と安全性の両立
```

**「冗長化」とは、同じデータやパリティを保持することで信頼性を高めること**です。
**この言葉が説明文に入っているかどうかが、RAID0 とそれ以外を分ける目印**になります。

> **この分野でよく出る「直列化」「並列化」は、容量の足し方の話**です。
> **RAID0 の「直列化」＝ 各ディスクの領域をつなげて 1 つの大きな領域にする**、
> **RAID1 の「並列化」＝ 同じ内容を並べて置く**、という意味です。
> **I/O の動きとしては、RAID0 も複数ディスクに同時アクセスします**（だから速い）。
> **「直列だから遅い」ではありません**——ここを取り違えないでください。

## RAIDを誰が計算するか

**「RAID」と一口に言っても、パリティの計算やミラーの書き分けを**
**誰がやっているかで 3 種類に分かれます。**
**Red Hat は公式ドキュメントでこの 3 つに分類しています。**

| 種類 | 誰が処理するか | Linux からどう見えるか |
|:--|:--|:--|
| **ハードウェア RAID** | **専用の RAID コントローラ**（カード or オンボード）。ホストから独立して動く | **1 台のディスクとして見える**（`/dev/sda` など）。OS は RAID だと気づかない |
| **ソフトウェア RAID** | **カーネルのブロックデバイス層**（md ドライバ） | **`/dev/md0` として見える**。`mdadm` で操作する |
| **ファームウェア RAID**（ATARAID / 俗に fakeRAID） | **BIOS/UEFI がメタデータ形式だけ決め、計算はホストの CPU** | **実体はソフトウェア RAID**。Red Hat も「a type of software RAID」と分類している |

> Red Hat の公式ドキュメント（RHEL 9 *Managing storage devices*）の表現です。
> - ハードウェア RAID … "A hardware-based array manages the RAID subsystem independently from the host."
> - ソフトウェア RAID … "A software RAID implements the various RAID levels in the kernel block device code."
> - ファームウェア RAID … "Firmware RAID, also known as ATARAID, is a type of software RAID"

**ファームウェア RAID（fakeRAID）が業務でいちばん厄介**です。

```text
  見た目    BIOS 画面に「RAID 設定」がある → ハードウェア RAID だと思ってしまう
  実体      計算はホストの CPU がやっている → 性能も信頼性もソフトウェア RAID 並み
  困る点    メタデータ形式がベンダ固有。別のマシンに差し替えると読めないことがある
```

**`dmraid` パッケージは RHEL 8 で削除されました。**
ファームウェア RAID を使う場合も **`mdadm` で扱います**
（`mdadm` は MD ネイティブ形式に加え、SNIA DDF と Intel IMSM に対応しています）。

**どれを選ぶかの判断**

| 状況 | 選ぶもの |
|:--|:--|
| **サーバに RAID コントローラ（BBU 付き）がある** | **ハードウェア RAID**。書き込みキャッシュが効く |
| **コントローラが無い** | **ソフトウェア RAID（`mdadm`）か LVM RAID** |
| **クラウド** | **冗長化目的の RAID は原則不要**（後述の「クラウドではRAIDをどう考えるか」） |
| **BIOS の「RAID 設定」しか無い** | **それは fakeRAID**。素直に `mdadm` で組んだほうが素性が分かる |

## RAID0 ストライピング

**RAID0 はストライピングとも言い、2 台以上のディスクを直列化して 1 台のディスクとします。**
**個々のディスクの領域をすべてまとめ、巨大なディスクにするというイメージ**です。

```text
  データ  A1 A2 A3 A4 A5 A6
            ↓
  ┌─ disk1 ─┐ ┌─ disk2 ─┐
  │ A1  A3  │ │ A2  A4  │      ← 交互に振り分けて書く
  │ A5      │ │ A6      │
  └─────────┘ └─────────┘
```

**RAID0 を利用すると、容量は基本的に全てのディスクの容量を合わせた容量となります。**
**また複数のディスクを同時に利用する事で、高速に読み書きが行えるようになります。**

**ただし、データの冗長化は一切行われていない**ため、
**RAID0 を構成している複数台のディスクのうちどれかに問題が発生しただけで
RAID0 全体が利用できなくなる可能性があります。**

**したがって RAID0 は安全性を高める目的ではなく、
大きく高速なディスク領域を確保する目的で利用します。**

| 説明 | 正誤 |
|:--|:-:|
| **ストライピングとも呼ばれる** | **○** |
| **2 台以上のディスクを使って構成する** | **○**（1 台では分散できない） |
| **シーケンシャルアクセスのパフォーマンスに優れる** | **○** |
| **複数台のディスクを利用しデータを冗長化する** | **✕**（**まとめるだけ。冗長化はしない**） |

> **シーケンシャルアクセスとは、大きなファイルを読み書きする場合など、
> ディスクを一方向に続けて利用するようなアクセス**のことです。
> **RAID0 では複数のディスクにデータが分散しているため、それぞれのディスクで同時に読み書きを行うことができ、
> ディスク台数が増えれば増えるほどシーケンシャルアクセスのスピードが高速になります。**

## RAID1 ミラーリング

**RAID1 はミラーリングとも言い、2 台以上のディスクを並列化して 1 台のディスクとします。**
**個々のディスクにはすべて同一のデータが書き込まれます。**

```text
  データ  A1 A2 A3
            ↓  同じものを全部に書く
  ┌─ disk1 ─┐ ┌─ disk2 ─┐
  │ A1 A2 A3│ │ A1 A2 A3│      ← 完全に同じ内容
  └─────────┘ └─────────┘
```

**したがってディスクを 2 台利用した場合には二重に、3 台利用した場合は三重に、
というようにデータが多重にディスクに保持されることになり、非常に冗長性が高い構成**です。

**RAID1 を構成しているディスクのうち何台かが故障したとしても、
1 台でも正常に動作するディスクが残っていれば RAID1 領域は安全に利用可能**です。
**そして故障したディスクを随時新しいディスクに交換していくことで、無用にシステムを止めずに済みます。**

**このように RAID1 は冗長化を行い、重要なデータの信頼性・安全性を高める目的で利用します。**

| 説明 | 正誤 |
|:--|:-:|
| **ミラーリングとも呼ばれる** | **○** |
| **データを多重化することで信頼性を高める** | **○** |
| **2 台以上のディスクを使って構成する** | **○** |
| **パリティを利用することでデータを冗長化する** | **✕**（**これは RAID5 の説明**。RAID1 はパリティを使わない） |

**「多重化」と「パリティ」を取り違えない**

```text
  RAID1  同じデータをそのまま 何枚も 持つ        … 多重化
  RAID5  元に戻せる 符号（パリティ）を持つ        … パリティ
```

## RAID5 パリティ分散

**RAID5 は 3 台以上のディスクで構成し、
パリティ領域と呼ばれるデータ復旧用の冗長なデータを各ディスクに分散して保持します。**

```text
  ┌─ disk1 ─┐ ┌─ disk2 ─┐ ┌─ disk3 ─┐
  │ A1      │ │ A2      │ │ Ap      │   ← Ap は A1,A2 のパリティ
  │ B1      │ │ Bp      │ │ B2      │   ← パリティの置き場所がずれていく
  │ Cp      │ │ C1      │ │ C2      │
  └─────────┘ └─────────┘ └─────────┘
       ↑ パリティが1台に固まらず、分散している
```

**基本的には RAID0 と同様に直列化されるので、ディスク台数を増やせば増やすほど RAID5 全体の容量は増えます。**
**具体的には、RAID5 では構成ディスクの全容量から 1 台分だけ減らした容量が利用可能**です。

**またパリティが存在するので、RAID0 とは異なり冗長性も確保されています。**
**構成しているディスクに障害が発生した場合は、
他のディスクのパリティ領域を利用することで復旧することができます。**

**このように RAID5 は全体の容量を増やしつつ冗長性も確保する目的で利用します。**

| 説明 | 正誤 | 理由 |
|:--|:-:|:--|
| **構成ディスク台数を増やすほど、利用できる容量が増加する** | **○** | **パリティは 1 台分だけ。残りはすべて使える** |
| **構成ディスクのうち 1 台をパリティ専用に使う** | **✕** | **1 台「分」の容量を使うが、専用ディスクがあるわけではない**。各ディスクに分散する |
| **構成ディスクのうち 1 台でも正常ならばデータが復旧できる** | **✕** | **これは RAID1 の説明**。RAID5 が耐えられるのは **1 台の障害まで** |
| **2 台以上のディスクで構成する** | **✕** | **3 台以上**が必要 |

**なぜ RAID5 は 3 台からなのか**

**仮にディスク 2 台で RAID5 を構成した場合を考えると、実際に利用できる容量は 1 台分**となります。
**しかし 2 台を利用し 1 台分の容量で良いならば、
そもそもパリティなど利用せず RAID1 としてミラーリングすれば良いわけです。**
**したがって RAID5 として意味があるのは 3 台から**です。

> **RAID3 や RAID4 というものもあり、これらはディスク 1 台をパリティ専用に使います**
> （その点を除いては RAID5 とほぼ同じ）。
> **「パリティ専用ディスク」という説明は RAID3 / RAID4 のもの**で、**RAID5 ではありません。**

## パリティの正体 XORを手で確かめる

**「パリティで復旧できる」と言われても、何が起きているのか分からない**——
ここがつまずきやすいところです。**実際は XOR（排他的論理和）1 つだけ**です。

**XOR はこういう演算です。**

```text
  0 XOR 0 = 0      同じなら 0
  1 XOR 1 = 0
  0 XOR 1 = 1      違うなら 1
  1 XOR 0 = 1
```

**この演算には「2 回かけると元に戻る」という性質があります。**

```text
  A XOR B = P        … これがパリティ
  B XOR P = A        … B とパリティから A が戻る    ★これが復旧
  A XOR P = B        … A とパリティから B が戻る
```

**本当に戻るのか、手元で確かめられます。**
以下は Linux 上で実際に実行した結果です（**実測**。`python3` と `od` だけで確認できます）。

```bash
$ cd "$(mktemp -d)"                       # 作業用の一時ディレクトリへ移動する
$ printf 'AAAA' > d1.bin                  # disk1 に書かれるデータ
$ printf 'BBBB' > d2.bin                  # disk2 に書かれるデータ
$ python3 -c "a=open('d1.bin','rb').read(); b=open('d2.bin','rb').read(); open('p.bin','wb').write(bytes(x^y for x,y in zip(a,b)))"   # XOR でパリティを作る
$ for f in d1 d2 p; do printf "%-8s %s\n" "$f.bin" "$(od -An -tx1 $f.bin)"; done   # 16進で中身を並べる
```

```text
d1.bin    41 41 41 41
d2.bin    42 42 42 42
p.bin     03 03 03 03
```

（`'A'` は `0x41`、`'B'` は `0x42`。`0x41 XOR 0x42 = 0x03`）

**ここで disk1 が壊れたとします。残った disk2 とパリティだけで復元してみます。**

```bash
$ python3 -c "b=open('d2.bin','rb').read(); p=open('p.bin','rb').read(); open('rec.bin','wb').write(bytes(x^y for x,y in zip(b,p)))"   # d2 XOR p で戻す
$ od -An -tx1 rec.bin                     # 復元結果を見る
$ cmp d1.bin rec.bin && echo "差分なし"   # 元データと比べる
```

```text
 41 41 41 41
差分なし
```

**`cmp` が何も言わずに「差分なし」まで進んだ**——つまり**1 バイトも違わずに戻っています。**

**1 バイト目をビットで並べると、何が起きたか一目で分かります。**

```text
  disk1 (A)   01000001
  disk2 (B)   01000010
  XOR         --------
  parity      00000011      ← これがパリティ

  disk2 (B)   01000010
  parity      00000011
  XOR         --------
  復元        01000001      ← disk1 の A が完全に戻った
```

> **この例では説明のためパリティを 1 か所に置いていますが、
> RAID5 ではストライプごとにパリティの置き場所を回します**（前節の図を参照）。
> **計算そのものは、置き場所がどこでも同じ XOR** です。

**ここから RAID5 の性質がすべて説明できます。**

| 性質 | XOR から導かれる理由 |
|:--|:--|
| **1 台までしか耐えられない** | **未知の値が 1 つなら方程式が解ける**。2 つになると解が定まらない |
| **パリティは 1 台分の容量で足りる** | **何台あってもパリティは「全部を XOR した 1 本」**。台数分は要らない |
| **3 台以上から意味がある** | **2 台だと `A XOR なし = A`** になり、ミラーと同じ |
| **書き込みが遅い** | **データを書くたびにパリティを作り直す**必要がある（次節） |

> **RAID6 は「XOR とは別のもう 1 本」を持ちます。**
> 未知の値が 2 つでも解けるように、ガロア体の演算を使った 2 種類目の符号（Q パリティ）を持ちます。
> **だから 2 台まで耐えられます。**

## RAID5の書き込みが遅い理由

**RAID5 の「書き込みが遅い」は、パリティを作り直す必要があるからです。**
**小さな書き込み 1 回のために、ディスクへの I/O が 4 回**発生します。

```text
  「ある1ブロックだけ書き換えたい」とき

  ① 読む   そのブロックの 古いデータ
  ② 読む   そのストライプの 古いパリティ
  ③ 書く   新しいデータ
  ④ 書く   新しいパリティ
       ▲ 論理的には「1回の書き込み」なのに、物理的には 4 回の I/O
```

**これを read-modify-write（RMW）と呼びます。**
**新しいパリティは、全部を読み直さなくても計算できます。**

```text
  新パリティ ＝ 旧パリティ XOR 旧データ XOR 新データ
                 ▲ だから「旧データ」と「旧パリティ」の 2 回の読みが要る
```

**Linux RAID wiki には、方法が 2 つあると書かれています。**

> "Updating a parity chunk requires either" the original chunk, the new chunk, and the old parity,
> "Or, all chunks (except for the parity chunk) in the stripe."

| 方法 | 読む対象 |
|:--|:--|
| **① RMW** | **旧データ ＋ 旧パリティ**（2 回の読み） |
| **② full-stripe read** | **ストライプ内の他のデータチャンク全部** |

**台数が少ないときは ② のほうが I/O が少なくなります。**
**上の「4 回」は ① の場合の数**です。
**実際にどちらが使われるかは、台数と実装で変わります。**

**RAID レベルごとの書き込み I/O 回数**

| レベル | 論理書き込み 1 回あたりの物理 I/O | 根拠 |
|:--|:--|:--|
| **RAID0** | **1** | そのまま書くだけ |
| **RAID1 / RAID10** | **2** | 2 面に書く（構造から導いた値。公式な出典は確認できていません） |
| **RAID5** | **4** | 読み 2 + 書き 2（ベンダ資料の一般的な説明） |
| **RAID6** | **6** | 読み 3 + 書き 3（パリティが 2 本） |

> **「4」「6」という数値はストレージベンダの資料で広く使われている一般的な説明**で、
> **kernel.org や Red Hat の公式文書で数値として確認できたものではありません。**
> **カーネル公式で確認できるのは RMW の仕組みそのもの**です。

**だから設計時にこうなります。**

```text
  書き込みが多い（DB のデータ領域、ログ、メール）    → RAID10
  読みが多い（ファイルサーバ、アーカイブ、配信）      → RAID5 / RAID6
```

> **ストライプ全体をまとめて書く場合は RMW が起きません**（full-stripe write）。
> 大きな連続書き込みでは RAID5 もそれなりに速くなります。
> **遅いのは「小さくランダムな書き込み」**です。

## 3つを並べて比べる

| | **RAID0** | **RAID1** | **RAID5** |
|:--|:--|:--|:--|
| **別名** | **ストライピング** | **ミラーリング** | — |
| **最低台数** | **2台** | **2台** | **3台** |
| **利用可能容量** | **全ディスクの合計** | **1 台分** | **合計から 1 台分を引いた分** |
| **冗長化** | **しない** | **する（多重化）** | **する（パリティ）** |
| **耐えられる障害** | **0 台** | **1 台でも残れば可** | **1 台まで** |
| **読み込み速度** | **速い** | やや速い | 速い |
| **書き込み速度** | **速い** | 遅め（全台に書く） | **遅め**（パリティ計算が要る） |
| **目的** | **大きく高速な領域** | **重要データの安全性** | **容量と冗長性の両立** |

**選び分けの考え方**

```text
  消えても作り直せるもの（キャッシュ、一時領域、中間ファイル）
      → RAID0      速さと容量を取る

  消えたら困るもの（OS 領域、DB のログ、設定）
      → RAID1      容量効率を犠牲にして安全を取る

  量があって、かつ消えたら困るもの（ファイルサーバ、アーカイブ）
      → RAID5      両取りする
```

## チャンクサイズ

**RAID0 / RAID5 / RAID10 では「どれくらいの大きさで区切って振り分けるか」を決めます。**
**この区切りの単位がチャンク（chunk）、別名ストライプサイズ**です。

```text
  チャンク 512KiB、ディスク2台の RAID0 に 2MiB のファイルを書くと

  ┌─ disk1 ─────────┐ ┌─ disk2 ─────────┐
  │ 0〜512KiB        │ │ 512KiB〜1MiB     │
  │ 1MiB〜1.5MiB     │ │ 1.5MiB〜2MiB     │
  └─────────────────┘ └─────────────────┘
       ▲ 512KiB ずつ交互に置かれる
```

**`mdadm` の既定チャンクサイズは 512 KiB** です。
`man 8 mdadm` に **"The default when creating an array is 512KB."** とあります。
**mdadm 3.1.1（2009 年）のアナウンスには
"The default chunk size for raid4/5/6 is now 512K." とあります。**

> **`--build`（メタデータを持たない作り方）だけは、互換性のため既定が 64KiB のまま**です
> （`man 8 mdadm`: "To ensure compatibility with earlier versions,
> the default when building an array with no persistent metadata is 64KB."）。

| 指定 | どうなるか |
|:--|:--|
| **チャンクが大きい**（1MiB など） | **大きなファイルの連続読み書きに有利**。小さな I/O では 1 台に偏る |
| **チャンクが小さい**（64KiB など） | **小さな I/O でも複数台に分散**するが、管理のオーバーヘッドが増える |

```bash
$ sudo mdadm -C /dev/md0 -l0 -n2 -c 256 /dev/sdb1 /dev/sdc1   # チャンクを256KiBにする
$ cat /proc/mdstat                     # 作ったアレイのチャンクサイズを確認する
```

> **RAID1 にチャンクサイズは関係ありません**（全台に同じものを書くだけなので区切る必要がない）。
> **`-c` が効くのは RAID0 / 4 / 5 / 6 / 10 と linear** です。
>
> **既定の 512KiB から変える判断は、実際のワークロードを測ってから**にしてください。
> **「とりあえず小さくする」は、たいてい逆効果**です。

## 容量の計算

**「◯GB のディスク N 台で RAID◯ を構成した。利用可能な容量は」という形でよく問われます。**
**業務でも容量設計のたびに使う計算**です。

| レベル | 計算式 |
|:--|:--|
| **RAID0** | **容量 × 台数** |
| **RAID1** | **容量 × 1**（台数は関係ない） |
| **RAID5** | **容量 × (台数 − 1)** |

**500GB のディスク 4 台で計算してみる**

| レベル | 計算 | 答え |
|:--|:--|:--|
| **RAID0** | **500GB × 4 = 2,000GB** | **2TB** |
| **RAID1** | **500GB × 1** | **500GB** |
| **RAID5** | **500GB × (4 − 1) = 1,500GB** | **1.5TB** |

**RAID1 は「何台使っても 1 台分」**

**RAID1 では何台のディスクを使って構成しても、1 台分の容量しか利用できません。**
**これは RAID1 は各ディスクに同じデータを保持する、という仕組みを考えれば明らかです。**

```text
  RAID1 で 4 台 → 4 枚とも中身が同じ → 見えるのは 1 枚分
```

**ここで「4 台だから 2TB」と答えてしまうのが典型的な誤答**です。

**RAID5 は台数を増やすほど得をする**

```text
  3 台 → 500 × 2 = 1TB    （効率 67%）
  4 台 → 500 × 3 = 1.5TB  （効率 75%）
  5 台 → 500 × 4 = 2TB    （効率 80%）
      ↑ パリティは常に 1 台分なので、台数が増えるほど効率が上がる
```

**ただし台数が増えるほど「2 台同時に壊れる確率」も上がります。**
**大量のディスクを束ねるときは、パリティを 2 台分持つ RAID6 を検討**します。

## 何台まで壊れて平気か

| レベル | 耐えられる障害 | 2 台壊れたら |
|:--|:--|:--|
| **RAID0** | **0 台**（1 台壊れれば全滅） | — |
| **RAID1**（2台構成） | **1 台** | **全滅** |
| **RAID1**（4台構成） | **3 台**（1 台残れば読める） | **平気** |
| **RAID5** | **1 台** | **全滅** |
| RAID6 | 2 台 | 平気 |

**RAID5 で 2 台同時はアウト**

**RAID5 はパリティという数学的に元データを復旧することができる符号を使ってデータを冗長化していますが、
これにより復旧できるのはディスク 1 台の障害まで**です。
**2 台以上に同時に障害が発生した場合は、RAID5 のパリティでは復旧ができません。**

**「1 台でも正常ならばデータが復旧できる」のは RAID1 の説明**です。
**RAID1 は同じデータをすべてのディスクに書き込み保持しているので、1 台でも無事ならば問題ありません。**

```text
  RAID5 も RAID1 もデータを冗長化しているが、
  RAID1 では 容量効率を犠牲にして RAID5 より一層の安全性を確保している
```

**再構築中がいちばん危ない**

**1 台壊れた RAID5 を交換して再構築している間は、残り全台をフルに読みます。**
**このタイミングで 2 台目が壊れると全滅**です。
**再構築中は「冗長性がゼロの RAID0 と同じ」**だと考えて扱います。

**「2 台目が壊れる」だけが危険ではありません。**
**1 ブロック読めないだけでも、そこは復元できなくなります。**

```text
  通常時      あるブロックが読めなかった
                  → パリティから計算して返せる（冗長性があるから救える）

  再構築中    あるブロックが読めなかった
                  → 救う材料がもう無い → そのブロックを復元できない
```

**これが URE（Unrecoverable Read Error、回復不能読み取りエラー）**です。
**そのブロックのデータを失う、あるいは再構築が止まる**ことになります。
**ディスクの仕様書に「10^14 ビットあたり 1 回」などと書かれている確率**で、
**正常なディスクでも起こりうる**ものです。

```text
  4TB × 6本 の RAID5 を再構築する
      → 残り5本 × 4TB ≒ 20TB ≒ 1.6 × 10^14 ビット を読む
      → URE が 10^14 ビットに 1 回なら、遭遇する確率は無視できない
```

**だから台数が多い / 容量が大きい構成では RAID6 を選びます。**
**RAID6 なら再構築中もまだ冗長性が 1 つ残っている**ので、URE が 1 回出ても救えます。

> **この URE の議論は、ストレージベンダや IBM のブログなどで広く語られているもの**で、
> **kernel.org や Red Hat の公式文書で確認できたものではありません。**
> **上の確率計算もディスクの仕様値からの試算**で、実測値ではありません。
>
> **「HDD で 6 本以上、または 1 本 4TB 以上なら RAID6」は、
> ストレージベンダの資料でよく見かける経験則**です。
> **公式な基準ではありません。**実際の判断は、使うディスクの URE 仕様値と
> 許容できるリスクから決めてください。

**再構築を少しでも安全にする**

| 対策 | 効果 |
|:--|:--|
| **ホットスペアを置く** | **冗長性ゼロの時間を最短にする** |
| **定期的に整合性チェックを走らせる** | **再構築の前に、読めないブロックを見つけて直せる**（[RAIDの監視と保守](./RAIDの監視と保守.md)） |
| **write-intent bitmap を付ける** | **一時的に外れただけのディスクなら、差分だけの再同期で済む** |
| **SMART を監視する** | **壊れる前に交換できる**（[ディスクの健全性監視_SMART](./ディスクの健全性監視_SMART.md)） |
| **同じロットのディスクで固めない** | **同時期に同じように壊れるのを避ける** |

## ホットスペア

**ホットスペアは「アレイに参加させず、待機させておく予備ディスク」**です。

```text
  通常時   [ disk1 ][ disk2 ][ disk3 ]   [ spare ]  ← 何もしていない
                                              │
  disk2 故障    [ disk1 ][  ×  ][ disk3 ]      │
                                              ▼
  自動で        [ disk1 ][ spare ][ disk3 ]  ← 人の手を介さず再構築が始まる
```

**これがあると「深夜に叩き起こされない」**のが最大の価値です。
人が現場に行ってディスクを差すまでの間、**冗長性ゼロで過ごす時間を無くせます。**

```bash
$ sudo mdadm -C /dev/md0 -l5 -n3 -x1 /dev/sd{b,c,d,e}1   # 構成3台＋予備1台
$ cat /proc/mdstat                     # (S) と表示されるのが予備
```

`man 8 mdadm` に **"If the array is degraded, it will immediately start to rebuild data onto that spare."**
（アレイが縮退していれば、ただちにそのスペアへの再構築を開始する）とあります。

**複数アレイで 1 本のスペアを共有する**

**`mdadm.conf` の `ARRAY` 行に同じ `spare-group` 名を付けると、
スペアを持たない縮退アレイへ、同じグループの別アレイからスペアが移動します。**

```text
ARRAY /dev/md0 spare-group=group1 UUID=...
ARRAY /dev/md1 spare-group=group1 UUID=...
```

`man 5 mdadm.conf` に
**"All arrays with the same spare-group name are considered to be part of the same group."** とあります。

> **このスペア移動は `mdadm --monitor`（RHEL では `mdmonitor` サービス）が動いていないと起きません。**
> **スペアを用意しただけでは不十分**で、**監視も動かす**必要があります
> （[RAIDの監視と保守](./RAIDの監視と保守.md)）。

**スペアと「未使用ディスク」の違い**

| | スペア（`-x` で登録） | 単に差してあるディスク |
|:--|:--|:--|
| `/proc/mdstat` | **`(S)` と表示される** | **出てこない** |
| 故障時 | **自動で再構築が始まる** | **人が `mdadm -a` するまで何も起きない** |

## 組み合わせたレベル

**RAID0 と RAID1 を組み合わせたものもあります。**

| 呼び方 | 構成 | 最低台数 | 特徴 |
|:--|:--|:-:|:--|
| **RAID10（1+0）** | **ミラーしてからストライプ** | **4台** | **速くて強い**。容量は半分 |
| RAID01（0+1） | ストライプしてからミラー | 4台 | RAID10 より障害に弱い |
| RAID6 | パリティを 2 台分持つ | 4台 | **2 台まで耐える**。書き込みはさらに遅い |
| linear（JBOD） | 単に連結するだけ | 2台 | 速度も冗長性も無い |

**`mdadm` の `--level=` が受け取る値**（mdadm 4.3 の `--help` で確認）

```text
  raid level: 0,1,4,5,6,10,linear,multipath and synonyms
```

**RAID10 と RAID01 はなぜ耐性が違うのか**

**表に「RAID01 は RAID10 より障害に弱い」と書きましたが、
理由は「どの 2 台が壊れたら死ぬか」を数えると分かります。**

```text
  【RAID10（1+0）】 まずミラー、それをストライプ
      ┌── ミラー対A ──┐  ┌── ミラー対B ──┐
      │ D1   ≡   D2   │  │ D3   ≡   D4   │
      └───────┬───────┘  └───────┬───────┘
              └──── ストライプ ────┘
      → 死ぬのは「同じミラー対の2台」が壊れたときだけ

  【RAID01（0+1）】 まずストライプ、それをミラー
      ┌─ ストライプ群X ─┐  ┌─ ストライプ群Y ─┐
      │ D1   +   D2    │≡ │ D3   +   D4    │
      └────────────────┘  └────────────────┘
      → 片方の群が1台でも欠けるとその群ごと死ぬ
         両方の群から1台ずつ壊れると全滅
```

**4 台構成で「2 台壊れる組み合わせ」は全部で 6 通り**です。
**どの組み合わせで生き残るかを並べると差が見えます。**

| 壊れた 2 台 | RAID10 | RAID01 |
|:--|:-:|:-:|
| D1 と D2（同じミラー対 / 同じストライプ群） | **全滅** | **生存** |
| D3 と D4（同じミラー対 / 同じストライプ群） | **全滅** | **生存** |
| D1 と D3 | **生存** | **全滅** |
| D1 と D4 | **生存** | **全滅** |
| D2 と D3 | **生存** | **全滅** |
| D2 と D4 | **生存** | **全滅** |
| **生存する割合** | **6 通り中 4 通り** | **6 通り中 2 通り** |

**だから「ミラーしてからストライプ」（RAID10）のほうを選びます。**

> SUSE の公式ドキュメントも
> **"RAID 0+1 provides high levels of I/O performance and data redundancy,
> but slightly less fault tolerance than a 1+0."** と記述しています。
>
> **上の 6 通りの表は、この構造から導いたもの**です。
> **Red Hat の公式ドキュメントには RAID 0+1 の記述が無く**、
> この表そのものの公式な出典は確認できていません。
>
> なお **`mdadm` の `raid10` は古典的な 1+0 とは別の独自実装**で、
> 3 台や 5 台など偶数以外の台数でも組めます。
> **`--layout`（`n` near / `f` far / `o` offset、既定は `n2`）で複製の置き方が変わります**
> （[ソフトウェアRAIDの管理_mdadm](./ソフトウェアRAIDの管理_mdadm.md)）。
> **置き方が変われば、どの 2 台が壊れたときに生き残るかも変わりえます**が、
> その対応関係は実機で確認できていないため、上の表は古典的な 1+0 の話として読んでください。

**実務では RAID10 か RAID6 の二択**になることが多いです。

```text
  DB のデータ領域（書き込みが多い）        → RAID10
  ファイルサーバ・アーカイブ（読みが多い）  → RAID6
```

## クラウドではRAIDをどう考えるか

**クラウドのブロックストレージは、すでにその内部で冗長化されています。**
**そのため「冗長化のための RAID」は原則として不要**になります。

**AWS EBS の場合（AWS 公式ドキュメントの見解）**

| レベル | AWS の見解 |
|:--|:--|
| **RAID0** | **推奨**。"Use RAID 0 when I/O performance is of the utmost importance."（I/O 性能が最優先なら使う） |
| **RAID1** | **非推奨**。"RAID 1 requires more Amazon EC2 to Amazon EBS bandwidth than non-RAID configurations"／"RAID 1 does not provide any write performance improvement." |
| **RAID5 / RAID6** | **非推奨**。"the parity write operations of these RAID modes consume some of the IOPS available to your volumes"／RAID0 比で **"20-30% fewer usable IOPS"** |

**なぜ RAID1 が不要なのか**は、AWS 自身がこう書いています。

> "Amazon EBS volume data is replicated across multiple servers in an Availability Zone
> to prevent the loss of data from the failure of any single component."
> （EBS のデータは AZ 内の複数サーバに複製されており、単一コンポーネントの障害ではデータを失わない）

**つまりクラウドでは RAID の役割が変わります。**

```text
  オンプレ    RAID = 冗長化 ＋ 性能
  クラウド    冗長化はストレージ側がやる
              RAID0 = 1ボリュームの上限を超えるスループット / IOPS を出すため
```

> **RAID0 の危険性は変わりません。**
> AWS も **"the loss of a single volume in the set results in a complete data loss for the array."**
> と明記しています。**冗長化はされていても、RAID0 で束ねた 1 本が切り離されれば全滅**です。
>
> また AWS は **"You should avoid booting from a RAID volume."**（RAID ボリュームからの起動は避ける）
> とも書いています。
>
> **GCP の Persistent Disk も「複数の物理ディスクに分散して書く」と公式に記述**されていますが
> （"Compute Engine stores data on Persistent Disk with multiple parallel writes to ensure built-in redundancy."）、
> **RAID の方針についての明確な公式見解は確認できていません。**

**クラウドで RAID0 を組むときの考え方**

| 目的 | 代わりの手 |
|:--|:--|
| **スループットが足りない** | **まずボリューム 1 本の上限を上げる**（gp3 なら IOPS / スループットを個別に指定できる） |
| **それでも足りない** | **RAID0 で複数ボリュームを束ねる**。ただし全滅リスクを受け入れる |
| **消えたら困るデータ** | **スナップショット（EBS Snapshot）で守る**。RAID では守らない |

> **RAID0 で複数ボリュームを束ねている場合、ボリュームを個別にスナップショットしても
> 互いの整合は取れません。**
> **AWS は複数ボリュームをまとめて取る multi-volume snapshots を用意**しています。
> **束ねたなら、スナップショットも束ねて取る**——ここを合わせてください。

## 説明の入れ替えに気をつける

**この分野の設問は「説明のうち誤っているものはどれか」という形が中心です。**
**レベル同士の説明を入れ替えたものが必ず紛れ込みます。**

| 説明 | 本当はどのレベルか |
|:--|:--|
| **ストライピングとも呼ばれる** | **RAID0** |
| **ミラーリングとも呼ばれる** | **RAID1** |
| **データを多重化することで信頼性を高める** | **RAID1** |
| **パリティを利用することでデータを冗長化する** | **RAID5** |
| **1 台でも正常ならばデータが復旧できる** | **RAID1** |
| **構成ディスクのうち 1 台をパリティ専用に使う** | **RAID3 / RAID4**（RAID5 ではない） |
| **台数を増やすほど利用できる容量が増加する** | **RAID0 と RAID5**（RAID1 は増えない） |
| **冗長化を一切行わない** | **RAID0** |

**キーワードで引ける表**

```text
  「ストライピング」「直列化」「冗長化しない」      → RAID0
  「ミラーリング」「並列化」「多重化」「同一データ」 → RAID1
  「パリティ」「分散して保持」「3 台以上」          → RAID5
  「パリティ専用ディスク」                         → RAID3 / RAID4
```
