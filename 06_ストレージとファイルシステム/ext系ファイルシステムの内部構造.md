## まずこれだけ

| ブロックの種類 | 何を保持しているか |
|:--|:--|
| **データブロック** | **実際のファイル内容** |
| **i ノードブロック** | **ファイル単位のメタ情報**（ファイルサイズ、アクセス権、所有者、各種日時など） |
| **スーパーブロック** | **ファイルシステム全体に関わる重要な情報**（マウント回数、ブロックサイズ、データブロック数など） |

**押さえる 4 点**

| 論点 | 結論 |
|:--|:--|
| ブロックサイズ | **ファイルシステムの作成時に決まり、あとから変わらない**。`1024` / `2048` / `4096` バイトのいずれか |
| i ノードの数 | **作成時に決められ、ファイルを作っても増えない**。使い切るとファイルが作れなくなる |
| スーパーブロックの数 | **1 つではない**。ブロックグループごとにコピーが置かれ**冗長化**されている |
| ジャーナリング | **整合性チェックと修復を助ける**機能。**「完全性を保証する」わけではない** |

**中身を見るコマンド**

| やりたいこと | コマンド |
|:--|:--|
| **スーパーブロックの内容を見る** | **`dumpe2fs -h デバイス`** または **`tune2fs -l デバイス`** |
| **予備スーパーブロックの位置を調べる** | **`dumpe2fs デバイス` の `Backup superblock at`** |
| **i ノードの空きを見る** | **`df -i`** |
| 個々の i ノードを覗く | `debugfs デバイス` の `stat` |

## ブロックという単位

**ext2 / ext3 / ext4 ファイルシステムは「ブロック」という単位でデータを管理しています。**

ディスクの物理的な最小単位はセクタ（512 バイトまたは 4096 バイト）ですが、
**ファイルシステムはそれをまとめた「ブロック」という単位で扱います。**

```text
  物理ディスク    セクタ（512B）が並んでいるだけ
        ↓
  ファイルシステム  ブロック（1024B / 2048B / 4096B）にまとめて管理する
        ↓          ├─ データブロック      … ファイルの中身
                   ├─ i ノードブロック    … ファイルごとの情報
                   └─ スーパーブロック    … ファイルシステム全体の情報
```

**「ブロック」という同じ名前で 3 つの違う役割のものを指す**ので、
**まずこの 3 つを区別する**ところから始めます。

---

## 3種類のブロックを見分ける

**試験では「◯◯ブロックの説明として正しいものはどれか」という形で問われます。**
**選択肢は 3 つの役割を入れ替えたもの**なので、表で押さえるのが最短です。

| 説明 | データブロック | i ノードブロック | スーパーブロック |
|:--|:-:|:-:|:-:|
| **実際のファイル内容を保持している** | **○** | ✕ | ✕ |
| **各ファイルについてのメタ情報を保持している** | ✕ | **○** | ✕ |
| **マウント回数やブロックサイズなどの情報を含む** | ✕ | ✕ | **○** |
| **ブロック内に複数の i ノードが含まれている** | ✕ | **○** | ✕ |
| **冗長化されており、同一の内容が複数存在する** | ✕ | ✕ | **○** |
| **ブロックサイズはファイルシステム作成時に決められる** | **○** | ○ | ○ |
| ブロックサイズは格納するファイル内容に応じて変化する | ✕ | ✕ | ✕ |
| 新しいファイルを作成するごとに追加されていく | ✕ | ✕ | ✕ |

**引っかかりやすい 3 つ**

| 誤りの選択肢 | どこが違うか |
|:--|:--|
| **データブロックは「ファイルサイズについてのメタ情報を含む」** | **メタ情報を持つのは i ノードブロック**。データブロックは中身だけ |
| **i ノードブロックは「マウント回数やブロックサイズなどの情報を含む」** | **i ノードが持つのはファイル単位の情報に限られる**。全体の情報はスーパーブロック |
| **スーパーブロックは「各ファイルについてのメタ情報を含む」** | **これは i ノードブロックの説明**。スーパーブロックは全体についてのメタデータ |

**覚え方**

```text
  スーパーブロック   ファイルシステム 全体 の情報   … 会社の就業規則
  i ノードブロック   ファイル 1 つ分 の情報        … 社員の人事カード
  データブロック     ファイルの 中身               … 社員が書いた書類そのもの
```

## データブロック

**データブロックは実際のファイル内容を保持しているブロック**です。

### ブロックサイズは作成時に決まる

**ext2 / ext3 ファイルシステムでは各データをブロックという単位で管理しており、
そのサイズはファイルシステムを作成する際に `1024` / `2048` / `4096` バイトのいずれかに決定されます。**

```bash
$ sudo mke2fs -b 1024 /dev/sda3                # ブロックサイズを 1024 バイトで作る
```

**`-b` がブロックサイズの指定**です（[ディスクを追加する手順](./ディスクを追加する手順.md) の
`mke2fs` のオプション表にあります）。

**重要なのは「作成時に決まり、あとから変わらない」**という点です。

| よくある誤解 | 実際 |
|:--|:--|
| **ブロックサイズは格納するファイル内容に応じて変化する** | **誤り。作成時に決められており固定** |
| ファイルが大きければブロックも大きくなる | **誤り。大きいファイルは複数のブロックに分けて格納される** |

### 小さいファイルでも1ブロックを占有する

**大きなファイルを扱う場合には複数のデータブロックに分けてデータを格納し、
ブロックサイズ未満の小さなファイルを扱う場合には 1 ブロックを占有します。**

```text
  ブロックサイズ 4096 バイトのとき

  10000 バイトのファイル  →  ブロック3つ（4096 + 4096 + 1808 使用、残り 2288 は無駄）
      1 バイトのファイル  →  ブロック1つ（4096 まるごと占有。4095 バイトが無駄）
```

**どちらの場合も、ブロック単位でデータが格納されるという点が重要**です。

**だからブロックサイズの選び方に意味が出てきます。**

| 状況 | 向いているブロックサイズ | 理由 |
|:--|:--|:--|
| **小さいファイルが大量にある**（メールスプール、キャッシュ） | **1024** | 端数の無駄が小さくなる |
| **大きいファイルが中心**（動画、DB のデータファイル） | **4096** | 1 ファイルあたりのブロック数が減り、管理が速い |
| 判断がつかない | **4096**（既定） | 現代のディストリビューションの既定値 |

## iノードブロック

**i ノードブロックはファイルのメタ情報（ファイルサイズ、アクセス権、所有者、各種日時など）を
保持しているブロック**です。

### 1ブロックに複数のiノードが入る

**i ノード 1 つのサイズは小さいため、ブロックサイズに応じて
i ノードブロック内に i ノードが複数格納されています。**

```text
  ブロックサイズ 1024 バイト、i ノード 128 バイトのとき

  ┌──────── i ノードブロック（1024 バイト）────────┐
  │ inode │ inode │ inode │ inode │ inode │ ... │   1024 / 128 = 8 個
  └───────────────────────────────────────────────┘
```

> **実機で確認した注意**
> **Ping-t の解説では i ノード 1 つのサイズを 128 バイト**としています。
> **`e2fsprogs 1.47.0` の既定は 256 バイト**でした。
> 試験では **128 バイト**で計算して構いませんが、**実機の値は `dumpe2fs` で確認**します。
> **「1 ブロックに複数の i ノードが入る」という結論は、どちらでも変わりません。**

```bash
$ sudo dumpe2fs -h /dev/sdb1 | grep -i "inode size"   # 実際の i ノードサイズを見る
Inode size:               256
```

### iノードは作成時に確保され増えない

**i ノードブロックの数はファイルシステムの作成時に決められ、
その数に応じた i ノードがあらかじめ確保されています。**

**ファイルを作成する際には、そのうち未使用のものを消費しています。
ファイルを追加しても i ノード（ブロック）が増えることはありません。**

**したがって、ファイルをあまりに大量に作りすぎると
i ノードが尽きてしまい、それ以上ファイルが作成できないという問題が起こります。**

```bash
$ df -i /data                                  # i ノードの使用状況を見る
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sdb1       655360  12043  643317    2% /data
```

**`df` は容量、`df -i` は i ノード**です。
**「No space left on device と言われるのに `df` では空いている」**ときは、
**まず `df -i` を見る**のが定石です。

```text
  df       … Use%   が 100% → 容量が足りない
  df -i    … IUse%  が 100% → i ノードが足りない  ← こちらは df だけでは見えない
```

**作成時に i ノード数を増やしておく方法**

```bash
$ sudo mke2fs -N 1000000 /dev/sdb1             # i ノード数を直接指定する
$ sudo mke2fs -i 4096 /dev/sdb1                # 4096 バイトごとに i ノードを 1 つ作る
$ sudo mke2fs -n /dev/sdb1                     # 作らずに、できあがる i ノード数だけ確認する
```

**`-n`（実際には実行せず確認のみ）で事前に足りるか見ておく**のが実務での使い方です。

### ファイル名はどこにあるのか

> **Ping-t の解説では、i ノードが保持するメタ情報の例として「ファイル名」が挙げられています。**
> **実装上は、ファイル名は i ノードではなくディレクトリ（のデータブロック）が持ちます。**
> ディレクトリは「ファイル名 → i ノード番号」の対応表であり、i ノード自身は名前を持ちません。
> **「i ノードはファイル単位のメタ情報を持つ」という結論は変わらない**ので、
> **試験では Ping-t の説明のまま**で差し支えありませんが、
> **ハードリンクが「同じ i ノードに別の名前を付ける」仕組みなのは、この構造によるもの**です。

```bash
$ ls -i /etc/hosts                             # ファイルの i ノード番号を見る
131073 /etc/hosts
$ stat /etc/hosts                              # i ノードが持っている情報を見る
```

## スーパーブロック

**スーパーブロックはファイルシステム全体に関わる重要な情報を保持しているブロック**です。

### ファイルシステム全体の情報を持つ

| 保持している情報 | 例 |
|:--|:--|
| **ブロックサイズ** | `1024` / `2048` / `4096` |
| **データブロック数** | 総ブロック数と空きブロック数 |
| **i ノード数** | 総数と空き数 |
| **マウント回数** | 前回の検査から何回マウントしたか |
| **予約ブロック数** | root 用予備領域の大きさ |
| ファイルシステムの状態 | `clean` / `not clean` |
| ラベル・UUID | `e2label` や `tune2fs -L` で設定した値 |
| 前回検査した日時 | 自動 fsck の判断に使う |

**ラベルもスーパーブロックの中に保存されています。**
`e2label` で付けたラベルの置き場所がここです。

### 冗長化されている

**スーパーブロックの保持する情報は特に重要なので、
ブロックグループというファイルシステム内の単位ごとにコピーが作られ、冗長化されています。**

```text
  ┌─ ブロックグループ0 ─┬─ ブロックグループ1 ─┬─ ブロックグループ2 ─┬ ...
  │ スーパーブロック    │ 予備のコピー        │ 予備のコピー        │
  │ （これが使われる）  │                     │                     │
  └────────────────────┴────────────────────┴────────────────────┘
```

**これにより、何らかの理由でメインのスーパーブロックの内容が不正に書き換わってしまった場合にも、
他のバックアップスーパーブロックから正しい内容を復元することができます。**

**復元には `e2fsck` コマンドの `-b` オプション**を使います。

```bash
$ sudo dumpe2fs /dev/sdb1 | grep -i "superblock at"   # 予備の位置を調べる
  Primary superblock at 1, Group descriptors at 2-2
  Backup superblock at 8193, Group descriptors at 8194-8194
  Backup superblock at 24577, Group descriptors at 24578-24578
  Backup superblock at 40961, Group descriptors at 40962-40962
$ sudo e2fsck -b 8193 /dev/sdb1                # 予備を使って復元する
```

**位置はブロックサイズによって変わります。**

| ブロックサイズ | 最初の予備スーパーブロック |
|:--|:--|
| **1024 バイト** | **8193** |
| **2048 / 4096 バイト** | **32768** |

**試験でよく出る `32768` は、ブロックサイズ 4096 のときの値**です。
**実際の位置は必ず `dumpe2fs` で調べます。**

詳しい復旧手順は [fsckとファイルシステムの修復](./fsckとファイルシステムの修復.md) にあります。

## ジャーナリング

### 何をしているのか

**ジャーナリングとは、実データをディスクに書き込む前にメタデータを専用の領域に書き込んでおくことで、
不正にシステムが終了してしまいファイルシステム内での整合性がとれなくなってしまう状況を防ぐ機能**です。

```text
  ジャーナルなし（ext2）
    ① メタデータを書く ──┐ ここで電源断
    ② データを書く    ──┘ → 「書いたつもりの情報」と「実際の中身」が食い違う
                            → 起動時に全体を舐めて検査するしかない（数十分）

  ジャーナルあり（ext3 / ext4）
    ① これから何をするかをジャーナル領域に書く
    ② メタデータを書く ──┐ ここで電源断
    ③ データを書く    ──┘
    ④ ジャーナルの記録を消す
                            → 起動時にジャーナルを読み、やり残しだけを片付ける（数秒）
```

**検査が高速化され、修復率も向上します。**

### 完全性の保証ではない

**試験で最も狙われるのはここです。**

| 選択肢 | 正誤 | 理由 |
|:--|:-:|:--|
| **ファイルシステムの整合性チェック、および修復を助ける機能である** | **○** | **これが正しい説明** |
| **ファイルシステムの完全性を保証する機能である** | **✕** | **「完全性を保証」まではできない** |
| ファイルシステムのアクセス高速化のための機能である | ✕ | 全くの誤り |
| ファイルシステムのバックアップ、および復元を助ける機能である | ✕ | 全くの誤り |

**チェックが高速化され、修復率も向上しますが、
ジャーナリング機能によりシステムクラッシュ時にファイルシステムを確実に保護できるわけではありません。**

**なぜ「保証」できないのか**

| 理由 | 説明 |
|:--|:--|
| **既定では メタデータ しか守らない** | ext3 / ext4 の既定は `data=ordered`。**ファイルの中身そのものは書き戻されない** |
| **ディスク自体の故障は対象外** | 不良セクタやコントローラ障害はジャーナルでは救えない |
| **ジャーナル領域自体が壊れることもある** | 同じディスク上にあるため無敵ではない |

**「整合性を保つのを助ける」であって「データを守る」ではない**、と覚えます。
**データを守るのはバックアップの仕事**です。

### ジャーナルを持つファイルシステム

**ext3 / ext4 以外にも ReiserFS、XFS 等、高機能なファイルシステムはジャーナリング機能を持っています。**
**内部の仕組みは ext3 / ext4 と異なる場合もありますが、機能としては同様**です。

| ファイルシステム | ジャーナル |
|:--|:-:|
| **ext2** | **✕** |
| **ext3 / ext4** | **○** |
| **XFS** | **○** |
| **ReiserFS** | **○** |
| **JFS** | **○** |
| **Btrfs** | **✕（CoW という別方式で同じ目的を達成する）** |

**ext2 と ext3 の主な違いはジャーナリング機能を持っているかどうかであり、
その他の部分では両者の間には高い互換性があります。**

**だから `tune2fs -j` であとから変換できます。**

```bash
$ sudo tune2fs -j /dev/sdb1                    # ext2 にジャーナルを足して ext3 にする
tune2fs 1.47.0 (5-Feb-2023)
Creating journal inode: done
```

**この `tune2fs -j` は、データを退避する必要がないばかりか、
対象の ext2 ファイルシステムをマウントしたままでも ext3 に変換でき、
極めて小さな労力で目的を達成できます。**

| 方法 | 使えるか | 労力 |
|:--|:-:|:--|
| **`tune2fs -j デバイス`** | **○** | **最小。マウントしたままでよい** |
| `mke2fs -j デバイス` | ✕ | **作り直しなのでデータが消える** |
| `debugfs` の対話環境 | ✕ | **ext2 → ext3 の変換は扱えない** |
| 退避 → `mke2fs -j` → 書き戻し | △ | できるが `tune2fs` より遥かに手間がかかる |

変換の全体像は [Btrfsとサブボリューム](./Btrfsとサブボリューム.md) の「ファイルシステムの変換」にもあります。

## root用予備領域

**root ユーザ用の予備領域とは、通常の領域とは別に確保された root ユーザのみが使える予備領域**で、
**予約ブロック**とも言います。

**このように分けておくことで、通常の領域を使い切ってしまった場合にも、
root ユーザは専用の領域を使ってメンテナンス作業が可能になります。**

**既定は 5%** です。

| やりたいこと | コマンド |
|:--|:--|
| **作成時に割合を決める** | **`mke2fs -m 1 /dev/sda1`** |
| **作成後に割合を変える** | **`tune2fs -m 1 /dev/sda1`** |

```bash
$ sudo tune2fs -m 1 /dev/sda1                  # 予備領域を 5% から 1% に変更する
tune2fs 1.47.0 (5-Feb-2023)
Setting reserved blocks percentage to 1% (163 blocks)
```

**`mke2fs` はファイルシステムを作成するコマンドなので、
作成済みのものを変えたいときは `tune2fs` を使います。**

| 書き方 | 意味 |
|:--|:--|
| **`tune2fs -m 1 /dev/sda1`** | **予備領域を 1% にする**（正しい） |
| `tune2fs -L 1 /dev/sda1` | **ラベルを `1` にする**。予備領域は変わらない |
| `mke2fs -m 1 /dev/sda1` | **作り直してしまう**。作成済みには使わない |
| `mke2fs -L 1 /dev/sda1` | 同上 |

**`-m` は margin、`-L` は Label** と結びつけると取り違えません。

**実務での目安**

| 用途 | 割合 |
|:--|:--|
| **ルートファイルシステム** | **5%（既定のまま）**。空きゼロで root がログインできなくなるのを防ぐ |
| **データ専用のディスク** | **0 〜 1%**。1TB で 5% なら 50GB が使えないままになる |

## 手を動かして確かめる

**① ブロックサイズを指定して作り、内部構造を見る**

```bash
$ dd if=/dev/zero of=t.img bs=1M count=64      # 64MB の空ファイルを用意する
$ mke2fs -q -b 1024 t.img                      # ブロックサイズ 1024 で ext2 を作る
$ dumpe2fs -h t.img                            # スーパーブロックの内容だけを表示する
Inode count:              16384
Block count:              65536
Reserved block count:     3276
Free blocks:              60124
Free inodes:              16373
Block size:               1024
Blocks per group:         8192
Inode blocks per group:   512
Inode size:               256
```

**読み取れること**

| 欄 | 値 | 意味 |
|:--|:--|:--|
| **`Block size`** | `1024` | **指定どおりのブロックサイズになっている** |
| **`Block count`** | `65536` | **1024 × 65536 = 64MB。指定した容量と一致する** |
| **`Reserved block count`** | `3276` | **65536 の 5%。既定の予備領域** |
| **`Inode count`** | `16384` | **作成時に確保された i ノードの総数。これ以上は増えない** |
| **`Inode blocks per group`** | `512` | **2048 個 × 256 バイト ÷ 1024 = 512 ブロック。計算が合う** |

**② 予備スーパーブロックの位置を調べる**

```bash
$ dumpe2fs t.img | grep -i "superblock at"   # 予備スーパーブロックの位置を調べる
  Primary superblock at 1, Group descriptors at 2-2
  Backup superblock at 8193, Group descriptors at 8194-8194
  Backup superblock at 24577, Group descriptors at 24578-24578
  Backup superblock at 40961, Group descriptors at 40962-40962
  Backup superblock at 57345, Group descriptors at 57346-57346
```

**ブロックサイズ 1024 なので、最初の予備は 8193**です。

**③ 予備領域の割合を変える**

```bash
$ tune2fs -m 1 t.img                           # 5% から 1% へ
Setting reserved blocks percentage to 1% (655 blocks)
$ dumpe2fs -h t.img | grep -i reserved         # 予備領域が変わったか確かめる
Reserved block count:     655
```

**④ ext2 を ext3 に変換する**

```bash
$ blkid u.img                                  # 変換前
u.img: UUID="92e6..." BLOCK_SIZE="4096" TYPE="ext2"
$ tune2fs -j u.img                             # ジャーナルを足す
Creating journal inode: done
$ blkid u.img                                  # 変換後
u.img: UUID="92e6..." SEC_TYPE="ext2" BLOCK_SIZE="4096" TYPE="ext3"
```

**UUID が変わっていない**のがポイントです。**`/etc/fstab` を書き換える必要がありません。**

**⑤ i ノード枯渇を再現する**

```bash
$ mke2fs -q -b 1024 -N 32 i.img                # i ノードを 32 個しか作らない
$ sudo mount -o loop i.img /mnt/test           # ループバックでマウントする
$ df -i /mnt/test                              # i ノードの使用状況
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop0         32    11    21   35% /mnt/test
$ sudo touch /mnt/test/f{1..30}                # 空ファイルを 30 個作る
touch: cannot touch '/mnt/test/f22': No space left on device
$ df -i /mnt/test                              # i ノードは使い切っている
/dev/loop0         32    32     0  100% /mnt/test
$ df -h /mnt/test                              # 容量はまだ空いている
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0      8.0M   14K  7.6M   1% /mnt/test
```

**「容量は空いているのに No space left on device」**が再現できます。
**このとき見るべきは `df -h` ではなく `df -i`** です。

## 結果画面の見方

**`dumpe2fs -h` の出力**

```text
Filesystem volume name:   <none>
Filesystem features:      ext_attr resize_inode dir_index filetype sparse_super large_file
Filesystem state:         clean
Inode count:              16384
Block count:              65536
Reserved block count:     3276
Free blocks:              60124
Free inodes:              16373
Block size:               1024
Inode size:               256
Mount count:              0
Maximum mount count:      -1
Reserved blocks uid:      0 (user root)
```

| 欄 | 何が分かるか | 見るべきとき |
|:--|:--|:--|
| **`Filesystem features`** | **有効な機能**。`has_journal` があれば ext3 以上 | **ext2 か ext3 かを判別したいとき** |
| **`Filesystem state`** | **`clean` なら正常に外された。`not clean` なら異常終了している** | **障害後の一次確認** |
| **`Inode count` / `Free inodes`** | **i ノードの総数と空き** | **「ファイルが作れない」とき** |
| **`Block count` / `Free blocks`** | **ブロックの総数と空き** | 容量の確認 |
| **`Reserved block count`** | **root 用予備領域の大きさ**（ブロック数） | 割合を見直すとき |
| **`Block size`** | **ブロックサイズ。あとから変えられない** | 設計の見直し |
| **`Inode size`** | i ノード 1 つのサイズ | 1 ブロックに何個入るかの計算 |
| **`Maximum mount count`** | **`-1` は「回数では自動 fsck しない」** | 自動検査の設定確認 |

**`tune2fs -l` でも同じ内容が見られます。**

```text
  dumpe2fs -h デバイス    スーパーブロックの内容 だけ を表示する（専用コマンド）
  dumpe2fs    デバイス    ＋ ブロックグループの情報まで大量に出る
  tune2fs -l  デバイス    スーパーブロックの内容を表示する（設定コマンドの表示機能）
```

**「スーパーブロックを参照して i ノード数・ブロックサイズ・空きブロック数・予約ブロック数を確認する」
という問いの答えは `dumpe2fs` と `tune2fs -l` の 2 つ**です。

| コマンド | スーパーブロックの内容を確認できるか |
|:--|:-:|
| **`dumpe2fs`** | **○** |
| **`tune2fs -l`** | **○** |
| `tune2fs -L` | ✕（**ラベルを設定する**オプション） |
| `e2label` | ✕（**ラベルを操作する**コマンド。設定したラベルはスーパーブロック内に保存されるが、内容の確認はできない） |
| `e2fsck -b` | ✕（**スーパーブロックを修復する**オプション。確認ではない） |

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| **`No space left on device` なのに `df` は空いている** | **i ノードの枯渇** | **`df -i` で確認**。不要な小ファイルを消すか、作り直して `-N` / `-i` で増やす |
| **ブロックサイズを後から変えたい** | **作成時に決まるので変えられない** | **`mke2fs -b` で作り直す**しかない |
| **`tune2fs -L 1` で予備領域が変わらない** | **`-L` はラベル、`-m` が予備領域** | **`tune2fs -m 1`** を使う |
| **`e2fsck -b 32768` が失敗する** | **ブロックサイズが 1024 だと予備は 8193** | **`dumpe2fs` で実際の位置を調べる** |
| **`mke2fs -j` で既存を ext3 にしようとした** | **`mke2fs` は作成コマンド。データが消える** | **`tune2fs -j`** を使う |
| **`mke2fs -L ext3` で ext3 を作ったつもり** | **`-L` はラベル名。形式は ext2 のまま** | **`-j` か `-t ext3`** を使う |
| **ジャーナルがあるからデータは守られると思った** | **既定はメタデータのみ。中身は対象外** | **バックアップは別途必要** |
| **`debugfs` で ext2 を ext3 に変換しようとした** | **`debugfs` は調査・操作用で、変換は扱えない** | **`tune2fs -j`** を使う |

## クラウド実務メモ

**① EBS / Persistent Disk を増設したときの既定値を知っておく**

**クラウドのボリュームは「大きいファイルが中心」であることが多い**ので、
**既定の 4096 バイトで作って構いません。**

```bash
$ sudo mkfs.ext4 /dev/nvme1n1                  # 既定（4096バイト）で作る
$ sudo dumpe2fs -h /dev/nvme1n1 | grep -i "block size"   # 既定のブロックサイズを確認する
Block size:               4096
```

**② データ専用ボリュームは予備領域を削る**

```bash
$ sudo tune2fs -m 0 /dev/nvme1n1               # データ専用なら 0% にしてよい
```

**1TB の EBS で 5% なら 50GB、gp3 の料金で月あたり数ドルが使えないまま**です。
**ルートボリュームは 5% のまま残します**（空き 0 で root が入れなくなるのを防ぐため）。

**③ コンテナのイメージ置き場は i ノードが枯渇しやすい**

**`/var/lib/docker` や `/var/lib/containerd` は小さいファイルが膨大に増えます。**
**監視は「容量」だけでなく「i ノード」も見ます。**

```bash
$ df -i /var/lib/docker                        # i ノードの使用率を見る
```

**CloudWatch や Ops Agent の既定メトリクスは容量だけのことがある**ので、
**`disk_inodes_free` を明示的に有効にしておく**と、深夜の障害を 1 つ減らせます。

**④ AMI やゴールデンイメージを作るときは `Filesystem state` を確認する**

```bash
$ sudo dumpe2fs -h /dev/nvme0n1p1 | grep -i state        # 正常に外されたか確認する
Filesystem state:         clean
```

**`not clean` のままスナップショットを取ると、そこから起動した全インスタンスが
起動時 fsck を走らせます。** 停止してからスナップショットを取るのが安全です。

**⑤ Terraform / Ansible で作るときも `-m` は明示する**

```yaml
# Ansible の例：意図を残すために既定値でも書いておく
- name: データ用ファイルシステムを作成する
  community.general.filesystem:
    fstype: ext4
    dev: /dev/nvme1n1
    opts: -m 0 -L DATA            # 予備領域 0%、ラベル DATA
```

**「なぜ 0% なのか」をコードに残す**ことが、半年後の自分と次の担当者を助けます。
