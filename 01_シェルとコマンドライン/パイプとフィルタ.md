## まずこれだけ

| 記号 / コマンド | 何をするか | 一言 |
|:--|:--|:--|
| `\|` | 左の**標準出力**を右の**標準入力**につなぐ | **ファイルを経由しない** |
| `2>&1 \|` | 標準エラー出力も一緒に右へ渡す | `\|` だけでは**エラーは流れない** |
| `tee` | 標準入力を**画面とファイルの両方**に出す | 三叉路（T字）のイメージ |
| `xargs` | 標準入力の文字列から**コマンドラインを組み立てる** | 「渡す」ではなく「**組み立てる**」 |
| `tr` | **1 文字単位**で置換・削除・圧縮する | **標準入力からしか読まない** |
| `wc` | 行数・語数・バイト数を数える | `-l` `-w` `-c` |

**最重要の 2 つ**

1. **`|` が運ぶのは 1 番（標準出力）だけ。** エラーも渡したいなら `2>&1 |` と書く
2. **`xargs` は「標準入力を右のコマンドの標準入力に渡す」のではない。** 標準入力の中身を**引数に並べ直して、新しいコマンドラインを作る**

## パイプとは何か

### 出口と入口を直接つなぐ

リダイレクトは**出口をファイルにつなぎ替える**操作でした。
パイプは**出口を、別のコマンドの入口に直接つなぐ**操作です。

```text
 リダイレクト
   コマンドA ── 1番 ──▶ ファイル

 パイプ
   コマンドA ── 1番 ──▶ 0番 ── コマンドB
                    ↑
              ファイルを経由しない
```

同じことをリダイレクトだけでやると、**一時ファイルが必要**になります。

```bash
$ dmesg > /tmp/tmp.txt     # いったんファイルに落として
$ less /tmp/tmp.txt        # それを読む
$ rm /tmp/tmp.txt          # 後始末が要る
```

パイプなら 1 行です。

```bash
$ dmesg | less             # カーネルメッセージをページ送りで読む
```

**一時ファイルが要らない・ディスクに書かない・後始末が要らない。**
これがパイプを使う理由です。

> **補足**：パイプの実体は**カーネルが用意する名前の無いバッファ**です。
> 左が書き、右が読む。バッファが一杯なら左が待ち、空なら右が待ちます。
> ディスク上のファイルではないので、`ls` しても見えません。

---

### パイプに乗るのは 1 番だけ

**ここが最初のつまずきどころ**です。
`|` が右に渡すのは**標準出力（1 番）だけ**で、**標準エラー出力（2 番）は渡りません**。

存在しないディレクトリを `ls` して、行数を数えてみます。

```bash
$ ls /nonexistent | wc -l                    # エラーはパイプに乗らない
ls: cannot access '/nonexistent': No such file or directory
0
```

**エラーメッセージは画面にそのまま出て、`wc -l` は 0 を返しました。**
2 番は端末に直結したままで、パイプを素通りしたからです。

```text
 ls ── 1番 ──▶ 0番 ── wc      （1番には何も来ていない → 0 行）
    └─ 2番 ──▶ 端末           （エラーはここに出た）
```

両方を渡したいなら、**パイプの手前で 2 番を 1 番に合わせます**。

```bash
$ ls /nonexistent 2>&1 | wc -l               # 2番を1番に合わせてから渡す
1
```

```bash
$ ls /nonexistent 2>&1 | tr a-z A-Z          # エラーもフィルタに通せる
LS: CANNOT ACCESS '/NONEXISTENT': NO SUCH FILE OR DIRECTORY
```

**`2>&1` は `|` の左側、コマンドの直後に書きます。**
`| 2>&1` のように右側に書くのは誤りです。

なお、**エラーだけ別ファイルに逃がす**書き方もできます。

```bash
$ ls /nonexistent 2> err.log | wc -l         # 1番はパイプへ、2番はファイルへ
0
$ cat err.log                                 # エラーはこちらに残っている
ls: cannot access '/nonexistent': No such file or directory
```

> **bash 限定の省略形**
> `コマンド |& コマンド` は `コマンド 2>&1 | コマンド` と同じ意味です。
> ただし **`sh`（dash）では使えません**。**スクリプトでは `2>&1 |` と書くほうが安全**です。

---

### 左と右は同時に動いている

パイプは「左が終わってから右が動く」のではありません。**両方が同時に動きます。**

```bash
$ ( echo start; sleep 0.3; echo end ) | cat   # start が先に表示され、0.3秒後に end
start
end
```

`echo start` の時点で `cat` はもう動いていて、受け取ったそばから出力します。

この性質のおかげで、**巨大なファイルでもメモリを食い潰さずに処理できます**。
また、右側が先に終了すると左側は `SIGPIPE` で止まります。

```bash
$ seq 1 1000000 | head -3                     # 100万行を全部作らずに止まる
1
2
3
```

**`head` が 3 行受け取って終了した時点で、`seq` も終わります。**

## フィルタという考え方

**標準入力から受け取り、加工して、標準出力に出す**コマンドを**フィルタ**と呼びます。
フィルタだけを `|` でつないでいくのが、Linux の基本的な調査スタイルです。

| フィルタ | 何をするか |
|:--|:--|
| `cat` | そのまま流す |
| `grep` | 条件に合う行だけ通す |
| `sort` | 並べ替える |
| `uniq` | 隣り合う重複をまとめる |
| `head` / `tail` | 先頭 / 末尾だけ通す |
| `cut` | 列を切り出す |
| `tr` | 文字を置換・削除・圧縮する |
| `wc` | 数える |
| `sed` / `awk` | 行単位で編集・集計する |
| `tee` | 流しつつ、途中でファイルにも書く |

```bash
$ head -2 /etc/passwd | cut -d: -f1,7          # : 区切りの1列目と7列目だけ取り出す
root:/bin/bash
daemon:/usr/sbin/nologin
```

**「1 つのことをうまくやるコマンドを、つないで使う」**という設計思想です。

## tee 画面にもファイルにも出す

`tee` は**標準入力を、標準出力とファイルの両方に出す**コマンドです。
名前は**配管の T 字継手（tee）**から来ています。流れが二股に分かれるからです。

```text
                  ┌──▶ 標準出力（画面や次のパイプ）
   標準入力 ──▶ tee ┤
                  └──▶ ファイル
```

```bash
$ echo hello | tee out1.txt                    # 画面にも出て、ファイルにも書かれる
hello
$ cat out1.txt                                 # ファイルにも同じ内容がある
hello
```

### 上書きと追記

| 書き方 | 動き |
|:--|:--|
| `tee ファイル` | **上書き**（`>` と同じ） |
| `tee -a ファイル` | **追記**（`>>` と同じ） |

```bash
$ echo again | tee -a out1.txt                 # -a を付けると追記になる
again
$ cat out1.txt                                  # 2行に増えている
hello
again
```

**`-a` を忘れると前の内容が消えます。** ログを取り続ける用途では必ず `-a` を付けます。

### ファイル名を省略したとき

`tee` はファイル名を省略しても動きます。その場合は**標準出力に出すだけ**です。

```bash
$ echo ping-t | tee | cat                      # tee は素通し、cat がそれを表示する
ping-t
```

**`tee` は何も書く先が無いので、受け取った文字列をそのまま次へ流します。**
結果として `echo ping-t` と同じ出力になります。

### 複数のファイルに同時に書く

```bash
$ echo multi | tee t1.txt t2.txt > /dev/null   # 2つのファイルに同時に書き、画面には出さない
$ cat t1.txt t2.txt                             # 両方に入っている
multi
multi
```

### 実務でいちばん使う形

**管理者権限が必要なファイルへの書き込み**です。

```bash
$ echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf   # sudo が効くのは tee 側
```

`sudo echo "..." >> /etc/sysctl.conf` は**失敗します**。
`>>` を解釈するのは**シェル自身**で、そのシェルは一般ユーザーのまま動いているからです。
**`sudo` を効かせたいのは書き込む側なので、`sudo tee` にします。**

## xargs 標準入力からコマンドラインを組み立てる

### なぜ xargs が必要なのか

**ここが誤解の多いところです。**
多くのコマンドは、**ファイル名を「引数」で受け取ります**。標準入力では受け取りません。

```bash
$ printf 'x1.txt\nx2.txt\n' > names.txt        # 作りたいファイル名の一覧
$ cat names.txt | touch                        # これは動かない（touch は標準入力を読まない）
```

`touch` は標準入力を見に行かないので、**何も起きません**。
ここで `xargs` の出番です。

```bash
$ cat names.txt | xargs touch                  # 標準入力を引数に並べ直して touch を実行する
$ ls x*.txt                                     # 2つとも作られている
x1.txt
x2.txt
```

**`xargs` がやっているのは「渡す」ではなく「組み立てる」です。**

```text
 標準入力：  x1.txt
             x2.txt
                 │
                 ▼  xargs が引数に並べ直す
 実行される： touch x1.txt x2.txt
```

| 書き方 | 実際に実行されること |
|:--|:--|
| `cat names.txt \| touch` | `touch`（引数なし。標準入力は読まれない） |
| `cat names.txt \| xargs touch` | `touch x1.txt x2.txt` |

もう一例。`cat` はファイル名を引数で受け取ります。

```bash
$ echo /etc/hostname | xargs cat               # cat /etc/hostname が組み立てられて実行される
vm
```

`echo /etc/hostname | cat` だと、**文字列 `/etc/hostname` がそのまま表示される**だけです。
**「ファイル名という文字列」を「ファイル名という引数」に変えるのが `xargs`** だと考えると分かりやすいです。

---

### verbose で組み立て結果を見る

**`--verbose`（`-t`）を付けると、組み立てたコマンドラインを標準エラー出力に表示してから実行します。**
何が実行されるのか分からないときは、まずこれを付けます。

```bash
$ cat names.txt | xargs --verbose touch        # 実行されるコマンドラインが表示される
touch x1.txt x2.txt
```

**表示されたのは `touch x1.txt x2.txt` の 1 行**です。
2 行の入力が、**1 回の `touch` の引数 2 つ**になったことが確認できます。

### 1 回あたりの個数を決める

`-n` で、1 回のコマンドラインに載せる引数の数を指定します。

```bash
$ printf 'a b c d\n' | xargs -n 2 echo "PAIR:"  # 2つずつに分けて echo を実行する
PAIR: a b
PAIR: c d
```

### 位置を指定して差し込む

`-I` を使うと、**引数を末尾に付けるのではなく、指定した位置に差し込め**ます。

```bash
$ printf 'a\nb\n' | xargs -I@ echo "[@]"        # @ の位置に1行ずつ差し込む
[a]
[b]
```

`-I` を使うと**自動的に 1 行 1 回の実行**になります。

| オプション | 意味 |
|:--|:--|
| `-t` / `--verbose` | 実行するコマンドラインを表示する |
| `-n 数` | 1 回あたりの引数の個数 |
| `-I 文字列` | 指定した文字列の位置に差し込む（1 行ずつ実行） |
| `-0` | **区切りを NUL 文字にする**（`find -print0` と組で使う） |
| `-p` | 実行前に確認する |

---

### 区切りの落とし穴

**`xargs` は既定で空白と改行を区切りとして扱います。**
そのため、**ファイル名に空白が入っていると壊れます**。

```bash
$ find 'sp ace' -type f | xargs ls              # 空白でファイル名が割れてしまう
ls: cannot access 'sp': No such file or directory
ls: cannot access 'ace/my': No such file or directory
file.txt
```

`sp ace/my file.txt` が、`sp` と `ace/my` と `file.txt` の 3 つに割れました。

対策は **`find -print0` と `xargs -0` の組**です。
**区切り文字を NUL（`\0`）にすれば、空白は区切りになりません。**

```bash
$ find 'sp ace' -type f -print0 | xargs -0 ls   # NUL 区切りなら空白入りでも壊れない
sp ace/my file.txt
```

**スクリプトで `find | xargs` を書くときは、`-print0` と `-0` をセットにする**のが定石です。

## tr 文字を置き換える 削る まとめる

`tr` は **translate（変換）** の略で、**1 文字ずつ対応させて置き換える**コマンドです。
**行単位ではなく文字単位**なのが `sed` との違いです。

```bash
$ printf 'PING-T\nping-t\nPingT\n' > case.txt  # 検証用のファイルを作る
$ tr PINGT pingt < case.txt                     # P→p, I→i, N→n, G→g, T→t
ping-t
ping-t
pingt
```

**`PINGT` の 1 文字目 `P` が `pingt` の 1 文字目 `p` に、2 文字目 `I` が `i` に……**と、
**位置どうしが対応**します。`-` はどちらの集合にも無いので、そのまま残ります。

パイプで渡しても同じ結果です。

```bash
$ cat case.txt | tr PINGT pingt                 # cat で流し込んでも結果は同じ
ping-t
ping-t
pingt
```

### 削除と圧縮

| オプション | 意味 |
|:--|:--|
| `-d` | 指定した文字を**削除**する |
| `-s` | **連続した同じ文字を 1 つにまとめる**（squeeze） |
| `-c` | 指定した集合の**補集合**を対象にする |

```bash
$ printf 'apple\nbanana\ncherry\n' > file.txt   # 検証用のファイルを作る
$ tr -d 'aeiou' < file.txt                       # 母音をすべて削除する
ppl
bnn
chrry
```

```bash
$ printf 'a###b####c\n' > hash.txt               # # が連続したファイルを作る
$ tr -s '#' < hash.txt                            # 連続する # を1つにまとめる
a#b#c
```

**集合を 2 つ書くと、置換してから圧縮します。**

```bash
$ tr -s '#' 'X' < hash.txt                        # # を X に置換し、連続する X をまとめる
aXbXc
```

よく使う組み合わせも挙げておきます。

```bash
$ echo "hello world" | tr a-z A-Z                # 小文字を大文字にする
HELLO WORLD
```

```bash
$ tr -s ' ' < spaces.txt                          # 連続する空白を1つにまとめる
```

```bash
$ tr -d '\r' < win.txt > unix.txt                 # Windows の改行コード CR を削除する
```

最後の例は**実務で頻出**です。Windows で作ったファイルを Linux に持ち込むと
行末に `\r` が付いていて、スクリプトが謎のエラーを出すことがあります。

---

### tr はファイル名を受け取らない

**`tr` は引数でファイル名を取れません。標準入力からしか読みません。**

```bash
$ tr PINGT pingt case.txt                        # ファイル名を引数にすると失敗する
tr: extra operand 'case.txt'
Try 'tr --help' for more information.
```

`tr` の引数は**集合 1 と集合 2 の最大 2 つだけ**なので、3 つ目が来るとエラーになります。

**だから `tr` は必ず `<` かパイプで渡します。**

```bash
$ tr PINGT pingt < case.txt                      # リダイレクトで渡す
$ cat case.txt | tr PINGT pingt                  # パイプで渡す
```

**この 2 つは結果が同じです。** ただし意味は違います。

| 書き方 | 起動するプロセス | 特徴 |
|:--|:--|:--|
| `tr … < file` | `tr` だけ | **プロセスが 1 つ**。こちらが素直 |
| `cat file \| tr …` | `cat` と `tr` | 余分な `cat` が 1 つ増える |

**結果が同じなら `<` のほうが無駄がありません。**
（`cat file | コマンド` を「`cat` の無駄づかい」と呼ぶことがあります。
ただし読みやすさを優先してあえてこう書く人もいるので、間違いというわけではありません。）

**入力と出力をまとめて書くこともできます。**

```bash
$ tr -s '#' < file1.txt > file2.txt              # file1 を読んで、結果を file2 に書く
```

```bash
$ cat file1.txt | tr -s '#' > file2.txt          # 上と同じ結果になる
```

**`<` と `>` は 1 つのコマンドに両方書けます。** 順番はどちらが先でも構いません。

## wc 行数 語数 バイト数を数える

`wc` は **word count** の略ですが、実際には行・語・バイトを数えます。

| オプション | 数えるもの |
|:--|:--|
| `-l` | 行数（lines） |
| `-w` | 語数（words） |
| `-c` | バイト数（characters / bytes） |
| `-m` | **文字数**（マルチバイトを 1 文字として数える） |
| 無し | 行数・語数・バイト数をまとめて表示 |

```bash
$ wc -l file.txt                                 # ファイル名を引数に渡すと、ファイル名も表示される
3 file.txt
$ wc -w file.txt                                 # 語数を数える
3 file.txt
$ wc -c file.txt                                 # バイト数を数える
20 file.txt
```

**標準入力から渡すと、ファイル名は表示されません。**

```bash
$ cat file.txt | wc -l                           # パイプで渡すと数字だけになる
3
$ wc -l < file.txt                               # リダイレクトでも数字だけになる
3
```

**スクリプトで数値だけ欲しいときは `<` かパイプで渡す**のがコツです。
`wc -l file.txt` だとファイル名が付いてきて、そのままでは計算に使えません。

> **細かい話**：`wc -l` が数えているのは**改行文字の個数**です。
> 最後の行に改行が無いファイルでは、見た目より 1 少なくなることがあります。

なお、**grep で数えるなら `grep -c` のほうが素直**です。

```bash
$ printf 'err\nok\nerr\n' | grep -c err          # 一致した行数を grep 自身が数える
2
```

## パイプとリダイレクトの使い分け

**迷ったら「右側が何か」で決めます。**

| 右にあるもの | 使う記号 | 例 |
|:--|:--|:--|
| **ファイル** | `>` `>>` `<` | `ls > list.txt` |
| **コマンド** | `\|` | `ls \| wc -l` |
| **文字列そのもの** | `<<<` | `tr a-z A-Z <<< hello` |
| **複数行の文字列** | `<<` | `cat << EOF` |

```bash
$ ls > list.txt                                   # 右はファイル → リダイレクト
$ ls | wc -l                                      # 右はコマンド → パイプ
```

**`ls | list.txt` は「list.txt というコマンドを実行しようとして失敗する」**ので、
記号を取り違えると分かりやすいエラーになります。

**組み合わせもよく使います。**

```bash
$ ps aux | grep nginx > nginx_procs.txt          # パイプで絞り込み、結果をファイルへ
```

**`|` は左から順に処理され、最後の `>` が最後のコマンドの出力先を決めます。**
上の例では `grep` の標準出力が `nginx_procs.txt` に向きます。

## パイプの終了ステータス

**`$?` に入るのは、パイプの一番右のコマンドの終了ステータスだけ**です。
途中が失敗していても気づけません。

```bash
$ false | true                                    # 左は失敗、右は成功
$ echo $?                                          # 右だけを見るので 0 になる
0
```

**途中の状態は `PIPESTATUS` 配列に入っています。**

```bash
$ false | true                                    # もう一度実行する
$ echo "${PIPESTATUS[@]}"                          # 左から順の終了ステータス
1 0
```

**左が 1（失敗）、右が 0（成功）**と分かります。

パイプのどこかが失敗したら全体を失敗にしたい場合は **`pipefail`** を設定します。

```bash
$ set -o pipefail                                 # パイプの途中の失敗を拾う設定にする
$ false | true                                     # 左が失敗している
$ echo $?                                           # 1 になる
1
$ set +o pipefail                                  # 設定を戻す
```

**スクリプトの冒頭に `set -euo pipefail` と書く**のは、この `pipefail` を含めた定型です。
**バッチ処理やデプロイスクリプトでは、これが無いと失敗を見逃します。**

> `PIPESTATUS` と `pipefail` は **bash の機能**です。
> `sh`（dash）では使えないので、`#!/bin/bash` を明示してください。

## よく使うフィルタの組み合わせ

**出現回数の多い順に並べる**

```bash
$ printf 'b\na\nb\nc\nb\n' | sort | uniq -c | sort -rn   # 並べ替え→集計→多い順
      3 b
      1 c
      1 a
```

**`uniq` は隣り合う重複しか見ない**ので、**先に `sort` が必要**です。ここはよく間違えます。

**ログから特定の語を含む行だけ数える**

```bash
$ grep -c "ERROR" /var/log/syslog                 # grep 自身に数えさせる
```

**上位のプロセスを見る**

```bash
$ ps aux --sort=-%mem | head -6                   # メモリ使用率の高い順に5件（+ヘッダ）
```

**画面にも出しつつログにも残す**

```bash
$ ./deploy.sh 2>&1 | tee -a deploy.log            # エラーも含めて、画面とログの両方に出す
```

**パイプの途中を確認する**

```bash
$ cat access.log | grep 500 | tee /tmp/500.txt | wc -l   # 途中結果を保存しつつ行数も出す
```

**`tee` はパイプの途中に挟めます。** デバッグのときに便利です。

## つまずきポイント

**1. `|` にエラーが流れない**

```bash
$ ./script.sh | tee log.txt                       # エラーはログに残らない
$ ./script.sh 2>&1 | tee log.txt                  # こちらが正しい
```

**`2>&1` はパイプの左側、コマンドの直後**に書きます。
理由は [標準入出力とリダイレクト](./標準入出力とリダイレクト.md) の「書く順番で結果が変わる」を参照してください。

**2. `xargs` を「標準入力を渡すもの」だと思っている**

`xargs` は**コマンドラインを組み立て直します**。
`echo abc | xargs cat` は `cat abc` を実行しようとします（`abc` というファイルを探す）。
**分からなくなったら `--verbose` を付けて、何が組み立てられるか見る**のが確実です。

**3. `tr` にファイル名を渡してしまう**

`tr` は標準入力専用です。`<` かパイプで渡します。

**4. `tee` の `-a` を忘れて上書きする**

ログを追記したいのに毎回消えている場合は `-a` の付け忘れです。

**5. `uniq` の前に `sort` を忘れる**

`uniq` は**隣り合う行しか比較しません**。離れた重複は残ります。

**6. パイプの中で変数を代入しても残らない**

```bash
$ count=0; printf 'a\nb\n' | while read l; do count=$((count+1)); done   # パイプの右は子プロセス
$ echo $count                                                            # 0 のまま
0
```

**パイプの各段は子プロセス（サブシェル）で動く**ため、
**その中での変数代入は親のシェルに戻りません。**

`bash` ならプロセス置換でこれを避けられます。

```bash
$ count=0; while read l; do count=$((count+1)); done < <(printf 'a\nb\n')  # 親シェルでループする
$ echo $count                                                              # 2 になる
2
```

**7. `$?` だけ見て「成功した」と判断する**

パイプの途中の失敗は `$?` に出ません。`PIPESTATUS` か `pipefail` を使います。

## クラウド実務メモ

**ログの絞り込みは結局これ**

```bash
$ sudo journalctl -u nginx --since "1 hour ago" | grep -i error | tail -20   # 直近1時間のエラーを20件
```

クラウド上のサーバでも、**まず `journalctl` をパイプで絞る**のが最短です。
[systemctl サービスの操作と確認](../05_起動プロセスとカーネル/systemctl_サービスの操作と確認.md) も合わせて参照してください。

**設定ファイルへの追記は sudo tee**

```bash
$ echo "vm.swappiness = 10" | sudo tee -a /etc/sysctl.d/99-custom.conf   # sudo を書き込み側に効かせる
```

**EC2 や GCE の初期化スクリプト（ユーザーデータ）で、設定を足すときの定番**です。
`sudo echo ... >> ファイル` では権限エラーになります。

**一括処理は find と xargs**

```bash
$ find /var/log -name "*.log" -mtime +30 -print0 | xargs -0 gzip   # 30日より古いログを圧縮する
```

**`-print0` と `-0` をセットにする**のを忘れないでください。

**デプロイスクリプトの冒頭**

```bash
$ set -euo pipefail                               # 失敗を見逃さないための定型
```

| 設定 | 意味 |
|:--|:--|
| `-e` | コマンドが失敗したら即座に終了する |
| `-u` | 未定義の変数を使ったらエラーにする |
| `-o pipefail` | **パイプの途中の失敗も拾う** |

**CI/CD やデプロイの自動化では、`pipefail` が無いと「失敗しているのに成功扱い」**になります。
ここは事故に直結するので、必ず入れてください。

**名前付きパイプ**

```bash
$ mkfifo mypipe                                   # 名前付きパイプを作る
$ ls -l mypipe                                    # 種別は p（pipe）と表示される
prw-r--r-- 1
```

**ファイルの種別が `p`** になっているのが分かります。
`|` は名前を持たないパイプ、`mkfifo` で作るのは**ファイルシステム上に名前を持つパイプ**です。
[ファイルの種類とタイムスタンプ](./ファイルの種類とタイムスタンプ.md) も参照してください。
