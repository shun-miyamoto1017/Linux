## メタキャラクタとは

**メタキャラクタとは、シェルによって特別に解釈される文字です。**

大事なのは、**シェルがコマンドを実行する「前」に文字列を書き換えている**という点です。

```bash
$ rm *.log                          # 拡張子 .log のファイルをまとめて削除したい
```

このとき `rm` は `*.log` という文字列を受け取っていません。
シェルが先にファイル名へ置き換えてから `rm` を起動します。

```bash
$ rm app.log error.log access.log   # シェルが実際に実行しているのはこの形
```

この置き換えを **展開（expansion）** と呼びます。

展開はシェルが行うため、**コマンド側の仕様とは無関係**です。
`ls *.txt` も `cp *.txt /tmp` も、`*` の解釈ルールはまったく同じになります。

> **表記の注意**
> 日本語フォントでは `\`（バックスラッシュ）が **`¥`（円記号）** に見えることがあります。
> 見た目が違うだけで、文字コード上は同じもの（U+005C）です。
> 教材の画面では `¥` と表示されることがありますが、実際に入力するのは `\` です。

## パス名展開で使う記号の一覧

| メタキャラクタ | 説明 |
|:--|:--|
| `*` | 0 文字以上の文字列 |
| `?` | 任意の 1 文字 |
| `[ ]` | `[ ]` 内のいずれか 1 文字<br>　`[abc]` … a, b, c のどれか 1 文字<br>　`[a-z]` … 小文字のアルファベット 1 文字<br>　`[!abc]` … a, b, c 以外の 1 文字 |
| `{ }` | 列挙や連番から**文字列を生成**する（ブレース展開） |

| ディレクトリの特殊記号 | 説明 |
|:--|:--|
| `~` | ホームディレクトリ |
| `.` | カレントディレクトリ |
| `..` | カレントディレクトリの 1 つ上の階層 |

> **`$` `'` `"` `` ` `` `\` も同じメタキャラクタの仲間**ですが、
> こちらは「打ち消す・値を差し込む」側の記号なので
> [クォートとエスケープ](./クォートとエスケープ.md) にまとめています。

## ワイルドカードでファイルを指定する

以下の例は、すべてこのファイル構成のディレクトリで実行しています。

```bash
$ ls                                # これから使う練習用ファイルを確認
A.txt  a-z.txt  abc.txt  b.txt  x.txt
```

---

### アスタリスク

**意味** … 0 文字以上の文字列

**例文**

```bash
$ ls *.txt                          # 「なんでも + .txt」で終わるファイル
A.txt  a-z.txt  abc.txt  b.txt  x.txt

$ ls a*                             # 「a で始まる」ファイル
a-z.txt  abc.txt

$ ls a*.txt                         # 「a で始まり .txt で終わる」ファイル
a-z.txt  abc.txt
```

**補足** … 「**0 文字以上**」なので、`b` というファイルがあれば `b*` はそれ自身にもマッチします。

```bash
$ touch b                           # 拡張子なしの「b」を作って試す
$ ls b*                             # b 自身も 0 文字マッチとして拾われる
b  b.txt
```

---

### クエスチョン

**意味** … 任意の 1 文字

**例文**

```bash
$ ls ?.txt                          # 「ちょうど1文字 + .txt」
A.txt  b.txt  x.txt

$ ls ???.txt                        # 「ちょうど3文字 + .txt」
a-z.txt  abc.txt
```

**補足** … `?` は **0 文字にはマッチしません**。ここが `*` との決定的な違いです。

| パターン | `b.txt` | `abc.txt` | `a-z.txt` |
|:--|:-:|:-:|:-:|
| `*.txt`   | ○ | ○ | ○ |
| `?.txt`   | ○ | × | × |
| `???.txt` | × | ○ | ○ |

---

### ブラケット

**意味** … `[ ]` 内のいずれか **1 文字**

**例文**

```bash
$ ls [abc].txt                      # a または b または c のどれか1文字 + .txt
b.txt

$ ls [a-c].txt                      # 範囲指定。a から c までの1文字
b.txt

$ ls [!abc].txt                     # a, b, c 以外の1文字
A.txt  x.txt
```

**補足その1 … `[abc]` は「abc という並び」ではありません**

これが最も間違えやすいポイントです。**`[ ]` は「集合から 1 個選ぶ」**と覚えてください。
`[abc].txt` の候補になりうるのは `a.txt` `b.txt` `c.txt` の 3 つだけで、`abc.txt` は対象外です。

```bash
$ ls [abc].txt                      # abc.txt は3文字なので候補にならない
b.txt

$ ls abc.txt                        # そのまま書けばもちろんマッチする
abc.txt

$ ls ???.txt                        # 「任意の3文字」ならマッチする
a-z.txt  abc.txt
```

**補足その2 … `[ ]` は大文字と小文字を区別します**

`[abc]` は小文字の `a` `b` `c` にだけマッチし、大文字の `A` にはマッチしません。

```bash
$ ls [abc].txt                      # 小文字指定なので A.txt は出てこない
b.txt

$ ls [ABC].txt                      # 大文字で指定すればマッチする
A.txt

$ ls [aAbBcC].txt                   # 両方拾いたいなら大文字小文字を並べて書く
A.txt  b.txt
```

大文字小文字を無視して一致させたい場合は `nocaseglob` を有効にします。
ただし恒久的に有効にすると事故のもとなので、一時的に使うのが無難です。

```bash
$ shopt -s nocaseglob               # 大文字小文字を区別しないモードにする
$ ls [abc].txt                      # A.txt も拾われるようになる
A.txt  b.txt
$ shopt -u nocaseglob               # 元に戻す（付けっぱなしにしない）
```

**補足その3 … `[ ]` の中と外で `-` の意味が変わります**

**`[ ]` の中の `-` は範囲を表す記号**ですが、**`[ ]` の外の `-` はただの文字**です。
`[a-z]` と `a-z.txt` は見た目が似ているので混乱しやすい箇所です。

```bash
$ ls [a-z].txt                      # [ ] の中の - → 「a から z の1文字」という範囲指定
b.txt  x.txt

$ ls a-z.txt                        # [ ] の外の - → ただのファイル名の一部
a-z.txt
```

---

### ブラケットの細かいルール

#### 否定は `!` でも `^` でも書ける

GNU Bash マニュアルの Pattern Matching には、
「`[` の直後の文字が `!` または `^` の場合、囲まれていない任意の文字にマッチする」と記載されています。

```bash
$ ls [!abc].txt                     # ! による否定
A.txt  x.txt

$ ls [^abc].txt                     # ^ による否定（bash では同じ結果）
A.txt  x.txt
```

ただし **POSIX で規定されているのは `!`** です。移植性を考えると `!` が安全です。

#### 範囲指定はロケールに依存する

`[a-z]` の「順序」は `LC_COLLATE`（照合順序のロケール）が決めます。
辞書順のロケールでは、`[a-c]` が `aAbBcC` のように**大文字も拾う**ことがあります。

ここで注意したいのは、**コマンドの前に `LC_ALL=C` を置いても効かない**ことです。
`[a-z]` を展開するのは**シェル自身**で、コマンド前置の変数代入は「展開が終わったあとに、
起動するコマンドの環境へ渡される」ものだからです。

```bash
$ LC_ALL=C ls [a-z].txt             # ← 効かない。ls の環境が変わるだけ
b.txt  x.txt

$ (export LC_ALL=C; ls [a-z].txt)   # ← シェル自身に設定すれば効く（( ) で影響を閉じ込める）
b.txt  x.txt
```

確実に小文字だけを指定するなら、ロケールに頼らず **文字クラス**を使うのが安全です。

```bash
$ ls [[:lower:]].txt                # ロケールに関係なく「小文字1文字」を指定
b.txt  x.txt
```

| 書き方 | 意味 |
|:--|:--|
| `[[:alpha:]]` | アルファベット 1 文字 |
| `[[:digit:]]` | 数字 1 文字 |
| `[[:alnum:]]` | 英数字 1 文字 |
| `[[:lower:]]` | 小文字 1 文字 |
| `[[:upper:]]` | 大文字 1 文字 |
| `[[:space:]]` | 空白文字 1 文字 |
| `[[:punct:]]` | 記号 1 文字 |

**外側の `[ ]` が必要**な点に注意します。`[:digit:]` ではなく `[[:digit:]]` です。

```bash
$ ls log[[:digit:]].txt             # log0.txt 〜 log9.txt にマッチする
```

運用スクリプトでは先頭に `export LC_ALL=C` を書いておくと、
サーバのロケール差による「なぜか本番だけ挙動が違う」を防げます。
時刻表示や `sort` の並び順も同時に安定するため、手順書のコード化では定番の作法です。

#### 記号そのものを指定したいとき

| 指定したい文字 | 書き方 | 理由 |
|:--|:--|:--|
| `]` | `[]abc]` | `[` の直後に置くと文字として扱われる |
| `-` | `[abc-]` または `[-abc]` | 先頭か末尾に置くと範囲記号にならない |

```bash
$ ls [a-]*.txt                      # 「a」か「-」で始まるファイル（- を末尾に置く）
a-z.txt  abc.txt
```

## パス名展開の三つの落とし穴

GNU Bash マニュアルの Filename Expansion に明記されている、実務で効くルールです。

### 一つめ 先頭のドットはマッチしない

```bash
$ ls -a                             # -a を付けると隠しファイルも表示される
.  ..  .bashrc  b.txt

$ ls *                              # * では .bashrc が出てこない
b.txt

$ ls -d .*                          # ドット始まりを明示的に指定すると出る
.  ..  .bashrc
```

`-d` を付けているのは、付けないと `ls` が `.`（カレント）と `..`（親）を
**ディレクトリとして中身まで展開してしまう**ためです。
なお bash 5.2 以降は既定で `globskipdots` が有効なので、`.*` から `.` と `..` が除かれ、
結果は `.bashrc` だけになります。

これは「スラッシュ直後のドット」にも適用されます。
`shopt -s dotglob` で拾えるようになりますが、**`rm *` の事故を招く**ので通常は有効にしません。

> **なぜこの仕様なのか**
> `rm *` で `.bashrc` などの設定ファイルまで消えたら困るためです。
> 隠しファイルは「意図的に指定したときだけ触る」という設計になっています。

### 二つめ スラッシュは越えられない

```bash
$ ls *.conf                         # カレント直下だけを見る（サブディレクトリは見ない）
$ ls */*.conf                       # 1階層下を見たいなら / を自分で書く
```

再帰的に探すなら `find` を使うか、`globstar` を有効にして `**/` を使います。

```bash
$ shopt -s globstar                 # ** で任意の深さを表せるようにする
$ ls **/*.conf                      # 任意の深さのサブディレクトリを対象にする
```

### 三つめ マッチしないとパターンがそのまま残る

```bash
$ ls *.zip                          # .zip が1つも無い状態で実行してみる
ls: cannot access '*.zip': No such file or directory
```

「`*.zip` というファイルが無い」というエラーに見えますが、実際は
「マッチ 0 件だったので `*.zip` という文字列がそのまま `ls` に渡された」結果です。

| 設定 | マッチ 0 件のときの挙動 |
|:--|:--|
| 既定 | パターン文字列がそのまま渡される |
| `shopt -s nullglob` | その単語ごと消える（引数が 0 個になる） |
| `shopt -s failglob` | bash がエラーを出し、コマンドを実行しない |

## ハイフンで始まるファイル名の扱い

`-100` のように**ハイフンから始まる名前**のファイルは、普通に指定すると失敗します。

```bash
$ touch -100                        # -100 という名前のファイルを作りたい
touch: invalid option -- '1'        # オプションだと思われてしまう
Try 'touch --help' for more information.
```

`-100` が「`-1` `-0` `-0` というオプションの並び」と解釈され、
`-1` なんてオプションは無い、と怒られています。

### なぜクォートやエスケープでは解決しないのか

ここが一番のポイントです。**クォートもバックスラッシュも効きません。**
（クォートとエスケープそのものは [クォートとエスケープ](./クォートとエスケープ.md) を参照）

```bash
$ touch '-100'                      # シングルクォートで囲む
touch: invalid option -- '1'        # 変わらない

$ touch \-100                       # バックスラッシュでエスケープする
touch: invalid option -- '1'        # やはり変わらない
```

理由は、**クォートとエスケープが誰に向けた指示なのか**にあります。

| 段階 | 誰が処理するか | 何をするか |
|:--|:--|:--|
| 1 | **シェル（bash）** | メタキャラクタを展開し、クォートを取り除いて、引数の配列を作る |
| 2 | **コマンド（touch）** | 受け取った引数のうち、`-` で始まるものをオプションとして解釈する |

クォートやバックスラッシュは、**1 の段階でシェルに「これは特別扱いしないで」と伝える記号**です。
けれども今回困っているのは **2 の段階**、つまり `touch` 側の解釈です。

```text
$ touch '-100'
      │
      ▼ ① シェルがクォートを外す
   touch に  -100  という引数が渡る   ← ここまでは成功している
      │
      ▼ ② touch が引数を見る
   「- で始まる。オプションだな」     ← ここで失敗する
```

**そもそも `-`（ハイフン）はメタキャラクタではありません。**
`*` や `?` や `$` と違い、シェルは `-` を特別扱いしていないので、
**打ち消す対象が最初から存在しない**のです。クォートは空振りします。

**補足** … ダブルクォートの中のバックスラッシュはさらに紛らわしい結果になります。

```bash
$ touch "\-100"                     # ダブルクォート内の \ は文字として残る
$ ls                                # \-100 という名前のファイルができてしまう
\-100
```

### 正しい 2 つの方法

`-` で始まる名前を**オプションではなくファイル名として渡す**には、次のどちらかを使います。

**方法1 … `--` を付ける（オプションの終わり）**

**意味** … `--` は「オプションの指定はここで終わり。**以降はすべてオプション以外**として扱え」
という、多くのコマンドが共通で持つ特別な引数です。

```bash
$ touch -- -100                     # -- 以降はファイル名として扱われる
$ ls                                # 作られたことを確認する
-100
```

削除も同じです。

```bash
$ rm -100                           # そのままでは消せない
rm: invalid option -- '1'
Try 'rm ./-100' to remove the file '-100'.
Try 'rm --help' for more information.

$ rm -- -100                        # -- を付ければ消せる
```

`rm` は親切にも「`rm ./-100` を試してみて」とヒントまで出してくれます。

**方法2 … パスを付けて書く**

**意味** … 先頭が `-` でなくなれば、コマンドはオプションだと思いません。
`./`（カレントディレクトリ）や絶対パスを頭に付けます。

```bash
$ touch ./-200                      # 相対パスのカレントディレクトリ ./ を付ける
$ ls                                # 作られたことを確認する
-200

$ pwd                               # いまいる場所を確認する
/home/staff/dir1
$ rm /home/staff/dir1/-200          # 絶対パスで指定しても同じ
```

`./-200` も `/home/staff/dir1/-200` も、**先頭の文字が `.` や `/` なので
オプションには見えません**。ファイル名としてそのまま届きます。

`./` そのものの意味は [`./` を付ける理由](#-を付ける理由) を参照してください。

### 早見表

| やり方 | 効くか | 理由 |
|:--|:-:|:--|
| `touch -- -100` | **○** | `--` 以降をオプション扱いしないと、コマンド側に伝えている |
| `touch ./-100` | **○** | 先頭が `.` なので、そもそもオプションに見えない |
| `touch /path/to/-100` | **○** | 同上。先頭が `/` |
| `touch '-100'` | ✕ | シェルへの指示であり、コマンドの解釈は変えられない |
| `touch "-100"` | ✕ | 同上 |
| `touch \-100` | ✕ | `-` はメタキャラクタではないので、打ち消す対象がない |

**「ハイフンで始まるファイルは扱えない」わけではありません。** 上の方法で普通に作成・削除できます。

### 実務での使いどころ

`--` は「変な名前のファイル」だけのための機能ではありません。
**変数の中身が `-` で始まるかもしれない場面**で効きます。

```bash
$ grep -- "$pattern" file.txt       # $pattern が -v などでも検索語として扱われる
$ git checkout -- config.yml        # ブランチ名ではなくファイル名だと明示する
```

スクリプトの中でユーザ入力やファイル名を扱うときは、
**`--` を挟むだけで想定外の挙動を防げます**。同じ発想で、変数は必ずクォートします。

```bash
$ rm -- "$file"                     # -- でオプション誤認を防ぎ、"" で単語分割を防ぐ
```

## ディレクトリの特殊記号

| 記号 | 意味 | 例文 |
|:--|:--|:--|
| `~` | ホームディレクトリ（`$HOME` と同じ） | `cd ~` |
| `~user` | 指定ユーザのホームディレクトリ | `cd ~apache` |
| `~+` | カレントディレクトリ（`$PWD`） | `echo ~+` |
| `~-` | 直前にいたディレクトリ（`$OLDPWD`） | `echo ~-` |
| `.` | カレントディレクトリ | `./script.sh` |
| `..` | 1 つ上の階層 | `cd ..` |
| `-` | 直前にいたディレクトリ | `cd -` |

```bash
$ pwd                               # いまいる場所を確認
/home/shun/work

$ cd ..                             # 1つ上の階層へ移動
$ pwd                               # 移動先を確認
/home/shun

$ cd -                              # 直前にいたディレクトリへ戻る
$ pwd                               # 戻れたことを確認
/home/shun/work

$ ./script.sh                       # カレントにある script.sh を実行
```

### チルダが展開される条件

`~` の直後から**最初の `/` まで**の文字列が「ユーザ名」と解釈されます
（これを**チルダプレフィクス**と呼びます）。
中身によって、展開されるかどうかが決まります。

| チルダプレフィクスの中身 | 展開結果 |
|:--|:--|
| 空（`~` だけ、または `~/`） | 自分のホームディレクトリ（`$HOME`） |
| 実在するユーザ名（`~root`） | そのユーザのホームディレクトリ |
| 実在しないユーザ名（`~work`） | 展開されず、そのまま残る |
| クォートやエスケープを含む（`~\work`） | ユーザ名と見なされず、そのまま残る |

```bash
$ echo ~                            # 単語の終わり → 展開される
/home/shun

$ echo ~/                           # 直後が / → 展開される
/home/shun/

$ echo ~/work                       # 直後が / → 展開される
/home/shun/work

$ echo ~work                        # 「work」というユーザ名と解釈される
~work                               # そんなユーザはいないので展開されない

$ echo ~root                        # 存在するユーザ名なら展開される
/root

$ echo ~\\work                      # ~ の直後が \ でエスケープされている → ユーザ名と見なされない
~\work
```

### `./` を付ける理由

自作スクリプトに `./` を付けるのは、**カレントディレクトリが `PATH` に含まれていない**ためです。
含まれていると、`/tmp` などで `ls` という名前の悪意あるファイルを踏む危険があるため、
意図的に外されています。

```bash
$ echo $PATH                        # カレント(.)が含まれていないことを確認
/usr/local/bin:/usr/bin:/bin

$ script.sh                         # PATH に無いので見つからない
bash: script.sh: command not found

$ ./script.sh                       # 場所を明示すれば実行できる
```

## 展開が起きる順番

bash は 1 行を読んでから、次の順で処理します（主要なものだけ抜粋）。

```
ブレース展開 {a,b}
  → チルダ展開 ~
    → 変数展開・コマンド置換 $VAR $( )
      → 単語分割
        → パス名展開 * ? [ ]
          → クォート除去
```

この順番を知っていると、次の挙動が説明できます。

```bash
$ PAT="*.txt"                       # 変数にワイルドカードの文字列を入れる

$ echo $PAT                         # 変数展開のあとにパス名展開が走る
A.txt a-z.txt abc.txt b.txt x.txt

$ echo "$PAT"                       # クォート内なのでパス名展開されない
*.txt
```

## ブレース展開

**ブレース展開 `{ }` は、ファイルが存在しなくても展開されます。**
パス名展開は実ファイルを見ますが、ブレース展開は単なる**文字列生成**だからです。

```bash
$ echo {1..5}                       # 存在しない値でも連番の文字列を生成できる
1 2 3 4 5

$ echo {a..e}                       # 文字の連番も作れる
a b c d e

$ echo {01..10}                     # ゼロ埋めもできる
01 02 03 04 05 06 07 08 09 10

$ echo file{1,3,5}.txt              # 列挙で組み合わせを作る
file1.txt file3.txt file5.txt
```

実務での定番の使い方です。

```bash
$ cp nginx.conf{,.bak}              # → cp nginx.conf nginx.conf.bak（バックアップの定番）

$ mv app.log{,.$(date +%F)}         # → mv app.log app.log.2026-08-27（日付を付けて退避）

$ mkdir -p log/{app,db}/{2025,2026} # 2×2 の組み合わせで4つのディレクトリを一括作成
$ find log -type d                  # 作られた構造を確認
log
log/app
log/app/2025
log/app/2026
log/db
log/db/2025
log/db/2026
```

## 展開結果を先に確かめる

**パス名展開の早見表**

| 記法 | 意味 | よく使う場面 |
|:--|:--|:--|
| `*` | 0 文字以上 | `rm *.log`、`ls /etc/*.conf` |
| `?` | 任意の 1 文字 | `ls access.log.?` |
| `[abc]` | a/b/c のいずれか 1 文字 | `ls messages-[123]` |
| `[a-z]` | 範囲内の 1 文字 | `ls [a-c]*` |
| `[!abc]` | a/b/c 以外の 1 文字 | `ls [!.]*` |
| `[[:digit:]]` | 数字 1 文字 | `ls log[[:digit:]].txt` |
| `{a,b}` | ブレース展開（文字列生成） | `cp file{,.bak}` |
| `~` | ホームディレクトリ | `cd ~` |
| `.` `..` | カレント／1 つ上 | `./run.sh`、`cd ..` |

**危険なコマンドの前は `echo` を付けて展開結果を確認する。** これが最も確実な事故防止策です。

```bash
$ echo rm -rf /var/log/*.gz         # 実行せず、何が削除対象になるかだけ確認
rm -rf /var/log/app.log.1.gz /var/log/app.log.2.gz
```

より本格的には `set -x`（トレース）を使います。

```bash
$ set -x                            # 展開後のコマンドを表示するモードにする
$ ls *.txt                          # 何に展開されたかが + 行に出る
+ ls A.txt a-z.txt abc.txt b.txt x.txt
A.txt  a-z.txt  abc.txt  b.txt  x.txt
$ set +x                            # 元に戻す
```
