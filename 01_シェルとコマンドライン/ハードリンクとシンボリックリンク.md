## Linux がファイルを管理する仕組み

リンクを理解するには、**Linux がファイルを 2 つに分けて管理している**ことを先に押さえます。

```text
  ファイルの実体（データ本体）  … 中身そのもの。ディスク上のどこかにある
  inode（アイノード）           … そのファイルの「管理台帳」
                                   ・パーミッション、所有者、タイムスタンプ
                                   ・実体がディスクのどこにあるかというアドレス
```

**ファイル名は inode に付けられた「ラベル」**にすぎません。
ディレクトリは「ファイル名 → inode 番号」の対応表を持っているだけです。

```text
      ディレクトリ                 inode               実体
  ┌────────────────────┐    ┌──────────────────┐    ┌─────────┐
  │ workfile -> 902391 │--> │ #902391          │--> │ content │
  │                    │    │ 所有者/権限/日時 │    │         │
  └────────────────────┘    └──────────────────┘    └─────────┘
```

**この「ラベル」を増やすのがハードリンク**、
**別の場所に「行き先メモ」を置くのがシンボリックリンク**です。

---

## ハードリンク

**意味** … **ファイルの実体を直接参照するリンク**です。
同じ実体を指すラベルをもう 1 つ増やしているだけなので、**同じ inode 番号を持ちます**。

**ファイルを新規作成した時点で、そのファイルはハードリンクが 1 つある状態**です。
つまり「普通のファイル名」も、実体から見ればハードリンクの 1 つにすぎません。

**例文**

```bash
$ echo "content" > workfile           # 元になるファイルを作る
$ ln workfile hardlink                # ハードリンクを作る（オプション無し）
$ ls -i                               # inode 番号を付けて一覧する
902391 hardlink  902391 workfile      # 番号が同じ＝同じ実体を指している
```

**補足** … **コピーと違い、ディスク容量をほとんど消費しません。**
増えるのはディレクトリ内の「ファイル名 → inode 番号」の 1 行だけで、実体は 1 つのままだからです。
そのため、**更新されないファイルのバックアップ手段**としてハードリンクが使われることがあります。

---

## シンボリックリンク

**意味** … **元ファイルの場所（パス）を指し示すリンク**です。
Windows のショートカットにあたります。

**シンボリックリンクが持っている情報は「元ファイルがどこにあるか」というパス文字列だけ**で、
実体は指していません。そのため **inode 番号は元ファイルと別になります**。

**例文**

```bash
$ ln -s workfile symlink              # シンボリックリンクを作る（-s が必須）
$ ls -i                               # inode 番号を付けて一覧する
902391 hardlink  902483 symlink  902391 workfile   # symlink だけ番号が違う
```

**補足** … **シンボリックリンクはディレクトリにも、別のファイルシステムにも作れます。**
中身がただのパス文字列なので、指す先に制約がないためです。

## lnコマンド

**意味** … リンクを作成するコマンドです。

```text
ln [オプション] リンク元 リンク名
```

**引数の順番は `cp` と同じ**で、「元 → 新しく作る名前」の順です。

### よく使うオプション

| オプション | 意味 |
|:--|:--|
| **（なし）** | **ハードリンク**を作る |
| **`-s`** / `--symbolic` | **シンボリックリンク**を作る（`s` は symbolic） |
| **`-f`** / `--force` | リンク名が既に存在していたら**削除してから作る** |
| `-i` / `--interactive` | 上書きする前に確認する |
| **`-n`** / `--no-dereference` | **リンク名がディレクトリへのシンボリックリンクだったとき、その中に作らず、リンク自体を置き換える** |
| `-v` / `--verbose` | 作成したリンクを表示する |
| `-r` / `--relative` | シンボリックリンクの参照先を相対パスにする |
| `-b` / `--backup` | 上書きする前にバックアップを取る |

```bash
$ ln -s /opt/app/v2 /opt/app/current       # バージョン切り替え用のリンクを張る
$ ln -sfn /opt/app/v3 /opt/app/current     # 向き先を v3 に張り替える（-f と -n をセットで）
```

**補足 … 張り替えでは `-n` を忘れないでください**

`/opt/app/current` が既にディレクトリへのシンボリックリンクになっているとき、
`-n` を付けずに `ln -sf` を実行すると、**リンクをたどった先のディレクトリの中**に
`v3` という名前のリンクが作られてしまいます。`-sfn` をセットで覚えるのが安全です。

## どちらのリンクか見分ける

**作成済みのリンクがハードリンクかシンボリックリンクかは、`ls` で判別できます。**
見分ける方法は 2 つあり、**どちらも `ls` コマンド**です。

| 方法 | 見るところ | 判定 |
|:--|:--|:--|
| **`ls -i`** | **inode 番号** | 元ファイルと**同じ番号ならハードリンク** |
| **`ls -l`** | **パーミッションの先頭 1 文字** | **`l` ならシンボリックリンク**、`-` なら通常ファイル（＝ハードリンクを含む） |

### inode 番号で見分ける

```bash
$ ls                                  # まず普通に一覧する
hardlink  symlink  workfile           # 見た目では区別がつかない

$ ls -i                               # inode 番号を付けて一覧する
902391 hardlink  902483 symlink  902391 workfile
```

**`workfile` と `hardlink` の inode 番号が `902391` で同じ**なので、
この 2 つがハードリンクの関係だと分かります。

### パーミッションの先頭で見分ける

```bash
$ ls -l                               # 詳細情報を表示する
total 8
-rw-r--r-- 2 root root 8 Sep 18 21:56 hardlink
lrwxrwxrwx 1 root root 8 Sep 18 21:56 symlink -> workfile
-rw-r--r-- 2 root root 8 Sep 18 21:56 workfile
```

**`symlink` の行だけ先頭が `l`（小文字のエル）** になっています。
さらに `->` で参照先が表示されるため、`ls -l` は「どこを指しているか」まで分かります。

**補足** … `ls -F` でも判別できます。**シンボリックリンクには末尾に `@` が付きます。**

```bash
$ ls -F                               # 名前の後ろにファイルタイプの記号を付ける
hardlink  symlink@  workfile          # symlink にだけ @ が付く
```

## シンボリックリンクのパーミッション

**ここが最大の勘違いポイント**です。

**シンボリックリンクのパーミッションは、いつでも `lrwxrwxrwx`** と表示されます。
**中身は関係なく、常にこの固定値**です。

```bash
$ ls -l link target.txt               # リンクと参照先を並べて見る
lrwxrwxrwx 1 root root 10 Sep 19 23:34 link -> target.txt
-r--r--r-- 1 root root  7 Sep 19 23:34 target.txt
```

**リンクは `rwxrwxrwx`、参照先は `r--r--r--`（誰も書けない）**という状態です。

**「リンクが 777 なら誰でも書ける」と読んではいけません。**
**実際のアクセス可否は、参照先のパーミッションで決まります。**

```bash
$ su tu -c 'echo added >> link'       # 一般ユーザが追記しようとすると
sh: 1: cannot create link: Permission denied
$ echo $?                             # 失敗している
2
$ su tu -c 'cat link'                 # 読むほうは参照先が r-- なので通る
target
```

```text
   ls -l で見えるもの        実際に効くもの
   ┌──────────────┐          ┌──────────────┐
   │  lrwxrwxrwx  │  ──▶     │  -r--r--r--  │ ← こちらで判定される
   │    link      │          │  target.txt  │
   └──────────────┘          └──────────────┘
```

**`Permission denied` が出たときは、リンクではなく参照先を見てください。**

```bash
$ ls -lL link                         # -L で参照先の情報を表示する
-r--r--r-- 1 root root 7 Sep 19 23:34 link
$ readlink -f link                    # 参照先の絶対パスを調べる
/tmp/w19/perm/target.txt
```

**`ls -lL` は「リンクをたどった先」を表示**します。
**`readlink -f` は最終的な実体のパス**を返します。
**どちらも原因の切り分けに効きます。**

**補足 … ハードリンクには、この問題がありません**

ハードリンクは**実体そのものに別名を付けている**だけなので、
**`ls -l` に出るパーミッションが、そのまま効くパーミッション**です。

## 二つのリンクの違い

| | **ハードリンク** | **シンボリックリンク** |
|:--|:--|:--|
| 実体との関係 | **実体を直接参照する** | **元ファイルのパスを指す** |
| inode 番号 | **元ファイルと同じ** | **元ファイルと違う** |
| `ls -l` の先頭 | `-`（通常ファイルと同じ） | **`l`** |
| ディスク消費 | **ほとんど消費しない**（名前を 1 行足すだけ） | **ほとんど消費しない**（パス文字列ぶんだけ） |
| リンク越しに編集すると | **元ファイルも変わる**（そもそも同じ実体） | **元ファイルも変わる**（実体にたどり着いて書くため） |
| **元ファイルを削除すると** | **中身は残る**（別のラベルから辿れるため） | **リンクは残るが、たどるとエラー** |
| **別のファイルシステムへ** | **作れない** | **作れる** |
| **ディレクトリに対して** | **作れない** | **作れる** |

**「ハードリンク先を編集すると元ファイルも変わる」は、正確には「どちらも同じ実体だから区別がない」**という意味です。
どちらが「元」でどちらが「リンク」という区別は、作った後には残りません。

### 元ファイルを消すとどうなるか

**ここが二つの最大の違い**です。

```bash
$ rm workfile                         # 元ファイルを削除する
$ ls -l                               # 残ったものを確認する
total 4
-rw-r--r-- 1 root root 8 Sep 18 21:56 hardlink
lrwxrwxrwx 1 root root 8 Sep 18 21:56 symlink -> workfile

$ cat hardlink                        # ハードリンクは問題なく読める
content

$ cat symlink                         # シンボリックリンクは参照先が無い
cat: symlink: No such file or directory
```

**シンボリックリンクは「リンクそのもの」は残ります。** 消えるわけではありません。
ただし**指し示す先が無いのでアクセスするとエラー**になります
（この状態を**壊れたリンク／dangling symlink** と呼びます）。

**ハードリンクが読める理由**は、`ls -l` の 2 列目に出ています。

```text
-rw-r--r-- 2 root root 8 …  hardlink   ← 削除前：リンク数 2
-rw-r--r-- 1 root root 8 …  hardlink   ← 削除後：リンク数 1
                ↑
        この実体を指しているラベルの数
```

**`rm` が消しているのはラベル 1 枚**で、実体が消えるのは**リンク数が 0 になったとき**だけです。

### ハードリンクが作れない二つの場合

**① 別のファイルシステムには作れません。**

```bash
$ ln /tmp/link/hardlink /dev/shm/hl   # 別ファイルシステムへ張ろうとする
ln: failed to create hard link '/dev/shm/hl' => '/tmp/link/hardlink': Invalid cross-device link
```

**inode 番号はファイルシステムごとに管理されている**ためです。
`/tmp` の `902391` と `/dev/shm` の `902391` は別物なので、番号だけでは相手を特定できません。

**② ディレクトリには作れません。**

```bash
$ mkdir d                             # 確認用のディレクトリを作る
$ ln d dlink                          # ディレクトリにハードリンクを張ろうとする
ln: d: hard link not allowed for directory
```

ディレクトリにハードリンクを許すと**ディレクトリツリーに循環が生まれ**、
`find` や `rm -r` が無限にたどってしまうためです。

## 結果画面の見方

`ls -li` の出力を 1 列ずつ読むと、リンクの状態がすべて分かります。

```text
902391 -rw-r--r-- 2 root root    8 Sep 18 21:56 hardlink
  ↑        ↑      ↑   ↑    ↑     ↑       ↑          ↑
  ①        ②     ③   ④    ⑤     ⑥       ⑦          ⑧
```

| # | 列 | 意味 | リンクを見るとき |
|:-:|:--|:--|:--|
| ① | inode 番号 | ファイルの管理台帳の番号 | **同じ番号同士がハードリンク** |
| ② | ファイル種別とパーミッション | 先頭 1 文字が種別 | **`l` ならシンボリックリンク** |
| ③ | **リンク数** | **この実体を指しているハードリンクの数** | **1 なら他にラベルは無い。2 以上ならどこかに同じ実体がある** |
| ④ | 所有ユーザ | | |
| ⑤ | 所有グループ | | |
| ⑥ | サイズ | シンボリックリンクは**パス文字列の長さ** | 参照先 `workfile` が 8 文字なのでサイズ 8 |
| ⑦ | 最終更新日時 | | |
| ⑧ | ファイル名 | シンボリックリンクは `名前 -> 参照先` | |

**⑥ が紛らわしい点です。** シンボリックリンクのサイズは**元ファイルのサイズではなく、
記録しているパス文字列の長さ**です。上の例で `symlink` が 8 バイトなのは、
`workfile` という 8 文字を保持しているからです。

**リンク数が 2 以上のファイルを探す**には `find` を使います。

```bash
$ find /path -type f -links +1        # ハードリンクが 2 つ以上あるファイルを探す
```

## 実務での使い分け

| やりたいこと | どちらを使うか | 理由 |
|:--|:--|:--|
| **アプリのバージョン切り替え**（`current → v2`） | **シンボリックリンク** | ディレクトリを指せる。張り替えるだけでロールバックできる |
| **設定ファイルを複数の場所から参照** | **シンボリックリンク** | どれが実体か `ls -l` で一目で分かる |
| **同じファイルを消えないように保険をかける** | **ハードリンク** | 片方を消しても実体が残る |
| **別パーティションのファイルを参照** | **シンボリックリンク**（ハードリンクは不可） | inode がファイルシステムをまたげない |

**迷ったらシンボリックリンク**で構いません。
`ls -l` に参照先が出るため、**後から見た人が構造を追える**のが最大の理由です。
ハードリンクは `ls` で見ても普通のファイルと区別が付かず、意図が伝わりません。

**補足 … バックアップツールが使うハードリンク**

`rsync --link-dest` や `cp -al` は、**変更が無かったファイルをハードリンクで使い回します**。
毎日フルバックアップを取っているように見えて、実際のディスク消費は差分だけ、という仕組みです。
