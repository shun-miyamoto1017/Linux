## まずこれだけ

**3 つの出入口には、それぞれ番号が付いています。**

```text
                     ┌──────────┐
  キーボード ──0──▶  │          │ ──1──▶  ディスプレイ
   （標準入力）      │ コマンド  │        （標準出力）
                     │          │ ──2──▶  ディスプレイ
                     └──────────┘        （標準エラー出力）
```

| 番号 | 名前 | 既定の相手 | 何が流れるか |
|:-:|:--|:--|:--|
| **0** | **標準入力**（STDIN） | **キーボード** | コマンドが読み込むデータ |
| **1** | **標準出力**（STDOUT） | **ディスプレイ** | **正常な結果** |
| **2** | **標準エラー出力**（STDERR） | **ディスプレイ** | **エラーメッセージ・警告** |

**やりたいことから引く表**

| やりたいこと | 書き方 |
|:--|:--|
| 結果をファイルに**保存**（上書き） | **`コマンド > file`**（`1> file` と同じ） |
| 結果をファイルに**追記** | **`コマンド >> file`**（`1>> file` と同じ） |
| **エラーだけ**をファイルへ | **`コマンド 2> file`** ／ 追記は `2>> file` |
| **両方まとめて**ファイルへ | **`コマンド > file 2>&1`** ← **順番が重要** |
| **ファイルから読ませる** | **`コマンド < file`** |
| **その場で打った複数行**を読ませる | **`コマンド << EOF`**（ヒアドキュメント） |
| **1 つの文字列**を読ませる | **`コマンド <<< '文字列'`**（ヒアストリング） |
| **結果を捨てる** | **`コマンド > /dev/null`** |
| **全部捨てる** | **`コマンド > /dev/null 2>&1`** |

**外しやすい 3 点**

| 論点 | 結論 |
|:--|:--|
| **`>` は `1>` の省略形** | **`0` と `1` は省略できる。`2` は省略できない** |
| **`2>&1` は「2 を 1 と同じ場所へ」** | **`&` が無いと `1` という名前のファイルに書いてしまう** |
| **`> file 2>&1` と `2>&1 > file` は別物** | **左から順に処理されるため。**後述の実験で確かめます |

## 標準入出力とは何か

**コマンドは「箱」です。** 箱には**入口が 1 つ、出口が 2 つ**あります。

```text
 ┌─────────────────────────────────────────────────┐
 │                                                 │
 │   入口（標準入力）      箱（コマンド）    出口     │
 │                                                 │
 │   キーボード ────▶  [  grep  ]  ────▶ ディスプレイ │
 │                                  └──▶ ディスプレイ │
 │                                                 │
 └─────────────────────────────────────────────────┘
```

**大事なのは、この 3 本が「繋ぎ替えられる」**ということです。
**繋ぎ替えるのがリダイレクト**、**出口を別のコマンドの入口に繋ぐのがパイプ**です。

**コマンド自身は、繋ぎ先を知りません。**

```bash
$ cat file.txt                       # 出口はディスプレイ
$ cat file.txt > out.txt             # 出口をファイルに繋ぎ替えた
```

`cat` は**どちらの場合も「1 番へ書く」としかしていません。**
**1 番がどこに繋がっているかを決めるのはシェル**です。
だからこそ、**どのコマンドでも同じリダイレクトが使えます**。

### ファイルディスクリプタという番号

**ファイルディスクリプタ（FD）とは、プロセスが開いているファイルに付けられた番号**です。
「ファイル」といってもディスクのファイルとは限らず、**端末・パイプ・ソケットも含みます**。

**どのプロセスも、起動時に 0・1・2 の 3 つを最初から持っています。**

```bash
$ ls -l /proc/self/fd                # いま動いているプロセスの FD を見る
lrwx------ 1 shun shun 64 Sep 14 17:00 0 -> /dev/pts/0    # 標準入力 → 端末
lrwx------ 1 shun shun 64 Sep 14 17:00 1 -> /dev/pts/0    # 標準出力 → 端末
lrwx------ 1 shun shun 64 Sep 14 17:00 2 -> /dev/pts/0    # 標準エラー出力 → 端末
```

**3 つとも同じ端末（`/dev/pts/0`）を指しています。**
**だから普段は、正常な出力もエラーも、同じ画面に混ざって出る**のです。

```bash
$ ls -l /proc/self/fd > fd.txt       # 標準出力だけファイルに繋ぎ替えて実行する
$ cat fd.txt                         # 1 だけが別の場所を指している
lrwx------ 1 shun shun 64 Sep 14 17:00 0 -> /dev/pts/0
l-wx------ 1 shun shun 64 Sep 14 17:00 1 -> /home/shun/fd.txt   ← ここだけ変わった
lrwx------ 1 shun shun 64 Sep 14 17:00 2 -> /dev/pts/0
```

> **リダイレクトとは、この矢印の先を書き換える操作**です。
> **「番号 → 行き先」の対応表を、コマンドが動き出す前にシェルが書き換える**、と理解すると全部つながります。

**3 番以降も使えます**

```bash
$ exec 3> extra.log                  # 3 番を extra.log に繋ぐ
$ echo "3番へ書く" >&3               # 3 番に書き込む
$ exec 3>&-                          # 3 番を閉じる
$ cat extra.log                      # 確認する
3番へ書く
```

**0・1・2 は「最初から用意されている」だけで、特別な仕組みではありません。**

### なぜ出口が 2 つに分かれているのか

**「結果」と「エラー」を分けて扱えるようにするため**です。

```bash
$ find /etc -name httpd.conf > result.txt     # 結果だけをファイルへ
find: '/etc/audit': 許可がありません           # エラーは画面に残る
```

**もし出口が 1 つしかなければ、`result.txt` にエラーメッセージが混ざります。**
分かれているおかげで、**「結果はファイルに、エラーは画面で確認」**ができます。

| 分かれていることで得られるもの | 具体例 |
|:--|:--|
| **結果を汚さずに保存できる** | `find … > list.txt` の中身がファイル名だけになる |
| **エラーだけを監視できる** | `command 2>> error.log` でエラーだけ蓄積 |
| **パイプに乗るのは標準出力だけ** | `command \| grep …` は**エラーを拾わない** |

> **パイプに流れるのは 1 番だけ**です。ここは非常に大きな性質なので、
> [パイプとフィルタ](./パイプとフィルタ.md) でも扱います。

## 出力のリダイレクト

**意味** … **出口（1 番または 2 番）の行き先を、ディスプレイからファイルに切り替える**

| 記号 | 何番を | どうする |
|:--|:--|:--|
| **`>`** | **標準出力（1）** | **上書き**（`1>` と同義） |
| **`>>`** | **標準出力（1）** | **追記**（`1>>` と同義） |
| **`2>`** | **標準エラー出力（2）** | **上書き** |
| **`2>>`** | **標準エラー出力（2）** | **追記** |

> **`>` と `1>`、`>>` と `1>>` は完全に同じ意味**です。
> **`1` は省略できる**からで、**`2` は省略できません**（省略したら `1` の意味になってしまいます）。

**例文 … 上書きと追記の違い**

```bash
$ date > log.txt                     # 新規作成、または上書き
$ cat log.txt                        # 1行だけ
Mon Apr  8 16:28:55 JST 2019

$ date >> log.txt                    # 末尾に追記する
$ cat log.txt                        # 2行になった
Mon Apr  8 16:28:55 JST 2019
Mon Apr  8 16:29:13 JST 2019
```

| | ファイルが**無い**とき | ファイルが**ある**とき |
|:--|:--|:--|
| **`>`** | **新規作成**する | **中身を消して上書き**する |
| **`>>`** | **新規作成**する | **末尾に追記**する |

**どちらもファイルが無ければ作られます。** 違うのは**既にあるときの動き**だけです。

**例文 … エラーだけをファイルへ**

```bash
$ rm ./* 2> rm.log                   # エラーメッセージだけを rm.log へ
$ cat rm.log                         # 中身を確認する
rm: cannot remove './dir': ディレクトリです
rm: cannot remove './dir2': ディレクトリです
```

**正常に消せたファイルについては何も出ません**（`rm` は成功時に何も言わないため）。
**ファイルに残るのはエラーだけ**です。

**補足 … `>` はコマンドが動く前に実行されます**

```bash
$ sort file.txt > file.txt           # これは動かない（file.txt が空になる）
```

**シェルは `sort` を起動する前に `file.txt` を空にします。**
その後 `sort` が読みに行っても、もう中身がありません。

```bash
$ sort file.txt > sorted.txt && mv sorted.txt file.txt   # 別ファイルを経由する
$ sort -o file.txt file.txt                              # sort なら -o が安全
```

**「同じファイルを読みながら書く」は必ず別ファイルを経由**します。

## 入力のリダイレクト

**入口（0 番）の行き先を、キーボードから別のものに切り替えます。**
**似た記号が 3 つあり、ここが最も混乱しやすいところ**です。

```text
 <     … ファイルの中身を流し込む
 <<    … その場でキーボードから複数行を打ち、終了文字で締める
 <<<   … その場で書いた 1 つの文字列を流し込む
```

### 小なり 1 つ ファイルから読む

**意味** … **標準入力元を、キーボードから指定したファイルに切り替える**（`0<` と同義）

```bash
$ tr A-Z a-z < file.txt              # file.txt の中身を tr に流し込む
```

**例文**

```bash
$ cat file.txt                       # 元のファイルの中身
XYZ
$ tr A-Z a-z < file.txt              # 小文字に変換する
xyz
```

**なぜ `tr file.txt` と書けないのか**

**`tr` は変換対象を標準入力からのみ受け付けるコマンド**だからです。
**引数にファイル名を書いても、それを「読むファイル」とは解釈しません。**

```bash
$ tr A-Z a-z file.txt                # 誤り。file.txt は変換元とは見なされない
```

**`<` を使うか、パイプで渡します。**

```bash
$ tr A-Z a-z < file.txt              # リダイレクトで渡す
$ cat file.txt | tr A-Z a-z          # パイプで渡す（結果は同じ）
```

**補足 … `cat file | コマンド` と `コマンド < file` の違い**

| | `cat file \| コマンド` | `コマンド < file` |
|:--|:--|:--|
| **プロセスの数** | **2 つ**（`cat` と本体） | **1 つ** |
| **速さ** | わずかに遅い | **速い** |
| **読みやすさ** | **左から右に流れて読みやすい** | 慣れが要る |

**結果は同じ**です。**`cat` を 1 つ余計に起動しているだけ**なので、
**厳密さを問われる場面以外では好みで構いません**（`cat` を挟む書き方を UUOC と呼ぶことがあります）。

### 小なり 2 つ ヒアドキュメント

**意味** … **終了文字が現れるまで、標準入力への入力を続ける**

```text
コマンド << 終了文字
（ここに何行でも書く）
終了文字
```

**ヒアドキュメント**（here document）と呼びます。

**例文**

```bash
$ cat << world                       # 終了文字を world にして cat を実行する
> Hello world 1
> Hello world 2
> world
Hello world 1
Hello world 2
```

**何が起きているか**

```text
 $ cat << world
 > Hello world 1   ← キーボードから入力
 > Hello world 2   ← キーボードから入力
 > world           ← 終了文字を入力（ここで入力が終わる）
 Hello world 1     ← ここから cat の実行結果
 Hello world 2
```

**終了文字そのものは出力されません。**

**補足 … 「終了文字のみの行」だけが終了と見なされます**

**`Hello world 1` の中の `world` は、終了文字として認識されません。**
**行全体が終了文字と一致したときだけ**終わります。

**補足 … 終了文字は何でもよい**

`EOF` が慣例ですが、**シェルにとっては単なる目印**です。

```bash
$ cat << END                         # END でもよい
> 1行目
> END
1行目
```

**`EOF`（End Of File）が使われるのは、意味が伝わりやすいからというだけ**です。

**補足 … `<<-` なら行頭のタブを無視できます**

```bash
$ cat <<- EOF                        # ハイフンを付けると行頭のタブが除かれる
	インデントしたまま書ける
	EOF
インデントしたまま書ける
```

**除かれるのはタブだけで、半角スペースは除かれません。**
スクリプトの中で `if` 文の内側に書くときに使います。

### 小なり 3 つ ヒアストリング

**意味** … **指定した文字列を、そのままコマンドの標準入力に送る**

```bash
$ cat <<< 'Hello, World!'            # 1行の文字列を流し込む
Hello, World!
```

**ヒアストリング**（here string）と呼びます。**1 行で完結するのが特徴**です。

**変数も展開されます。**

```bash
$ cat <<< $PATH                      # 変数の中身が流し込まれる
/usr/local/bin:/usr/bin:/bin:/home/shun/bin
```

**実務での使いどころ**

```bash
$ grep -c error <<< "$LOG_LINE"      # 変数の中身を grep に渡す（一時ファイル不要）
$ tr a-z A-Z <<< "hello"             # ちょっとした変換を試す
HELLO
```

**`echo "$VAR" | コマンド` の代わり**になり、**パイプもプロセスも 1 つ減ります**。

### 3 つの使い分け

| | **`<`** | **`<<`** | **`<<<`** |
|:--|:--|:--|:--|
| **名前** | 入力リダイレクト | **ヒアドキュメント** | **ヒアストリング** |
| **何を渡すか** | **ファイルの中身** | **その場で打つ複数行** | **その場で書く 1 つの文字列** |
| **右に書くもの** | **ファイル名** | **終了文字** | **文字列** |
| **行数** | ファイル次第 | **複数行** | **原則 1 行** |
| **省略しない形** | `0<` | `0<<` | — |
| **典型例** | `tr a-z A-Z < f.txt` | `cat << EOF` | `cat <<< "文字列"` |

```text
 <    右はファイル名   ……「このファイルを読んで」
 <<   右は終了文字     ……「ここから終了文字までを読んで」
 <<<  右は文字列そのもの……「この文字列を読んで」
```

> **右側に何を書くかで覚えると、取り違えません。**
> **`<` の右にあるのはファイル名**、**`<<` の右にあるのは終了文字**、
> **`<<<` の右にあるのは中身そのもの**です。

**よくある取り違え**

| 書き方 | 実際に起きること |
|:--|:--|
| `cat << file.txt` | **`file.txt` という終了文字**を待ち続ける（ファイルは読まれない） |
| `cat < EOF` | **`EOF` という名前のファイル**を探しに行き、無ければエラー |
| `cat <<< file.txt` | **`file.txt` という 7 文字の文字列**が出力される（中身ではない） |

## ヒアドキュメントのクォート

**ここが最もつまずくところ**です。**`<<EOF` と `<<'EOF'` は動きが違います。**

```bash
$ VAR=world                                   # 展開されるかどうかを見るための変数

$ cat << EOF                         # クォート無し
> 変数は $VAR に展開される
> コマンド置換も $(date +%Y) 動く
> EOF
変数は world に展開される
コマンド置換も 2026 動く

$ cat << 'EOF'                       # 終了文字をシングルクォートで囲む
> 変数は $VAR のまま
> コマンド置換も $(date +%Y) 動かない
> EOF
変数は $VAR のまま
コマンド置換も $(date +%Y) 動かない
```

| 書き方 | ヒアドキュメントの中身 |
|:--|:--|
| **`<< EOF`** | **展開される**（`$VAR` `` `cmd` `` `$( )` `\` がすべて働く） |
| **`<< 'EOF'`** ／ `<< "EOF"` | **一切展開されない**（打った文字がそのまま渡る） |

**なぜクォートで挙動が変わるのか**

**終了文字（`EOF`）にクォートが 1 つでも含まれていると、
シェルは「この中身は展開しない」と判断する**、という仕様です。

```text
 << EOF      … 終了文字にクォートが無い  → 中身を展開する
 << 'EOF'    … 終了文字にクォートがある  → 中身を展開しない
 << "EOF"    … 同上（シングルでもダブルでも結果は同じ）
 << \EOF     … 同上（エスケープでも「クォートされている」扱い）
```

> **囲んでいるのは「中身」ではなく「終了文字」**です。
> **`'EOF'` という書き方は、シェルへの「展開するな」というスイッチ**だと理解すると迷いません。
> **中身のクォートの有無は関係ありません。**

**どちらを使うべきか**

| 場面 | 書き方 | 理由 |
|:--|:--|:--|
| **設定ファイルをそのまま書き出す** | **`<< 'EOF'`** | **`$` を含む内容が化けない** |
| **スクリプトを生成する** | **`<< 'EOF'`** | **中の `$1` `$VAR` が展開されては困る** |
| **awk や sed のコードを書く** | **`<< 'EOF'`** | **`$1` `$2` が消える事故を防ぐ** |
| 変数の値を埋め込みたい | `<< EOF` | そのために展開させる |

**事故の例 … クォートを忘れると起きること**

```bash
$ cat > script.sh << EOF             # クォート無しで生成してしまった
> #!/bin/bash
> echo "引数は \$1 です"
> echo "ホームは $HOME です"
> EOF

$ cat script.sh                      # 生成されたファイルを見る
#!/bin/bash
echo "引数は $1 です"                # \$ でエスケープしたので残った
echo "ホームは /home/shun です"      # ← 展開されてしまった
```

**`$HOME` が、生成した時点の値で焼き付いてしまいました。**
**別のユーザで実行しても `/home/shun` のまま**です。

```bash
$ cat > script.sh << 'EOF'           # クォート有りなら、打ったとおりに書かれる
> #!/bin/bash
> echo "引数は $1 です"
> echo "ホームは $HOME です"
> EOF
```

> **迷ったら `<< 'EOF'` を使います。**
> **展開してほしいときだけクォートを外す**、という向きで考えるほうが事故が少なくなります。

**補足 … 一部だけ展開したいとき**

```bash
$ cat << 'EOF' > app.conf            # まず展開なしで基本を書き
> path = $APP_PATH
> EOF
$ sed -i "s|\$APP_PATH|/opt/app|" app.conf   # あとから置き換える
```

**「全部展開する／全部しない」の 2 択**なので、混ぜたいときは**後から置換**します。

## 出力先を別の出口と同じにする

### アンパサンド付きの意味

**`>&` は、左に書いたファイルディスクリプタの出力先を、
右に書いたファイルディスクリプタの出力先に変更する**という意味です。

```text
 2>&1
 │ │ │
 │ │ └── 1番（標準出力）の「行き先」
 │ └──── & は「これは番号であって、ファイル名ではない」という印
 └────── 2番（標準エラー出力）を
```

**読み下すと「2 番の行き先を、いま 1 番が向いているところと同じにする」**です。

| 書き方 | 意味 |
|:--|:--|
| **`2>&1`** | **標準エラー出力を、標準出力と同じ場所へ** |
| **`1>&2`**（`>&2` と同義） | **標準出力を、標準エラー出力と同じ場所へ** |
| `>&2` | `1>&2` の省略形。**`1` は省略できる** |

**`>&2` はスクリプトの中で使います**

```bash
#!/bin/bash

echo "これは標準出力1です"
echo "これは標準エラー出力です" >&2     # わざと 2 番へ出す
echo "これは標準出力2です"
```

**なぜわざわざ 2 番に出すのか**

**そのメッセージが「結果」ではなく「お知らせ」だと宣言するため**です。

```bash
$ ./test.sh > result.txt             # 結果だけを保存する
これは標準エラー出力です              # ← 画面に残る
$ cat result.txt                     # ファイルには結果だけ
これは標準出力1です
これは標準出力2です
```

**`>&2` を付けておくと、呼び出す側が「結果だけ保存」を選べます。**
**エラーや進捗メッセージを `echo` するときは `>&2` を付ける**のが作法です。

| メッセージの種類 | どこへ出すか |
|:--|:--|
| **処理結果そのもの**（他のコマンドに渡す値） | **標準出力（1）** |
| **エラー・警告** | **標準エラー出力（2）** → `>&2` |
| **進捗の表示**（「処理中…」など） | **標準エラー出力（2）** → `>&2` |

> **「パイプに乗せたいものだけを 1 番に出す」**と考えると、迷いません。
> 進捗メッセージが 1 番に混ざると、**受け取った側のコマンドが誤動作**します。

### なぜ 2 番の行き先を 1 番に合わせるのか

**`&` を忘れると、まったく違う意味になります。**

```bash
$ コマンド 2> 1                      # 「1」という名前のファイルにエラーを書く
$ ls                                 # 1 というファイルができている
1  file.txt

$ コマンド 2>&1                      # 標準出力と同じ場所へ
```

| 書き方 | 意味 |
|:--|:--|
| **`2> 1`** | **`1` というファイル**にエラーを書く |
| **`2>&1`** | **1 番の行き先**にエラーを書く |

**`&` は「これは番号だ」という印**です。**これが無いとファイル名として扱われます。**

**覚え方**

```text
 2>&1   →  「2 を、& 1（アンド・イチ）へ」
            & が付いていたら番号、付いていなければファイル名
```

## 書く順番で結果が変わる

**ここが最大の落とし穴**です。**`> out.log 2>&1` と `2>&1 > out.log` は違う結果になります。**

**検証に使うスクリプト**

```bash
$ cat test.sh                        # 標準出力2回、標準エラー出力1回を出すだけ
#!/bin/bash

echo "これは標準出力1です"
echo "これは標準エラー出力です" >&2
echo "これは標準出力2です"
```

**① 正しい書き方 … `> out.log 2>&1`**

```bash
$ sh test.sh > out.log 2>&1          # 両方をファイルへ
$                                    # 画面には何も出ない
$ cat out.log                        # 3行すべて入っている
これは標準出力1です
これは標準エラー出力です
これは標準出力2です
```

**② よくある誤り … `2>&1 > out.log`**

```bash
$ sh test.sh 2>&1 > out.log          # 順番を逆にした
これは標準エラー出力です              # ← エラーだけ画面に出てしまう
$ cat out.log                        # ファイルには標準出力だけ
これは標準出力1です
これは標準出力2です
```

**なぜこうなるのか — 左から順に処理されるから**

**シェルはリダイレクトを、書かれた順に 1 つずつ処理します。**
**「そのとき 1 番がどこを向いているか」がすべて**です。

**① `> out.log 2>&1` の場合**

```text
 最初      1 → 端末      2 → 端末

 ① > out.log を処理
           1 → out.log   2 → 端末

 ② 2>&1 を処理（1 の現在の行き先 ＝ out.log を見る）
           1 → out.log   2 → out.log     ← 両方ファイル ○
```

**② `2>&1 > out.log` の場合**

```text
 最初      1 → 端末      2 → 端末

 ① 2>&1 を処理（1 の現在の行き先 ＝ 端末 を見る）
           1 → 端末      2 → 端末        ← 何も変わらない

 ② > out.log を処理
           1 → out.log   2 → 端末        ← 2 は端末のまま ✕
```

> **`2>&1` は「1 番の行き先をコピーする」**のであって、
> **「1 番に付いていく」わけではありません。**
> **コピーした後に 1 番が引っ越しても、2 番は付いていかない**——これが答えです。

**たとえるなら**

```text
 2>&1 は「いま 1 番が住んでいる住所を書き写す」操作。

 ① 先に 1 番が引っ越してから住所を写す  → 新しい住所（out.log）が写る ○
 ② 住所を写してから 1 番が引っ越す      → 古い住所（端末）を持ったまま ✕
```

**この性質を逆に利用することもあります**

```bash
$ sh test.sh 2>&1 > out.log | grep エラー    # 標準出力はファイル、エラーだけパイプへ
```

**「結果はファイルに保存しつつ、エラーだけ画面で監視する」**という書き方ができます。
**誤りではなく、意図してこう書く場面もある**ということです。

**正しい順番の覚え方**

```text
 ファイルに向けてから、コピーする。

 コマンド > ファイル 2>&1        ← ○ 行き先を決めてから写す
 コマンド 2>&1 > ファイル        ← ✕ 写してから行き先を変える
```

**`&>` という短い書き方もあります**

```bash
$ sh test.sh &> out.log              # 両方まとめて out.log へ（bash の書き方）
$ sh test.sh &>> out.log             # 追記版
```

| | `> file 2>&1` | `&> file` |
|:--|:--|:--|
| **対応するシェル** | **POSIX 準拠。`sh` でも動く** | **bash / zsh のみ** |
| **順番の間違い** | **起きうる** | **起きない** |
| どちらを使うか | **移植性が要るスクリプト** | 手元の bash なら簡潔 |

> **`#!/bin/sh` と書いたスクリプトでは `&>` は使えません。**
> **試験でも実務でも、`> file 2>&1` を正しく書けることが基本**です。

## リダイレクト演算子の一覧

| 記号 | 説明 |
|:--|:--|
| **`<`** | **標準入力の入力元を指定**（`0<` と同義） |
| **`<<`**（ヒアドキュメント） | **標準入力の入力元を指定し、終了文字まで入力**（`0<<` と同義） |
| **`<<<`**（ヒアストリング） | **指定した文字列をコマンドの標準入力に送る** |
| **`>`** | **標準出力の出力先を指定**（`1>` と同義） |
| **`>>`** | **標準出力の出力先を指定し、出力先に追記**（`1>>` と同義） |
| **`2>`** | **標準エラー出力の出力先を指定** |
| **`2>>`** | **標準エラー出力の出力先を指定し、出力先に追記** |
| **`>&2`** | **標準出力の出力先を、標準エラー出力の出力先と同じにする**（`1>&2` と同義） |
| **`2>&1`** | **標準エラー出力の出力先を、標準出力の出力先と同じにする** |
| `&>` / `&>>` | 標準出力と標準エラー出力をまとめて指定（bash 独自） |
| `<>` | 読み書き両用で開く（あまり使わない） |

**同じ意味になる組み合わせ**

| 組 | 理由 |
|:--|:--|
| **`>` と `1>`** | **`1` は省略できる** |
| **`>>` と `1>>`** | 同上 |
| **`<` と `0<`** | **`0` は省略できる** |
| **`>&2` と `1>&2`** | 同上 |

> **省略できるのは `0` と `1` だけ**です。**`2` は必ず書きます。**

## devnull に捨てる

**`/dev/null` は、入力された全てのデータを消す特殊なファイル**です。
**書き込んでも何も残らず、読み出すと即座に終わり（空）になります。**

```bash
$ ls -l /dev/null                    # キャラクタ型の特殊ファイル
crw-rw-rw- 1 root root 1, 3 Sep 14 17:00 /dev/null
```

| やりたいこと | 書き方 |
|:--|:--|
| **結果だけ捨てる**（エラーは見たい） | **`コマンド > /dev/null`** |
| **エラーだけ捨てる**（結果は見たい） | **`コマンド 2> /dev/null`** |
| **全部捨てる**（成否だけ知りたい） | **`コマンド > /dev/null 2>&1`** |

**例文**

```bash
$ sh test.sh > /dev/null             # 標準出力を捨てる
これは標準エラー出力です              # エラーだけ残る

$ sh test.sh 2> /dev/null            # エラーを捨てる
これは標準出力1です
これは標準出力2です

$ sh test.sh > /dev/null 2>&1        # 全部捨てる
$                                    # 何も出ない
```

**「成功したかどうか」だけを見たいときの定番**

```bash
$ grep -q error app.log > /dev/null 2>&1 && echo "エラーあり" || echo "エラーなし"   # 出力は要らない。終了ステータスだけ使う
```

> **`/dev/null` に捨てるのは、あくまで「見なくてよい」と判断したときだけ**にします。
> **cron のジョブで `> /dev/null 2>&1` を付けて、障害に気づかなかった**——これは実際によくある事故です。
> **`2>` だけは残す**、という判断ができるとかなり安全になります。

## スクリプト全体をリダイレクトする

**1 行ずつ書かなくても、スクリプトの先頭で一括指定できます。**

```bash
#!/bin/bash
exec >> /var/log/myapp.log 2>&1      # これ以降の出力はすべてログへ

echo "処理を開始します"               # ファイルに書かれる
some_command                         # このコマンドの出力もファイルへ
```

**`exec` にコマンドを書かずリダイレクトだけを書くと、
そのシェル自身のファイルディスクリプタが変更されます。**

| 書き方 | 効果 |
|:--|:--|
| **`exec > file`** | **以降の標準出力をすべて file へ** |
| **`exec 2> file`** | **以降の標準エラー出力をすべて file へ** |
| **`exec >> file 2>&1`** | **以降の両方を file へ追記** |

**画面にも残しつつログにも書きたい場合**

```bash
#!/bin/bash
exec > >(tee -a /var/log/myapp.log) 2>&1   # 画面とファイルの両方へ
```

**`>(…)` はプロセス置換**といい、**コマンドをファイルのように扱う書き方**です。
`tee` については [パイプとフィルタ](./パイプとフィルタ.md) を参照してください。

**補足 … 上書きを防ぐ `noclobber`**

```bash
$ set -o noclobber                   # > による上書きを禁止する
$ date > log.txt                     # 既にあるとエラーになる
bash: log.txt: cannot overwrite existing file
$ date >| log.txt                    # >| なら強制的に上書きできる
$ set +o noclobber                   # 元に戻す
```

**`>|` は「noclobber を無視して上書き」**という意味です。
**対話シェルでの事故防止**に使います（→ [シェルのオプション設定](./シェルのオプション設定.md)）。

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| **`2>&1` を付けたのにエラーがファイルに入らない** | **`2>&1` を `> file` より先に書いた** | **`> file 2>&1` の順にする** |
| **`1` という名前のファイルができた** | **`2> 1` と書いた**（`&` 忘れ） | `2>&1` と書く |
| **`>` で元のファイルが空になった** | **コマンドが動く前にシェルが空にする** | 別ファイルを経由する。`sort -o` を使う |
| **ヒアドキュメントで `$VAR` が展開されてしまった** | **`<< EOF`（クォート無し）** | **`<< 'EOF'` にする** |
| **ヒアドキュメントで変数を展開したいのにされない** | `<< 'EOF'` にしている | クォートを外す |
| **ヒアドキュメントが終わらない** | **終了文字の行に余分な空白がある**／綴りが違う | 行に終了文字だけを書く。`<<-` ならタブのみ除去 |
| `cat << file.txt` が固まる | **`<<` の右は終了文字**。ファイル名ではない | ファイルを読むなら `<` |
| **パイプに `grep` してもエラーが引っかからない** | **パイプに乗るのは 1 番だけ** | `コマンド 2>&1 \| grep …` |
| **`&>` が `sh` で動かない** | **bash 独自の書き方** | `> file 2>&1` と書く |
| cron のジョブが失敗しても気づかない | **`> /dev/null 2>&1` で全部捨てている** | **`2>` は残す**か、ログに出す |
| スクリプトの進捗表示がパイプ先を壊す | **進捗を 1 番に出している** | **`>&2` を付けて 2 番へ** |

## クラウド実務メモ

**cron ではリダイレクトを必ず書く**

**cron はジョブの出力をメールで送ろうとします。** メールが設定されていないと**出力は失われます**。

```cron
# 悪い例 … 失敗しても何も残らない
0 3 * * * /opt/app/backup.sh > /dev/null 2>&1

# 良い例 … ログに残す（時刻も付ける）
0 3 * * * /opt/app/backup.sh >> /var/log/backup.log 2>&1
```

**`> /dev/null 2>&1` はつい書いてしまう定型句**ですが、
**「障害が起きても誰も気づかない」状態を作ります**。ログに落とすのが原則です。

**systemd のサービスでは journald が受け取る**

```ini
[Service]
ExecStart=/opt/app/run.sh
StandardOutput=journal        # 既定。1番を journald へ
StandardError=journal         # 既定。2番を journald へ
```

**systemd 配下では、リダイレクトを書かなくても `journalctl -u サービス名` で両方見られます。**
**むしろ、スクリプト側で `> file` するとログが二重管理**になります。

**Docker のログは 1 番と 2 番をそのまま拾う**

```bash
$ docker logs mycontainer            # 標準出力と標準エラー出力の両方が出る
$ docker logs mycontainer 2> /dev/null   # 2番（stderr）だけ捨てて見る
```

**コンテナでは「ログファイルに書かず、標準出力に出す」のが定石**です。
アプリが自分でファイルに書くと、**`docker logs` にも CloudWatch にも流れません**。

```dockerfile
# nginx の公式イメージがやっていること（ログを標準出力に繋ぐ）
RUN ln -sf /dev/stdout /var/log/nginx/access.log && \
    ln -sf /dev/stderr /var/log/nginx/error.log
```

**`/dev/stdout` と `/dev/stderr` へのシンボリックリンク**で、
**ファイルに書くつもりのアプリの出力を、そのまま 1 番・2 番に流し込んでいます**。

**ユーザーデータ（EC2）のログはここに出る**

```bash
$ sudo cat /var/log/cloud-init-output.log     # ユーザーデータの出力が残る
```

**ユーザーデータは標準出力・標準エラー出力の両方がこのファイルに記録されます。**
**起動時のスクリプトが失敗したときは、まずここを見ます。**

**ログを画面でも見たいときの定型**

```bash
$ ./deploy.sh 2>&1 | tee -a deploy_$(date +%Y%m%d_%H%M%S).log   # 画面にも出しつつ、日時つきのログにも残す
```

**`2>&1` を `|` の前に置く**のが要点です。これが無いと**エラーがログに残りません**。
