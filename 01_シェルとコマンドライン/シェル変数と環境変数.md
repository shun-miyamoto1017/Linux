## まずこれだけ

| やりたいこと | コマンド |
|:--|:--|
| 変数を作る | `NAME=value` |
| 変数の中身を見る | `echo $NAME` |
| **環境変数を作る** | **`export NAME=value`** または **`declare -x NAME=value`** |
| **既存のシェル変数を環境変数にする** | **`export NAME`** または **`declare -x NAME`** |
| シェル変数と環境変数をすべて見る | `set` / `declare` |
| 環境変数だけ見る | `env` / `printenv` |
| 特定の環境変数だけ見る | `printenv NAME` |
| 変数を消す | `unset NAME` |

**役割の切り分けがここの要点です。**

| したいこと | 使うコマンド |
|:--|:--|
| 変数を**作る／環境変数に昇格させる** | `export` と `declare -x` |
| 変数を**見る**だけ | `set` / `declare` / `env` / `printenv` |
| シェルの**オプション**を設定する | `set`（[別ノート](./シェルのオプション設定.md)） |

## シェル変数と環境変数のちがい

**環境変数は、変数を設定したシェル上と、そこから起動されるシェルやアプリケーション、コマンドで
有効な変数です。これは設定が子プロセスに引き継がれる事を意味します。**

| 種類 | 説明 | 子プロセスに引き継がれるか |
|:--|:--|:-:|
| **シェル変数** | 変数を設定したシェル上でのみ有効な変数 | ✗ |
| **環境変数** | `export` 属性が付いたシェル変数 | ✓ |

**例文**

```bash
$ MYVAR=hello                       # シェル変数として定義する
$ echo $MYVAR                       # いまのシェルでは値が見える
hello

$ bash -c 'echo "[$MYVAR]"'         # 子シェルを起動して同じ変数を見る
[]                                  # 引き継がれていないので空

$ export MYVAR                      # エクスポート属性を付けて環境変数に昇格
$ bash -c 'echo "[$MYVAR]"'         # もう一度、子シェルから見る
[hello]                             # 今度は引き継がれている
```

**補足 … `bash -c 'コマンド'` とは**

「新しいシェルを起動して、そこで 1 回だけコマンドを実行する」書き方です。
子プロセスに引き継がれるかどうかを確かめるのに便利なので、このノートでは何度も使います。
`[ ]` で囲んでいるのは、**値が空でも分かるようにする**ためです。

**補足 … なぜこの仕組みなのか**

プロセスが起動するとき、親プロセスは「環境（environment）」という文字列の配列を子に渡します。
ここに載せるかどうかを決めるのが `export` です。

**シェル変数は「シェルというプログラムのローカル変数」、
環境変数は「OS がプロセス間で受け渡す値」** と考えると腑に落ちます。

実際にプロセスに渡された環境は `/proc` から確認できます。

```bash
$ cat /proc/$$/environ | tr '\0' '\n' | head -5   # 環境変数の実体を直接のぞく
                                    # $$ は自分自身のプロセスID
SHELL=/bin/bash                     # tr で区切り文字を改行に変換して読む
PWD=/home/shun
LANG=ja_JP.UTF-8
```

## 変数を作る

```bash
$ NAME=shun                         # = の前後にスペースを入れない
$ echo $NAME                        # $ を付けると中身が取り出される
shun
```

**`=` の前後にスペースを入れてはいけません。** シェルはスペース区切りで単語を分けるため、
`NAME = shun` は「`NAME` というコマンドに `=` と `shun` を渡す」と解釈されます。

```bash
$ NAME = shun                       # スペースを入れると失敗する
bash: NAME: command not found
```

**値にスペースを含めるときはクォートで囲みます。**

```bash
$ MSG="hello world"                 # スペースを含む値はクォートする
$ echo "$MSG"                       # 参照するときもクォートする
hello world
```

**変数名の直後に文字を続けるときは `${ }` で区切りを明示します。**

```bash
$ echo $NAMEsan                     # 「NAMEsan」という別の変数を探すので空になる

$ echo ${NAME}san                   # { } でどこまでが変数名かを示す
shunsan
```

### 代入するときに `$` は付けない

`$変数名` は「変数の**中身を取り出す**」記法です。**代入するときは `$` を付けません。**

```bash
$ LPIC=test                         # 正しい書き方（$ を付けない）
$ echo $LPIC                        # 取り出すときだけ $ を付ける
test

$ $LPIC=test                        # $LPIC が中身の test に展開されてしまう
bash: test=test: command not found  # 「test=test」というコマンドを探しに行く
```

**書き間違いのパターンを並べると、違いがはっきりします。**

| 書き方 | 結果 |
|:--|:--|
| `LPIC=test` | **正しい**。シェル変数 `LPIC` に `test` を代入する |
| `$LPIC=test` | 誤り。`$LPIC` が先に展開されてしまう |
| `LPIC test` | 誤り。`LPIC` という**コマンド**を `test` を引数にして実行しようとする |
| `LPIC = test` | 誤り。同上（`=` と `test` が引数として渡る） |
| `export LPIC=test` | **環境変数**として作成する。シェル変数を作りたいだけなら不要 |

```bash
$ LPIC test                         # コマンドとして解釈される
bash: LPIC: command not found

$ LPIC = test                       # 同じくコマンドとして解釈される
bash: LPIC: command not found
```

**補足** … `export LPIC=test` も文法としては正しいのですが、**環境変数**になります。
「シェル変数を作りたい」だけなら `LPIC=test` で十分です。
`export` は「子プロセスにも渡したい」ときに使うもの、と切り分けて覚えます。

**補足 … 変数名の規則**

| 規則 | 例 |
|:--|:--|
| 使える文字は英数字と `_` | `APP_NAME` `path2` |
| 数字で始められない | `2path` は不可 |
| **大文字小文字を区別する** | `$DATE` と `$date` は別の変数 |
| 慣習として環境変数は大文字 | `PATH` `HOME` `LANG` |

```bash
$ DATE=today                        # 大文字で定義する
$ echo "[$date]"                    # 小文字で参照すると別の変数扱い
[]                                  # 未定義なので空になる
```

## 環境変数にする

環境変数は `export` や `declare -x` を以下のように実行すると作成できます。

```
export 環境変数=値
declare -x 環境変数=値
```

また、`export` や `declare -x` により
**シェル変数（変数を設定したシェル上でのみ有効な変数）を環境変数に変更できます。**

```
export シェル変数名
declare -x シェル変数名
```

**例文 … シェル変数を設定した後に環境変数にする**

```bash
$ LPIC=study_linux                  # まずシェル変数として定義する
$ export LPIC                       # エクスポート属性を付けて環境変数にする
```

**動作を確認する**

```bash
$ LPIC=study_linux                  # シェル変数として定義
$ bash -c 'echo "[$LPIC]"'          # 子シェルから見えるか確認
[]                                  # 引き継がれていない

$ export LPIC                       # 環境変数に昇格させる
$ bash -c 'echo "[$LPIC]"'          # もう一度、子シェルから確認
[study_linux]                       # 引き継がれた

$ declare -x LINUC=study_linuc      # 定義と環境変数化を同時に行う書き方
$ bash -c 'echo "[$LINUC]"'         # 子シェルから確認
[study_linuc]

$ declare -p LPIC LINUC             # 属性を確認（-x が付いていれば環境変数）
declare -x LPIC="study_linux"
declare -x LINUC="study_linuc"
```

### `declare` のオプション

`declare` コマンドは「オプション無し」で全てのシェル変数と環境変数を表示し、
**「`-x`」で環境変数を宣言できます**。

`declare` には他にも属性を付けるオプションがあり、`-x` はそのうちの 1 つ、という位置づけです。

| オプション | 意味 | 例 |
|:--|:--|:--|
| `-x` | 環境変数にする（`export` と同義） | `declare -x LPIC=study_linux` |
| `-r` | 読み取り専用にする | `declare -r VERSION=1.0` |
| `-i` | 整数として扱う | `declare -i COUNT=5` |
| `-a` | 配列 | `declare -a LIST` |
| `-A` | 連想配列 | `declare -A MAP` |
| `-f` | 関数の定義を表示する | `declare -f` |
| `-p` | 属性と値を表示する | `declare -p HOME` |

```bash
$ declare -r VERSION=1.0            # 読み取り専用の変数を作る
$ VERSION=2.0                       # 書き換えを試みる
bash: VERSION: readonly variable    # 拒否される

$ declare -i COUNT=5                # 整数属性を付けた変数を作る
$ COUNT=COUNT+3                     # 整数属性があると式として計算される
$ echo $COUNT                       # 計算結果を確認
8

$ NUM=5                             # 属性なしの変数と比較する
$ NUM=NUM+3                         # 文字列として連結されるだけ
$ echo $NUM                         # 計算されず文字列になっている
NUM+3
```

**補足** … `readonly` コマンドは `declare -r` と同じ働きをします。

```bash
$ readonly APP_ENV=production       # 書き換え不可の変数を作る
$ APP_ENV=staging                   # 変更を試みる
bash: APP_ENV: readonly variable
```

### `export` のオプション

| オプション | 意味 |
|:--|:--|
| （なし） | 環境変数を一覧表示する |
| `-p` | 一覧表示（POSIX 形式。オプション無しと同じ） |
| `-n` | **エクスポート属性を外す**（変数自体は残る） |

```bash
$ export -n MYVAR                   # エクスポート属性だけ外す
$ bash -c 'echo "[$MYVAR]"'         # 子シェルからは見えなくなる
[]
$ echo $MYVAR                       # 自分のシェルには値が残っている
hello
```

## 変数を表示するコマンド

| コマンド | 説明 |
|:--|:--|
| `set` | 全てのシェル変数と環境変数を表示 |
| `declare` | 全てのシェル変数と環境変数を表示 |
| `env` | 全ての環境変数を表示 |
| `printenv` | 指定の、または全ての環境変数を表示 |

```bash
$ env | head -3                     # 環境変数の一覧（先頭3行だけ表示）
SHELL=/bin/bash
PWD=/home/shun
LANG=ja_JP.UTF-8

$ printenv HOME                     # 変数を1つだけ取れるのは printenv
/home/shun

$ declare -p PATH                   # 属性つきで1変数だけ表示（-x が環境変数の印）
declare -x PATH="/usr/local/bin:/usr/bin:/bin"

$ export                            # 環境変数の一覧（declare -x 形式で出る）
declare -x HOME="/home/shun"
declare -x LANG="ja_JP.UTF-8"
```

**補足 … 見える範囲の違いを実際に確かめる**

`set` と `declare` はシェル変数も含めて表示するので、
**「`export` していない変数が見えるかどうか」で使い分けられます**。

```bash
$ MYVAR=hello                       # export していないシェル変数を用意

$ set | grep '^MYVAR'               # set はシェル変数も表示するので見つかる
MYVAR=hello

$ declare | grep '^MYVAR'           # declare も同様に見つかる
MYVAR=hello

$ env | grep '^MYVAR'               # env は環境変数だけなので見つからない
                                    # （何も出力されない）

$ printenv MYVAR                    # printenv も見つからない
$ echo $?                           # 終了ステータスを確認
1                                   # 1 = 見つからなかった
```

## 四つのコマンドの使い分け

| コマンド | 変数の表示 | 変数の作成・昇格 | シェルのオプション設定 |
|:--|:-:|:-:|:-:|
| `set` | ○（シェル変数＋環境変数） | ✗ | **○** |
| `declare` | ○（シェル変数＋環境変数） | **○**（`-x` で環境変数に） | ✗ |
| `env` | ○（環境変数のみ） | △（**一時的**にだけ設定できる） | ✗ |
| `printenv` | ○（環境変数のみ） | ✗ | ✗ |
| `export` | ○（環境変数のみ） | **○** | ✗ |

### `set` は表示専用（変数に関しては）

`set` は全てのシェル変数と環境変数を「表示」します。
シェルのオプションは設定できますが、**変数を環境変数に昇格させることはできません**。

```bash
$ MYVAR=hello                       # シェル変数を作る
$ set | grep '^MYVAR'               # 表示はできる
MYVAR=hello

$ bash -c 'echo "[$MYVAR]"'         # set しただけでは引き継がれない
[]
```

ただし `set -o allexport` を有効にしておけば、
**それ以降に定義した変数**は自動的に環境変数になります。
「変数を指定して昇格させる」わけではない点が `export` との違いです。

```bash
$ set -o allexport                  # 自動エクスポートを有効にする
$ NEWVAR=world                      # 以降に定義した変数は自動で環境変数になる
$ bash -c 'echo "[$NEWVAR]"'        # 子シェルから確認
[world]
$ set +o allexport                  # 元に戻す
```

### `env` は一時的な設定に使える

`env` にはもう 1 つ、
**一時的に環境変数を設定してコマンドを実行する**という使い方があります。

```bash
$ env LANG=C date                   # この date の実行中だけ LANG を C にする
Thu Aug 27 23:24:40 JST 2026        # 英語表記になる

$ date                              # 元の設定では日本語表記
2026年  8月 27日 木曜日 23:24:45 JST

$ echo $LANG                        # 元のシェルの値を確認
ja_JP.UTF-8                         # 変わっていない
```

**呼び出し元のシェルには影響しません。** ここが「環境変数を作成する」`export` との違いです。

`-i` を付けると、**環境変数を空にした状態**でコマンドを実行できます。
再現性のあるテストや、環境変数の影響を切り分けたいときに使います。

```bash
$ env -i bash -c 'env'              # 環境変数をすべて空にして起動する
PWD=/home/shun
SHLVL=1
_=/usr/bin/env
```

### `printenv` は表示専用

指定の、または全ての環境変数を「表示」するだけのコマンドです。
設定する機能はありません。

```bash
$ printenv | head -3                # 環境変数の一覧（先頭3行）
SHELL=/bin/bash
PWD=/home/shun
LANG=ja_JP.UTF-8

$ printenv HOME                     # env との違いは「1つだけ取れる」こと
/home/shun
```

**補足 … 終了ステータスで存在確認ができます**

`printenv VAR` は、変数が未定義なら終了ステータス `1` を返します。
スクリプトのチェック処理で使えます。

```bash
$ printenv AWS_PROFILE > /dev/null || echo "AWS_PROFILE が未設定です"   # 未設定なら知らせる
AWS_PROFILE が未設定です
```

この 1 行は 3 つの部品でできています。

| 部分 | 意味 |
|:--|:--|
| `printenv AWS_PROFILE` | 変数があれば値を表示して成功（終了ステータス 0）、無ければ失敗（1） |
| `> /dev/null` | 表示された値を捨てる。**成否だけ知りたいので出力は要らない** |
| `\|\| echo "..."` | **直前が失敗したときだけ**右側を実行する |

`/dev/null` は「書き込んだものが消えるゴミ箱」のような特殊ファイルです。
`||` は「左が失敗したら右」、`&&` は「左が成功したら右」を意味します。

```bash
$ export AWS_PROFILE=prod           # 変数を設定してから同じ行を試す
$ printenv AWS_PROFILE > /dev/null || echo "AWS_PROFILE が未設定です"   # 今度は設定済み
                                    # 成功したので右側は実行されず、何も出ない

$ printenv AWS_PROFILE && echo "設定済みです"   # && なら成功したときに右側が動く
prod
設定済みです
```

## 代表的な環境変数

あらかじめ用意されている代表的な環境変数には以下のようなものがあります。

| 環境変数 | 説明 |
|:--|:--|
| `HISTFILE` | コマンド履歴保存ファイルのパス |
| `HISTSIZE` | 現在のシェルでのコマンド履歴の保存数 |
| `HISTFILESIZE` | コマンド履歴保存ファイルへの履歴保存数 |
| `HOSTNAME` | ホスト名 |
| `HOME` | ログインしているユーザのホームディレクトリ |
| `LANG` | ロケール（言語設定） |
| `PATH` | コマンドやプログラムを検索するディレクトリのリスト |
| `PWD` | カレントディレクトリのパス |
| `USER` | ログインしているユーザ |

**例文**

```bash
$ echo $HOME                        # ホームディレクトリの場所
/home/shun

$ echo $PWD                         # いまいるディレクトリ（pwd コマンドと同じ内容）
/home/shun/work

$ echo $USER                        # ログインユーザ名
shun

$ echo $HOSTNAME                    # ホスト名
web01

$ echo $LANG                        # 言語設定
ja_JP.UTF-8

$ echo $PATH                        # コマンドを探しにいくディレクトリの並び（: 区切り）
/usr/local/bin:/usr/bin:/bin

$ echo $HISTFILE                    # 履歴が保存されるファイルの場所
/home/shun/.bash_history
```

**そのほかよく使う環境変数**

| 環境変数 | 説明 |
|:--|:--|
| `SHELL` | ログインシェルのパス |
| `PS1` | プロンプトの表示形式 |
| `EDITOR` / `VISUAL` | 既定のエディタ |
| `TERM` | 端末の種類 |
| `TZ` | タイムゾーン |
| `LOGNAME` | ログイン名（`USER` とほぼ同じ） |
| `OLDPWD` | 直前にいたディレクトリ |
| `UID` | ユーザ ID（シェル変数） |

```bash
$ echo $SHELL                       # ログインシェルの種類
/bin/bash

$ echo $EDITOR                      # crontab -e などで起動するエディタ
vi

$ echo $UID                         # ユーザID（0 なら root）
1000
```

### PATH の見方

`PATH` は「コマンドを探しにいくディレクトリのリスト」です。`:` で区切られ、**左から順に探します**。

```bash
$ echo $PATH | tr ':' '\n'          # : を改行に変換して見やすくする
/usr/local/bin
/usr/bin
/bin

$ which ls                          # ls がどこで見つかったかを確認する
/usr/bin/ls

$ type -a ls                        # 同名のコマンドが複数ある場合すべて表示する
ls is aliased to `ls --color=auto'
ls is /usr/bin/ls
```

**PATH に追記するときは、既存の値を壊さないように書きます。**

```bash
$ export PATH="$PATH:/opt/app/bin"  # 末尾に追加する（既存の値を含めるのが重要）
$ export PATH="/opt/app/bin:$PATH"  # 先頭に追加する（こちらが優先される）

$ export PATH="/opt/app/bin"        # ← これは危険。ls も cat も使えなくなる
```

**補足 … `HIST` 系は厳密には環境変数ではありません**

`HISTFILE` `HISTSIZE` `HISTFILESIZE` は bash が用意する**シェル変数**で、
既定では `export` されていません。試験では「環境変数」としてまとめて出題されますが、
実務で「子プロセスに引き継がれるか」を判断するときはこの違いが効いてきます。

```bash
$ set | grep '^HISTSIZE'            # set なら見つかる
HISTSIZE=1000

$ env | grep '^HISTSIZE'            # env では見つからない
                                    # （何も出力されない）
```

> 履歴関連の変数の詳しい話は [コマンド履歴](./コマンド履歴.md) を参照してください。

## 変数を消す

```bash
$ MYVAR=hello                       # 変数を作る
$ unset MYVAR                       # 変数を消す
$ echo "[$MYVAR]"                   # 確認する
[]                                  # 空になっている
```

| コマンド | 動作 |
|:--|:--|
| `unset VAR` | 変数そのものを削除する |
| `export -n VAR` | エクスポート属性だけ外す（変数は残る） |
| `VAR=` | 値を空にする（変数は残る） |

**「空の変数」と「未定義の変数」は違います。**

```bash
$ EMPTY=                            # 空文字を代入する（定義はされている）
$ unset UNDEF                       # こちらは未定義

$ echo "${EMPTY:-未設定}"            # :- は「空か未定義なら代替値」
未設定
$ echo "${EMPTY-未設定}"             # - は「未定義のときだけ代替値」
                                    # 空文字なので何も出ない
```

**補足** … `set -u`（`nounset`）を有効にすると、未定義変数の参照がエラーになります。
スクリプトのタイポ事故を防ぐ定番の設定です
（[シェルのオプション設定](./シェルのオプション設定.md) を参照）。

## 設定ファイルの一括読み込み

実務では次の 1 行をよく見かけます。まずこれが何をしているかを分解します。

```bash
$ set -a; source .env; set +a       # ← この1行を以下で分解して説明する
```

**手順1 … `.env` ファイルとは**

`変数名=値` を 1 行ずつ書いただけのテキストファイルです。
接続先やパスワードなどの設定値を、プログラム本体とは別に切り出しておくために使います。

```bash
$ cat .env                          # .env の中身を表示して確認する
DB_HOST=10.0.1.20
DB_PORT=5432
APP_ENV=production
```

**手順2 … `source` とは**

`source ファイル名` は、**そのファイルに書かれた行を、いま自分がいるシェルで実行する**コマンドです。
`.env` を `source` すると、中の 3 行がそのまま打ち込まれたのと同じ状態になります。

```bash
$ source .env                       # .env の3行をいまのシェルで実行する
$ echo $DB_HOST                     # 変数として読み込まれたか確認
10.0.1.20
```

**手順3 … `source` だけでは足りない理由**

`source` しただけでは**シェル変数**にしかならないため、
`docker` や `terraform` といった別のコマンド（＝子プロセス）には渡りません。

```bash
$ source .env                       # 読み込む
$ bash -c 'echo "[$DB_HOST]"'       # 子シェルから見えるか確認
[]                                  # 引き継がれていない
```

かといって `.env` の全行に `export` を書き足すのは面倒です。

**手順4 … そこで `allexport` で挟む**

`source` の前後を `set -a` と `set +a` で挟むと、
読み込んだ変数がすべて自動で環境変数になります。

```bash
$ set -a                            # ここから定義する変数は自動で環境変数になる
$ source .env                       # .env を読み込む（3つとも環境変数になる）
$ set +a                            # 自動エクスポートを解除して元に戻す

$ bash -c 'echo "[$DB_HOST]"'       # 子シェルから見えるか確認
[10.0.1.20]                         # 引き継がれた
```

**手順5 … 1 行にまとめる**

この 3 つを `;`（セミコロン）でつないだものが、冒頭の 1 行です。
**`;` は「コマンドを順番に実行する」という区切り記号**で、3 回に分けて打つのと同じ意味です。

| 部分 | やっていること |
|:--|:--|
| `set -a` | これ以降に定義する変数を自動で環境変数にする |
| `source .env` | `.env` の中身をいまのシェルで実行して、変数を定義する |
| `set +a` | 自動エクスポートをやめて、元の状態に戻す |

**注意点が 2 つあります。**

1. **`set +a` を書き忘れない**。忘れると、それ以降に作る変数がすべて環境変数になってしまいます。
2. **`.env` に書いたパスワードが、そこから起動するすべてのコマンドに見えます**。
   実務では Secrets Manager や Parameter Store から取得する方式のほうが、監査面で望ましい選択です。

> **`source` と `.` は同じもの**
> `source .env` は `. .env` とも書けます（こちらが POSIX 準拠の書き方）。
> どちらも「いまのシェルでファイルを読み込む」という意味です。
>
> 一方 `bash .env` と書くと**別のシェルが起動してそこで実行される**ため、
> 変数が手元のシェルに残りません。ここは間違えやすいポイントです。
>
> ```bash
> > $ bash .env            # 子シェルで実行され、終わると同時に消える
> > $ echo $DB_HOST        # 手元のシェルに残っているか確認
> >                        # 空。何も残らない
> ```

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| `NAME = value` でエラーになる | `=` の前後にスペースを入れている | `NAME=value` と書く |
| `env` に自分の変数が出てこない | `export` していないシェル変数 | `export VAR` するか `set` で確認 |
| 子プロセスに変数が渡らない | シェル変数のまま | `export` する |
| `$DATE` と `$date` が別物になる | 変数名は大文字小文字を区別する | 名前を統一する |
| `echo $VARsan` が空になる | どこまでが変数名か曖昧 | `${VAR}san` と書く |
| `PATH` を書き換えたらコマンドが使えなくなった | 既存の値を含めずに上書きした | `export PATH="$PATH:/new"` |
| スペース入りの値が分割される | クォートしていない | `"$VAR"` と書く |
| `.env` を読んだのにツールに渡らない | `source` だけではシェル変数 | `set -a; source .env; set +a` |

## クラウド実務メモ

**環境変数で AWS の向き先が変わる**

`AWS_PROFILE` `AWS_REGION` `AWS_DEFAULT_REGION` は環境変数なので、
`export` した瞬間から子プロセス（`aws` コマンド、`terraform`）すべてに効きます。
**本番と検証を取り違える事故の主要因**なので、作業前に必ず確認します。

```bash
$ printenv AWS_PROFILE AWS_REGION   # いまどのプロファイル・リージョンを向いているか確認
prod
ap-northeast-1

$ aws sts get-caller-identity       # 実際にどの AWS アカウントに繋がるかを確認する
{
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/shun"
}
```

**優先順位を理解しておく**

AWS CLI は「コマンドラインオプション → 環境変数 → 設定ファイル → IAM ロール」の順に見ます。
環境変数が残っていると、`~/.aws/config` の設定より優先されます。

```bash
$ unset AWS_PROFILE AWS_REGION      # 環境変数を消して設定ファイルに戻す
```

**EC2 のユーザーデータは非対話・非ログインシェルで動く**

`~/.bashrc` も `~/.bash_profile` も読まれません。`PATH` は明示的に設定します。

```bash
#!/bin/bash
export PATH=/usr/local/bin:/usr/bin:/bin    # 明示的に設定する
export AWS_DEFAULT_REGION=ap-northeast-1
```

**コンテナでは環境変数が設定の主役**

Docker や Kubernetes では、設定を環境変数で渡すのが基本です。
`docker run -e` や `env:` の指定は、そのまま `export` された環境変数になります。

```bash
$ docker run -e APP_ENV=production myapp    # 環境変数を渡してコンテナを起動する
$ docker exec -it container-name env        # コンテナ内の環境変数を確認する
```

**秘密情報を環境変数で渡すリスク**

環境変数は `/proc/<pid>/environ` から読める場合があり、
`ps eww` でも見えることがあります。パスワードは Secrets Manager や
Parameter Store から取得し、ファイル経由で渡すほうが安全です。
