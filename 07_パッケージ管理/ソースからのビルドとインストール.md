## なぜソースから入れるのか

```text
   パッケージで入る   → 迷わずパッケージを使う（依存解決も更新も自動）
        ↓ 入らない
   ソースからビルドする
```

**ソースビルドを選ぶ理由は、だいたいこの4つ**です。

| 理由 | 例 |
|:--|:--|
| 必要なバージョンがパッケージに無い | 脆弱性対応版がまだ RPM 化されていない |
| ビルドオプションを変えたい | 特定のモジュールを有効にしたい |
| そもそもパッケージが存在しない | 社内ツール、研究用ソフトウェア |
| 配布物を自分で作りたい | ビルドしてから RPM / deb にパッケージ化する |

**代償もあります。**

```text
  ✗ yum update で更新されない  → 脆弱性対応を自分で追う必要がある
  ✗ 依存の解決を自分でやる
  ✗ 他のサーバに同じものを入れる再現性が落ちる
```

このため、**本番では「ビルドしてからパッケージ化して配る」**のが定石です。

## 手順の全体像

```text
  ① tar xf ソース.tar.gz      アーカイブを展開する
  ② ./configure               環境を調べて Makefile を作る
  ③ make                      コンパイルする
  ④ su / sudo                 必要なら権限を上げる
  ⑤ make install              所定のディレクトリへ配置する
```

**この順番は変えられません。** 各段が前の段の成果物を使うからです。

```text
   configure  →  Makefile を生成
                      ↓
   make       →  Makefile を読んでバイナリを作る
                      ↓
   make install → 作ったバイナリを配置する
```

## 手順1 展開する

```bash
$ tar xzf hello-1.0.tar.gz                  # gzip 圧縮の tar を展開する
$ cd hello-1.0                              # 展開されたディレクトリへ移動する
$ ls                                        # 中身を確認する
```

**まず読むべきファイル**

| ファイル | 内容 |
|:--|:--|
| `README` | 概要と基本的な使い方 |
| `INSTALL` | **ビルド手順とオプション** |
| `NEWS` / `ChangeLog` | 変更履歴 |
| `configure` | この後実行するスクリプト |

**`INSTALL` を読まずに始めると、必要な開発パッケージが足りずに詰まります。**

> 展開の詳細は [圧縮とアーカイブ](../01_シェルとコマンドライン/圧縮とアーカイブ.md) を参照してください。

## 手順2 configure

### configure は何をしているのか

**`configure` は、ビルドする環境を調べて `Makefile` を生成するシェルスクリプト**です。
ソースアーカイブに**同梱されています**。自分で作るものではありません。

```text
   configure が調べること
     ・コンパイラは何か、使えるか
     ・必要なヘッダファイルとライブラリがあるか
     ・OS 固有の差異（関数名、型のサイズ）
     ・インストール先をどこにするか
        ↓
   Makefile.in の @変数@ を実際の値に置き換えて Makefile を出力する
```

### 実際に動かしてみる

検証用に小さな autoconf プロジェクトを作って実行しました。

```bash
$ ./configure                               # 環境を調べて Makefile を作る
```

```text
checking for gcc... gcc
checking whether the C compiler works... yes
checking for C compiler default output file name... a.out
checking for suffix of executables... 
checking whether we are cross compiling... no
checking for suffix of object files... o
checking whether the compiler supports GNU C... yes
checking whether gcc accepts -g... yes
checking for gcc option to enable C11 features... none needed
configure: creating ./config.status
config.status: creating Makefile
```

**`checking ...` の羅列が環境調査**で、最後に **`creating Makefile`** と出ます。

実行前後でディレクトリを比べると、生成物がはっきり分かります。

```text
[ 実行前 ]                      [ 実行後 ]
Makefile.in                     Makefile        ← 生成された
configure                       Makefile.in
configure.ac                    config.log      ← 調査結果のログ
src                             config.status   ← 設定を再現するスクリプト
                                configure
                                configure.ac
                                src
```

`Makefile.in` のテンプレートが、実際の値に置き換わりました。

```bash
$ head -2 Makefile                          # 生成された Makefile の先頭を見る
```

```text
prefix = /usr/local
CC     = gcc
```

**`@prefix@` が `/usr/local` に、`@CC@` が `gcc` に置き換わっています。**

> **`config.log` は必ず残してください。**
> configure が途中で失敗したとき、原因はほぼここに書かれています。

### prefix でインストール先を決める

**`--prefix` はインストール先のルートを指定**します。

```bash
$ ./configure --help | grep -A2 -- "--prefix=PREFIX"   # 既定値を確認する
```

```text
  --prefix=PREFIX         install architecture-independent files in PREFIX
                          [/usr/local]
  --exec-prefix=EPREFIX   install architecture-dependent files in EPREFIX
```

**既定は `/usr/local`** です。角括弧の中が既定値を表します。

```bash
$ ./configure --prefix=/opt/hello           # インストール先を変えて実行する
$ head -1 Makefile                          # Makefile に反映されたか確認する
```

```text
prefix = /opt/hello
```

配置先は prefix の下に展開されます。

```text
   --prefix=/opt/myapp
        ↓
   /opt/myapp/bin       実行ファイル
   /opt/myapp/lib       ライブラリ
   /opt/myapp/share     データ・ドキュメント
   /opt/myapp/etc       設定ファイル
```

**`/usr/local` を避けて `/opt/アプリ名` にすると、アンインストールがディレクトリ削除だけで済みます。**
実務ではこちらを勧めます。

### よく使う configure オプション

| オプション | 意味 |
|:--|:--|
| `--prefix=PATH` | インストール先のルート（既定 `/usr/local`） |
| `--exec-prefix=PATH` | アーキテクチャ依存のファイルの置き場所 |
| `--bindir=PATH` | 実行ファイルの置き場所 |
| `--sysconfdir=PATH` | 設定ファイルの置き場所 |
| `--enable-機能` | 機能を有効にする |
| `--disable-機能` | 機能を無効にする |
| `--with-パッケージ` | 外部パッケージを使う |
| `--without-パッケージ` | 外部パッケージを使わない |
| `--help` | **使えるオプションの一覧**（ソフトごとに違う） |

**`./configure --help` はソフトウェアごとに内容が違います。** 必ず一度は読んでください。

## 手順3 make

**`make` は `Makefile` の記述に従って、ソースをコンパイルします。**

```bash
$ make                                      # Makefile に従ってビルドする
```

```text
gcc -o hello src/hello.c
```

```bash
$ ls -l hello                               # 作られたバイナリを確認する
```

```text
-rwxr-xr-x 1 root root 15960 Sep 23 15:20 hello
```

**引数なしの `make` は、Makefile の最初のターゲット**（慣例的に `all`）を実行します。

### 依存関係チェック

**`make` の本質は「必要なものだけ作り直す」ことです。**

```bash
$ make                                      # もう一度実行する
```

```text
make: Nothing to be done for 'all'.
```

**何もしません。** ソースよりバイナリが新しいので、作り直す必要がないと判断しています。

ソースのタイムスタンプを更新してから、もう一度。

```bash
$ touch src/hello.c                         # ソースを更新したことにする
$ make                                      # 再度ビルドする
```

```text
gcc -o hello src/hello.c
```

**今度はコンパイルが走りました。**

```text
   ターゲット（hello）のタイムスタンプ  <  依存（hello.c）のタイムスタンプ
        → 作り直す

   ターゲット（hello）のタイムスタンプ  >  依存（hello.c）のタイムスタンプ
        → 何もしない
```

**巨大なプロジェクトで1ファイルだけ直したとき、そのファイルだけ再コンパイルされる**のはこの仕組みです。

### 作り直す前に make clean

**ソースを修正して作り直すときは、`make clean` を先に実行します。**

```bash
$ make clean                                # 前回の生成物を削除する
$ ls hello                                  # バイナリが消えたことを確認する
```

```text
rm -f hello src/*.o
ls: cannot access 'hello': No such file or directory
```

**消えるのは `clean` ターゲットに書かれたものだけ**です。
`configure` が作った `Makefile` や `config.status` は残ります（それらを消すのは `make distclean`）。

**なぜ必要か**

```text
   make は「タイムスタンプ」でしか判断しない
        ↓
   ヘッダファイルの変更、configure のオプション変更など、
   タイムスタンプに現れない変更は検出されない
        ↓
   古い .o が残ったままリンクされ、修正が反映されないバイナリができる
```

**「直したはずなのに動作が変わらない」の典型的な原因**がこれです。
`configure` のオプションを変えたときは、`make clean`（場合によっては `make distclean`）を必ず挟んでください。

## 手順4 make install

**`make install` は、作ったバイナリを所定のディレクトリへ配置します。**

```bash
$ make install                              # ビルド成果物を配置する
```

```text
install -d /opt/hello/bin
install -m 0755 hello /opt/hello/bin/hello
```

```bash
$ find /opt/hello -type f                   # 配置されたか確認する
$ /opt/hello/bin/hello                      # 動くか確認する
```

```text
/opt/hello/bin/hello
hello, world
```

**`uninstall` ターゲットがあれば、消すのも一発**です。

```bash
$ make uninstall                            # インストール済みのファイルを削除する
```

```text
rm -f /opt/hello/bin/hello
```

### 権限が無いと失敗する

**インストール先への書き込み権限が無いと、ここで止まります。** 実測します。

一般ユーザ `tu` のホームでソースを展開し、`--prefix=/usr/local` のままビルドした状態で試します。

```bash
$ su tu -c 'cd ~/hello-1.0 && ./configure --prefix=/usr/local && make'   # 一般ユーザでビルドする
$ su tu -c 'cd ~/hello-1.0 && make install'                              # そのままインストールしてみる
```

```text
gcc -o hello src/hello.c
install -d /usr/local/bin
install -m 0755 hello /usr/local/bin/hello
install: cannot create regular file '/usr/local/bin/hello': Permission denied
make: *** [Makefile:11: install] Error 1
```

**`Permission denied` で失敗します。** 対処は2つ。

**対処1 … 権限を上げる**

```bash
$ su -                                      # root になる
$ make install                              # root で配置する
```

**対処2 … 書き込めるディレクトリに入れる**

```bash
$ su tu -c 'cd ~/hello-1.0 && make install prefix=$HOME/local'   # 自分のホーム配下に入れる
```

```text
install -d /home/tu/local/bin
install -m 0755 hello /home/tu/local/bin/hello
```

```bash
$ su tu -c 'ls -l $HOME/local/bin/hello'    # 配置されたか確認する
$ su tu -c '$HOME/local/bin/hello'          # 動くか確認する
```

```text
-rwxr-xr-x 1 tu tu 15960 Sep 23 15:20 /home/tu/local/bin/hello
hello, world
```

**成功しました。** 本来は `./configure --prefix=$HOME/local` からやり直すのが筋です。

> **注意 … 変数名は小文字の `prefix`** です。
> GNU の Makefile 規約が定めているのは `prefix` であって `PREFIX` ではありません。
> 大文字で渡しても無視されます。
>
> ```text
> $ su tu -c 'cd ~/hello-1.0 && make install PREFIX=$HOME/local'
> install -d /usr/local/bin
> install -m 0755 hello /usr/local/bin/hello
> install: cannot create regular file '/usr/local/bin/hello': Permission denied
> ```
>
> `PREFIX` を受け付けるのは、独自に書かれた一部の Makefile だけです。

```text
   root になれる          → su / sudo して make install
   root になれない        → ./configure --prefix=$HOME/local からやり直す
```

**ホーム配下に入れた場合は `PATH` の設定も必要**です。

```bash
$ echo 'export PATH=$HOME/local/bin:$PATH' >> ~/.bashrc   # PATH に追加する
```

### install コマンド

**`make install` の中で実際に配置を行っているのが `install` コマンド**です。

**`cp` との違いは、コピーとパーミッション設定を同時にできること**です。実測で比べます。

```bash
$ ls -l script.sh                           # 元ファイルのモードを見る
$ cp script.sh dest/by-cp.sh                # cp でコピーする
$ ls -l dest/by-cp.sh                       # モードを確認する
```

```text
-rw-r--r-- 1 root root 19 Sep 23 14:50 script.sh
-rw-r--r-- 1 root root 19 Sep 23 14:50 dest/by-cp.sh
```

**`cp` はモードをそのまま引き継ぎます。** 実行権を付けるには別途 `chmod` が要ります。

```bash
$ install -m 0755 script.sh dest/by-install.sh   # モードを指定してコピーする
$ ls -l dest/by-install.sh                       # モードを確認する
```

```text
-rwxr-xr-x 1 root root 19 Sep 23 14:50 dest/by-install.sh
```

**1コマンドで実行権が付いています。**

| オプション | 意味 |
|:--|:--|
| `-m モード` | パーミッションを指定する |
| `-o ユーザ` | 所有者を指定する |
| `-g グループ` | グループを指定する |
| `-d` | **ディレクトリを作る**（`mkdir -p` 相当） |
| `-s` | バイナリのシンボルを削除する（`strip`） |
| `-b` | 既存ファイルをバックアップしてから上書きする |

```bash
$ install -d dest/newdir                    # ディレクトリを作る
$ ls -ld dest/newdir                        # 作られたか確認する
```

```text
drwxr-xr-x 2 root root 4096 Sep 23 14:50 dest/newdir
```

```bash
$ install -m 0644 -o tu -g tu script.sh dest/owned.txt   # 所有者とモードを同時指定する
$ ls -l dest/owned.txt                                   # 結果を確認する
```

```text
-rw-r--r-- 1 tu tu 19 Sep 23 14:50 dest/owned.txt
```

**所有者・グループ・モードが一度に設定されました。**
Makefile の `install` ターゲットがこのコマンドを使うのは、この簡潔さのためです。

> **`--with access` のようなオプションは `install` にも `cp` にも存在しません。**
> ```text
> install: unrecognized option '--with'
> ```

## Makefile のターゲット

**慣例的に用意されるターゲット**です。名前は自由に付けられますが、この 6 つはほぼ共通です。

| ターゲット | 実行内容 |
|:--|:--|
| `all`（既定） | ビルドする |
| **`install`** | 成果物を所定のディレクトリへ配置し、パーミッションを設定する |
| **`uninstall`** | インストール済みのファイルを削除する |
| **`clean`** | ビルドで生成した中間ファイルと成果物を削除する |
| `distclean` | `clean` に加えて `configure` の生成物も削除する |
| `check` / `test` | テストを実行する |

```bash
$ make                                      # all（既定のターゲット）を実行する
$ make install                              # install ターゲットを実行する
$ make clean                                # clean ターゲットを実行する
$ make uninstall                            # uninstall ターゲットを実行する
```

**`uninstall` は用意されていないことも多い**ので、過信しないでください。
だから `--prefix=/opt/アプリ名` にしておくと安全、という話に戻ります。

## 順番を間違えるとどうなるか

| やったこと | 結果 |
|:--|:--|
| `configure` せずに `make` | `Makefile` が無いので実行できない |
| `make` せずに `make install` | 配置するバイナリが無い。多くの Makefile では `install: hello` と依存が書かれているため、**自動で `make` が走る** |
| `make clean` せずに作り直す | 古い中間ファイルが残り、**修正が反映されない** |
| `configure` のオプションを変えて `make clean` しない | 古い設定のオブジェクトが混ざる |

**この検証用 Makefile では `install: hello` と依存を書いてあるため、
`make install` だけでもビルドが走ります。**
ただしソフトウェアによっては依存が書かれておらず、その場合は本当に失敗します。
**素直に `./configure` → `make` → `make install` の順で実行してください。**

## 実務での注意

**1. ビルドに必要な開発パッケージを先に入れる**

```bash
$ dnf groupinstall "Development Tools"      # RHEL 系の開発ツール一式
$ apt install build-essential               # Debian 系の開発ツール一式
```

ヘッダが足りないと `configure` が失敗します。エラーは `config.log` を読んでください。

**2. 入れたものを記録する**

パッケージ管理の外に置くため、**何をどこに入れたか誰も分からなくなる**のが最大の問題です。

```text
  対策1  /opt/アプリ名-バージョン/ に入れて、シンボリックリンクで切り替える
  対策2  checkinstall や fpm でパッケージ化してから配る
  対策3  Dockerfile にビルド手順ごと書いて、イメージとして配る
```

**3. 脆弱性を自分で追う**

`yum update` の対象外になります。
**使っているソフトの announce メーリングリストか GitHub の Releases を購読**してください。

**4. 再現性を確保する**

```bash
$ ./configure --prefix=/opt/hello --enable-foo 2>&1 | tee configure.log   # 実行内容をログに残す
```

**実行したオプションをログに残す**だけで、次に同じものを作るときの事故が激減します。
`config.status` にも記録されているので、これも一緒に保管してください。
