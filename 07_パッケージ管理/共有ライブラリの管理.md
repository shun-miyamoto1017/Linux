## 共有ライブラリとは

**複数のプログラムが共通で使う処理を、1つのファイルにまとめたもの**です。
Linux では拡張子 **`.so`**（Shared Object）。Windows の DLL にあたります。

```text
   [ 静的リンク ]                    [ 動的リンク（共有ライブラリ） ]

   program1 ┌──────────┐             program1 ─┐
            │ライブラリ │                       │
            └──────────┘                       ├─▶ libfoo.so  ← 1つを共有
   program2 ┌──────────┐             program2 ─┘
            │ライブラリ │
            └──────────┘             （実行時に読み込まれる）
   （コピーが実行ファイルに埋まる）
```

**利点**

```text
   ✓ ディスクとメモリを節約できる（1つを全員で使う）
   ✓ ライブラリだけ更新すれば全プログラムに反映される
        → 脆弱性対応が楽。glibc の修正が全部のプログラムに効く
```

**欠点**

```text
   ✗ 実行時にライブラリが見つからないと起動しない
   ✗ バージョンの食い違いで壊れることがある（依存地獄）
```

---

## 静的リンクとの違い

| | 静的リンク | 動的リンク（共有ライブラリ） |
|:--|:--|:--|
| ライブラリの位置 | **実行ファイルの中** | 外部の `.so` ファイル |
| 実行ファイルのサイズ | 大きい | 小さい |
| 実行時の依存 | **無い** | **ある**（`.so` が必要） |
| ライブラリの更新 | **再ビルドが必要** | `.so` を入れ替えるだけ |
| メモリ使用量 | プロセスごとにコピー | 共有される |
| 使いどころ | レスキュー用バイナリ、Go のバイナリ | **通常はこちら** |

**レスキューモードで使うコマンドが静的リンクなのは、`/usr` がマウントできない状態でも動く必要があるから**です。

## ファイル名の三つの呼び名

**1つの共有ライブラリに、3つの名前が付きます。** ここが最初の関門です。

```bash
$ ls -l                                     # 作成したライブラリのファイル一覧を見る
```

```text
lrwxrwxrwx 1 root root    13 Sep 23 14:50 libgreet.so -> libgreet.so.1
lrwxrwxrwx 1 root root    15 Sep 23 14:50 libgreet.so.1 -> libgreet.so.1.0
-rwxr-xr-x 1 root root 15552 Sep 23 14:50 libgreet.so.1.0
```

| 名前 | 呼び名 | 誰が使うか |
|:--|:--|:--|
| `libgreet.so` | **linker name**（リンカ名） | **ビルド時**。`gcc -lgreet` が探す |
| `libgreet.so.1` | **soname** | **実行時**。動的リンカが探す |
| `libgreet.so.1.0` | **real name**（実体） | 本体のファイル |

```text
   libgreet.so     ──▶ libgreet.so.1 ──▶ libgreet.so.1.0
   （シンボリックリンク）（シンボリックリンク）（実体）
        ↑                    ↑
   ビルド時に使う        実行時に使う
```

**バージョン番号の意味**

```text
   libgreet.so.1.0
             │ └─ マイナー … 互換性がある変更
             └─── メジャー … 互換性が壊れる変更（soname が変わる）
```

**soname にメジャー番号だけが入る**のがポイントです。
マイナー更新なら実体を差し替えるだけで済み、メジャーが上がると別のライブラリとして共存できます。

## ldd で依存を調べる

**`ldd` は、実行ファイルが必要とする共有ライブラリを一覧**します。

```bash
$ ldd ./app                                 # 依存する共有ライブラリを調べる
```

```text
	linux-vdso.so.1 (0x00007f892a7b5000)
	libgreet.so.1 => not found
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f892a400000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f892a7b7000)
```

**読み方**

| 行 | 意味 |
|:--|:--|
| `libc.so.6 => /lib/.../libc.so.6` | **見つかっている**。右側が実際のパス |
| `libgreet.so.1 => not found` | **見つかっていない**。これが原因 |
| `linux-vdso.so.1` | カーネルが提供する仮想的なライブラリ。ファイルとして存在しない |
| `/lib64/ld-linux-x86-64.so.2` | **動的リンカ本体**。ライブラリを探して結び付ける役 |

**`not found` が1つでもあれば、そのプログラムは起動しません。**

> **`ldd` の注意** … `ldd` は内部でプログラムを実行する実装があるため、
> **信頼できないバイナリに `ldd` を使ってはいけません。**
> 代わりに `objdump -p ファイル | grep NEEDED` を使います。

## 見つからないときに何が起きるか

実際に実行してみます。

```bash
$ ./app                                     # 実行してみる
$ echo "exit=$?"                            # 終了ステータスを確認する
```

```text
./app: error while loading shared libraries: libgreet.so.1: cannot open shared object file: No such file or directory
exit=127
```

**`error while loading shared libraries`** — このメッセージを見たら共有ライブラリの問題です。
終了ステータスは **127**。

```text
   error while loading shared libraries: ★★★.so.N: cannot open shared object file
                                          ↑
                             この名前を探せばよい
```

## 解決方法1 LD_LIBRARY_PATH

**環境変数 `LD_LIBRARY_PATH` に、ライブラリのあるディレクトリを追加**します。

```bash
$ LD_LIBRARY_PATH=/tmp/w20/liblab ldd ./app   # パスを指定して依存を再確認する
```

```text
	libgreet.so.1 => /tmp/w20/liblab/libgreet.so.1 (0x00007f9bd76f0000)
```

**`not found` が解消しました。** 実行もできます。

```bash
$ LD_LIBRARY_PATH=/tmp/w20/liblab ./app     # パスを指定して実行する
```

```text
greetings from libgreet
```

**恒久的に設定する場合**は、既存の値を残して追記します。

```bash
$ export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/opt/myapp/lib   # 既存の値に追加する
$ echo $LD_LIBRARY_PATH                                     # 設定を確認する
```

**`$LD_LIBRARY_PATH:` を先頭に付けるのを忘れないでください。**
忘れると既存の設定を消してしまいます。

| 長所 | 短所 |
|:--|:--|
| **root 権限が要らない** | **プロセスごとの設定**。他のユーザ・他のセッションには効かない |
| すぐ試せる | cron や systemd から起動すると効かない |
| 一時的な検証に向く | セキュリティ上の問題がある（後述） |

**systemd のサービスで使う場合**は Unit ファイルに書きます。

```text
[Service]
Environment=LD_LIBRARY_PATH=/opt/myapp/lib
```

## 解決方法2 ldconfig に登録する

**システム全体に効かせるなら、`/etc/ld.so.conf.d/` に登録して `ldconfig` を実行**します。

`/etc/ld.so.conf` の中身を見ると、実体は include だけです。

```bash
$ cat /etc/ld.so.conf                       # 設定ファイルの中身を見る
```

```text
include /etc/ld.so.conf.d/*.conf
```

**`/etc/ld.so.conf.d/` に `.conf` を置く**のが現在の作法です。

```bash
$ echo "/tmp/w20/liblab" > /etc/ld.so.conf.d/greet.conf   # 検索パスを追加する
$ ldconfig                                                # キャッシュを再構築する
$ ldconfig -p | grep libgreet                             # 登録されたか確認する
```

```text
	libgreet.so.1 (libc6,x86-64) => /tmp/w20/liblab/libgreet.so.1
	libgreet.so (libc6,x86-64) => /tmp/w20/liblab/libgreet.so
```

```bash
$ ldd ./app | grep libgreet                 # 依存が解決されたか確認する
$ ./app                                     # 実行してみる
```

```text
	libgreet.so.1 => /tmp/w20/liblab/libgreet.so.1 (0x00007f4284633000)
greetings from libgreet
```

**環境変数なしで動くようになりました。**

設定を外すと、また見つからなくなります。

```bash
$ rm -f /etc/ld.so.conf.d/greet.conf        # 設定を削除する
$ ldconfig                                  # キャッシュを再構築する
$ ldd ./app | grep libgreet                 # 依存を再確認する
```

```text
	libgreet.so.1 => not found
```

**`ldconfig` の役割**

```text
   /etc/ld.so.conf.d/*.conf  に書かれたディレクトリを走査
        ↓
   soname とファイルの対応表を作る
        ↓
   /etc/ld.so.cache に保存する  ← 動的リンカはこれを読むので起動が速い
```

| オプション | 意味 |
|:--|:--|
| `ldconfig` | キャッシュを再構築する |
| `ldconfig -p` | **現在のキャッシュの内容を表示する** |
| `ldconfig -v` | 処理内容を表示しながら再構築する |
| `ldconfig -n DIR` | キャッシュを更新せず、指定ディレクトリのリンクだけ作る |

**ライブラリを置いたら `ldconfig` を忘れない。** これが鉄則です。
`.so.1` のシンボリックリンクも `ldconfig` が自動で作ってくれます。

## 二つの方法の使い分け

| | `LD_LIBRARY_PATH` | `/etc/ld.so.conf.d/` + `ldconfig` |
|:--|:--|:--|
| 効く範囲 | **そのプロセスとその子だけ** | **システム全体** |
| 必要な権限 | 一般ユーザ | **root** |
| 永続性 | セッション限り（`.bashrc` に書けば継続） | 永続 |
| 速度 | 毎回ディレクトリを走査する | **キャッシュを引くので速い** |
| 向いている場面 | **一時的な検証**、権限の無い環境 | **本番の恒久設定** |

```text
   検証で「パスを通せば動くか」を確かめる      → LD_LIBRARY_PATH
   動いたので恒久設定にする                    → /etc/ld.so.conf.d/ + ldconfig
```

**`LD_LIBRARY_PATH` を本番の恒久設定にしてはいけない理由**

```text
   ✗ setuid されたプログラムでは（安全のため）無視される
   ✗ 書き込み可能なディレクトリを混ぜると、偽ライブラリを読ませる攻撃が成立する
   ✗ cron / systemd から起動したときに効かず、「手で動かすと動く」という混乱を生む
```

## 探索の順序

動的リンカが `.so` を探す順番です。

```text
   ① 実行ファイルに埋め込まれた DT_RPATH   （DT_RUNPATH が無い場合のみ）
   ② 環境変数 LD_LIBRARY_PATH
   ③ 実行ファイルに埋め込まれた DT_RUNPATH
   ④ /etc/ld.so.cache                      （ldconfig が作ったキャッシュ）
   ⑤ 既定のディレクトリ                    （下表のとおりディストリで異なる）
```

**⑤ の既定ディレクトリはディストリによって違います。**

| 系統 | 既定で探すディレクトリ |
|:--|:--|
| RHEL 系（非 multiarch） | `/lib64`, `/usr/lib64`, `/lib`, `/usr/lib` |
| **Debian / Ubuntu（multiarch）** | `/lib/x86_64-linux-gnu`, `/usr/lib/x86_64-linux-gnu`, `/lib`, `/usr/lib` |

Ubuntu 24.04 で実測すると、`ldconfig` を通さずにライブラリを置いた場合の結果はこうなりました。

| 置いた場所 | 結果 |
|:--|:--|
| `/usr/lib` | 見つかる |
| `/usr/lib/x86_64-linux-gnu` | 見つかる |
| `/lib64` | **見つからない**（`error while loading shared libraries`） |

**`/lib64` は Debian 系では検索対象ではありません。**
RHEL 系の資料をそのまま Ubuntu に持ち込むと、ここで詰まります。

**`LD_LIBRARY_PATH` がキャッシュより先に見られる**ため、一時的な上書きに使えます。
逆に言えば、**意図しない値が入っていると正規のライブラリより優先されます。**

```bash
$ echo $LD_LIBRARY_PATH                     # 変な値が入っていないか確認する
```

「なぜか古いバージョンのライブラリが読まれる」ときは、まずここを疑ってください。

## 実務での切り分け手順

```text
  1. エラーメッセージからライブラリ名を特定する
        error while loading shared libraries: libfoo.so.5

  2. ldd で「not found」を確認する
        $ ldd /opt/myapp/bin/myapp | grep 'not found'

  3. そのファイルがシステム上にあるか探す
        $ find / -name 'libfoo.so*' 2>/dev/null
        $ ldconfig -p | grep libfoo

  4. あった → パスを通す
        一時的に  : LD_LIBRARY_PATH=... で動作確認
        恒久的に  : /etc/ld.so.conf.d/ に追加して ldconfig

  5. 無かった → 提供元のパッケージを入れる
        $ dnf provides '*/libfoo.so.5'
        $ apt-file search libfoo.so.5
```

**よくある原因**

| 症状 | 原因 |
|:--|:--|
| ソースから入れた直後に動かない | `ldconfig` を実行していない |
| 手で動かすと動くが、cron だと動かない | `LD_LIBRARY_PATH` に依存している |
| コンテナの中だけ動かない | ビルド環境にあったライブラリを実行イメージに入れていない |
| バージョンが違うと言われる | soname のメジャー番号が食い違っている（再ビルドが必要） |

**`Makefile` や `configure` を書き換えても解決しません。**
これはビルドの問題ではなく、**実行時にライブラリを探す仕組みの問題**だからです。
