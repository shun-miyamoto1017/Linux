## バックアップで決めることは3つ

バックアップ設計は、結局この3つを決める作業です。

```text
  ① 何を取るか        … 対象（ファイル / ファイルシステム / ディスク全体）
  ② どう取るか        … 方式（フル / 差分 / 増分）と道具（tar / rsync / dump / dd）
  ③ どこに置くか      … メディアと保管場所（同一拠点 / 別拠点）
```

この3つが決まると、自動的に**2つの指標**が決まります。

| 指標 | 意味 | 決めているもの |
|:--|:--|:--|
| **RPO**（目標復旧時点） | 最大でどこまでのデータを失ってよいか | バックアップの**間隔** |
| **RTO**（目標復旧時間） | 何時間以内に復旧させるか | バックアップの**方式**と保管場所 |

**毎日1回フルを取るなら RPO は 24 時間**、つまり「最悪1日分の更新は失う」という設計です。
ここを握らずにコマンドの話から入ると、設計として成立しません。

## フルと差分と増分

### フルバックアップ

**対象データを丸ごと全部コピーする方式**です。

```text
  月  フル ████████████████  （全データ）
  火  フル ████████████████
  水  フル ████████████████
```

| | |
|:--|:--|
| **取得時間** | 長い |
| **必要な容量** | 大きい（毎回フルサイズ） |
| **復元に必要なもの** | **フル1つだけ** |
| **復元の速さ** | 最速 |

毎日フルを取れるならそれが一番安全です。
**取得時間と容量が許さないから、差分と増分という工夫が出てくる**、という順序で理解してください。

### 差分バックアップ

**直近のフルバックアップ以降に変更されたものだけ**をコピーします。
基準は常に**フル**なので、日が経つほど差分は太っていきます。

```text
  月  フル ████████████████
  火  差分 ██                （月のフル以降の変更）
  水  差分 ████              （月のフル以降の変更 … 火の分も含む）
  木  差分 ██████            （月のフル以降の変更 … 火水の分も含む）
```

### 増分バックアップ

**直近のバックアップ（フルでも増分でもよい）以降に変更されたものだけ**をコピーします。
基準が毎回ずれていくので、1回あたりは常に小さいままです。

```text
  月  フル ████████████████
  火  増分 ██                （月のフル以降）
  水  増分 ██                （火の増分以降）
  木  増分 ██                （水の増分以降）
```

### 三方式の比較

| | フル | 差分 | 増分 |
|:--|:--|:--|:--|
| 基準にするもの | なし（全部） | **直近のフル** | **直近のフルまたは増分** |
| 1回の取得時間 | 長い | 中（日が経つと伸びる） | **短い** |
| 1回の容量 | 大きい | 中（日が経つと増える） | **小さい** |
| 復元に必要な数 | **1つ** | **2つ**（フル＋最新の差分） | フル＋**その後の全増分** |
| 復元の速さ | 速い | 中 | **遅い** |
| 1つ壊れたときの影響 | その世代だけ | その世代だけ | **以降の鎖が全部切れる** |

**覚え方**

```text
  差分（differential）… 「フルとの差」   → 基準が固定 → 太る  → 復元は2つ
  増分（incremental） … 「前回からの増え分」→ 基準が移動 → 細い → 復元は全部
```

### 復元に必要なものが決定的に違う

ここが試験でも実務でも最重要です。**木曜に壊れた場合**を比べます。

```text
  差分運用:  [月フル] + [水差分]              → 2つあれば戻る
                       ↑ 最新の差分だけでよい（火の差分は不要）

  増分運用:  [月フル] + [火増分] + [水増分]   → 全部そろわないと戻らない
                       ↑ 1つでも欠けるとそこから先が復元できない
```

増分は**取得が軽いかわりに、復元が重く、欠損に弱い**。
差分は**取得がだんだん重くなるかわりに、復元が軽い**。
どちらを選ぶかは「夜間バッチの時間枠」と「許される復旧時間」で決まります。

> **どの方式でも、最初に一度はフルバックアップが必要です。**
> 差分も増分も「基準になるフル」がなければ成立しません。

## dump のレベルで増分を実測する

ext 系ファイルシステム用の `dump` は、**レベル 0〜9** という数字で増分の基準を表します。

```text
  レベル0        … フルバックアップ
  レベル1以上    … 「自分より小さいレベルの最新のバックアップ」以降の変更分
```

以下は 32MiB のループバック ext4 を作って実際に叩いた結果です。

### レベル0でフルを取る

```bash
$ dd if=/dev/zero of=fs.img bs=1M count=32 status=none   # 検証用のイメージを作る
$ mkfs.ext4 -q -F fs.img                                 # ext4 を作る
$ mkdir m && mount -o loop fs.img m                      # マウントする
$ echo "old-1" > m/a.txt                                 # ファイルを置く
$ mkdir m/sub && echo "old-2" > m/sub/b.txt              # サブディレクトリにも置く
$ sleep 1                                                # ファイル作成とレベル0が同じ秒にならないよう1秒空ける
$ dump -0uf full.dump /tmp/w20/dumplab/m                 # レベル0（フル）で取得する
```

```text
  DUMP: Date of this level 0 dump: Wed Sep 23 14:57:39 2026
  DUMP: Volume 1 30 blocks (0.03MB)
  DUMP: DUMP IS DONE
```

`restore -t` で中身を確認します。

```bash
$ restore -tf full.dump                     # アーカイブの中身を一覧する
```

```text
Dump   date: Wed Sep 23 14:57:39 2026
Dumped from: the epoch
Level 0 dump of /tmp/w20/dumplab/m on vm:/dev/loop0
Label: none
         2	.
        11	./lost+found
        12	./a.txt
        13	./sub
        14	./sub/b.txt
```

**`Dumped from: the epoch`** が「基準なし = フルバックアップ」を表しています。

### レベル1で増分を取る

ファイルを1つ足してから、レベル1で取ります。

```bash
$ echo "new" > m/c.txt                      # 新しいファイルを1つ追加する
$ dump -1uf inc1.dump /tmp/w20/dumplab/m    # レベル1（増分）で取得する
$ restore -tf inc1.dump                     # 増分の中身を一覧する
```

```text
Dump   date: Wed Sep 23 14:57:42 2026
Dumped from: Wed Sep 23 14:57:39 2026
Level 1 dump of /tmp/w20/dumplab/m on vm:/dev/loop0
Label: none
         2	.
        15	./c.txt
```

**`./c.txt` しか入っていません。** `Dumped from:` にレベル0を取った時刻が入り、
そこからの変更分だけが選ばれたことがそのまま読み取れます。

> **注意** … `dump` の変更判定は **ctime を秒単位**で比べます。
> ファイルを作った秒とレベル0を取った秒が同じだと、そのファイルが次のレベル1にも入ってしまいます（実測）。
> 上のレベル0の手前で `sleep 1` を挟んでいるのはこのためです。

サイズも違います。

```bash
$ ls -l full.dump inc1.dump                 # フルと増分のサイズを比べる
```

```text
-rw-r--r-- 1 root root 30720 Sep 23 14:57 full.dump
-rw-r--r-- 1 root root 20480 Sep 23 14:57 inc1.dump
```

### restore で戻す

**フル → 増分の順**に `restore -r` を重ねます。順番を逆にしてはいけません。

```bash
$ restore -rf ../full.dump                  # まずフルを展開する
$ find . -type f | sort                     # 中身を確認する
```

```text
./a.txt
./restoresymtable
./sub/b.txt
```

```bash
$ restore -rf ../inc1.dump                  # つづけて増分を重ねる
$ find . -type f | sort                     # c.txt が増えているか確認する
```

```text
./a.txt
./c.txt
./restoresymtable
./sub/b.txt
```

`restoresymtable` は `restore -r` が次の増分を重ねるために作る作業ファイルです。
**全部重ね終わったら削除して構いません。**

### dumpdates はどこにあるか

**`-u` は「取得した日時を dumpdates ファイルに記録する」オプション**です。
レベル1が「レベル0以降」を正しく拾えたのは、このファイルを読んで基準時刻を決めているからです。

**ファイルの場所はディストリによって違います。**

| 系統 | 既定のパス |
|:--|:--|
| **Debian / Ubuntu** | **`/var/lib/dumpdates`** |
| RHEL 系 / BSD | `/etc/dumpdates` |

Ubuntu 24.04 で実測した中身です。

```bash
$ cat /var/lib/dumpdates                    # 記録された内容を確認する
```

```text
/tmp/w20/dumplab/m 0 Wed Sep 23 14:57:39 2026 +0000
/tmp/w20/dumplab/m 1 Wed Sep 23 14:57:42 2026 +0000
```

**「対象 / レベル / 日時」の3項目**が1行ずつ記録されています。
レベル1の `Dumped from:` に出ていた時刻は、この1行目そのものです。

`dump -W` でも同じ情報を読めます。

```bash
$ dump -W                                   # 最後に取得したレベルと日時を一覧する
```

```text
Last dump(s) done (Dump '>' file systems):
  /dev/vda	(     /) Last dump: never
  /dev/vdc	(/opt/claude-code) Last dump: never
  /dev/loop0	(/tmp/w20/dumplab/m) Last dump: Level 1, Date Wed Sep 23 14:57:42 2026
```

**マウント中の対象は「デバイス名（マウントポイント）」の形で出ます。**
`Last dump: never` は一度も取っていないという意味です。

**このファイルが更新されないと、翌日のレベル1が「いつ以降なのか」を見失います。**
`-u` を付け忘れると記録されないので、定期ジョブでは必ず付けてください。

> `-A ファイル` で記録先を明示することもできます。
> 複数のバックアップ系統を同じホストで回す場合は、こちらで分けると安全です。

## 何をどの道具で取るか

**バックアップの単位によって、使う道具が変わります。**

| 取りたい単位 | 道具 | 特徴 |
|:--|:--|:--|
| ファイル・ディレクトリ | `tar` / `cpio` / `zip` | 一番手軽。アーカイブ1本にまとまる |
| ファイル・ディレクトリ（同期） | `rsync` | 差分だけ転送。ネットワーク越しが得意 |
| ファイルシステム単位 | `dump` / `restore`（ext系）<br>`xfsdump` / `xfsrestore`（XFS） | **レベルによる増分**が使える |
| デバイス・ディスク全体 | `dd` | ブロック単位。MBR やパーティションごと取れる |
| 複数ホストをまとめて | Amanda / Bacula / Bareos / BackupPC | スケジュール・カタログ・世代管理つき |

```text
  ファイル1本を戻したい          → tar / rsync
  ファイルシステムごと戻したい   → dump / xfsdump
  起動しないサーバを丸ごと戻したい → dd（またはイメージバックアップ製品）
```

> `dd` の詳細は [ddコマンド](../06_ストレージとファイルシステム/ddコマンド.md)、
> `tar` の詳細は [圧縮とアーカイブ](../01_シェルとコマンドライン/圧縮とアーカイブ.md) を参照してください。

## バックアップしなくてよい場所

**「中身が実体ではない場所」は取っても意味がありません。**

| 場所 | 取らなくてよい理由 |
|:--|:--|
| `/proc` | カーネルが動的に見せている**擬似ファイルシステム**。ディスク上に実体がない |
| `/sys` | 同じく擬似ファイルシステム。デバイス情報を見せているだけ |
| `/dev` | デバイスファイル。`udev` が起動時に作り直す |
| `/run` `/tmp` | 再起動で消える一時領域 |
| **スワップ領域** | 物理メモリから追い出された一時データ。復元しても無意味 |
| `/proc/kcore` など | 物理メモリを見せる巨大な見かけ上のファイル。取ろうとすると事故になる |

逆に、**必ず取るべき**なのはこのあたりです。

```text
  /etc     … 設定のすべて。ここがないと同じサーバを作り直せない
  /home    … ユーザデータ
  /var     … ログ、メール、DB のデータ、Web コンテンツ
  /usr/local … 自前でビルドして入れたもの
  /root    … 忘れがち。root の作業スクリプトが埋まっている
```

## 保管場所 オンサイトとオフサイト

| 用語 | 意味 | 強いところ / 弱いところ |
|:--|:--|:--|
| **オンサイト** | バックアップ元と**同じ拠点**に保管する | 復旧が速い / **拠点ごと被災すると同時に失う** |
| **オフサイト** | **別の拠点**に保管する | 災害に強い / 取りに行く手間と時間がかかる |

```text
   同じ建物のラックに置いたテープ
        ↓  火災・水害・地震
   本番もバックアップも同時に消える  ← オンサイトだけの構成の弱点
```

**実務では両方持つのが定石**です。

```text
  日次の増分   → オンサイト（速く戻せる）
  週次のフル   → オフサイト（拠点ごと失っても戻せる）
```

> クラウドでは「別リージョンへのコピー」がオフサイトにあたります。
> S3 のクロスリージョンレプリケーション、AWS Backup のリージョン間コピー、
> Azure の GRS ストレージなどは、すべてこの発想の実装です。

## ネットワーク越しの置き場所 NASとSAN

| | NAS | SAN |
|:--|:--|:--|
| 正式名 | Network Attached Storage | Storage Area Network |
| 見え方 | **ファイル共有**として見える | **ブロックデバイス**として見える |
| プロトコル | NFS / SMB(CIFS) | FibreChannel / iSCSI |
| 使う側の操作 | マウントしてファイルを置く | パーティションを切って `mkfs` する |
| 速度 | ネットワーク共有相応 | **専用ネットワークで高速** |
| 費用 | 安い | 高い（FC なら専用 HBA とスイッチが要る） |

```text
  NAS … 「共有フォルダが増えた」感覚      → /backup を NFS マウントして tar を置く
  SAN … 「ディスクが1本増えた」感覚       → /dev/sdc として見えるので fdisk できる
```

**iSCSI は TCP/IP の上でブロックアクセスを行う**ため、既存の LAN をそのまま使えます。
FibreChannel より安く SAN を組めるのが利点です。

> iSCSI の実際の設定は [iSCSIの設定と管理](../06_ストレージとファイルシステム/iSCSIの設定と管理.md) を参照してください。

## 現実的な運用計画の立て方

大容量のファイルサーバを想定した、よくある組み方です。

```text
  月曜 02:00   フルバックアップ   → 取得に4時間 → 別拠点へ搬送（オフサイト）
  火〜日 02:00 増分バックアップ   → 取得に15分 → 同一拠点に保管（オンサイト）
  保持世代     フル4世代（約1か月）／増分は次のフルまで
```

**この設計が答えているもの**

| 問い | 答え |
|:--|:--|
| RPO は | 24時間（夜間1回のため） |
| RTO は | フル1本＋増分最大6本のリストア時間 |
| 拠点被災に耐えるか | 耐える（フルがオフサイト） |
| 夜間バッチ枠に収まるか | 収まる（平日は15分） |

**やってはいけない設計**

```text
  ✗ フルを月1回だけにする
       → 月末に壊れると、直前1か月分の増分を全部重ねる羽目になる
       → 増分が1本でも壊れていたらそこで終わり

  ✗ バックアップを取るだけでリストア訓練をしない
       → 「取れているつもり」が一番多い事故
       → 四半期に1度は実際に戻して、手順書どおりに動くか確かめる
```

**最後にもうひとつ。**
バックアップは「取れていること」ではなく「**戻せること**」が目的です。
`restore -t` や `tar tf` で中身を一覧する確認を、取得ジョブの最後に必ず入れてください。
