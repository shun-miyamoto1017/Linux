## 2つの方式

**ファームウェア**は、電源を入れた直後に動く、**マザーボードに組み込まれたプログラム**です。
古くからの **BIOS** と、現在主流の **UEFI** の 2 方式があります。

| | **BIOS**（レガシー） | **UEFI**（現在の主流） |
|:--|:--|:--|
| **正式名称** | Basic Input/Output System | Unified Extensible Firmware Interface |
| **ブートローダをどこから読むか** | **MBR**（ディスクの先頭セクタ） | **ESP**（EFI システムパーティション）の中の**ファイル** |
| **対応するパーティション形式** | 主に **MBR** | 主に **GPT** |
| **扱えるディスクの大きさ** | **2TB まで**（MBR の制限） | **2TB 超も扱える** |
| **パーティションの数** | 基本パーティション**4 つまで** | **128 個まで**（GPT の既定） |
| **セキュアブート** | 無い | **ある** |
| **画面** | テキスト | グラフィカルなことが多い |

```text
 ■ BIOS ブート
    ディスクの先頭 512 バイト（MBR）を読む
        └─ そこにブートローダの先頭部分が書いてある

 ■ UEFI ブート
    ESP（FAT でフォーマットされた小さなパーティション）を読む
        └─ /EFI/<配布元>/grubx64.efi のような「ファイル」を実行する
```

**今どちらで動いているか調べる**

```bash
$ ls /sys/firmware/efi                               # このディレクトリがあれば UEFI で起動している
$ [ -d /sys/firmware/efi ] && echo UEFI || echo BIOS  # 判定を1行で書く
$ sudo efibootmgr -v                                 # UEFI の起動エントリを一覧する（UEFI環境のみ）
```

**補足**

- `[ -d パス ]` … そのパスがディレクトリなら成立する条件式。`&&` は成立したとき、`||` は成立しなかったときに実行します
- **`/sys/firmware/efi` の有無で判定する**のが定番です。UEFI で起動したときだけ、カーネルがこのディレクトリを作ります

## ESPはUEFIが最初に読む領域

**ESP**（EFI System Partition ／ EFI システムパーティション）は、
**UEFI 環境で、電源投入後の起動シーケンスにおいて最初にアクセスされる領域**です。

> **BIOS における MBR にあたるもの**が、UEFI では ESP です。
> ただし MBR が「ディスクの先頭 512 バイト」という**場所**なのに対し、
> **ESP は独立した 1 つのパーティション**で、**中にファイルが置かれます。**

```text
   ■ BIOS               ■ UEFI
   ディスクの先頭        ESP（独立したパーティション）
   ┌──────────┐         ┌────────────────────────────┐
   │ MBR 512B │         │ /EFI/centos/grubx64.efi     │
   └──────────┘         │ /EFI/centos/grub.cfg        │
     ↑                  │ /EFI/BOOT/BOOTX64.EFI       │
   バイト列を読む         └────────────────────────────┘
                           ↑ ファイルとして読む
```

**ESP の決まりごと**

| 項目 | 内容 |
|:--|:--|
| **フォーマット** | **FAT16 または FAT32**。**それ以外は使えない**（ext4 も xfs も NTFS も不可） |
| **Linux でのマウント先** | **`/boot/efi`** |
| **中に置くもの** | **拡張子 `.efi` のファイル**（ブートローダに相当するプログラム）と、その設定 |
| **パーティション形式との関係** | **GPT の一部**として作られることが多い（ESP は GPT そのものではない） |

**なぜ FAT なのか**

**ファームウェアが読めるファイルシステムが FAT だから**です。
UEFI は OS より前に動くので、**OS のドライバに頼らず自力で読める、単純な形式**である必要があります。

> **ESP に置かれる `.efi` ファイルそのもの**（`bootx64.efi` / `grubx64.efi` / `shim.efi` / `systemd-boot`）と、
> **セキュアブートの仕組み**は [その他のブートローダ](./その他のブートローダ.md) にまとめています。

**例文**

```bash
$ ls /sys/firmware/efi >/dev/null 2>&1 && echo UEFI || echo BIOS   # UEFI かどうかを判定する
UEFI
$ mount | grep efi                                   # ESP がどこにマウントされているか見る
/dev/sda1 on /boot/efi type vfat (rw,relatime,…)     # vfat = FAT。/boot/efi にマウントされている
$ ls /boot/efi/EFI/                                  # ディストリごとのディレクトリを見る
BOOT  centos
$ ls /boot/efi/EFI/centos/                           # 実際の .efi ファイルを見る
grub.cfg  grubx64.efi  shimx64.efi
$ sudo parted /dev/sda print | head -8               # ESP のフラグを確認する
Number  Start   End     Size    File system  Name  Flags
 1      1049kB  630MB   629MB   fat32              boot, esp
```

**取り違えやすい用語**

| 用語 | 何か | 混同しやすい相手 |
|:--|:--|:--|
| **ESP** | **UEFI で最初にアクセスされる領域**（パーティション） | MBR（**こちらは BIOS 側**） |
| **FAT32 / FAT16** | **ESP に使えるファイルシステムの種類** | **領域の名前ではない。** ESP の中身の形式 |
| **GPT** | **パーティションテーブルの規格** | **ESP はこの中に作られる一区画**。GPT そのものではない |
| **MBR** | **BIOS で最初にアクセスされる領域**（ディスク先頭 512 バイト） | ESP（**こちらは UEFI 側**） |

**補足**

- **`vfat` と表示されるのが FAT** です。`mount` の出力で `type vfat` を確認できます
- **ESP を間違ってフォーマットすると起動しなくなります。** `/boot/efi` は普段触らない場所だと覚えておいてください
- **UEFI は BIOS に比べて、起動が速く、2TiB を超えるディスクからも起動できます。** 2TB の上限は BIOS 側（MBR 形式）の制約です

## UEFIシェル

**UEFI には、ファームウェア自身が持つ「シェル環境」があります。**これを **UEFI シェル** と呼びます。

> **シェル** … コマンドを打って操作する環境のことです。Linux の `bash` と同じ位置づけですが、
> **UEFI シェルは OS の外側、ファームウェアの上で動きます。**

**いちばん大事な点は、「OS を起動しなくても使える」ことです。**

| できること | 具体例 |
|:--|:--|
| **OS を起動せずにハードウェア周りの設定を行う** | ブート順序の変更、機器の状態確認 |
| **デバイスドライバを読み込んで使う** | UEFI 用のドライバを追加して、機器を認識させる |
| **TCP/IP スタックを利用する** | **ネットワーク越しにファイルを取りに行く**、疎通確認をする |
| ファイルを操作する | ESP の中のファイルを一覧・コピー・削除する |
| EFI アプリケーションを実行する | `.efi` ファイルを直接起動する |

```text
  ■ UEFI シェルの位置づけ

     電源ON
       │
       ▼
   ┌──────────────────────────────────────┐
   │ UEFI ファームウェア                    │
   │   ├─ UEFI シェル  ← OS なしでここまで来られる │
   │   └─ ブートマネージャ                   │
   └──────────────────────────────────────┘
       │  ブートローダ（grubx64.efi）を起動
       ▼
     OS（Linux）
```

## UEFI まわりの用語を取り違えない

**名前が似ているものが多く、「どこで動くのか」で区別します。**

| 名前 | 何か | **どこで動くか** |
|:--|:--|:--|
| **UEFI シェル** | **ファームウェアが持つシェル環境** | **OS の外**（OS を起動せずに使える） |
| **`efibootmgr`** | **UEFI のブートエントリを操作する Linux のコマンド** | **OS 上**（Linux が起動している必要がある） |
| **`efivar` / `efivarfs`** | UEFI の変数を読み書きするしくみ | **OS 上** |
| **ESP**（EFI システムパーティション） | ブートローダのファイルを置く FAT のパーティション | （場所であって、プログラムではない） |

> **「OS を起動せずに」と書かれていたら UEFI シェル、「Linux 上から」なら `efibootmgr`** と覚えると取り違えません。

**例文（OS 上から UEFI の起動エントリを扱う）**

```bash
$ sudo efibootmgr -v                                 # 登録されている起動エントリを詳しく一覧する
BootCurrent: 0001
BootOrder: 0001,0002
Boot0001* debian  HD(1,GPT,…)/File(\EFI\debian\shimx64.efi)
Boot0002* UEFI: Built-in EFI Shell                   # UEFI シェルもエントリとして並ぶ

$ sudo efibootmgr -o 0002,0001                       # 起動順序を変える（先頭が最優先）
$ sudo efibootmgr -b 0002 -B                         # 指定した番号のエントリを削除する
$ mount | grep efi                                   # ESP がどこにマウントされているか見る
/dev/sda1 on /boot/efi type vfat (rw,relatime,…)
```

**補足**

- **`-v`**（verbose）… ファイルのパスまで含めて詳しく表示します。**どの `.efi` を起動しているかを確かめたいとき**に必要です
- **`-o`** は BootOrder（起動順序）、**`-b` + `-B`** はエントリの削除です。**`-B` は元に戻せない**ので、実行前に `efibootmgr -v` の出力を控えておいてください
- **クラウドの仮想マシンでは、UEFI シェルに入る機会はほとんどありません。**物理サーバやワークステーションで、OS が起動しない機器を調べるときに使う道具です

## MBRの構造

**MBR**（Master Boot Record）は、**ディスクの先頭 512 バイト**にある領域です。
BIOS はここを読んで、ブートローダを起動します。

```text
   ディスクの先頭 512 バイト
   ┌──────────────────────────────┬──────────────┬────┐
   │  ブートストラップローダ        │ パーティション │ 署名│
   │  （446 バイト）                │ テーブル      │ 2  │
   │                              │ （64 バイト）  │バイト│
   └──────────────────────────────┴──────────────┴────┘
        ブートローダの先頭部分        4 区画 × 16 バイト   0x55AA
```

| 領域 | 大きさ | 中身 |
|:--|--:|:--|
| **ブートストラップローダ** | **446 バイト** | **ブートローダの最初の部分**。ここから残りを読み込む |
| **パーティションテーブル** | **64 バイト** | **基本パーティションの情報 4 個分**（1 個 16 バイト） |
| **ブートシグネチャ** | **2 バイト** | `0x55AA`。**これが無いと起動可能なディスクとみなされない** |
| **合計** | **512 バイト** | — |

> **基本パーティションが 4 つまで**なのは、**64 ÷ 16 = 4** だからです。
> それ以上に分けたいときは、1 つを**拡張パーティション**にして、その中に**論理パーティション**を作ります。

**例文**

```bash
$ sudo dd if=/dev/sda of=/tmp/mbr.bin bs=512 count=1   # MBR を丸ごと退避する
$ sudo hexdump -C /tmp/mbr.bin | tail -3               # 末尾の 55 aa を確認する
000001f0  00 00 00 00 00 00 00 00  00 00 00 00 00 00 55 aa
$ sudo fdisk -l /dev/sda                               # パーティションテーブルを見る
$ lsblk                                                # ディスクとパーティションの階層を見る
```

**補足**

- **MBR の退避は、ディスクを触る前の定番の保険**です。`dd` の `bs=512 count=1` で先頭 1 セクタだけをコピーします
- 戻すときは `if` と `of` を入れ替えます。**間違えると中身を壊すので、`of=` の指定は必ず二度確認してください**

## ブートローダが第1段階と第2段階に分かれる理由

**MBR に入るブートローダの領域は、わずか 446 バイトしかありません。**
**GRUB のような機能の多いブートローダは、とうていここに収まりません。**

```text
   MBR の 512 バイトのうち、ブートローダが使えるのは 446 バイトだけ
        │
        ▼
   GRUB 本体（メニュー表示、ファイルシステムの読み取り、対話シェル…）は入らない
        │
        ▼
   だから 2 段階に分ける

     第1段階  MBR の 446 バイト     … 第2段階を呼び出すだけの、ごく小さなプログラム
        │
        ▼  呼び出す
     第2段階  /boot/grub/ などに配置 … メニュー表示・カーネルの読み込みなど本来の仕事
```

| 段階 | どこにあるか | 何をするか |
|:--|:--|:--|
| **第1段階ブートローダ** | **MBR（ディスクの先頭 446 バイト）** | **第2段階を見つけて呼び出すだけ**。機能はほぼ無い |
| **第2段階ブートローダ** | **`/boot/grub/`（ファイルシステム上）** | **メニューの表示、起動オプションの受付、カーネルのロード** |

> **これは GRUB Legacy でも GRUB2 でも同じ**です。
> 「GRUB2 なら全体が MBR に入る」という説明は誤りで、**どちらも 2 段階に分かれています。**

**OS が Linux 1 つだけのとき、第1段階は通常 MBR に置かれます。**
複数の OS を入れる構成では、各 OS のパーティションの先頭（PBR）に置く方式もあります。

## ブートローダだけを復元する

**別の OS を入れて MBR を書き換えられてしまい、GRUB が起動しなくなった**——
このとき、**パーティションテーブルは残したまま、ブートローダ部分だけを戻したい**ことがあります。

```text
   MBR を丸ごと（bs=512）戻すと……
        パーティションテーブル（64 バイト）まで上書きされてしまう
        → いまのディスク構成が壊れる

   ブートローダ部分だけ（bs=446）戻すと……
        先頭 446 バイトだけが書き換わる
        → パーティションテーブルとブートシグネチャは無事
```

**例文**

```bash
$ sudo dd if=/dev/sda of=mbr_backup.img bs=512 count=1   # ①事前に MBR を丸ごと退避しておく

# --- MBR が壊れたあと、レスキュー環境で ---
$ sudo dd if=mbr_backup.img of=/dev/sda bs=446 count=1   # ②ブートローダ部分だけを書き戻す
$ sudo fdisk -l /dev/sda                                 # ③パーティションが残っているか確認する
```

| 指定 | 意味 |
|:--|:--|
| **`if=`** | **入力元**（input file）。ここではバックアップしたイメージ |
| **`of=`** | **出力先**（output file）。ここでは書き戻す対象のディスク |
| **`bs=446`** | **一度に読み書きするサイズ**（block size）。**ブートローダ領域だけに絞るための値** |
| **`count=1`** | **その大きさで 1 回だけ処理する** |

**補足**

- **`bs=512` と `bs=446` の使い分けが要点**です。**丸ごと戻したいなら 512、ブートローダだけなら 446**
- **`of=` にディスク全体（`/dev/sda`）を指定します。** パーティション（`/dev/sda1`）ではありません
- **退避していなければ復元できません。** ディスク構成を変える前に `bs=512 count=1` で控えておくのが定番です
- `dd` の詳しい使い方は [dd コマンド](../06_ストレージとファイルシステム/ddコマンド.md) にまとめています

## MBRとGPTの違い

| | **MBR** | **GPT** |
|:--|:--|:--|
| **正式名称** | Master Boot Record | GUID Partition Table |
| **どこにある** | ディスクの**先頭 512 バイト** | ディスクの**先頭と末尾**（複製を持つ） |
| **パーティション数** | **基本 4 つまで**（拡張で増やす） | **128 個まで**（既定） |
| **ディスクの上限** | **2TB** | **9.4ZB**（実質無制限） |
| **壊れたときの復旧** | **1 か所しかないので弱い** | **末尾に複製があるので復旧しやすい** |
| **組み合わせるファームウェア** | 主に BIOS | 主に UEFI |

**例文**

```bash
$ sudo parted /dev/sda print                         # パーティション形式（msdos か gpt か）を確認する
Partition Table: gpt
$ sudo gdisk -l /dev/sda                             # GPT を詳しく見る
$ lsblk -f                                           # ファイルシステムと UUID を一覧する
```
