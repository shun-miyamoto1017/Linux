## まずこれだけ

| 知りたいこと | 答え |
|:--|:--|
| **今のバージョンを知りたい** | **`uname -r`**（`uname -a` でも分かる） |
| **他の確認方法は** | **`cat /proc/version`** ／ ソースがあれば **`cat /usr/src/linux/Makefile`** |
| **リリースの種類は** | **`prepatch`** → **`mainline`** → **`stable`** → **`longterm`** の **4 つ** |
| **長く使えるのは** | **`longterm`**（＝ **LTS**）。**約 2 年**、重要なバグ修正が続く |
| **配布物に入っているもの** | カーネルソース／モジュールのソース／ドキュメント／`Makefile` |
| **配布物に入っていないもの** | **コンパイラ（`gcc`）と `make`**。これは**自分で用意する** |

## バージョンを確認する4つの方法

### 一覧

| 方法 | コマンド | どんなときに使うか | 注意 |
|:--|:--|:--|:--|
| **`uname`** | **`uname -r`** / `uname -a` | **いちばん確実で手軽**。どの環境でも使える | — |
| **`/proc/version`** | **`cat /proc/version`** | ビルド日時やコンパイラの版まで知りたいとき | — |
| **ソースの `Makefile`** | `cat /usr/src/linux/Makefile` | **ソースからビルドした環境**で、そのソースの版を知りたいとき | **動いているカーネルとは限らない** |
| **`/boot` のファイル名** | `ls /boot/` | 入っているカーネルを**すべて**知りたいとき | 動いているものだけではない |

> **`cat /proc/sys/kernel` ではバージョンは分かりません。**
> `/proc/sys/kernel` は**ディレクトリ**なので、`cat` するとエラーになります。

```bash
$ cat /proc/sys/kernel                               # ディレクトリなので cat はエラーになる
cat: /proc/sys/kernel: 無効な引数です
```

### uname を使う

**意味**

**`uname`**（unix name）は、**動いているシステムの情報を表示する**コマンドです。
オプションで「どの情報を出すか」を選びます。

**よく使うオプション**

| オプション | 表示されるもの | 補足 |
|:--|:--|:--|
| **`-r`** / `--kernel-release` | **カーネルのバージョン** | **最重要**。`6.1.0-18-amd64` のような文字列 |
| **`-a`** / `--all` | **上記すべての情報** | **迷ったらこれ**。バージョンも当然含まれる |
| **`-s`** / `--kernel-name` | **カーネルの名前** | ほぼ常に `Linux`。**オプション無しの `uname` と同じ** |
| **`-n`** / `--nodename` | **ホスト名** | `hostname` コマンドと同じ結果 |
| **`-m`** / `--machine` | **ハードウェア名（アーキテクチャ）** | `x86_64` / `aarch64` など |
| **`-p`** / `--processor` | **CPU タイプ** | `unknown` になることが多い |
| **`-i`** / `--hardware-platform` | ハードウェアプラットフォーム | `unknown` になることが多い |
| **`-v`** / `--kernel-version` | **ビルドされた回数と日時** | **バージョン番号ではない**（紛らわしい） |
| **`-o`** / `--operating-system` | OS 名 | ほぼ常に `GNU/Linux` |

> **`-v` は「バージョン」ではありません。**
> カーネルの**バージョン番号を出すのは `-r`**。`-v` が出すのは**ビルド日時と回数**です。
> ここは名前から誤解しやすいので、**バージョンは `-r`（release）** と覚えてください。

**例文**

```bash
$ uname -r                                           # カーネルのバージョンだけを表示する
6.1.0-18-amd64

$ uname -a                                           # すべての情報をまとめて表示する
Linux web01 6.1.0-18-amd64 #1 SMP PREEMPT_DYNAMIC Debian 6.1.76-1 (2024-02-01) x86_64 GNU/Linux

$ uname                                              # オプション無しは -s と同じ
Linux

$ uname -m                                           # 32ビットか64ビットかを確認する
x86_64
```

### uname の結果画面の見方

```bash
$ uname -a                                           # すべての情報をまとめて表示する
Linux web01 6.1.0-18-amd64 #1 SMP PREEMPT_DYNAMIC Debian 6.1.76-1 (2024-02-01) x86_64 GNU/Linux
```

**左から順に、対応するオプションが並んでいます。**

```text
  Linux   web01   6.1.0-18-amd64   #1 SMP …   x86_64   GNU/Linux
    │       │            │            │          │         │
   -s      -n           -r           -v         -m        -o
  名前   ホスト名    バージョン    ビルド情報  アーキ     OS名
```

| 表示されている位置 | オプション | 意味 | どこを見るか | 異常と判断する目安 |
|:--|:--|:--|:--|:--|
| `Linux` | **`-s`** | **カーネルの名前** | ほぼ常に `Linux` | — |
| `web01` | **`-n`** | **ホスト名** | 作業対象のサーバで合っているかの確認 | 想定と違うなら**別のサーバにいる** |
| `6.1.0-18-amd64` | **`-r`** | **カーネルのリリース（バージョン）** | **最重要**。`/lib/modules/` や `/boot/config-` のディレクトリ名と一致する | 一致しないとモジュールが読み込めない |
| `#1 SMP PREEMPT_DYNAMIC …` | **`-v`** | **ビルドされた回数と日時** | `#1` は「そのバージョンで 1 回目のビルド」 | 自前ビルドだと数字が増える |
| `x86_64` | **`-m`** | **ハードウェアのアーキテクチャ** | 32 ビットか 64 ビットか | パッケージの種類が合わない原因になる |
| （省略されることあり） | **`-p`** | プロセッサの種類 | `unknown` が普通 | — |
| （省略されることあり） | **`-i`** | ハードウェアプラットフォーム | `unknown` が普通 | — |
| `GNU/Linux` | **`-o`** | OS 名 | ほぼ常に `GNU/Linux` | — |

**補足**

- **`uname -r` の文字列は、`/lib/modules/` の下のディレクトリ名とまったく同じ**です。ここが食い違うと、モジュールが読み込めません

```bash
$ uname -r                                           # 動いているカーネルのバージョン
6.1.0-18-amd64
$ ls -d /lib/modules/$(uname -r)                     # 対応するモジュールのディレクトリがあるか確認する
/lib/modules/6.1.0-18-amd64
```

### proc version を使う

**意味**

**`/proc/version`** は、**動いているカーネルのバージョンと、ビルドされたときの情報**が 1 行で書かれた仮想ファイルです。

**例文**

```bash
$ cat /proc/version                                  # バージョンとビルド情報を1行で見る
Linux version 2.6.32-5-686 (Debian 2.6.32-31) (ben@decadent.org.uk) (gcc version 4.3.5 (Debian 4.3.5-4) ) #1 SMP Tue Mar 3 21:36:00 UTC 2011
```

**結果画面の見方**

| 部分 | 意味 |
|:--|:--|
| `Linux version 2.6.32-5-686` | **カーネルのバージョン**（`uname -r` と同じ文字列） |
| `(Debian 2.6.32-31)` | ディストリビューションのパッケージ版 |
| `(ben@decadent.org.uk)` | **ビルドした人／環境** |
| `(gcc version 4.3.5 …)` | **ビルドに使ったコンパイラの版** |
| `#1 SMP Tue Mar 3 …` | **ビルド回数と日時**（`uname -v` と同じ） |

**補足**

- `/proc` は**ディスク上に実体がない仮想ファイル**です。詳しくは [カーネルの実行時管理 dmesgとsysctl](./カーネルの実行時管理_dmesgとsysctl.md) を参照してください

### ソースの Makefile を使う

**意味**

ソースからビルドした環境なら、**`/usr/src/linux/Makefile` の先頭**にバージョンが書かれています。

**例文**

```bash
$ cat /usr/src/linux/Makefile                        # ソースのバージョンを確認する
... （略）
VERSION = 2
PATCHLEVEL = 6
SUBLEVEL = 32
EXTRAVERSION = 5
... （略）
```

| 行 | 意味 | 上の例での値 |
|:--|:--|:--|
| **`VERSION`** | **メジャーバージョン** | `2` |
| **`PATCHLEVEL`** | **マイナーバージョン** | `6` |
| **`SUBLEVEL`** | **リビジョン**（修正の回数） | `32` |
| **`EXTRAVERSION`** | **追加の識別子** | `5` |

つなげると **`2.6.32-5`** になります。

**補足**

- **これはあくまで「そのソースのバージョン」**です。**今動いているカーネルのバージョンとは限りません。**
  動いているものを知りたいなら `uname -r` を使ってください

## バージョン番号の読み方

現在のバージョン番号は、**3 つの数字**でできています。

```text
        6  .  11  .  6
        │      │      │
        │      │      └─ SUBLEVEL   … 修正の回数（stable として重ねた回数）
        │      └──────── PATCHLEVEL … マイナーバージョン
        └─────────────── VERSION    … メジャーバージョン
```

| 表記の例 | 何を表すか |
|:--|:--|
| **`6.12-rc3`** | **`prepatch`**。6.12 のリリース候補 第 3 版 |
| **`6.11.0`** | **`mainline`**。リリースされた時点の正式版 |
| **`6.11.6`** | **`stable`**。6.11 に 6 回の修正が重ねられたもの |
| **`6.6.52`** | **`longterm`** になっている系列の、52 回目の修正 |

> **末尾に `-rc` が付いていたら開発版**（prepatch）です。本番では使いません。

**ディストリビューションのカーネルは、これに独自の文字列が付きます。**

```text
   6.1.0-18-amd64
   └───┘ └┘ └───┘
   カーネル 独自 アーキ
   本体の版 の版
```

## リリースのカテゴリ

Linux カーネルのリリースは、**4 つのカテゴリ**に分かれます。**この 4 つ以外はありません。**

### 全体の流れ

```text
 ① prepatch（RC）   新機能入り・テストが必要な開発版
      │              例）6.12-rc1、6.12-rc2 …
      │  不具合を直しながら、ある程度安定したら
      ▼
 ② mainline         Linus Torvalds が数か月ごとに出す正式版
      │              例）6.12.0
      │  リリースされた時点で「安定版の第0版」とみなされる
      ▼
 ③ stable           mainline で見つかった不具合を修正した安定版
      │              例）6.12.1、6.12.2 …
      │  この中から、特定のバージョンが選ばれて
      ▼
 ④ longterm（LTS）  約2年、重要な修正が続く長期サポート版
                     例）6.6.52
```

---

### 4つのカテゴリ

| カテゴリ | 読み | 位置づけ | 誰が出すか | バージョン表記の例 |
|:--|:--|:--|:--|:--|
| **`prepatch`** | プレパッチ | **リリース候補（RC）**。**テストが必要な新機能**が含まれる開発版。開発者・最新機能を試したい人向け | Linus Torvalds | **`6.12-rc3`** |
| **`mainline`** | メインライン | **`prepatch` の後**にリリースされる正式版。**新機能はここで入る**。リリース時点で**安定版の第 0 版**とみなされる | Linus Torvalds | **`6.11.0`** |
| **`stable`** | ステーブル | **`mainline` の後**にリリースされる安定版。**mainline で見つかった不具合の修正**が行われる | 指定されたカーネルメンテナ | **`6.11.6`** |
| **`longterm`** | ロングターム | **過去の `stable` の中から選ばれた**特定のバージョン。**約 2 年**という長い期間、重要なバグ修正が続く。**LTS** と略される | 指定されたカーネルメンテナ | **`6.6.52`** |

> **`development` というカテゴリはありません。**開発版にあたるのは **`prepatch`（RC）** です。

---

### longterm を正しくつかむ

**`longterm` は、試験で最も細かく問われるカテゴリ**です。3 点だけ押さえます。

| 論点 | 正しいのは |
|:--|:--|
| **どこから選ばれるか** | **`stable` の中から選ばれる**（`prepatch` からではない） |
| **何が行われるか** | **長い期間、バグフィックスが行われる**（新機能の追加ではない） |
| **どのくらいの期間か** | **約 2 年**（業界の要望があれば延長されることもある） |

```text
   stable   6.6.1  6.6.2  6.6.3 …          ← 通常は短期間でEOL
     │
     └─ この系列が longterm に選ばれると
                                            ↓
   longterm 6.6.4 … 6.6.52 …                ← 約2年、重要な修正が続く
```

**`stable` と `longterm` の違い**

| | `stable` | `longterm`（LTS） |
|:--|:--|:--|
| **サポート期間** | **短い**。新しい `mainline` が出ると、**あまり間をおかずに EOL** | **約 2 年**と長い |
| **選ばれ方** | `mainline` がリリースされると**自動的に** | `stable` の中から**特定のものが選ばれる** |
| **入る修正** | 見つかった不具合の修正 | **重要なバグ修正のみ**。リリース頻度も低め |
| **本番サーバ向きか** | 短期なら可 | **長く動かすサーバはこちら** |

> **EOL**（End Of Life）… 「（製品の）寿命」から転じて、**サポート期間の終了**を指す言葉です。
> EOL を過ぎたカーネルには、**脆弱性が見つかっても修正が出ません。**

### 開発のサイクル

`mainline` がリリースされた直後には、**マージウィンドウ**という期間が設けられます。

```text
  mainline 6.11.0 リリース
        │
        ▼
  ┌───────────────┐
  │ マージウィンドウ │  ← 次の版に向けて、新機能の取り込みを行う期間（約2週間）
  └───────────────┘
        │  クローズ
        ▼
   6.12-rc1  ← 最初の prepatch（リリース候補 その1）
   6.12-rc2
   6.12-rc3  ← rc のうちに不具合修正を重ねる
     …
        │  ある程度安定したら
        ▼
  mainline 6.12.0
```

**このサイクルが、数か月ごとに繰り返されます。**

| 用語 | 意味 |
|:--|:--|
| **マージウィンドウ** | Linus Torvalds が**次の版に向けて新機能を取り込む期間**。この間だけ新機能を受け付ける |
| **`rc1`** | マージウィンドウがクローズされた後に出る、**最初のリリース候補** |
| **EOL** | サポート期間の終了 |

### 実務での使いどころ

| 場面 | 何に効くか |
|:--|:--|
| **サーバの OS を選ぶ** | ディストリの LTS 版は、**longterm のカーネル**を採用していることが多い。長く動かすなら必須 |
| **脆弱性対応** | EOL を過ぎた系列は修正が出ない。**動いているカーネルの系列がまだ生きているか**を確認する |
| **クラウドの AMI 選定** | Amazon Linux / Ubuntu LTS は longterm ベース。サポート期限が運用計画に直結する |
| **新機能を試す** | `prepatch`（RC）は**検証環境だけ**で。本番に入れない |

## 配布物に含まれるもの

Linux カーネルは、**`tar.gz` 形式または `tar.xz` 形式**でまとめて配布されます。

### 含まれるもの

| 含まれるもの | 中身 |
|:--|:--|
| **カーネルソース** | カーネルをコンパイルするのに必要な**ソースコード一式** |
| **カーネルモジュールのソース** | デバイスドライバなど。**主なモジュールのソースは、すべてカーネル本体のソースに含まれている** |
| **ドキュメント** | `Documentation/` ディレクトリ。ファイルシステムやドライバの使い方、カーネルパラメータ、起動時に渡すコマンドラインなど |
| **`Makefile`** | **ビルドに必要な `make` ターゲットを定義したファイル**。`config` / `menuconfig` / `oldconfig` / `xconfig` / `install` / `modules_install` は、**これが無いと動かない** |

### 含まれないもの

| 含まれないもの | 誰が用意するか |
|:--|:--|
| **コンパイラ（GNU C コンパイラ＝`gcc`）** | **ユーザが自分で用意する** |
| **ビルドツール（`make`）** | **ユーザが自分で用意する** |

> **「ソースと Makefile は付いてくるが、それをビルドする道具は付いてこない」**
> と覚えると、取り違えません。

**例文**

```bash
$ sudo apt install build-essential                   # Debian系：gcc と make をまとめて入れる
$ sudo dnf groupinstall "Development Tools"          # RHEL系：同じくビルド用の一式を入れる
$ gcc --version                                      # コンパイラが入っているか確認する
$ make --version                                     # make が入っているか確認する
```

**補足**

- `build-essential` … Debian 系で、`gcc` / `make` / 標準ヘッダをまとめて入れるパッケージ
- カーネルのビルドには、これに加えて `libncurses-dev`（`menuconfig` 用）や `bison` / `flex` なども必要になります

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| **`cat /proc/sys/kernel` でエラーになる** | **`/proc/sys/kernel` はディレクトリ**。`cat` できない | バージョンは `uname -r` か `cat /proc/version` |
| **`uname -v` を打ったのにバージョンが出ない** | `-v` は**ビルド回数と日時**。バージョンではない | **`uname -r`** を使う |
| **`/usr/src/linux/Makefile` の版と `uname -r` が違う** | Makefile は**ソースの版**。動いているカーネルとは別物 | 動いているものは `uname -r` で確認する |
| **`cat /usr/src/linux/Makefile` でファイルが無いと言われる** | ディストリのパッケージだけだと**ソース一式は入っていない** | `uname -r` か `/proc/version` を使う |
| **`make` が「コマンドが見つかりません」** | **ビルドツールは配布物に含まれない** | `build-essential` / `Development Tools` を入れる |
| **`gcc` が無くてビルドできない** | 同上。**コンパイラも自分で用意する** | 同上 |
| **`-rc` 付きのカーネルを本番に入れてしまった** | `prepatch` は**テストが必要な開発版** | `stable` か `longterm` の系列に戻す |
| **使っているカーネルに脆弱性の修正が来ない** | その系列が **EOL** になっている可能性がある | kernel.org のリリース一覧で系列の状態を確認し、更新する |
| **モジュールが読み込めない** | `uname -r` と `/lib/modules/` のディレクトリ名が食い違っている | [カーネルモジュールの管理](./カーネルモジュールの管理.md) を参照 |

## クラウド実務メモ

| 場面 | 何に効くか |
|:--|:--|
| **インスタンスに入って最初にやること** | **`uname -a`**。ホスト名で「作業対象を間違えていないか」、バージョンで「どのカーネルか」を同時に確認できる |
| **AMI / イメージの棚卸し** | `uname -r` を一斉に集めると、**古いカーネルのまま残っているインスタンス**が見つかる |
| **脆弱性対応（CVE）** | 「このカーネル系列に修正が入ったか」を判断するのに、**系列（`6.1.x` など）と longterm かどうか**が要る |
| **Amazon Linux / Ubuntu LTS** | **longterm ベース**のカーネル。サポート期限が OS のライフサイクルと連動する |
| **コンテナのベースイメージ** | コンテナは**ホストのカーネルを共有する**。イメージ内の `uname -r` は**ホストの値**が返る |
| **構成管理での確認** | Ansible の `ansible_kernel` ファクトが `uname -r` 相当。台数が多いときはこれで集める |

**補足**

- コンテナの中で `uname -r` を打つと、**コンテナのイメージではなくホストのカーネル**が表示されます。ここは混乱しやすいポイントです

```bash
$ uname -r                                           # ホスト側で確認する
6.1.0-18-amd64
$ docker run --rm alpine uname -r                    # コンテナ内でも同じ値が返る
6.1.0-18-amd64
```
