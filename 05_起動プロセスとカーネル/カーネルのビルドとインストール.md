## 再構築の全体の流れ

まず全体像を 1 枚で見ます。**このノートで一番大事な図です。**

```text
 ① 初期化          make mrproper        ← 前回のゴミと古い .config を消す
      │
      ▼
 ② 設定            make menuconfig      ← .config を作る（config / xconfig / oldconfig でも可）
      │                                    成果物：/usr/src/linux/.config
      ▼
 ③ ビルド          make                 ← 翻訳する。ここが一番時間がかかる
      │                                    成果物：arch/x86/boot/bzImage、各種 .ko
      ▼
 ④ モジュール導入  make modules_install ← .ko を配置
      │                                    配置先：/lib/modules/(バージョン)/
      ▼
 ⑤ 本体の導入      make install         ← カーネル本体を配置＋ブートローダに登録
                                           配置先：/boot/vmlinuz-(バージョン) など
                                           ここまでやって初めて起動メニューに出る
```

**この 5 ステップはすべて、ソースを展開したディレクトリの直下で実行します。**

---

### 現在の設定を引き継ぐ場合の順序

「今動いているカーネルの設定をそのまま使って、新しいソースをビルドしたい」というのが一番よくある要件です。
そのときのターゲットの順序は、**この 5 つで固定**です。

```text
   mrproper  →  oldconfig  →  all  →  modules_install  →  install
   ─────────    ──────────    ───    ───────────────     ─────────
    初期化       設定を引継ぐ   ビルド   モジュールを配置    本体を配置＋登録
```

| 順 | ターゲット | やること |
|:-:|:--|:--|
| **1** | **`make mrproper`** | 設定ファイルを含めて初期化する。**必ず最初** |
| **2** | **`make oldconfig`** | 現在のカーネルの設定を引き継ぐ。**ビルドより前** |
| **3** | **`make all`**（＝`make`） | カーネル本体とモジュールをビルドする |
| **4** | **`make modules_install`** | モジュールを `/lib/modules/` へ配置する |
| **5** | **`make install`** | カーネル本体を `/boot` へ配置し、ブートローダに登録する |

---

### 順序を入れかえるとどうなるか

**なぜこの順番でなければいけないのか**を、1 つずつ確かめます。

| ありがちな間違い | 何が起きるか |
|:--|:--|
| **`oldconfig` を `mrproper` より先にやる** | せっかく作った `.config` が `mrproper` に**消される**。設定をやり直すはめになる |
| **設定をせずに `all` から始める** | `.config` が無い／古いままなので、**狙った構成のカーネルにならない** |
| **`install` を `all` より先にやる** | ビルドされたものがまだ無いので、**配置するものが存在しない** |
| **`modules_install` を `all` より先にやる** | 同様に、配置すべきモジュールがまだできていない |
| **`install` を忘れる** | **起動メニューに新しいカーネルが出てこない**（最頻出） |

> **`modules_install` と `install` の前後**については、
> 通常は **`modules_install` → `install`** の順です。
> `make install` の中で初期RAMディスクが作られるため、**その時点でモジュールが配置済みである**必要があるからです。

## 手順1 設定を初期化する

### 何のためにやるのか

ダウンロードしたソースに、作者の環境の設定が残っていることがあります。
また、同じディレクトリで前回ビルドした残骸があると、混ざって変な結果になります。
**それを全部消して、まっさらな状態から始めるため**です。

**例文**

```bash
$ cd /usr/src/linux                                  # ソースの直下へ移動する
$ make mrproper                                      # 設定ファイルも含めて全部消す
  CLEAN   scripts/basic
  CLEAN   .config .config.old include/config
```

**補足**

- **`mrproper`** は「ミスター・プロパー」という洗剤の商品名から来ています。**一番きれいにするターゲット**という意味
- `.config` も消えるので、**前の設定を残したいなら先に退避**してください

```bash
$ cp /usr/src/linux/.config ~/config-backup          # 設定を退避してから初期化する
```

## 手順2 設定を行う

### 何のためにやるのか

「このカーネルに、どの機能を入れるか」を決めて **`.config`** を作るためです。
**ビルドの前に必ず行います。**設定していない状態でビルドしても、目的のカーネルにはなりません。

**例文**

```bash
$ make menuconfig                                    # コンソール内のメニューで設定する
$ make xconfig                                       # X 上の GUI で設定する
$ make oldconfig                                     # 現在のカーネルの設定を引き継ぐ
```

**今動いているカーネルの設定を引き継ぎたいとき**は、`/boot/config-$(uname -r)` を `.config` としてコピーしてから実行します。

```bash
$ cp /boot/config-$(uname -r) /usr/src/linux/.config  # 今動いているカーネルの設定を持ってくる
$ cd /usr/src/linux                                  # ソースの直下へ移動する
$ make oldconfig                                     # 増えた項目だけ質問される
```

**補足**

- `$(uname -r)` … 今動いているカーネルのバージョン文字列に置き換わる書き方。`uname -r` の実行結果をその場に埋め込みます
- 各設定ターゲットの違い（`config` / `menuconfig` / `xconfig` / `oldconfig`）、`y` / `m` / `n` の意味、設定画面の見方は
  [カーネルソースとmakeターゲット](./カーネルソースとmakeターゲット.md) にまとめています

## 手順3 ビルドする

### 何のためにやるのか

`.config` の内容にしたがって、**ソースコードを実行できる形に翻訳する**ためです。

**例文**

```bash
$ make                                               # 依存関係の解消・本体・モジュールを一括でビルドする
$ make all                                           # make と同じ（明示的に書いた形）
$ make -j4                                           # CPU 4 個を同時に使ってビルドを速くする
$ make V=1 all                                       # 実行中のコマンドをすべて表示する（原因調査用）
```

**補足**

- 現在の `make` は、**依存関係の解消・カーネル本体のビルド・モジュールのビルド**を自動で行います（**`make clean` にあたる後片付けはしません**。必要なら別途打ちます）
- 古い資料にある `make dep`（依存関係の解消）を別に打つ手順は、**2.6 系以降では不要**です
- `-j` … 同時に走らせるジョブ数。**CPU コア数と同じか +1** が目安。`nproc` でコア数を確認できます
- ビルドには数十分〜数時間かかります

**できあがるもの**

| ファイル | 中身 |
|:--|:--|
| `arch/x86/boot/bzImage` | **カーネル本体**（圧縮済みイメージ）。64 ビット x86 の場合のパス |
| `vmlinux` | 圧縮前のカーネル。デバッグ用 |
| `System.map` | **カーネルのアドレスマップ**（関数名とメモリ番地の対応表） |
| 各ディレクトリの `*.ko` | **モジュール** |

## 手順4 モジュールをインストールする

### 何のためにやるのか

ビルドでできた `.ko` ファイルは、**ソースディレクトリの中に散らばったまま**です。
システムが探しに行く場所へ**まとめて配置する**のがこの手順です。

**例文**

```bash
$ sudo make modules_install                          # モジュールをシステムへ配置する
  INSTALL /lib/modules/2.6.35.10/kernel/fs/xfs/xfs.ko
  DEPMOD  2.6.35.10
```

**配置先**

```text
/lib/modules/(カーネルのバージョン)/
                 ↑
        uname -r で表示される文字列と同じ
```

| 使うコマンド | 配置先 |
|:--|:--|
| `uname -r` が `2.6.35.10` なら | `/lib/modules/2.6.35.10/` |
| `uname -r` が `6.1.0-18-amd64` なら | `/lib/modules/6.1.0-18-amd64/` |

**補足**

- **`make modules`** … モジュールを**ビルドするだけ**。配置はしないので、これだけでは使えません
- **`make modules_install`** … ビルド済みのモジュールを**配置する**。最後に `depmod` が自動で走り、依存関係の一覧（`modules.dep`）を作り直します
- **バージョンごとにディレクトリが分かれる**ので、古いカーネルのモジュールが消えることはありません
- `INSTALL_MOD_PATH=/somewhere` を付けると、配置先の先頭にそのパスが付きます（コンテナイメージ作成などで使用）

**例文**

```bash
$ ls /lib/modules/                                   # 入っているカーネルの一覧が分かる
6.1.0-17-amd64  6.1.0-18-amd64

$ modinfo xfs                                        # モジュールの情報と実体のパスを見る
filename:       /lib/modules/6.1.0-18-amd64/kernel/fs/xfs/xfs.ko
```

## 手順5 カーネル本体をインストールする

### 何のためにやるのか

**カーネル本体を `/boot` に置き、ブートローダに「新しいカーネルがある」と登録する**ためです。
**ここまでやらないと、起動メニューに出てきません。**

**例文**

```bash
$ sudo make install                                  # カーネル本体を配置しブートローダに登録する
```

**`make install` が自動でやってくれること**

| | やること | 結果 |
|:-:|:--|:--|
| **①** | **ビルドされたカーネルイメージを `/boot` に移動する** | `/boot` 直下に置かれる |
| **②** | **バージョンがファイル名に付くようリネームする** | `vmlinuz-2.6.38.10` のように、基本の名前にバージョンを足した形になる |
| **③** | `System.map` を `/boot` に配置する | `/boot/System.map-(バージョン)` ができる |
| **④** | `.config` を `/boot` に配置する | `/boot/config-(バージョン)` ができる |
| **⑤** | **必要に応じて初期RAMディスクのイメージを作成する** | カーネルに組み込まれたモジュールの情報から判断して、必要なら `/boot/initrd.img-(バージョン)` が作られる |
| **⑥** | **ブートローダに新しいカーネルを使った起動設定を追加する** | GRUB のメニューに新しいカーネルの項目が追加される |

**`make install` が「やらないこと」**

ここが問われます。**やってくれそうで、やってくれない**ものを並べます。

| やってくれないこと | 正しくは |
|:--|:--|
| **カーネルモジュールを `/lib/modules/(バージョン)/` に配置する** | **`make install` はモジュールの面倒を見ません。**先に **`make modules_install`** を実行する必要があります |
| **古くなったカーネルイメージを削除する** | **あえて残します。**新しいカーネルに問題があっても**古いカーネルで起動できるように**するためです |

> **「起動はできたが、必要なモジュールがロードできなかった」**
> これは **`make modules_install` の忘れ**です。`make install` だけでは配置されません。

**補足**

- **配置先を変えたいとき**は `INSTALL_PATH` を指定します（既定は `/boot`）
- 新しいカーネルを実際に使うには、**別途 GRUB の設定（既定で起動するカーネルの指定）が必要になる場合があります**

---

### make install を忘れるとどうなるか

**症状の切り分け表**です。ここは実務でも試験でも効きます。

| 実行し忘れたもの | 起こること | 見分け方 |
|:--|:--|:--|
| **`make install`** | **起動メニューに新しいカーネルが出てこない。そもそも選べない** | `ls /boot/` に新しい `vmlinuz-…` が無い |
| **`make modules_install`** | **カーネルは選べるが**、起動途中でドライバが見つからず止まる／機器が認識されない | `ls /lib/modules/` に新しいバージョンのディレクトリが無い |
| **`mkinitramfs` / `mkinitrd`** | カーネルは選べるが、**ルートファイルシステムをマウントできず** kernel panic | `ls /boot/` に対応する `initrd.img-…` が無い |
| **`make mrproper`** | 古い設定が残り、意図しない構成になる可能性がある | ビルドは通るので気づきにくい |
| **`make clean`** | **ビルド前の後片付けなので、「ビルドが正常終了した」なら無関係** | — |

**覚え方**

```text
  起動メニューに「出てこない」     → カーネル本体が無い     → make install 忘れ
  起動メニューに「出るが落ちる」   → 部品が無い             → modules_install / initrd 忘れ
```

## 手作業でインストールする場合

`make install` を使わず、1 つずつ手で置くこともできます。
**`make install` が中で何をしているかを理解するのに役立つ**ので、手順を置いておきます。

| 手順 | やること | コマンド例 |
|:--|:--|:--|
| **①** | カーネル本体（`bzImage`）を `/boot/vmlinuz-(バージョン)` としてコピー | `cp arch/x86/boot/bzImage /boot/vmlinuz-2.6.35.10` |
| **②** | `System.map` を `/boot/System.map-(バージョン)` としてコピー | `cp System.map /boot/System.map-2.6.35.10` |
| **③** | `/boot/vmlinuz` と `/boot/System.map` のシンボリックリンクを張り直す | `ln -sfn vmlinuz-2.6.35.10 /boot/vmlinuz` |
| **④** | 初期RAMディスクを作って `/boot/initrd.img-(バージョン)` に置く | `mkinitramfs -o /boot/initrd.img-2.6.35.10 2.6.35.10` |
| **⑤** | ブートローダの設定を更新する | 下の表を参照 |

**例文**

```bash
$ sudo cp arch/x86/boot/bzImage /boot/vmlinuz-2.6.35.10       # カーネル本体を配置する
$ sudo cp System.map /boot/System.map-2.6.35.10               # アドレスマップを配置する
$ sudo cp .config /boot/config-2.6.35.10                      # ビルド設定を控えとして残す
$ sudo ln -sfn vmlinuz-2.6.35.10 /boot/vmlinuz                # 既定のカーネルのリンクを張り替える
$ sudo mkinitramfs -o /boot/initrd.img-2.6.35.10 2.6.35.10    # 初期RAMディスクを作る
```

### ブートローダの設定はどれを触るか

| ブートローダ | 編集するファイル | 反映のしかた |
|:--|:--|:--|
| **GRUB Legacy**（GRUB 0.9x） | **`/boot/grub/menu.lst`**（環境により `grub.conf`） | **このファイルを直接編集する**。反映コマンドは不要 |
| **GRUB2**（現在の主流） | **`/etc/default/grub`** と **`/etc/grub.d/`** 配下 | **`update-grub`**（Debian 系）または **`grub2-mkconfig -o /boot/grub2/grub.cfg`**（RHEL 系）で `grub.cfg` を生成する |

> **`/boot/grub/grub.cfg` を直接編集してはいけません。**
> GRUB2 の `grub.cfg` は**自動生成されるファイル**なので、次に生成コマンドが走ると書いた内容が消えます。

**例文**

```bash
$ sudo update-grub                                   # Debian系：grub.cfg を作り直す
$ sudo grub2-mkconfig -o /boot/grub2/grub.cfg        # RHEL系：grub.cfg を作り直す
```

### rdev カーネルイメージ自身に既定値を書き込む

**ブートローダが無かった時代の名残のコマンド**です。
**カーネルイメージ（`bzImage` や `vmlinuz`）の中に、ルートデバイスなどの既定値を直接書き込みます。**

```bash
$ rdev                                               # 現在のルートデバイスを表示する
/dev/sda2 /

$ rdev /boot/vmlinuz-2.6.35.10                       # そのカーネルイメージに書かれたルートデバイスを表示する
Root device /dev/sda2

$ sudo rdev /boot/vmlinuz-2.6.35.10 /dev/sda3        # ルートデバイスを /dev/sda3 に書き換える
```

**書式**

```text
rdev [オプション] [カーネルイメージ [設定する値]]
       │            │                 └─ 省略すると「表示」、書けば「変更」
       │            └─ 省略すると、今動いているシステムのルートデバイスを表示
       └─ 何を操作するかを選ぶ
```

| オプション | 書き込む対象 | 別名のコマンド |
|:--|:--|:--|
| **（なし）** | **ルートデバイス** | — |
| **`-R`** | ルートを**読み込み専用でマウントするか**のフラグ | `rootflags` |
| **`-r`** | **RAM ディスクのサイズ** | `ramsize` |
| **`-s`** | **スワップデバイス** | `swapdev` |
| **`-v`** | **ビデオモード** | `vidmode` |

**なぜこんなコマンドがあるのか**

| | 当時 | 今 |
|:--|:--|:--|
| **ルートデバイスの伝え方** | **カーネルイメージ自身に埋め込む**（`rdev`） | **ブートローダが `root=` で渡す**（GRUB の `linux` 行） |
| **変更のしかた** | カーネルイメージを書き換える | **設定ファイルを直すだけ**。カーネルは触らない |

> **今のディストリで使うことはまずありません。** GRUB が `root=/dev/sda2` のように渡すほうが
> 柔軟で、カーネルイメージを書き換えずに済むからです。
> **新しい環境では `rdev` コマンド自体が入っていないことが多い**ので、
> 「**カーネルイメージに書き込む古い方法**」として名前を覚えておけば十分です。

## bootディレクトリの中身

`/boot` は、**起動に必要なファイルだけを置く専用ディレクトリ**です。
`make install` が置いていくものが、そのままここに並びます。

| パス | 内容 | もう少しくわしく |
|:--|:--|:--|
| **`grub/grub.cfg`** | **GRUB2 の設定ファイル** | 起動メニューの実体。`update-grub` などで自動生成される |
| **`grub/menu.lst`**（`grub.conf`） | **GRUB Legacy の設定ファイル** | 環境によって名前が違う。こちらは手で編集する |
| **`vmlinuz-<VER>`** | **カーネルイメージ** | カーネル本体。`z` は圧縮されていることを表す（gzip など） |
| **`System.map-<VER>`** | **カーネルのアドレスマップ** | カーネル内の関数名とメモリ番地の対応表。障害解析で使う |
| **`initrd.img-<VER>`** | **初期RAMディスクイメージ** | 起動の途中だけ使う小さなファイルシステム |
| **`config-<VER>`** | **ビルド時のカーネル設定** | `.config` のコピー。**今のカーネルがどう作られたか**を後から確認できる |

**例文**

```bash
$ ls /boot/                                          # 起動に必要なファイル一式を確認する
config-6.1.0-18-amd64   initrd.img-6.1.0-18-amd64   System.map-6.1.0-18-amd64
grub                    vmlinuz-6.1.0-18-amd64

$ uname -r                                           # 今動いているカーネルのバージョンを見る
6.1.0-18-amd64

$ grep CONFIG_XFS_FS /boot/config-$(uname -r)        # 今のカーネルで XFS が有効か調べる
CONFIG_XFS_FS=m
```

**補足**

- `=y` … カーネル本体に組み込み済み ／ `=m` … モジュール ／ `# … is not set` … 無効
- **`/boot` の空き容量不足**は実務でよく起こります。カーネルを更新するたびに一式が増えるためです

```bash
$ df -h /boot                                        # /boot の空き容量を確認する
$ dpkg --list | grep linux-image                     # Debian系：入っているカーネルの一覧
$ rpm -qa | grep ^kernel                             # RHEL系：入っているカーネルの一覧
```

### vmlinuz という名前の由来

| 名前 | 意味 |
|:--|:--|
| **`vmlinux`** | **圧縮されていない**カーネル。`vm` は Virtual Memory（仮想メモリ対応）の意味 |
| **`vmlinuz`** | **圧縮された**カーネル。末尾の `z` は圧縮（gzip の `z`）を表す |

---

### System.map はカーネルのアドレスマップ

**`/boot/System.map-(バージョン)`** は、**カーネルがメモリ上に展開されたときの「シンボル（名前）とアドレス（番地）の対応表」**です。

```text
   カーネルの中の関数や変数            メモリ上の番地
   ───────────────────              ──────────────
   printk                    ←→     ffffffff81234560
   schedule                  ←→     ffffffff812a1f00
   init_task                 ←→     ffffffff82011840
```

| | |
|:--|:--|
| **いつ作られるか** | **カーネルのビルド時**に、`/usr/src/linux/System.map` として**同時に作られる** |
| **どこへ配置されるか** | `make install`（または手作業）で **`/boot/System.map-(バージョン)`** |
| **何に使うか** | **カーネルパニックの解析**。ログに出た番地から、どの関数で落ちたかを引く |
| **無いとどうなるか** | 起動はできる。ただし障害解析でメッセージが番地のままになり、読めなくなる |

**`/boot` にある 4 種類のファイルは、名前が似ていて取り違えやすいので並べます。**

| ファイル | 正体 | ひとこと |
|:--|:--|:--|
| **`vmlinuz-<VER>`** | **カーネルイメージ** | カーネル本体そのもの |
| **`System.map-<VER>`** | **カーネルのアドレスマップ** | **名前と番地の対応表**。カーネル本体ではない |
| **`initrd.img-<VER>`** | **初期RAMディスクイメージ** | 起動の途中だけ使う小さなファイルシステム |
| **`config-<VER>`** | **カーネルコンフィギュレーション** | ビルド時の `.config` の控え |

**例文**

```bash
$ ls -lh /boot/System.map-$(uname -r)                # アドレスマップが置かれているか確認する
$ head -3 /boot/System.map-$(uname -r)               # 先頭3行を見る（番地・種別・シンボル名）
ffffffff81000000 T _stext
ffffffff81000000 T _text
ffffffff81000030 T secondary_startup_64

$ grep " printk$" /boot/System.map-$(uname -r)       # 特定の関数の番地を引く
$ sudo cat /proc/kallsyms | head -3                  # 動いているカーネルから直接引くこともできる
```

**補足**

- 2 列目の 1 文字は**シンボルの種別**です。`T` … テキスト（関数、外部公開）／`t` … テキスト（内部のみ）／`D` … 初期値ありのデータ／`B` … 初期値なしのデータ
- `/proc/kallsyms` は**動いているカーネルが持っている同じ対応表**です。モジュールの分も含みます

`/boot` に置かれるのは **`vmlinuz`**（圧縮版）です。
圧縮されていますが、**自分で自分を展開するコード**が先頭に付いているので、そのまま起動できます。

### zImage と bzImage

**どちらも「カーネルイメージファイルの形式」**です。コマンドでもソースでもありません。

| | **`zImage`** | **`bzImage`** |
|:--|:--|:--|
| **正体** | **カーネルイメージの形式**（古い） | **カーネルイメージの形式**（現在の主流） |
| **圧縮** | **gzip で圧縮されている** | **同じく gzip で圧縮されている** |
| **展開** | 自分で自分を展開する（自己伸長） | 同じ |
| **サイズの制限** | **約 512KB 以下**しか扱えない | **制限がゆるい**。1MB を超えるものも扱える |
| **置かれるメモリ** | **ローメモリ**（`0x10000`＝64KB の位置）だけ | **ハイメモリ**（`0x100000`＝1MB より上）にも置ける |
| **現在の 2.6 系 / 3.x 系** | **使えない**（要求される機能が制限を超えるため） | **こちらだけが使われる** |

```text
   メモリ
   ┌──────────────────┐  高い番地
   │                  │
   │   ハイメモリ      │ ← bzImage はここに置ける
   │                  │
   ├──────────────────┤ 1MB（0x100000）
   │   ローメモリ      │ ← zImage はここまでしか使えない
   └──────────────────┘  低い番地
```

**押さえどころ**

| よくある誤解 | 正しくは |
|:--|:--|
| 「`bzImage` は圧縮されていない」 | **圧縮されている**（`zImage` と同じく gzip） |
| 「`bzImage` はカーネルソースを格納する形式」 | **カーネルイメージ**（ビルド済みの本体）の形式 |
| 「512KB 以下という制限があるのは `bzImage`」 | 制限があるのは **`zImage`** のほう |
| 「`zImage` のほうが後発で制限がゆるい」 | **逆**。`bzImage` が後発で制限がゆるい |
| 「`zImage` はハイメモリ、`bzImage` はローメモリ」 | **逆**。`zImage` がローメモリ、`bzImage` がハイメモリ |
| 「どちらもモジュールを操作するコマンド」 | **コマンドではない**。モジュール操作は `insmod` / `rmmod` / `modprobe` |

> **`bz` は bzip2 ではありません。**「**b**ig **zImage**」の略です。ここはよく誤解されます。
> 圧縮方式はどちらも gzip です。

**補足**

- `zImage` は現在も**仕様上は残っています**が、実質使われません。2.6 系以降のカーネルは機能が多く、512KB の制限に収まらないためです
- ビルドすると `arch/x86/boot/bzImage` ができます。これを `/boot/vmlinuz-(バージョン)` として配置します

## カーネルにパッチをあてる

### パッチとは

**パッチ**は、「ソースコードのこの行をこう書き換える」という**差分だけを書いたテキストファイル**です。
ソース全体を配り直さずに、変更点だけを配れます。

```text
  元のソース  +  パッチ（差分）  =  新しいソース
```

### あてたら再ビルドが必要

**パッチはソースコードを書き換えるだけです。**
ソースを書き換えても、すでに動いているカーネル（`/boot/vmlinuz-…`）は何も変わりません。

```text
  patch をあてる    → ソースが新しくなる
  make              → ビルドし直す        ← これが必要
  make modules_install / make install → 配置し直す  ← これも必要
  再起動            → やっと反映される
```

> **「パッチをあてれば終わり」ではありません。** ビルドとインストールと再起動まで必要です。

---

### バージョンを大きく上げるときは複数あてる

カーネルのパッチは、**隣り合うバージョン間の差分**として配布されます。

```text
  2.6.30 → 2.6.31 のパッチ
  2.6.31 → 2.6.32 のパッチ
  2.6.32 → 2.6.33 のパッチ
```

したがって、**2.6.30 から 2.6.33 に上げたいなら、3 つのパッチを順番に**あてる必要があります。
「1 つのパッチで一気に上げる」ことはできません。

**例文**

```bash
$ cd /usr/src/linux                                  # ソースの直下へ移動する
$ gunzip -c ../patch-2.6.31.gz | patch -p1           # 2.6.30 → 2.6.31 のパッチをあてる
$ gunzip -c ../patch-2.6.32.gz | patch -p1           # 続けて 2.6.32 へ
$ gunzip -c ../patch-2.6.33.gz | patch -p1           # 続けて 2.6.33 へ
```

**補足**

- `gunzip -c` … 圧縮ファイルを**展開した内容を画面（標準出力）へ流す**。元の `.gz` は消えません
- `|` … 左のコマンドの出力を、右のコマンドの入力につなぐ記号（パイプ）
- `patch -p1` … パッチの中に書かれたパスから**先頭 1 階層を取り除いて**あてる。カーネルのパッチは `linux-2.6.31/kernel/sched.c` のように 1 階層余分に付いているため

---

### patch-kernel スクリプト

この「順番に何個もあてる」作業を自動化するスクリプトが、**ソースに同梱されている `scripts/patch-kernel`** です。

| | 内容 |
|:--|:--|
| **場所** | `/usr/src/linux/scripts/patch-kernel` |
| **やること** | 指定したディレクトリにあるパッチを、**バージョン順に自動で適用する** |
| **必須か** | **必須ではない**。`patch` コマンドを手で繰り返しても同じ結果になる |

**例文**

```bash
$ ./scripts/patch-kernel /usr/src/linux /usr/src/patches   # パッチを順番に自動適用する
```

---

### 非公式パッチは先に外す

独自のパッチ（ディストリ独自・ベンダ独自・自作）をあてたソースに、
そのまま公式パッチをあてると、**同じ箇所を二重に書き換えようとして失敗します。**

**先に非公式パッチを取り消してから、公式パッチをあてます。**取り消しは **`patch -R`** です。

```text
  素のソース
     │ ①独自パッチをあてた（現在の状態）
     ▼
  独自パッチ入りソース
     │ ② patch -R で独自パッチを取り消す   ← これを先にやる
     ▼
  素のソースに戻る
     │ ③公式パッチをあてる
     ▼
  公式の新バージョン
```

**例文**

```bash
$ patch -R -p1 < ../my-custom.patch                  # あてた独自パッチを取り消す
$ patch -p1 --dry-run < ../patch-2.6.33              # 本当にあてる前に試す
$ patch -p1 < ../patch-2.6.33                        # 公式パッチをあてる
```

**補足**

- `-R` は reverse の略。**あてたパッチを元に戻す**
- `--dry-run` … 実際にはファイルを変更せず、**うまくいくかどうかだけ確認**する
- 失敗した箇所は `*.rej`（reject）というファイルに残るので、`find . -name "*.rej"` で探せます

---

## patch コマンドのよく使うオプション

| オプション | 意味 | 使いどころ |
|:--|:--|:--|
| **`-pN`** / `--strip=N` | パッチ内のパスから**先頭 N 階層を取り除く** | カーネルのパッチは基本 **`-p1`** |
| **`-R`** / `--reverse` | **あてたパッチを取り消す** | 独自パッチを外すとき |
| **`--dry-run`** | ファイルを変更せず、**結果だけ表示**する | 本番前の確認。**まずこれ** |
| **`-i ファイル`** / `--input` | パッチファイルを指定する（`<` の代わり） | スクリプトで書くとき読みやすい |
| **`-b`** / `--backup` | 元のファイルを **`.orig`** として残す | 失敗したときに戻せる |
| **`-N`** / `--forward` | **すでにあたっているパッチを飛ばす** | 二重適用の事故を防ぐ |
| **`-l`** / `--ignore-whitespace` | 空白やタブの違いを無視して照合する | メール経由で崩れたパッチを救うとき |
| **`-E`** / `--remove-empty-files` | 適用後に**空になったファイルを削除**する | ファイル削除を含むパッチ |
| **`-d ディレクトリ`** | **移動してから**適用する | `cd` を書かずに済ませたいとき |
| **`-t`** / `--batch` | 質問せずに処理を進める | 自動化の中で使う |

**例文**

```bash
$ patch -p1 --dry-run < ../patch-2.6.33              # まず試して、失敗しないか確認する
$ patch -p1 -b < ../patch-2.6.33                     # .orig のバックアップを残しつつ適用する
$ patch -p1 -i ../patch-2.6.33                       # -i でパッチファイルを指定する（< と同じ）
```

## パッチの階層指定の数え方

`-pN` はつまずきやすいので、図で示します。

パッチの中に、こう書かれているとします。

```text
--- linux-2.6.32/kernel/sched.c
+++ linux-2.6.33/kernel/sched.c
        │        │
        │        └─ ここから下が実際に使われる
        └─ 1 階層目（バージョン名のディレクトリ）
```

| 指定 | 実際に探しに行くパス | 使う場面 |
|:--|:--|:--|
| `-p0` | `linux-2.6.32/kernel/sched.c` | `/usr/src` にいるとき |
| **`-p1`** | **`kernel/sched.c`** | **`/usr/src/linux` の中にいるとき（通常はこちら）** |
| `-p2` | `sched.c` | ほぼ使わない |

**「ソースの直下にいるなら `-p1`」** と覚えれば、まず外しません。

## バージョンの確認

ビルドしたカーネルで正しく起動できたかは、**`uname -r`** で確かめます。

```bash
$ uname -r                                           # 今動いているカーネルのバージョンを見る
6.1.0-18-amd64
$ ls -d /lib/modules/$(uname -r)                     # 対応するモジュールのディレクトリがあるか確認する
/lib/modules/6.1.0-18-amd64
```
