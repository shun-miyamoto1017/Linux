## 起動の6段階

### 全体の流れ

**このノートで一番大事な図です。**

```text
 ① 電源ON
      │
      ▼
 ┌─────────────────────────────────────────┐
 │ ファームウェア（BIOS / UEFI）             │
 │  ・ハードウェアの初期化と自己診断          │
 │  ・起動デバイスを決めて、そこを読む        │
 └─────────────────────────────────────────┘
      │  ブートローダを読み込んで、制御を渡す
      ▼
 ┌─────────────────────────────────────────┐
 │ ブートローダ（GRUB）                      │
 │  ・起動メニューを出す                     │
 │  ・カーネルと初期RAMディスクをメモリへ読む │
 └─────────────────────────────────────────┘
      │  カーネルに制御を渡す
      ▼
 ┌─────────────────────────────────────────┐
 │ カーネル（vmlinuz）                       │
 │  ・自分自身を展開する                     │
 │  ・メモリとCPUを初期化する                │
 │  ・initramfs をメモリ上に展開する         │
 └─────────────────────────────────────────┘
      │
      ▼
 ┌─────────────────────────────────────────┐
 │ 初期RAMディスク（initramfs）              │
 │  ・必要なドライバを読み込む               │
 │  ・本物のルートファイルシステムを見つける │
 └─────────────────────────────────────────┘
      │  ルートを本物のディスクへ切り替える（switch_root）
      ▼
 ┌─────────────────────────────────────────┐
 │ 最初のプロセス（systemd = PID 1）         │
 │  ・default.target をたどってサービスを起動 │
 └─────────────────────────────────────────┘
      │
      ▼
 ⑥ ログインプロンプト
```

---

### 各段階でやっていること

| 段階 | 何をするか | 成果物・次への受け渡し |
|:--|:--|:--|
| **① ファームウェア** | ハードウェアを初期化し、自己診断（POST）を行う。**起動デバイスの順番**にしたがって、最初のセクタまたは ESP を読む | ブートローダを**メモリに読み込む** |
| **② ブートローダ** | 起動メニューを表示し、選ばれたエントリの設定を読む | **カーネルと初期RAMディスクをメモリに読み込み**、カーネルに制御を渡す |
| **③ カーネル** | 自分を展開し、メモリ・CPU・基本的なデバイスを初期化する | **initramfs を tmpfs に展開**する |
| **④ 初期RAMディスク** | `/init` が動き、**ルートFSを読むのに必要なドライバ**を読み込む | 本物のルートをマウントできる状態にする |
| **⑤ ルートの切り替え** | `switch_root` で、メモリ上の一時的なルートから**本物のルートへ**切り替える | メモリ上の一時ルートは捨てられる |
| **⑥ 最初のプロセス** | **`/sbin/init`（実体は systemd）が PID 1 として起動**し、`default.target` の依存をたどってサービスを起動する | ログインできる状態になる |

> **PID 1** … システムで**最初に起動するプロセス**で、すべてのプロセスの先祖にあたります。
> 現在の主要ディストリでは、この位置に **systemd** がいます。

### 「これは誰の仕事か」を取り違えない

**起動の話でいちばん混ざりやすいのが、ブートローダとカーネルと init の役割分担**です。
隣り合って動くので境目が見えにくく、「ブートローダがサービスを起動する」のような
**もっともらしい取り違え**が起こります。境目は次の 1 枚で押さえられます。

```text
 ファームウェア   ブートローダ        カーネル             init（systemd）
 （BIOS/UEFI）    （GRUB）            （vmlinuz）
 ─────────────   ─────────────────   ──────────────────   ────────────────────
 ハードウェアを   カーネルを          メモリ・CPU・        サービスを
 初期化する       見つけてロードする   デバイスを           起動する
                                      初期化する
 起動デバイスを   起動オプションを    initramfs を         ランレベル／ターゲット
 選ぶ             渡す                 展開する             にしたがって並べる
                  （ランレベルの指定も
                    ここで渡せる）
 ─────────────   ─────────────────   ──────────────────   ────────────────────
        「見つけて渡す」まで              「動く土台を作る」   「上物を建てる」
```

**ブートローダ（GRUB）の役割は、次の 3 つに整理できます。**

| ブートローダがやること | 具体的には |
|:--|:--|
| **カーネルイメージを見つけ、メモリにロードする** | `/boot/vmlinuz-…` と `initramfs-….img` を読み込む |
| **システムの起動オプションをカスタマイズする** | `root=` `ro` `quiet` などのカーネルパラメータを渡す。メニューで `e` を押せばその場で書き換えられる |
| **システム起動時のランレベル（ターゲット）を指定する** | 起動オプションの末尾に `3` や `single`、`systemd.unit=multi-user.target` を足す |

> **ランレベルを「指定する」のはブートローダ、「そのランレベルにしたがってサービスを起動する」のは init** です。
> ブートローダは**数字や文字列をカーネル経由で渡すだけ**で、どのサービスを上げるかは知りません。

**まちがえやすい割り当て**

| こう書かれていたら | 実際は誰の仕事か |
|:--|:--|
| ブートローダが**ランレベルに応じてサービスを自動的に起動する** | **init（systemd）** の仕事。ブートローダは**指定を渡すだけ** |
| ブートローダが**メモリを初期化する** | **カーネル**の仕事 |
| ブートローダが**ハードウェアの自己診断（POST）を行う** | **ファームウェア（BIOS / UEFI）** の仕事 |
| ブートローダが**ファイルシステムをマウントする** | **カーネル**と **initramfs** の仕事（ブートローダは読むだけで、マウントはしない） |
| カーネルが**`/etc/fstab` を読んで全部マウントする** | 起動後に **systemd**（`systemd-fstab-generator`）が行う。カーネルが自分でマウントするのは**ルートだけ** |

**init の側の役割分担**は [SysVinitの起動スクリプトとランレベル](./SysVinitの起動スクリプトとランレベル.md) の
「initがやること・やらないこと」にまとめています。

### どこで止まったかの切り分け

**コンソールに出た「最後のメッセージ」で、原因の範囲が絞れます。**

| 画面の様子 | どこで止まっているか | 次に見るもの |
|:--|:--|:--|
| **メーカーのロゴから進まない** | **① ファームウェア** | ハードウェア、起動順序の設定 |
| **`No bootable device` / `Operating System not found`** | **① → ② の受け渡し** | 起動デバイスの指定、MBR / ESP の破損 |
| **`GRUB` と出たまま止まる／`grub rescue>` が出る** | **② ブートローダ** | GRUB のインストール状態、`grub.cfg` → [GRUBの設定と復旧](./GRUBの設定と復旧.md) |
| **メニューは出るが、選ぶと何も起きない** | **② → ③** | カーネルイメージ（`/boot/vmlinuz-…`）の欠損 |
| **`Cannot open root device` / `VFS: Unable to mount root fs`** | **④ 初期RAMディスク** | ドライバ不足、`root=` の指定 → [初期RAMディスク initrdとinitramfs](./初期RAMディスク_initrdとinitramfs.md) |
| **`Kernel panic - not syncing`** | **③〜⑤** | 直前のメッセージが原因を示す |
| **文字は流れるが、途中で止まる／サービスが失敗する** | **⑥ systemd** | `systemctl --failed`、`journalctl -xb` |
| **ログインプロンプトが出ない（画面が真っ暗）** | **⑥**（`graphical.target` の失敗など） | `systemctl get-default`、ディスプレイ関連 |

**例文**

```bash
$ systemctl --failed                                 # 起動に失敗したユニットを一覧する
$ journalctl -xb                                     # 今回の起動のログを説明つきで見る
$ journalctl -k -b -1                                # 前回の起動のカーネルメッセージを見る
$ systemd-analyze blame                              # 起動に時間がかかっているユニットを調べる
$ systemd-analyze critical-chain                     # 起動を遅らせている連鎖を調べる
```

### 起動メッセージがどの段階のものか読み分ける

**`dmesg` に流れる起動メッセージは、上から順に「どの段階の話か」が切り替わっていきます。**
**行の形を見れば、その 1 行がどの段階のものか分かります。**これができると、障害の切り分けが一気に速くなります。

```bash
$ dmesg                                              # カーネルが記録した起動メッセージを見る
Bootdata ok (command line is ro root=/dev/hda1 hdd=ide-scsi)          ← ①カーネルロード時
Linux version 2.6.9-89.EL (mockbuild@builder10.centos.org) …          ← ①カーネルロード時
BIOS-provided physical RAM map:
 BIOS-e820: 0000000000000000 - 000000000009fc00 (usable)
Kernel command line: ro root=/dev/hda1 hdd=ide-scsi console=tty0      ← ①カーネルロード時
ide_setup: hdd=ide-scsi                                              ← ①カーネルロード時
Initializing CPU#0
PCI: Setting latency timer of device 0000:00:01.1 to 64
    ide0: BM-DMA at 0xc200-0xc207, BIOS settings: hda:pio, hdb:pio    ← ②ハードウェア初期化時
Probing IDE interface ide0...
hda: QEMU HARDDISK, ATA DISK drive                                   ← ②ハードウェア初期化時
ide0 at 0x1f0-0x1f7,0x3f6 on irq 14                                   ← ②ハードウェア初期化時
```

**見分け方の表**

| メッセージの形 | どの段階か | 何を意味しているか |
|:--|:--|:--|
| **`Bootdata ok (command line is …)`** | **① カーネルロード時** | **ブートローダからカーネルへ渡されたパラメータ**を、そのまま表示している |
| **`Kernel command line: …`** | **① カーネルロード時** | 同上。**実際にカーネルが受け取ったパラメータの全文** |
| **`<パラメータ名>_setup: <値>`**<br>（例 `ide_setup: hdd=ide-scsi`） | **① カーネルロード時** | **渡されたパラメータを、カーネルが実際に解釈した結果**。ここに出ていれば、そのパラメータは効いている |
| **`Linux version …`** | **① カーネルロード時** | カーネルのバージョンとビルド情報 |
| **`ide0: BM-DMA at …, BIOS settings: hda:pio, hdb:pio`** | **② ハードウェア初期化時** | **そのデバイスの DMA 設定**。`pio` は CPU 経由の転送、`DMA` は CPU を介さない直接転送 |
| **`ide0 at 0x1f0-0x1f7,0x3f6 on irq 14`** | **② ハードウェア初期化時** | **I/O ポートのアドレスと割り込み番号**（IRQ）が確定した |
| **`hda: QEMU HARDDISK, ATA DISK drive`** | **② ハードウェア初期化時** | 実際に見つかったデバイスの型名 |
| **`systemd[1]: Starting …`** | **⑥ 最初のプロセス** | systemd がサービスを起動し始めた |

> **順番は必ず「① カーネルロード → ② ハードウェア初期化 → …… → ⑥ init の初期化完了」です。**
> 上の例で `ide_setup:` が `ide0: BM-DMA …` より**前**に出ているのは、この順番どおりだからです。

**用語の補足**

| 用語 | 意味 |
|:--|:--|
| **カーネルパラメータ**（起動オプション） | **ブートローダがカーネルに渡す設定**。`root=` や `console=` など。`/proc/cmdline` でいつでも確認できる |
| **`pio`**（Programmed I/O） | **CPU が 1 バイトずつデータを運ぶ**転送方式。**遅いが、確実に動く** |
| **`DMA`**（Direct Memory Access） | **CPU を介さず、デバイスが直接メモリに読み書きする**方式。**速い**が、BIOS と機器の両方が対応している必要がある |
| **`irq`**（Interrupt ReQuest） | **デバイスが CPU に「処理してほしい」と知らせるための番号**。番号がぶつかると、機器が正しく動かないことがある |
| **`ide-scsi`** | IDE 接続の機器を **SCSI 機器のように見せかける**古いしくみ。指定すると、SCSI エミュレーション用のモジュールが組み込まれる |

**例文**

```bash
$ cat /proc/cmdline                                  # いまのカーネルが受け取ったパラメータを見る
BOOT_IMAGE=/vmlinuz-6.1.0-18-amd64 root=UUID=52ab… ro quiet

$ dmesg | grep -i "command line"                     # 起動メッセージ側からも同じ内容を確認する
$ dmesg | head -40                                   # ①カーネルロード時のメッセージを頭から読む
$ dmesg | grep -iE "irq|dma"                         # ②ハードウェア初期化時の割り当てを拾う
```

**補足**

- **「パラメータを足したのに効かない」ときは、`/proc/cmdline` を見るのが最短です。** ここに出ていなければ、そもそもカーネルに届いていません（＝ブートローダ側の書き方の問題）
- **`dmesg` の内容を詳しく読む方法**は [カーネルの実行時管理 dmesgとsysctl](./カーネルの実行時管理_dmesgとsysctl.md) にまとめています

### journalctl で systemd 側の起動を読み分ける

**`dmesg` が①〜⑤（カーネルまで）なら、`journalctl` は⑥（systemd 以降）です。**
**どのターゲットまで到達したかを追えば、止まった位置がそのまま分かります。**

> **ターゲット**（`.target`）… **複数のユニットをまとめたグループ**で、**起動の「区切り」**を表します。
> 「ここまで来た」という節目だと考えてください。

**ターゲットの到達順**

```text
  systemd 起動（PID 1）
      │
      ▼
  local-fs.target      ← /etc/fstab のローカルディスクをマウントし終えた
      │
      ▼
  sysinit.target       ← 初期化が終わった（swap、tmpfiles、udev など）
      │
      ▼
  basic.target         ← ソケットとタイマーの準備が終わった。ここから一般サービス
      │
      ▼
  multi-user.target    ← CUI で使える状態（サーバはここが終点）
      │
      ▼
  graphical.target     ← GUI まで上がった
```

**出力の行の形で読み分ける**

```bash
$ journalctl -xb --no-pager                          # 今回の起動のログを説明つきで頭から読む
systemd[1]: Reached target local-fs.target - Local File Systems.
systemd[1]: Starting systemd-udevd.service - Rule-based Device Manager...
systemd[1]: Started systemd-udevd.service - Rule-based Device Manager.
systemd[1]: Reached target sysinit.target - System Initialization.
systemd[1]: Starting nginx.service - The nginx HTTP server...
systemd[1]: nginx.service: Main process exited, code=exited, status=1/FAILURE
systemd[1]: Failed to start nginx.service - The nginx HTTP server.
systemd[1]: Dependency failed for myapp.service - My API server.
```

| 行の形 | 何を意味するか | どう読むか |
|:--|:--|:--|
| **`Reached target <名前>`** | **その区切りまで到達した** | **最後に出た `Reached target` が、到達できた一番先の地点**。ここから先で止まっている |
| **`Starting <ユニット>...`** | **起動を開始した**（末尾が `...`） | **`Started` が対になって出ていなければ、そこで固まっている** |
| **`Started <ユニット>`** | **起動が完了した** | 正常。対の `Starting` とセットで見る |
| **`Failed to start <ユニット>`** | **起動に失敗した** | **原因はこの行の直前**にある。`Main process exited` などを見る |
| **`Dependency failed for <ユニット>`** | **依存先が失敗したので、こちらは実行されなかった** | **このユニット自体は悪くない**。失敗した依存先をたどる |
| **`<ユニット>: Main process exited, code=…, status=…`** | **本体のプロセスが終了した** | `status=` の値が原因の手がかり（`203/EXEC` はパス誤りなど） |
| **`Timed out waiting for device …`** | **デバイスを待って時間切れになった** | **`/etc/fstab` に無いディスクを書いた**ときの定番 |
| **`Job <ユニット>/start timed out`** | **起動が既定の時間内に終わらなかった** | `TimeoutStartSec=` か、アプリ側の起動処理を疑う |
| **`Startup finished in …`** | **起動処理が全部終わった** | ここまで出ていれば systemd 側は完走している |

> **いちばん速い読み方は「最後の `Reached target` を探す」ことです。**
> `sysinit.target` で止まっていればディスクや udev、`basic.target` の先で止まっていれば個々のサービスが原因、
> という具合に、**次に見る場所が一手で決まります。**

**調べるときに使うオプション**

| 書き方 | 意味 |
|:--|:--|
| **`journalctl -xb`** | **今回の起動のログを、説明文つきで表示する**（`-x` が説明、`-b` が今回の起動） |
| **`journalctl -b -1`** | **1 つ前の起動のログを見る**（落ちて再起動したあとの調査で必須） |
| **`journalctl --list-boots`** | **記録が残っている起動の一覧**（`-1` などの番号を確認する） |
| **`journalctl -b -p err`** | **今回の起動の、エラー以上だけに絞る** |
| **`journalctl -k -b`** | **今回の起動の、カーネルのメッセージだけ**（＝`dmesg` と同じ範囲） |
| **`journalctl -u <ユニット> -b`** | **そのユニットの、今回の起動分だけ** |
| **`journalctl -b -o short-monotonic`** | **起動からの経過秒で表示する**（どこで時間を食ったか分かる） |

```bash
$ journalctl -xb --no-pager | grep "Reached target"  # どこまで到達したか一覧する
$ journalctl -xb -p err --no-pager                   # 今回の起動のエラーだけ拾う
$ journalctl --list-boots | tail -3                  # 直近の起動履歴を確認する
$ journalctl -b -1 -p err --no-pager                 # 前回の起動で出たエラーを見る
$ systemctl list-jobs                                # いま待ち状態で止まっているジョブを見る
```

**補足**

- **`-b -1` が「記録がない」と言われる場合、journal が永続化されていません。** 既定ではメモリ上（`/run/log/journal`）に置かれ、**再起動で消える**ことがあります。`/var/log/journal` を作って永続化すると、前回の起動を追えるようになります
- **`Dependency failed` が並んでいるときは、一番上の `Failed to start` だけを追ってください。** 下は巻き添えなので、原因ではありません
- **起動が遅いときは `systemd-analyze blame` と `critical-chain`** が、どのユニットが足を引っ張っているかを直接教えてくれます

### ルートファイルシステムが二度マウントされる理由

**起動中、ルートファイルシステムは「まず読み込み専用で、次に読み書き可で」と二度マウントされます。**
一見むだに見えますが、**ファイルシステムの検査（`fsck`）を安全に行うため**の手順です。

> **`fsck`**（File System ChecK）… **ファイルシステムの不整合を検査し、修復するコマンド**です。
> 起動時に自動で実行され、前回の停止が正常でなかった場合などに、壊れかけた状態を直します。

**なぜ読み込み専用でなければならないのか**

```text
   検査・修復をしている最中に、誰かが同じファイルシステムに書き込むと……

     fsck が「ここを直そう」と読んだ内容と、
     実際のディスクの内容が食い違う
              ↓
     直したつもりが、かえって整合性が崩れる
              ↓
     状態がさらに悪化する
```

**だから、書き込みが起きない状態を作ってから検査します。** 方法は 2 つあります。

| 方法 | どういうときに使うか |
|:--|:--|
| **アンマウントしておく** | ルート以外のファイルシステム。外してから `fsck` をかけられる |
| **`ro` オプションで読み込み専用としてマウントする** | **ルートファイルシステム**。**起動中は外せない**ので、こちらを使う |

**起動時の流れ**

```text
 ① ルートファイルシステムを  ro（読み込み専用）でマウントする
        │       ← この状態なら、誰も書き込めない
        ▼
 ② fsck で検査・修復する
        │
        ▼
 ③ 問題がなければ  rw（読み書き可）で再マウントする
        │       ← ここではじめてログの書き込みなどができるようになる
        ▼
 ④ 通常のサービス起動へ進む
```

> **ブートローダのカーネル行に `ro` と書かれているのは、このためです。**
> `grub.cfg` の `linux /boot/vmlinuz-… root=/dev/sda1 **ro**` の `ro` が、①の指定にあたります。

**例文**

```bash
$ cat /proc/cmdline                                  # 起動時に ro が渡されているか確認する
BOOT_IMAGE=/vmlinuz-6.1.0-18-amd64 root=UUID=52ab… ro quiet

$ mount | grep " / "                                 # 今のルートのマウント状態を見る
/dev/sda1 on / type ext4 (rw,relatime)               # 起動が終わった今は rw になっている

$ sudo mount -o remount,rw /                         # 読み込み専用のまま止まったときの復帰
$ sudo tune2fs -l /dev/sda1 | grep -i "mount count"  # 次にいつ自動 fsck が走るか確認する
```

**補足**

- **`remount`** … すでにマウントされているものを、**外さずにオプションだけ変える**指定です。緊急モードで作業するときの定番です
- **起動後もルートが `ro` のままなら、`fsck` が異常を見つけて止まっている可能性があります。** `dmesg` と `journalctl -xb` に `EXT4-fs error` などが出ていないか確認してください
- **CD-ROM を扱うためではありません。** 読み込み専用にする理由は、あくまで**検査中の書き込みを防ぐため**です

## ファームウェアとMBRは別ノートにある

**BIOS と UEFI の違い、ESP、MBR の構造、GPT** は
[BIOSとUEFI](./BIOSとUEFI.md) にまとめています。

| 知りたいこと | 見るところ |
|:--|:--|
| **BIOS と UEFI で何が違うか**（ブートローダの置き場所、扱えるディスク容量） | [BIOSとUEFI](./BIOSとUEFI.md) |
| **ESP とは何か**（FAT16 / FAT32、`/boot/efi`、`efibootmgr`） | 同上 |
| **MBR の 512 バイトの内訳**と、`dd bs=446` でのブートローダ復元 | 同上 |
| **第1段階／第2段階ブートローダに分かれる理由** | 同上 |
| **MBR と GPT の違い** | 同上 |

**このノートで押さえるのは、①ファームウェア → ②ブートローダの受け渡しだけ**です。

```text
 ① ファームウェア（BIOS / UEFI）
      │  BIOS  … ディスク先頭の MBR を読む
      │  UEFI  … ESP の中の .efi ファイルを読む
      ▼
 ② ブートローダ（GRUB）
```

**いまどちらで起動しているか**

```bash
$ ls /sys/firmware/efi               # このディレクトリがあれば UEFI で起動している
```

## 最初のプロセスとブートターゲット

### init と systemd

ルートファイルシステムに切り替わると、カーネルは **`/sbin/init`** を実行します。
これが **PID 1** になり、以降のサービス起動を受け持ちます。

| | **SysVinit**（古い方式） | **systemd**（現在の主流） |
|:--|:--|:--|
| **状態の呼び方** | **ランレベル**（0〜6 の数字） | **ターゲット**（`multi-user.target` などの名前） |
| **設定ファイル** | `/etc/inittab` | ユニットファイル（`/etc/systemd/system/` など） |
| **起動のしかた** | **スクリプトを順番に**実行する | **依存関係を見て並列に**起動する |
| **既定の状態** | `/etc/inittab` の `initdefault` 行 | **`default.target`**（シンボリックリンク） |

> **`/sbin/init` は、現在のディストリでは systemd へのシンボリックリンク**になっています。
>
> **SysVinit 側のしくみ**（`/etc/init.d/` の起動スクリプト、`/etc/rc3.d/S55sshd` のリンク、`/etc/inittab`、`chkconfig`）は
> [SysVinit の起動スクリプトとランレベル](./SysVinitの起動スクリプトとランレベル.md) にまとめています。

```bash
$ ls -l /sbin/init                                   # init の実体を確認する
lrwxrwxrwx 1 root root 20 Jan 1 00:00 /sbin/init -> /lib/systemd/systemd
$ ps -p 1 -o pid,comm                                # PID 1 が何かを確認する
  PID COMMAND
    1 systemd
```

### ランレベルとターゲットの対応

**試験でも実務でも、この対応表がそのまま問われます。**

| ランレベル | `runlevel*.target` | **systemd のターゲット** | 意味 |
|:-:|:--|:--|:--|
| **0** | `runlevel0.target` | **`poweroff.target`** | **シャットダウンして電源を切る** |
| **1** | `runlevel1.target` | **`rescue.target`** | **シングルユーザモード**（レスキューシェル） |
| **2** | `runlevel2.target` | `multi-user.target` | マルチユーザ（GUI なし）。SysVinit 時代の RHEL 系では**ネットワークファイル共有（NFS）なし**の意味だった |
| **3** | `runlevel3.target` | **`multi-user.target`** | **同上。サーバの標準** |
| **4** | `runlevel4.target` | `multi-user.target` | 同上（未使用の枠） |
| **5** | `runlevel5.target` | **`graphical.target`** | **マルチユーザ + GUI（ディスプレイマネージャあり）** |
| **6** | `runlevel6.target` | **`reboot.target`** | **再起動** |

> **`runlevel*.target` は、互換のためのシンボリックリンク**です。実体は右側のターゲットです。
>
> **覚え方**
>
> ```text
>   0 … 電源OFF   （0 = ゼロ＝止まる）
>   1 … レスキュー （1人＝シングルユーザ）
>   3 … CUI       （サーバはここ）
>   5 … GUI       （3 より上＝画面つき）
>   6 … 再起動    （0 と 6 が特殊な両端）
> ```

---

### ターゲットの確認と変更

| やりたいこと | コマンド |
|:--|:--|
| **既定のターゲットを確認する** | **`systemctl get-default`** |
| **既定のターゲットを変更する** | **`sudo systemctl set-default multi-user.target`** |
| **今すぐ切り替える** | **`sudo systemctl isolate multi-user.target`** |
| **レスキューモードに入る** | **`sudo systemctl rescue`** |
| **緊急モードに入る** | **`sudo systemctl emergency`** |
| **再起動する** | `sudo systemctl reboot` |
| **電源を切る** | `sudo systemctl poweroff` |

**例文**

```bash
$ systemctl get-default                              # 既定のターゲットを確認する
graphical.target

$ sudo systemctl set-default multi-user.target       # サーバ用にGUIなしを既定にする
$ sudo systemctl isolate multi-user.target           # 再起動せずに今すぐ切り替える
$ systemctl list-units --type=target                 # 今動いているターゲットを一覧する
$ ls -l /etc/systemd/system/default.target           # 既定のターゲットの実体を見る
```

**補足**

- **`set-default` は次回起動から、`isolate` は今すぐ**です。ここを取り違えると「変えたのに戻らない」ことになります
- `isolate` は「**指定したターゲットとその依存だけを動かし、それ以外を止める**」という意味です

### レスキューモードと緊急モード

**起動しなくなったときに入る 2 つのモード**です。**緊急モードのほうが最小限**です。

| | **レスキューモード**（`rescue.target`） | **緊急モード**（`emergency.target`） |
|:--|:--|:--|
| **ランレベルでいうと** | **1**（シングルユーザ） | — |
| **ルートファイルシステム** | **マウント済み**（読み書き可） | **読み取り専用でマウントされるだけ** |
| **他のファイルシステム** | マウントされる | **マウントされない** |
| **サービス** | 基本的なものだけ起動する | **ほぼ何も起動しない** |
| **ネットワーク** | 使えないことが多い | **使えない** |
| **使いどころ** | パスワード再設定、設定ファイルの修正 | **レスキューでも起動しないとき** |

**緊急モードで書き込みたいときは、読み書き可で再マウントします。**

```bash
$ mount -o remount,rw /                              # ルートを読み書き可でマウントし直す
$ vi /etc/fstab                                      # 設定を修正する
$ mount -a                                           # fstab の記述を試す（エラーが出ないか確認）
$ systemctl reboot                                   # 再起動する
```

> 起動時にこれらのモードへ入る方法（GRUB のメニューでカーネルパラメータを足す）は
> [GRUBの設定と復旧](./GRUBの設定と復旧.md) にまとめています。

## 起動時間の分析

`systemd-analyze` を使うと、**どこで時間がかかっているか**が分かります。

**例文**

```bash
$ systemd-analyze                                    # 起動全体の内訳を見る
Startup finished in 3.201s (kernel) + 8.442s (userspace) = 11.644s

$ systemd-analyze blame | head                       # 時間のかかったユニット順に並べる
$ systemd-analyze critical-chain                     # 起動を遅らせている依存の連鎖を見る
$ systemd-analyze plot > boot.svg                    # 起動の様子を図（SVG）に出力する
```

**結果画面の見方**

| 表示 | 意味 | どこを見るか |
|:--|:--|:--|
| **`(firmware)`** | ファームウェアにかかった時間 | 長ければ BIOS / UEFI の設定 |
| **`(loader)`** | ブートローダの待ち時間 | **GRUB のタイムアウト設定**が効く |
| **`(kernel)`** | カーネルの初期化と initramfs | 長ければドライバの読み込み |
| **`(initrd)`** | 初期RAMディスクの処理 | ストレージ関連 |
| **`(userspace)`** | **systemd がサービスを起動した時間** | **`blame` で内訳を見る** |
