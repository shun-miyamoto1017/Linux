## そもそも何をしたいのか

**金融系などの本番サーバは、インターネットに出られないことがよくあります。**
でも CVE（脆弱性）対応では、Red Hat が出した修正版の RPM を当てなければいけません。

**やりたいこと**

```text
  [ インターネットに出られる端末 ]        [ 本番サーバ（オフライン） ]
     Red Hat カスタマーポータル
            │ RPM をダウンロード
            ▼
       手元のファイル   ──── scp / USB ────▶   /opt/localrepo に置く
                                                      │
                                                      ▼
                                          依存関係ごと、まとめて当てる
```

**素朴にやると失敗します。**

```bash
$ sudo rpm -ivh openssh-server-8.7p1-43.el9.x86_64.rpm   # rpm で直接入れようとすると…
```

```text
error: Failed dependencies:
	libcrypto.so.3(OPENSSL_3.0.9)(64bit) is needed by openssh-server-8.7p1-43.el9.x86_64
```

**`rpm` コマンドは依存関係を自分で探してくれません。**「足りない」と言って止まるだけです。
そこで、**持ち込んだ RPM の置き場所を「リポジトリ」に見せかけて、`dnf` / `yum` に依存解決をやらせます。**
これが**ローカルリポジトリ**です。

## 本と目次のたとえ

| もの | たとえ | 役割 |
|:--|:--|:--|
| RPM ファイル | **本** | パッケージ本体 |
| **`repodata/`**（メタデータ） | **目次・索引** | 「どのパッケージが、どのバージョンで、何に依存しているか」の一覧 |
| `/etc/yum.repos.d/*.repo` | **図書館の案内板** | 「本棚はここにあるよ」と `dnf` / `yum` に教える設定 |
| `dnf` / `yum` | **司書** | 目次を読んで、必要な本をまとめて持ってきてくれる |

**ここがいちばん大事です。`dnf` / `yum` は RPM ファイルを直接見ません。目次だけを読んで判断します。**

```text
  dnf が見るもの                  dnf が見ないもの
  ┌──────────────────┐          ┌──────────────────┐
  │ /opt/localrepo/  │          │ /opt/localrepo/  │
  │   repodata/      │  ◀━━━━   │   *.rpm          │
  │     repomd.xml   │  読む     │                  │  ← 置くだけでは
  │     *-primary.xml│          │                  │     認識されない
  └──────────────────┘          └──────────────────┘
```

だから **RPM をフォルダに置くだけでは使えず、`createrepo`（RHEL 8 以降は `createrepo_c`）で目次を作る**必要があります。
そして **RPM を追加・削除したら、目次も作り直さないといけません。**

> **`createrepo` は目次を作るだけ**です。**RPM の中身や署名には一切触りません。**
> 「`createrepo` を通したから安全」ということはありません。署名確認は別にやります。

## 全体の流れ

```text
  ① RPM を取得       Red Hat カスタマーポータル（オンライン端末）
         │
  ② 転送             scp / WinSCP / USB
         │
  ③ 署名確認         rpm -K ＋ 署名が入っているかの確認（★ここに落とし穴あり）
         │
  ④ 目次を作る       createrepo_c /opt/localrepo
         │
  ⑤ 登録（初回のみ） /etc/yum.repos.d/localrepo.repo を書く
         │
  ⑥ キャッシュを消す  dnf clean all
         │
  ⑦ 下見             dnf --repo=localrepo upgrade --assumeno
         │
         ├─ 依存不足 ─▶ 足りない RPM を追加取得 → ③へ戻る（繰り返し）
         │
  ⑧ 適用             dnf --repo=localrepo upgrade
         │
  ⑨ 動作確認         バージョン確認・サービス確認・新規ログイン確認
```

**③〜⑦がぐるぐる回ります。**1 回で依存が閉じることはまずありません。

## yum と dnf の違い早見表

**RHEL 7.9 と RHEL 8 以降で、コマンド名と画面の文字が変わります。**
手順書を使い回すときはここを確認してください。

| 項目 | RHEL 7.9（yum v3） | RHEL 8 以降（dnf） |
|:--|:--|:--|
| **コマンド** | `yum` | `dnf`（`yum` と打っても中身は `dnf`） |
| **更新サブコマンド** | `update` | **`upgrade`**（`update` も通るが、公式は「非推奨の別名」に分類） |
| **目次作成ツール** | `createrepo` | **`createrepo_c`**（C 言語実装で高速） |
| **下見が正常終了したときの表示** | **`Exiting on user command`** | **`Operation aborted.`** |
| **依存不足エラーの形** | **`Requires: xxx`** | **`nothing provides xxx needed by yyy`** |
| **リポジトリを 1 つに絞る書き方** | `--disablerepo='*' --enablerepo=ID` | 左と同じ、または **`--repo=ID`** |
| **履歴** | `yum history` | `dnf history` |
| **モジュール（Modularity）** | なし | **あり**（後述） |
| **`best` 設定** | なし | **あり。依存不足のときの画面が変わる**（後述） |

> **`update` を `upgrade` の別名として使うのは避けてください。**
> DNF 公式のコマンドリファレンスは、`upgrade` の項に
> **`Deprecated aliases: update, upgrade-to, update-to, localupdate`** と書いています。
> 詳しくは [dnf解説① 基本とインストール系コマンド](../07_パッケージ管理/dnf解説①_基本とインストール系コマンド.md) に。

## 各ステップの「なぜ」

### なぜ目次を作り直すのか

`dnf` / `yum` は目次しか見ません。**RPM を 1 本足しても、目次を作り直さないと「無いもの」として扱われます。**

```bash
$ sudo createrepo_c /opt/localrepo             # 初回：目次をゼロから作る
$ sudo createrepo_c --update /opt/localrepo    # 2回目以降：差分だけ更新するので速い
$ ls /opt/localrepo/repodata/                  # repomd.xml などができているか見る
```

**「RPM を追加したのに同じエラーが出続ける」のは、ほぼこれの忘れです。**

### なぜキャッシュを消すのか

`dnf` / `yum` は、**前回読んだ目次を覚えています**（キャッシュ）。

```bash
$ sudo dnf clean all          # RHEL 8 以降
$ sudo yum clean all          # RHEL 7.9
```

目次を作り直したあとにキャッシュを消さないと、**古い目次のまま判断してしまうことがあります。**
そのため **`createrepo` とセットで毎回実行**します。

> **`metadata_expire` の既定値は 48 時間**です（DNF 公式 Configuration Reference：「The default corresponds to 48 hours.」）。
> つまり **放っておくと最大 2 日間、古い目次を使い続けます。**
> `clean all` の代わりに `--refresh` を付けても同じ効果が得られます。

### .repo ファイルの書き方

```ini
[localrepo]                     ← リポジトリID（コマンドで指定する名前）
name=Local Repo                 ← 表示名（人間が読む用）
baseurl=file:///opt/localrepo   ← ネットではなくローカルのフォルダを見る
enabled=1                       ← 有効にする
gpgcheck=1                      ← インストール時にも署名を確認する
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
```

| 行 | 初心者がつまずくところ |
|:--|:--|
| **`baseurl=file:///opt/...`** | **スラッシュが 3 つ**になります。`file://` のあとに絶対パス `/opt/...` が続くためです。`file://opt/...`（2 つ）は間違いです |
| **`gpgcheck=1`** | **必ず 1 にしてください。**インストールの瞬間にも署名を確認してくれます。`0` にすると、署名のない RPM が黙って入ります |
| **`gpgkey=`** | `gpgcheck=1` のときに使う公開鍵の置き場所。**RHEL 9.7 以降は鍵が増えています**（後述） |
| **ファイル名** | `/etc/yum.repos.d/何でも.repo` でよく、**リポジトリID と同じ名前でなくても動きます** |

> **設定ファイルの置き場所は、RHEL 8 以降も `/etc/yum.repos.d/` のまま**です。
> `dnf` になっても `/etc/dnf.repos.d/` にはなっていません。

### なぜ --disablerepo='*' を付けるのか

```bash
$ sudo dnf --disablerepo='*' --enablerepo=localrepo upgrade --assumeno   # 長い書き方
$ sudo dnf --repo=localrepo upgrade --assumeno                           # dnf なら短くこう書ける
```

- 「**いったん全リポジトリを無効化 → ローカルリポジトリだけ有効化**」という意味です
- **オフラインサーバでは、届かないリポジトリを見に行って待たされたりエラーになったりします。**これで防ぎます
- **`'*'` をシングルクォートで囲むのは、シェルが `*` をファイル名に展開してしまうのを防ぐため**です

> **`--disablerepo` と `--repo` は併用できません。**実測のエラーです。
>
> ```text
> Command line error: argument --repo/--repoid: not allowed with argument --disablerepo
> ```
>
> **`--repo=ID` だけで「そのリポジトリだけ使う」意味になる**ので、`--disablerepo` は不要です。

### --assumeno は「下見」専用のオプション

```bash
$ sudo dnf --repo=localrepo upgrade --assumeno    # 何が起きるかだけ見て、実行しない
```

- 確認プロンプト `Is this ok [y/N]:` に **自動で No と答える**オプションです
- **依存関係の解決までは本当にやる**ので、次のことが**システムを変更せずに**分かります
  - 何が、どのバージョンに更新されるか
  - 依存が足りているか
- DNF 公式の記載は **`Automatically answer no for all questions.`** です

**終了ステータスは 1 になります**（実測）。中止したからです。

```bash
$ sudo dnf --repo=localrepo upgrade --assumeno >/dev/null ; echo "exit=$?"   # 終了ステータスだけ見る
```

```text
exit=1
```

> **`set -e` を書いたスクリプトの中で呼ぶと、そこで止まります。**`|| true` などで受け止めてください。
> なお **`--assumeno` は rpm のダウンロードもしません**。解決結果を表示するだけです。
> **「オフライン用のオプション」ではありません。**オンラインでも使えるドライラン用のオプションです。

### パッケージ名を付けるか、付けないか

| 書き方 | 確認の対象 | 使いどころ |
|:--|:--|:--|
| `dnf ... upgrade --assumeno 'openssh*'` | **openssh 系だけ** | 特定パッケージだけ更新するとき |
| `dnf ... upgrade --assumeno` | **ローカルリポジトリの全 RPM** | **CVE 対応で集めた RPM をまとめて更新するとき** |

**⚠️ ここは事故が起きやすいところです。**
**99 本まとめて適用するつもりなのに `'openssh*'` だけで下見すると、残り 98 本の依存は確認されません。**
**本番と同じ範囲で下見してください。**

**パッケージ名を付けるときは、必ずクォートで囲みます。**

```bash
$ sudo dnf upgrade 'openssh*'    # ○ dnf にそのまま渡される
$ sudo dnf upgrade openssh*      # △ カレントに openssh-xxx.rpm があると、シェルがファイル名に展開してしまう
```

## 署名の仕組みと、rpm -K の落とし穴

**ここがこのノートでいちばん大事な節です。**
元になった手順書には、**署名のない RPM を素通りさせてしまう穴**がありました。

### たとえると「ハンコ」と「印鑑証明」

| もの | たとえ | 持っている人・場所 |
|:--|:--|:--|
| **秘密鍵** | 実印 | **Red Hat だけ**（外には出さない） |
| **署名** | 書類に押されたハンコ | **RPM ファイルの中**に埋め込まれている |
| **公開鍵** | 印鑑証明 | 誰でも持てる。サーバの `/etc/pki/rpm-gpg/` にある |

```text
  Red Hat : RPM を作る → 秘密鍵で署名 → ポータルで公開
     │
     ▼
  あなた  : ダウンロード → 転送 → rpm -K で検証（公開鍵を使う）
     │
     ▼
  createrepo_c : RPM を読んで目次を作るだけ（署名には触らない）
```

- 署名は **Red Hat が公開する前に RPM の中に埋め込んでいます**。あなたや `createrepo_c` が署名するわけではありません
- `rpm --import` は、公開鍵を「**信頼する鍵**」として rpm に登録する操作です

### rpm -K の 4 パターン（実測）

**検証環境（rpm 4.18.2）で、4 つの状態を実際に作って確かめました。**

| RPM の状態 | `rpm -K` の出力 | 終了ステータス |
|:--|:--|:--|
| 署名あり・鍵登録済み・壊れていない | **`digests signatures OK`** | **0** |
| 署名あり・**鍵が未登録** | **`digests SIGNATURES NOT OK`** | 1 |
| 署名あり・**壊れている** | **`DIGESTS SIGNATURES NOT OK`** | 1 |
| **署名が入っていない**・壊れていない | **`digests OK`** | **0** |
| 署名が入っていない・壊れている | **`DIGESTS NOT OK`** | 1 |

### 落とし穴：署名のない RPM は素通りする

**4 行目を見てください。署名が入っていない RPM は `digests OK`、終了ステータス 0 です。**
「`NOT OK` が出ていないか」だけを見る確認方法では、**何も検出できません。**

```bash
$ rpm -K /opt/localrepo/*.rpm                           # 署名なしの RPM を1本混ぜてみた
```

```text
/opt/localrepo/appx-1.0-1.noarch.rpm: digests signatures OK
/opt/localrepo/libbar-1.1-1.noarch.rpm: digests signatures OK
/opt/localrepo/libbaz-1.1-1.noarch.rpm: digests OK          ← 署名が無い
```

```bash
$ rpm -K /opt/localrepo/*.rpm | grep -E 'NOT OK|MISSING'   # よく使われる確認方法
```

```text
（何も表示されない）
```

**「何も表示されない＝OK」と判断すると、署名のない RPM がそのままリポジトリに入ります。**
**署名が無いということは「Red Hat が出したものだと確認できない」という意味**なので、これは見逃せません。

> **なぜ `digests OK` なのか。**
> `rpm -K` は「**ダイジェスト（壊れていないか）**」と「**署名（誰が作ったか）**」の 2 つを見ます。
> **署名が入っていない RPM には、検証する署名が存在しない**ので、ダイジェストだけを見て OK を返します。
> **「確認しなかった」ことが「問題なし」として出てくる**のが、この落とし穴の正体です。

### 正しい確認方法：署名があることを「肯定的に」確かめる

**「NG が出ていないこと」ではなく「署名が入っていること」を確認します。**

```bash
$ rpm -K /opt/localrepo/*.rpm | grep -Ei 'NOT OK|MISSING KEYS'   # ① 壊れ・鍵違いを拾う（何も出なければOK）
$ for f in /opt/localrepo/*.rpm; do \
    printf '%-40s %s\n' "$(basename "$f")" "$(rpm -qpi "$f" 2>/dev/null | sed -n 's/^Signature *: *//p')"; \
  done                                                            # ② 署名そのものを1本ずつ表示する
```

実測の表示です。

```text
appx-1.0-1.noarch.rpm                    RSA/SHA512, Tue Oct 13 12:51:52 2026, Key ID c4ce0ed6bfbfa33c
libbar-1.1-1.noarch.rpm                  RSA/SHA512, Tue Oct 13 12:51:52 2026, Key ID c4ce0ed6bfbfa33c
libbaz-1.1-1.noarch.rpm                  (none)                                    ← 署名なしが一目で分かる
```

| 表示 | 意味 | 判断 |
|:--|:--|:--|
| **`RSA/SHA512, ..., Key ID xxxxxxxxxxxxxxxx`** | 署名が入っている | Key ID を Red Hat 公式の一覧と照合する |
| **`(none)`** | **署名が入っていない** | **使わない。取り直す** |

**①と②の両方をやってください。**①だけでは署名なしを拾えず、②だけでは壊れを拾えません。

### 「Red Hat の正規品」まで言い切るには

`rpm -K` が見ているのは「**登録済みの鍵のどれか**で署名されているか」です。
EPEL など Red Hat 以外の鍵も登録してあると、**その鍵で署名された RPM でも `OK` になります。**

そこで、**作業前に 1 回、登録されている鍵を確認**します。

```bash
$ rpm -q gpg-pubkey --qf '%{VERSION}\t%{SUMMARY}\n'   # 登録済みの公開鍵を一覧する
```

| 部分 | 意味 |
|:--|:--|
| `rpm -q gpg-pubkey` | 登録済みの公開鍵を問い合わせる（**rpm は鍵を `gpg-pubkey` という特別なパッケージとして管理**している） |
| `--qf '...'` | 表示の形を指定する（query format） |
| **`%{VERSION}`** | **短い鍵ID（8桁）** |
| **`%{SUMMARY}`** | **鍵の持ち主の名前** |

実測の表示です（検証環境で作った自前の鍵）。

```text
bfbfa33c	Test Signer <test@example.local> public key
```

> **`gpg(Red Hat, Inc. ...)` という形の表示例を見かけますが、それは `%{SUMMARY}` ではありません。**
> 実測では `%{SUMMARY}` は **`<持ち主> public key`** の形で、
> **`gpg(<持ち主>)` の形は `%{PROVIDENAME}`**（パッケージが提供する能力名）の値でした。
>
> ```text
> $ rpm -q gpg-pubkey --qf '%{VERSION}\t%{PROVIDENAME}\n'
> bfbfa33c	gpg(Test Signer <test@example.local>)
> ```
>
> **どちらでも持ち主の名前は読めるので、確認目的ならどちらでもかまいません。**

### 鍵IDが 8 桁と 16 桁の 2 種類出てくる理由

**同じ鍵なのに、場所によって桁数が違います。**

```text
  rpm -q gpg-pubkey の %{VERSION}  →  bfbfa33c            （8桁）
  rpm -qpi の Key ID               →  c4ce0ed6bfbfa33c    （16桁）
                                           └──────┘
                                        16桁の末尾8桁が、8桁版と同じ
```

**16 桁の末尾 8 桁を見れば対応が取れます。**Red Hat 公式の一覧も 16 桁（と指紋）で載っています。

### Red Hat の鍵ID一覧（公式。2026-10-13 時点）

**Red Hat 公式「Product Signing Keys」に載っている、RPM の署名に使う鍵**です。
**どの鍵が入っているかは RHEL のバージョンで違います。**

| 鍵の名前 | 鍵ID（16桁 / 8桁） | 入っている RHEL |
|:--|:--|:--|
| **Red Hat, Inc. (release key 2)** | `199e2f91fd431d51` / **`fd431d51`** | **RHEL 6 / 7 / 8 / 9 / 10**（これが本命） |
| **Red Hat, Inc. (release key 4)** ※post-quantum | `d246d6276afedf8f` / **`6afedf8f`** | **RHEL 9.7 / 10.1**（2025年10月以降リリース分） |
| Red Hat, Inc. (auxiliary key) | `45689c882fa658e0` / **`2fa658e0`** | RHEL 5 / 6 / **7** |
| Red Hat, Inc. (auxiliary key 2) | `f76f66c3d4082792` / **`d4082792`** | **RHEL 8** |
| Red Hat, Inc. (auxiliary key 3) | `5054e4a45a6340b3` / **`5a6340b3`** | **RHEL 9 / 10** |

**`auxiliary key`（補助鍵）は、Red Hat が「災害復旧用」と説明している鍵**です。
ふだんの RPM はこれで署名されていませんが、**鍵としては登録されています。**
だから **`rpm -q gpg-pubkey` に 2 つ以上出てくるのが正常**です。

> **`Container Ready Key 1`（`1c711042`）は、公式に
> 「should NOT be enabled for YUM/DNF usage」と書かれています。**
> この鍵が登録されていたら、なぜ入っているのかを確認してください。

### RHEL 9.7 以降は署名の仕組みが増えている

**2025年10月以降にリリースされた RPM には、従来の RSA 署名に加えて
post-quantum（耐量子計算機暗号）の署名が付くようになりました。**

| RHEL | 対応状況（公式の記載） |
|:--|:--|
| **RHEL 9.6 以前** | **「the RPM utility verified only RPMv4 signatures.」**（従来の署名だけ） |
| **RHEL 9.7 以降** | **`dnf install dnf-plugin-multisig` を入れると RPMv6 署名に対応** |
| **RHEL 10.1 以降** | **「RPM provides native support for RPMv6 signatures」**（プラグイン不要） |

- 鍵ファイルも増えています。**`RPM-GPG-KEY-redhat-release` と `RPM-GPG-KEY-PQC-redhat-release`** の 2 つを
  `redhat-release` パッケージが配ります
- RHEL 9.7 以降で検証するコマンドは **`/usr/lib/pqrpm/bin/rpmkeys -Kv <ファイル>`** です
- 成功時の表示例（公式より）
  ```text
  Header V6 ML-DSA-87+Ed448/SHA512 Signature, key ID 05707a62: OK
  Header V4 RSA/SHA256 Signature, key ID fd431d51: OK
  ```

**対象サーバが RHEL 9.7 以降なら、公開鍵のインポートを `RPM-GPG-KEY-redhat-release` だけで済ませないでください。**

## エラータとは

**Red Hat が出す「修正のお知らせ」と「修正パッケージ一式」のセット**です。
**1 つのエラータに、関連する RPM が複数まとめて入っています。**

| 種類 | 正式名 | 意味 |
|:--|:--|:--|
| **RHSA** | Security Advisory | **セキュリティ修正。CVE 対応はこれ** |
| RHBA | Bug Fix Advisory | バグ修正 |
| RHEA | Enhancement Advisory | 機能追加 |

例として、openssl の CVE を直す RHSA には次の RPM が**同じバージョンで**まとめて入っています。

```text
  openssl          3.0.7-27.el9
  openssl-libs     3.0.7-27.el9
  openssl-devel    3.0.7-27.el9
  openssl-perl     3.0.7-27.el9
```

### なぜ「仲間ごと取る」のが大事なのか

**同じエラータの仲間どうしは、互いに同じバージョンを要求し合うことが多い**からです。

```text
  openssl-libs だけ取った場合
     ↓
  ラウンド1: 「openssl も 3.0.7-27 が必要」と言われる
     ↓
  openssl を取る
     ↓
  ラウンド2: 「openssl-perl も 3.0.7-27 が必要」と言われる   ← 繰り返しが増える
```

**カスタマーポータルで CVE 番号や RHSA 番号を開くと、そのエラータに含まれる RPM の一覧が見られます。**
**最初から仲間ごと取っておくと、繰り返しの回数が減ります。**

## 依存が足りないときの繰り返し

```text
 ┌─▶ ① 署名を確認する        rpm -K ＋ Signature 行の確認
 │   ② 目次を更新する        createrepo_c --update
 │   ③ キャッシュを消す      dnf clean all
 │   ④ 下見する              dnf --repo=localrepo upgrade --assumeno
 │   ⑤ 結果を見る
 │        ├─ OK  ─────────────▶ 完了
 │        └─ 依存不足
 │   ⑥ 足りない RPM を取得して置く
 └───┘（①に戻る）
```

> **いちばん大事なこと**
> **RPM を追加したら、必ず ② 目次の更新 と ③ キャッシュ削除 をしてから ④ を実行します。**
> 飛ばすと、追加した RPM が見えず、**同じエラーが出続けます。**

**1 回で終わらないのが普通です。**追加した RPM が、さらに別の RPM を必要とすることがあるためです。

### エラーの読み方（RHEL 8 以降）

```text
Error: 
 Problem: cannot install the best update candidate for package libbar-1.0-1.noarch
  - nothing provides libbaz needed by libbar-1.1-1.noarch
(try to add '--skip-broken' to skip uninstallable packages or '--nobest' to use not only best candidate packages)
```

**`nothing provides` と `needed by` の間が「足りないもの」**です。

```text
  - nothing provides libbaz needed by libbar-1.1-1.noarch
                     └────┘      └──────────────────┘
                   足りないもの      それを要求している RPM
```

読み方は「**`libbar-1.1` を入れるには `libbaz` が必要だが、それを持っている RPM がない**」です。

### エラーの読み方（RHEL 7.9）

```text
Error: Package: openssh-server-7.4p1-23.el7_9.x86_64 (localrepo)
           Requires: openssl-libs >= 1:1.0.2k-26
           Installed: 1:openssl-libs-1.0.2k-25.el7_9.x86_64 (@anaconda/7.9)
```

**`Requires:` の右側が「足りないもの」**です。
`Installed:` にいま入っている版が出るので、**どこまで上げればよいかが分かります。**
この例なら「`-25` が入っているが `-26` 以上が必要」です。

### best 設定で画面が変わる（RHEL 8 以降）

**同じ依存不足でも、`best` の設定で表示がまったく変わります。**検証環境で両方作って確かめました。

| `best` | 表示 | 終了ステータス |
|:--|:--|:--|
| **`True`**（RHEL 系で使われる値） | **`Error:` ＋ `Problem:` で停止** | **1** |
| **`False`**（dnf 本体の既定値） | **`Skipping packages with broken dependencies:` → `Nothing to do.` → `Complete!`** | **0** |

`best=False` のときの実測です。

```text
Skipping packages with broken dependencies:
 libbar           noarch           1.1-1              localrepo           6.0 k

Transaction Summary
Skip  1 Package

Nothing to do.
Complete!
```

**⚠️ ここが怖いところです。`best=False` だと、依存が足りていないのに `Complete!` で終わります。**
**「`Nothing to do.` が出たから更新対象が無いだけ」と判断すると、依存不足を見落とします。**

**自分の環境の値を先に確認してください。**

```bash
$ grep -nE '^best' /etc/dnf/dnf.conf                       # 設定ファイルに書かれているか
$ dnf config-manager --dump 2>/dev/null | grep -E '^best'  # 実際に効いている値（1=True / 0=False）
```

> **DNF 公式の既定値は `best = False`** です（Configuration Reference：「The default is `False`.」）。
> 同じページに **「`best` and `skip_if_unavailable` can be overridden by your distribution's configuration」**
> とあり、**Rocky Linux 9 の公式ドキュメントに載っている `/etc/dnf/dnf.conf` は `best=True`** です。
> **ただし「RHEL が配る設定が `True`」という Red Hat 公式の明記は確認できませんでした。**必ず実機で確かめてください。

## 依存確認の 2 つの方法

| 方法 | コマンド例 | 特徴 |
|:--|:--|:--|
| **rpm でテスト** | `rpm -Uvh --test /opt/localrepo/*.rpm` | **リポジトリ不要で手軽。**ただし**依存を自動で探さず、指定したファイルだけで判定** |
| **dnf / yum でドライラン** | `dnf --repo=localrepo upgrade --assumeno` | **リポジトリ内の RPM から依存を自動で探して判定。本番とまったく同じ計算結果** |

**ローカルリポジトリ運用なら、本番と同じ経路で確認できる後者を使ってください。**
`rpm -Uvh --test` は「転送が終わったか軽く見る」程度の用途です。

## RHEL 8 以降で特に気をつけること

### Modularity（モジュール）

- RHEL 8 以降には、同じソフトの複数バージョンを「ストリーム」として切り替える**モジュール**という仕組みがあります
  （`nodejs` / `php` / `postgresql` など）
- モジュールに属する RPM を **`createrepo_c` だけで作ったローカルリポジトリ**に入れると、
  モジュール情報（`modules.yaml`）が無いため、**`dnf` にフィルタされて見えない／入らない**ことがあります
- 症状は **`filtered out by modular filtering`** というメッセージです
- **`openssh` はモジュール対象ではない**ので、openssh の作業では気にしなくて大丈夫です
- CVE 対応の RPM にモジュール対象が含まれる場合は、`modules.yaml` を取り込む作業が必要になる**可能性があります**。
  **手順は未検証**なので、その場合は Red Hat 公式ドキュメントで確認してください

> **RHEL 10 ではモジュール機能が非推奨になりました。**
> Red Hat の「Considerations in adopting RHEL 10」に
> **「RHEL 10 では、モジュール機能は非推奨となり、今後のメジャーリリースで削除される予定です。」**
> **「RHEL 10 ではモジュールコンテンツは配布されません。」**と書かれています。

### --security は使えない

- `dnf upgrade --security` のようなセキュリティ絞り込みは、リポジトリ内の
  **`updateinfo.xml`（エラータ情報）**を元に動きます
- **`createrepo_c` で作っただけのローカルリポジトリには、これがありません**
- そのため **絞り込みは使えません。パッケージ名を明示するか、リポジトリ全体を対象に**更新します

```bash
$ dnf updateinfo summary     # 何も出なければ updateinfo が無い（＝--security は効かない）
```

**同じ理由で `dnf upgrade-minimal` も何もしません**（「最小限」の判断材料が無いため）。

### el8 / el9 の取り違え

- RPM のファイル名には **`el8` / `el9`** が入っています。**サーバと同じメジャーバージョンのもの**を使います
- サーバ側の確認方法

```bash
$ rpm -E 'el%{rhel}'                                         # el8 や el9 と表示される
$ ls /opt/localrepo/*.rpm | grep -v "$(rpm -E 'el%{rhel}')"   # 合わない RPM を洗い出す
```

**2 つ目は何も表示されないのが期待値**です。`noarch` のパッケージなどで表示されることもあるので、
**出てきたらファイル名を目で確認**してください。

### RHEL 10 では filelists が既定で落ちてこない

- RHEL 10 から、ファイル一覧のメタデータが既定でダウンロードされなくなりました
- **`dnf provides /パス` のようなファイル検索は自動で読み込まれるので動きます**
- ただし**ファイルパスの依存を解決する必要があるトランザクションは失敗することがあります**
- 恒久的に戻すなら、公式の記載どおり **`/etc/dnf/dnf.conf` の `optional_metadata_types` に `filelists` を追加**します

## RHEL 7.9 ならではの注意

### サポート状況（公式。2026-10-13 時点）

| 項目 | 公式の記載 |
|:--|:--|
| **フェーズ移行** | **2024年6月30日**に Maintenance Phase から **Extended Life Phase** へ移行 |
| **ELS なしの場合** | **「No bug fixes, security fixes, hardware enablement, or root-cause analysis will be available during this phase.」** |
| **ELS アドオンの期間** | **「from July 1, 2024 through May 31, 2029」** |
| **ELS の対象** | **「ELS is only supported on the last minor release. In this case, RHEL 7.9.」** |
| **ELS が出す修正** | **「Software maintenance for certain Critical, Important, and Moderate CVEs with a CVSS score of 7 or higher」** |

**つまり RHEL 7.9 で CVE 対応の RPM を取得できるかは、ELS 契約の有無で決まります。**
**ポータルに出てこない場合は、まず契約状況を確認してください。**

### メッセージが日本語になる

RHEL 7 の `yum` は、日本語環境だとエラーメッセージも日本語になります。
**`grep` でエラーを探すなら、先に英語にそろえてください。**

```bash
$ export LANG=C      # この端末だけ英語にする
$ yum --disablerepo='*' --enablerepo=localrepo update --assumeno   # yum に --repo は無いのでこの書き方
```

### createrepo の導入

RHEL 7 では `createrepo` パッケージに入っています。オフラインサーバに無い場合は 2 通りあります。

| やり方 | 内容 |
|:--|:--|
| **A. 対象サーバに入れる** | `createrepo` と依存 RPM（`deltarpm` / `python-deltarpm` / `libxml2-python` など）を取得して `yum install ./*.rpm` |
| **B. 別の端末で目次を作る** | **同じ RHEL 7 系の端末**で `createrepo` を実行し、**`repodata/` を含めたフォルダごと転送**する |

**B のほうが確実です。**対象サーバに余計なパッケージを入れずに済みます。

> **依存 RPM の名前は RHEL 7 のマイナーバージョンで変わる可能性があります。**
> 実機で `yum deplist createrepo` を打って確かめてください（**検証環境では未確認**）。

## やってはいけないこと

| やってはいけない | なぜ |
|:--|:--|
| **`--skip-broken` を付ける** | **エラーのあるパッケージを黙って外します。**しかも **`Complete!` 終了ステータス 0** で終わるので、**当たっていないのに当たったと報告する**事故になります |
| **`--nobest` を付ける**（RHEL 8 以降） | **1 つ前の版で妥協します。**修正が最新版にしか入っていなければ、**CVE は残ります** |
| **`rpm -Uvh --nodeps` で入れる** | 依存が壊れ、あとで別の障害になります |
| **`gpgcheck=0` にする** | **署名のない RPM が黙って入ります。**署名確認の意味がなくなります |
| **`rpm -K` の結果だけで署名OKとする** | **署名のない RPM を素通りさせます**（このノートの最重要ポイント） |

> **`--skip-broken` が実際に何もしてくれないことは、[dnf解説③ オプションの使い分け](../07_パッケージ管理/dnf解説③_オプションの使い分け.md)
> で実測つきで書いています。**
> `dnf5` 公式も、`upgrade --skip-broken` について
> **「Dropped `--skip-broken` option, as it was already available in DNF4 only for compatibility reasons」**
> と書いています（＝dnf-4 の時点で実質なにもしない）。

## よくあるエラーと対処

| エラー表示 | 原因 | 対処 |
|:--|:--|:--|
| `nothing provides xxx needed by ...` | 依存 RPM が不足 | 繰り返しで対応（手順書へ） |
| `Requires: xxx`（RHEL 7） | 同上 | 同上 |
| **RPM を追加したのに同じエラー** | **目次更新・キャッシュ削除を忘れている** | **`createrepo_c --update` → `clean all` をやってから再実行** |
| `Failed to download metadata for repo` / `Cannot retrieve repository metadata` | `repodata` が無い／`baseurl` のパス間違い | `createrepo_c` を実行、`baseurl` のスラッシュ 3 つを確認 |
| `Public key for xxx.rpm is not installed` | 公開鍵が未登録 | `rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release`（**RHEL 9.7 以降は PQC 鍵も**） |
| `Nothing to do.` | 目次が古い／既に同じか新しい版／`el8`・`el9` の取り違え／**`best=False` で依存不足** | 目次更新 → `rpm -q` で現バージョン確認 → **`best` の値も確認** |
| `filtered out by modular filtering` | モジュール対象パッケージ | Modularity の節を参照 |
| `Protected multilib versions`（RHEL 7） | 32bit版（i686）と64bit版のバージョンずれ | **i686 版も同じバージョンで取得** |
| `This system is not registered with an entitlement server` | サブスクリプション未登録 | **無視してよい。**ローカルリポジトリの利用には影響しません |
| `Unable to detect release version` | `$releasever` を解決できない | ローカルリポジトリの `baseurl` に `$releasever` を使っていなければ無視してよい |

## このノートの検証環境

**このノートに載せた出力は、次の環境で実際に実行した結果**です。

| 項目 | 内容 |
|:--|:--|
| rpm | **rpm 4.18.2** |
| dnf | **dnf 4.14.0** |
| createrepo_c | **0.17.3** |
| リポジトリ | `rpmbuild` で作った検証用パッケージを `createrepo_c` でリポジトリ化し、**`file:///opt/localrepo`** として登録したもの |
| 署名 | **検証用の GPG 鍵を自分で作って `rpm --addsign`** し、署名あり・署名なし・鍵未登録・壊れている の 4 状態を作って確認 |
| 依存関係 | `appx` → `libbar` と `libfoo`、`libbar` → `libbaz`（`libbaz` を抜いて「依存不足」を再現） |
| `best` | **`True` と `False` の両方**で同じ状況を実行して比較 |

**RHEL の実機で取った出力ではありません。**
**RHEL 7.9（rpm 4.11 / yum 3）の画面は実測できていません。**
`rpm -K` の表示文字列は rpm のバージョンで変わるため、**RHEL 7 では
`rsa sha1 (md5) pgp md5 OK` のような別の形**になります。
**「署名があることを肯定的に確かめる」という考え方は変わりません**が、
**文字列で判定する部分は対象バージョンで必ず確認してください。**
