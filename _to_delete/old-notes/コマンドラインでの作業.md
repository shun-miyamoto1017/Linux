## メタキャラクタとは

**メタキャラクタとは、シェルによって特別に解釈される文字です。**

大事なのは、**シェルがコマンドを実行する「前」に文字列を書き換えている**という点です。

```bash
$ rm *.log                          # 拡張子 .log のファイルをまとめて削除したい
```

このとき `rm` は `*.log` という文字列を受け取っていません。
シェルが先にファイル名へ置き換えてから `rm` を起動します。

```bash
$ rm app.log error.log access.log   # シェルが実際に実行しているのはこの形
```

この置き換えを **展開（expansion）** と呼びます。

> **表記の注意**
> 日本語フォントでは `\`（バックスラッシュ）が **`¥`（円記号）** に見えることがあります。
> 見た目が違うだけで、文字コード上は同じもの（U+005C）です。
> Ping-t の解説画面でも `¥` と表示されますが、実際に入力するのは `\` です。

## 一覧表

| メタキャラクタ | 説明 |
|:--|:--|
| `*` | 0 文字以上の文字列 |
| `?` | 任意の 1 文字 |
| `[ ]` | `[ ]` 内のいずれか 1 文字<br>　`[abc]` … a, b, c のどれか 1 文字<br>　`[a-z]` … 小文字のアルファベット 1 文字<br>　`[!abc]` … a, b, c 以外の 1 文字 |
| `$` | 変数 |
| `'` | `'` で囲まれた部分を文字列と見なす（メタキャラクタの意味を打ち消す） |
| `"` | `"` で囲まれた部分を文字列と見なす（メタキャラクタの意味を打ち消す。ただし `$` `` ` `` `\` `"` は除く） |
| `` ` `` | `` ` `` で囲まれた文字列（変数の場合は格納されている値）をコマンドと見なし、その実行結果を文字列として返す |
| `\` | 次の文字（メタキャラクタ）の意味を打ち消して通常の文字として扱う（エスケープする） |

| ディレクトリの特殊記号 | 説明 |
|:--|:--|
| `~` | ホームディレクトリ |
| `.` | カレントディレクトリ |
| `..` | カレントディレクトリの 1 つ上の階層 |

## ひとつずつ例文で確認

以下の例は、すべてこのファイル構成のディレクトリで実行しています。

```bash
$ ls                                # これから使う練習用ファイルを確認
A.txt  a-z.txt  abc.txt  b.txt  x.txt
```

---

### アスタリスク

**意味** … 0 文字以上の文字列

**例文**

```bash
$ ls *.txt                          # 「なんでも + .txt」で終わるファイル
A.txt  a-z.txt  abc.txt  b.txt  x.txt

$ ls a*                             # 「a で始まる」ファイル
a-z.txt  abc.txt

$ ls a*.txt                         # 「a で始まり .txt で終わる」ファイル
a-z.txt  abc.txt
```

**補足** … 「**0 文字以上**」なので、`b` というファイルがあれば `b*` はそれ自身にもマッチします。

```bash
$ touch b                           # 拡張子なしの「b」を作って試す
$ ls b*                             # b 自身も 0 文字マッチとして拾われる
b  b.txt
```

---

### クエスチョン

**意味** … 任意の 1 文字

**例文**

```bash
$ ls ?.txt                          # 「ちょうど1文字 + .txt」
A.txt  b.txt  x.txt

$ ls ???.txt                        # 「ちょうど3文字 + .txt」
a-z.txt  abc.txt
```

**補足** … `?` は **0 文字にはマッチしません**。ここが `*` との決定的な違いです。

| パターン | `b.txt` | `abc.txt` | `a-z.txt` |
|:--|:-:|:-:|:-:|
| `*.txt`   | ○ | ○ | ○ |
| `?.txt`   | ○ | × | × |
| `???.txt` | × | ○ | ○ |

---

### ブラケット

**意味** … `[ ]` 内のいずれか **1 文字**

**例文**

```bash
$ ls [abc].txt                      # a または b または c のどれか1文字 + .txt
b.txt

$ ls [ab-x].txt                     # 列挙(a,b)と範囲(b〜x)は混ぜて書ける
b.txt  x.txt

$ ls [!abc].txt                     # a, b, c 以外の1文字 + .txt
A.txt  x.txt
```

**補足** … `[abc]` は「**a か b か c のどれか 1 文字**」であって、「abc という並び」ではありません。
ここが最も間違えやすいポイントです。

また **`[ ]` による指定は大文字と小文字を区別します**。
`[abc]` は小文字の `a` `b` `c` にだけマッチし、大文字の `A` にはマッチしません。

```bash
$ ls [abc].txt                      # 大文字の A.txt は対象外になる
b.txt
```

### ドル記号

**意味** … 変数

**例文**

```bash
$ NAME=shun                         # シェル変数 NAME に値を入れる
$ echo $NAME                        # $ を付けると中身が取り出される
shun

$ echo $HOME                        # 最初から用意されている変数（ホームディレクトリ）
/home/shun
```

**補足** … 変数名の直後に文字を続けるときは `${ }` で区切りを明示します。

```bash
$ echo $NAMEsan                     # 「NAMEsan」という別の変数を探すので空になる

$ echo ${NAME}san                   # { } でどこまでが変数名かを示す
shunsan
```

### シングルクォート

**意味** … `'` で囲まれた部分を文字列と見なす（メタキャラクタの意味を打ち消す）

**例文**

```bash
$ echo '$HOME is my home'           # $ が打ち消されて展開されない
$HOME is my home

$ echo '*'                          # ワイルドカードも打ち消される
*

$ echo 'today is `date`'            # バッククォートも実行されない
today is `date`
```

**補足** … 打ち消しに例外はありません。**`~` も `\` も打ち消されます**（後述の問題で問われます）。
なお、中にシングルクォートは書けません。書きたいときはいったん閉じて連結します。

```bash
$ echo 'it'\''s ok'                 # 「it」+ エスケープした' + 「s ok」を連結
it's ok
```

---

### ダブルクォート

**意味** … `"` で囲まれた部分を文字列と見なす。
ただし `$` `` ` `` `\` `"` は特別な意味を保つ

**例文**

```bash
$ NAME=shun                         # 確認用に変数を用意

$ echo "$NAME"                      # $ は生きているので展開される
shun

$ echo '$NAME'                      # シングルクォートなら展開されない
$NAME

$ echo "today is `date +%F`"        # バッククォートも生きているので実行される
today is 2026-08-25

$ echo "*"                          # ワイルドカードは打ち消される
*

$ echo "~"                          # チルダも打ち消される（展開されない）
~

$ echo "price is \$100"             # \ でエスケープすれば $ も打ち消せる
price is $100
```

**補足** … 変数の値にスペースが入る場合、クォートしないと別々の引数に分割されます。
**変数参照は原則 `"$VAR"` と書く**のがシェルスクリプトの鉄則です。

```bash
$ FILE="my report.txt"              # スペースを含むファイル名を変数に入れる

$ rm $FILE                          # → rm my report.txt （2ファイル扱いになり失敗）
$ rm "$FILE"                        # → rm 'my report.txt' （1ファイルとして正しく渡る）
```

### バッククォート

**意味** … `` ` `` で囲まれた文字列をコマンドと見なし、その実行結果を文字列として返す

**例文**

```bash
$ echo "今日は `date +%F` です"      # date の実行結果が文中に埋め込まれる
今日は 2026-08-25 です

$ FILE_COUNT=`ls | wc -l`           # ls の行数を数えて変数に入れる
$ echo $FILE_COUNT                  # 数えた結果を確認
5
```

**補足** … 同じ動作を `$( )` でも書けます。**実務では `$( )` が推奨**です。

```bash
$ echo "今日は $(date +%F) です"     # バッククォートと同じ結果になる
今日は 2026-08-25 です
```

`$( )` を推す理由は 2 つあります。

**理由1 … 入れ子にできる**

コマンドの結果を、さらに別のコマンドに渡したいときがあります。
`$( )` なら素直に入れ子にできますが、バッククォートはエスケープが必要で読めなくなります。

```bash
$ echo "$(dirname "$(readlink -f "$0")")"    # スクリプト自身が置かれた場所を求める
/home/shun/bin

$ echo "`dirname \"\`readlink -f $0\`\"`"     # 同じことをバッククォートで書いた場合
```

上の例は内側から順に、次のように処理されています。

| 順番 | 部分 | やっていること |
|:-:|:--|:--|
| 1 | `$0` | 実行中のスクリプト自身のパス（例 `./bin/run.sh`） |
| 2 | `readlink -f "$0"` | シンボリックリンクを解決して絶対パスにする（例 `/home/shun/bin/run.sh`） |
| 3 | `dirname "..."` | パスからファイル名を除いてディレクトリ部分だけ取り出す |

**理由2 … 見分けやすい**

`` ` ``（バッククォート）と `'`（シングルクォート）は、フォントによってはほぼ同じに見えます。
`$( )` なら誤読の余地がありません。

試験では `` ` `` の意味が問われるので、**両方覚えて実務では `$( )` を使う**のが正解です。

### バックスラッシュ

**意味** … 次の文字（メタキャラクタ）の意味を打ち消して通常の文字として扱う（エスケープする）

**例文**

```bash
$ echo \$HOME                       # $ を打ち消すので変数展開されない
$HOME

$ echo \*                           # * を打ち消すのでファイル名に展開されない
*

$ touch "my file.txt"               # スペース入りのファイルを用意
$ ls my\ file.txt                   # スペースをエスケープして1つの名前として渡す
my file.txt
```

**補足その1** … **`\` 自身をエスケープするには `\\` と 2 つ重ねます。**
これが後述の `mkdir ~/\\work` の問題で問われます。

```bash
$ echo \\                           # \ を2つ書くと \ が1つ出力される
\

$ touch back\\slash                 # 「back\slash」という名前のファイルを作る
$ ls                                # 作成されたファイル名を確認
back\slash
```

**補足その2** … 行末に置くと**改行そのもの**をエスケープでき、長いコマンドを複数行に分けられます。

```bash
$ aws ec2 describe-instances \
    --filters "Name=instance-state-name,Values=running" \
    --query 'Reservations[].Instances[].InstanceId' \
    --output text
```
（各行末の `\` が「まだコマンドは続く」という意味になる）

`\` の後ろにスペースがあると行継続になりません。`cat -A` で行末を確認できます。

## ディレクトリの特殊記号

| 記号 | 意味 | 例文 |
|:--|:--|:--|
| `~` | ホームディレクトリ | `cd ~` |
| `~user` | 指定ユーザのホームディレクトリ | `cd ~apache` |
| `.` | カレントディレクトリ | `./script.sh` |
| `..` | 1 つ上の階層 | `cd ..` |
| `-` | 直前にいたディレクトリ | `cd -` |

```bash
$ pwd                               # いまいる場所を確認
/home/shun/work

$ cd ..                             # 1つ上の階層へ移動
$ pwd                               # 移動先を確認
/home/shun

$ cd -                              # 直前にいたディレクトリへ戻る
$ pwd                               # 戻れたことを確認
/home/shun/work

$ ./script.sh                       # カレントにある script.sh を実行
```

**補足** … `~` がホームディレクトリに展開されるのは、
**`~` の直後が `/` か、`~` で単語が終わっているとき**だけです。
`~\work` のように `/` 以外の文字が続くと、`\work` というユーザ名だと解釈され、
そのユーザが存在しなければ展開されずそのまま残ります。これが後述の問題の分かれ目になります。

```bash
$ echo ~                            # 単語の終わり → 展開される
/home/shun

$ echo ~/work                       # 直後が / → 展開される
/home/shun/work

$ echo ~work                        # work というユーザがいなければ展開されない
~work
```

**補足** … 自作スクリプトに `./` を付ける理由は、**カレントディレクトリが `PATH` に含まれていない**ためです。
含まれていると、`/tmp` などで `ls` という名前の悪意あるファイルを踏む危険があるため、意図的に外されています。

## マニュアルの参照

Linux では、コマンドや設定ファイルのためのオンラインマニュアルページ（man ページ）が用意されています。
**オンラインマニュアルを参照するコマンドは `man`** です。

### 書式

```
man [オプション] [セクション番号] キーワード
```

| オプション | 説明 |
|:--|:--|
| `-k` | キーワードに一部一致するコマンドやファイルの man ページを一覧表示（`apropos` コマンドと同じ） |
| `-f` | キーワードに完全一致するコマンドやファイルの man ページを一覧表示（`whatis` コマンドと同じ） |

**例文**

```bash
$ man ls                            # ls コマンドのマニュアルを開く
$ man -k password                   # 「password」を含む man ページを一覧表示
passwd (1)           - change user password
passwd (5)           - the password file
$ man -f passwd                     # 「passwd」に完全一致する man ページを一覧表示
passwd (1)           - change user password
passwd (5)           - the password file
```

**補足** … man ページの中では `less` と同じキー操作が使えます。

| キー | 動作 |
|:--|:--|
| `スペース` / `f` | 次のページへ |
| `b` | 前のページへ |
| `/文字列` | 下方向へ検索 |
| `n` / `N` | 次の / 前の検索結果へ |
| `q` | 終了 |

---

### セクション番号

なお、同じキーワードに man ページが複数用意されている場合があります
（例えば `passwd` コマンドと「`/etc/passwd`」ファイル）。
このような場合は、**セクション番号を指定して `man` コマンドを実行する**ことで、
目的の man ページを参照することが出来ます。
**セクション番号を指定しないで実行した場合は、セクション番号の小さいほうのマニュアルが表示されます。**

man ページのセクション番号は以下の通りです。

| セクション番号 | 内容 |
|:-:|:--|
| 1 | ユーザーコマンド |
| 2 | システムコール（カーネルが提供する関数） |
| 3 | ライブラリ呼び出し（プログラムライブラリに含まれる関数） |
| 4 | 特殊ファイル（通常 `/dev` 配下に存在するファイル） |
| 5 | **ファイルの書式と慣習**（例: `/etc/passwd`） |
| 6 | ゲーム |
| 7 | その他いろいろなもの（マクロパッケージや慣習などを含む）例えば man(7) や groff(7) |
| 8 | システム管理コマンド（通常は root 用） |
| 9 | カーネルルーチン［非標準］ |

**例文**

```bash
$ man passwd                        # 番号を省略 → 小さいほうのセクション1が開く
PASSWD(1)                    User Commands

$ man 5 passwd                      # セクション5を指定 → /etc/passwd の書式が開く
PASSWD(5)                    File Formats and Conversions
```

**補足** … 「そのキーワードにどのセクションが存在するか」は `man -f`（＝`whatis`）で確認できます。
設定ファイルの書式を知りたいときは **5**、root 用の管理コマンドなら **8** と覚えると実務で速いです。

```bash
$ man -f crontab                    # crontab に用意されている man ページを確認
crontab (1)          - maintain crontab files for individual users
crontab (5)          - tables for driving cron
```

## コマンド履歴の呼び出し

`bash` シェルには、過去に入力したコマンドの履歴を記録する機能があります。
**`history` コマンドは、このコマンドの履歴を表示します。**

```bash
$ history                           # 履歴を番号つきで表示する
    1  ls
    2  pwd
    3  cat hoge.txt
    4  cp hoge.txt hoge2.txt
    5  history
```

この番号や文字列を使って、過去のコマンドを打ち直さずに再実行できます。
この仕組みを **ヒストリ展開** と呼びます。

| 書き方 | 意味 |
|:--|:--|
| `!番号` | 指定した履歴番号のコマンドを再実行する |
| `!文字列` | 指定した文字列から始まる直近のコマンドを再実行する |
| `!!` | 直前のコマンドを再実行する |
| `!-2` | 2 つ前のコマンドを再実行する |
| `!$` | 直前のコマンドの**最後の引数**を再利用する |
| `Ctrl+R` | 履歴をインクリメンタル検索する |

**例文**

```bash
$ !3                                # 履歴番号3番のコマンドを再実行する
cat hoge.txt                        # ← 実行されるコマンドが表示されてから走る
hello

$ !ca                               # 「ca」で始まる直近のコマンドを再実行する
cat hoge.txt
hello

$ !!                                # 直前のコマンドをもう一度実行する
cat hoge.txt
hello
```

**補足その1** … `!$` は実務での時短効果が大きい書き方です。

```bash
$ mkdir /opt/app/config             # 長いパスのディレクトリを作る
$ cd !$                             # 直前の最後の引数（＝そのパス）を再利用する
cd /opt/app/config
```

**補足その2** … `sudo` を付け忘れたときの定番が `sudo !!` です。

```bash
$ systemctl restart nginx           # 権限が足りず失敗する
Failed to restart nginx.service: Access denied

$ sudo !!                           # 直前のコマンドに sudo を付けて再実行する
sudo systemctl restart nginx
```

**補足その3** … ヒストリ展開は `histexpand`（`set -H`）オプションで制御されています。
**対話シェルでは既定で有効、スクリプト内では既定で無効**です。
そのため、スクリプトに `!` を含む文字列を書いても展開されません。

```bash
$ set -o | grep histexpand          # 現在の設定を確認する
histexpand     on

$ echo "Hello!"                     # 対話シェルでは ! の後ろの文字次第でエラーになることがある
$ echo 'Hello!'                     # シングルクォートで囲めば安全
Hello!
```

> **履歴の「設定」はこちら**
> 何件残すか（`HISTSIZE`）、ファイルに何件書き出すか（`HISTFILESIZE`）、日時を付けるか
> （`HISTTIMEFORMAT`）といった**設定側の話**は
> [シェル環境のカスタマイズ](./シェル環境のカスタマイズ.md) にまとめています。
> このノートは**呼び出す側の操作**を扱います。

### ブラケットにマッチするファイル

> 証跡 1

**問題**

以下のコマンドを実行した場合に表示されるファイルはどれか。

```bash
$ ls                                # 現在のファイル一覧
A.txt  a-z.txt  abc.txt  b.txt  x.txt
$ ls [abc].txt                      # ← このコマンドの結果を答える
```

（1）`a-z.txt` （2）`abc.txt` （3）`A.txt` （4）`x.txt` （5）`b.txt`

---

**正解** … （5）`b.txt`

---

**解説**

上表より、「`[]`」は「`[]` 内のどれか **1 文字**」を意味します。
つまり「`[abc].txt`」は、「`a`」または「`b`」または「`c`」のどれか **1 文字** ＋「`.txt`」にマッチします。

したがって正解は `b.txt` です。

**実行例**

```bash
$ ls                                # 対象のファイル一覧を確認
A.txt  a-z.txt  abc.txt  b.txt  x.txt

$ ls [abc].txt                      # a/b/c のどれか1文字 + .txt にマッチするものだけ表示
b.txt
```

**補足** … 候補になりうるのは `a.txt` `b.txt` `c.txt` の 3 つだけです。
このディレクトリに実在するのは `b.txt` だけなので、答えは 1 つになります。

```bash
$ touch a.txt c.txt                 # 試しに a.txt と c.txt も作ってみる
$ ls [abc].txt                      # 3つとも候補なので、すべて表示される
a.txt  b.txt  c.txt
```

---

**誤答選択肢の解説**

#### abc.txt

`[abc]` は **1 文字にしかマッチしない**ため、この 3 文字の文字列全体としてはマッチしませんので、誤りです。

```bash
$ ls [abc].txt                      # abc.txt は3文字なので対象外
b.txt

$ ls abc.txt                        # そのまま書けばもちろんマッチする
abc.txt

$ ls ???.txt                        # 「任意の3文字」ならマッチする
a-z.txt  abc.txt
```

**補足** … `[abc]` を「abc という並び」と読んでしまうのが最頻出のミスです。
**`[ ]` は「集合から 1 個選ぶ」**と覚えてください。

---

#### A.txt

`[abc]` は小文字の `a`、`b`、`c` にのみマッチし、大文字の `A` にはマッチしませんので、誤りです。
**「`[]`」による指定は、大文字と小文字を区別します。**

```bash
$ ls [abc].txt                      # 小文字指定なので A.txt は出てこない
b.txt

$ ls [ABC].txt                      # 大文字で指定すればマッチする
A.txt

$ ls [aAbBcC].txt                   # 両方拾いたいなら大文字小文字を並べて書く
A.txt  b.txt
```

**補足** … 大文字小文字を無視して一致させたい場合は `nocaseglob` を有効にします
（ただし恒久的に有効にすると事故のもとなので、一時的に使うのが無難です）。

```bash
$ shopt -s nocaseglob               # 大文字小文字を区別しないモードにする
$ ls [abc].txt                      # A.txt も拾われるようになる
A.txt  b.txt
$ shopt -u nocaseglob               # 元に戻す（付けっぱなしにしない）
```

---

#### a-z.txt

この中で `[abc]` にマッチするのは最初の 1 文字 `a` のみで、残りの `-` と `z` はマッチしません。

```bash
$ ls [abc].txt                      # a-z.txt は3文字なので対象外
b.txt

$ ls [abc]*.txt                     # 「a/b/c で始まる」なら拾える
a-z.txt  abc.txt  b.txt
```

**補足** … `[a-z]` と `a-z.txt` の見た目が似ているため混乱しやすい選択肢です。
**`[ ]` の中の `-` は範囲を表す記号**ですが、**`[ ]` の外の `-` はただの文字**です。

```bash
$ ls [a-z].txt                      # [ ] の中の - → 「a から z の1文字」という範囲指定
b.txt  x.txt

$ ls a-z.txt                        # [ ] の外の - → ただのファイル名の一部
a-z.txt
```

---

#### x.txt

`a`、`b`、`c` のいずれにもマッチしませんので、誤りです。

```bash
$ ls [abc].txt                      # x は a/b/c に含まれないので対象外
b.txt

$ ls [!abc].txt                     # 「a,b,c 以外の1文字」なら拾える
A.txt  x.txt
```

### バックスラッシュを含むディレクトリ名

> 証跡 5

**問題**

ホームディレクトリに `\work` ディレクトリを作成することができるコマンドはどれか。

（1）`mkdir "~/\\work"`
（2）`mkdir ~/\\work`
（3）`mkdir '~/\\work'`
（4）`mkdir ~\\work`
（5）`mkdir ~/\work`

---

**正解** … （2）`mkdir ~/\\work`

---

**解説**

設問では名前に「`\`（バックスラッシュ）」のつくディレクトリを作成したいので、
「`\`」をエスケープする（メタキャラクタとして扱わない）ようにする必要があります。
その場合、**バックスラッシュを 2 つつなげる**ことで、「`\`」を文字として扱うことができます。

よって正解は `mkdir ~/\\work` です。

**実行例**（Ping-t の解説に掲載されている例）

```bash
$ pwd                               # いまいる場所（ホームディレクトリ）を確認
/home/staff
$ ls                                # 何も存在しないことを確認
$ mkdir ~/\\work                    # \ をエスケープしてディレクトリを作成
$ ls                                # 「\work」ができたことを確認
\work
```

**なぜそうなるか（引数の組み立てを 1 段ずつ追う）**

| 段階 | 状態 |
|:--|:--|
| 入力 | `~/\\work` |
| `\\` のエスケープ処理 | `\\` → `\` になる |
| チルダ展開（`~` の直後が `/`） | `~` → `/home/staff` |
| **`mkdir` が受け取る引数** | `/home/staff/\work` |

**確認のしかた** … `echo` を頭に付けると、シェルが何を渡すのか実行前に確認できます。

```bash
$ echo mkdir ~/\\work               # 実行せず、展開後の内容だけ表示する
mkdir /home/staff/\work
```

---

**誤答選択肢の解説**

#### mkdir ~/\work

「`\`」に続くメタキャラクタがないため、`mkdir` コマンドへの引数としては
「（ホームディレクトリパス）`/work`」が渡されます。
この場合、**ホームディレクトリに `work` ディレクトリを作成する**ことになるので、誤りです。

```bash
$ echo mkdir ~/\work                # 展開結果を確認すると \ が消えている
mkdir /home/staff/work

$ mkdir ~/\work                     # 実際に実行してみる
$ ls ~                              # 「\work」ではなく「work」ができている
work
```

**補足** … `\` は「直後の 1 文字を打ち消す」記号なので、
打ち消したあと **`\` 自身は消えます**。`\w` は単なる `w` になります。

```bash
$ echo \w                           # \ が消えて w だけが残る
w
$ echo \\w                          # \\ が \ になり、そこに w が続く
\w
```

---

#### mkdir '~/\\work'

「`~/\\work`」全体を「`'`（シングル・クォーテイション）」で囲んでいるため、
ホームディレクトリを意味するメタキャラクタ「`~`（チルダ）」と「`\`」がともに無視され、
`mkdir` コマンドへの引数としては「`~/\\work`」が渡されます。
この場合、**現在のディレクトリで「`~`」ディレクトリ配下に `\\work` ディレクトリを作成する**
ことになるので、誤りです。

```bash
$ echo mkdir '~/\\work'             # 展開結果を確認すると何ひとつ変換されていない
mkdir ~/\\work
```

**補足** … 実際に実行すると、カレントに `~` というディレクトリが存在しないため
親ディレクトリが無いというエラーになります（`-p` を付ければ `~` ごと作られます）。

```bash
$ mkdir '~/\\work'                  # 親ディレクトリ「~」が無いので失敗する
mkdir: cannot create directory '~/\\work': No such file or directory

$ mkdir -p '~/\\work'               # -p を付けると親ごと作られてしまう
$ ls                                # カレントに「~」という名前のディレクトリができる
~
```

---

#### mkdir "~/\\work"

「`~/\\work`」全体を「`"`（ダブル・クォーテイション）」で囲んでいるため、
ホームディレクトリを意味するメタキャラクタ「`~`（チルダ）」**だけ**が無視され、
`mkdir` コマンドへの引数としては「`~/\work`」が渡されます。
この場合、**現在のディレクトリで「`~`」ディレクトリ配下に `\work` ディレクトリを作成する**
ことになるので、誤りです。

```bash
$ echo mkdir "~/\\work"             # \\ は \ になるが、~ は展開されていない
mkdir ~/\work
```

**補足** … ダブルクォート内では `\` が生きているので `\\` → `\` の変換は行われます。
一方でチルダ展開は起きません。**「一部だけ生かす」というダブルクォートの性質**が、
ここではっきり出ています。

| 書き方 | `~` の展開 | `\\` → `\` |
|:--|:-:|:-:|
| `~/\\work`（クォートなし） | ○ | ○ |
| `"~/\\work"` | × | ○ |
| `'~/\\work'` | × | × |

---

#### mkdir ~\\work

`mkdir` コマンドへの引数としては「`~\work`」が渡されますが、
ホームディレクトリを意味するメタキャラクタ「`~`（チルダ）」に続けて
ディレクトリを意味する「`/`（スラッシュ）」がないため、
**現在のディレクトリで「`~\work`」ディレクトリを作成する**ことになるので、誤りです。

```bash
$ echo mkdir ~\\work                # ~ が展開されていないことを確認
mkdir ~\work

$ mkdir ~\\work                     # 実際に実行してみる
$ ls                                # カレントにこの名前のディレクトリができている
'~\work'
```

**補足** … `~` が展開されるのは **`~` の直後が `/` か、`~` で単語が終わっているとき**だけです。
`~\work` の場合、bash は `\work` をユーザ名だと解釈し、
そんなユーザはいないので展開せずそのまま残します。

```bash
$ echo ~                            # 単語の終わり → 展開される
/home/staff
$ echo ~/                           # 直後が / → 展開される
/home/staff/
$ echo ~work                        # ユーザ名と解釈され、存在しないので展開されない
~work
$ echo ~root                        # 存在するユーザ名なら展開される
/root
```

### マニュアルのセクション番号

> 証跡 7

**問題**

`/etc/crontab` についての man ページを参照したい。

```bash
$ man ___ crontab                   # ← 下線部に入るものを答える
```

（選択肢）`8` / `3` / `2` / `6` / `5` / `1` / `4` / `7` / `9`

---

**正解** … `5`

---

**解説**

Linux では、コマンドや設定ファイルのためのオンラインマニュアルページ（man ページ）が用意されています。
オンラインマニュアルを参照するコマンドは `man` です。

同じキーワードに man ページが複数用意されている場合があります
（例えば `passwd` コマンドと「`/etc/passwd`」ファイル）。
このような場合は、セクション番号を指定して `man` コマンドを実行することで、
目的の man ページを参照することが出来ます。

**設問は「`/etc/crontab`」という設定ファイルについて調べたい**ので、
「**ファイルの書式と慣習**」を扱う**セクション 5** を指定します。

**実行例**

```bash
$ man -f crontab                    # crontab に用意されている man ページを確認する
crontab (1)          - maintain crontab files for individual users
crontab (5)          - tables for driving cron

$ man 5 crontab                     # セクション5（ファイルの書式）を指定して開く
CRONTAB(5)                   File Formats
NAME
       crontab - tables for driving cron
...

$ man crontab                       # 番号を省略すると小さいほうのセクション1が開く
CRONTAB(1)                   User Commands
NAME
       crontab - maintain crontab files for individual users
```

**補足** … `crontab` は「**コマンド**（セクション1）」と「**設定ファイルの書式**（セクション5）」の
両方に man ページがあります。
`crontab -e` の使い方を知りたいならセクション1、
`/etc/crontab` に書く曜日や分の書式を知りたいならセクション5、という使い分けになります。

---

**誤答選択肢の解説**

その他の選択肢は上表の通り、求めるセクション番号と異なるため誤りです。
それぞれ何を扱うセクションかを、実際に開ける例で確認します。

#### 1（ユーザーコマンド）

一般ユーザが実行するコマンドのマニュアルです。
`/etc/crontab` は**ファイル**なので、ここには載っていません。

```bash
$ man 1 crontab                     # セクション1を指定して開く
CRONTAB(1)                   User Commands
       crontab - maintain crontab files for individual users
                                    # ファイルの書式ではなくコマンドの使い方が出る
```

---

#### 2（システムコール）

カーネルが提供する関数のマニュアルです。C 言語からカーネルを呼ぶときに参照します。

```bash
$ man 2 open                        # open システムコールのマニュアル
OPEN(2)                      Linux Programmer's Manual

$ man 2 crontab                     # crontab にセクション2は存在しない
No manual entry for crontab in section 2
```

---

#### 3（ライブラリ呼び出し）

プログラムライブラリに含まれる関数のマニュアルです。

```bash
$ man 3 printf                      # C言語の printf 関数のマニュアル
PRINTF(3)                    Linux Programmer's Manual

$ man 1 printf                      # 同じ名前でもセクション1はコマンドの printf
PRINTF(1)                    User Commands
```

---

#### 4（特殊ファイル）

通常 `/dev` 配下に存在するファイルのマニュアルです。

```bash
$ man 4 null                        # /dev/null のマニュアル
NULL(4)                      Device Drivers Manual
       null, zero - data sink
```

---

#### 6（ゲーム）

ゲームのマニュアルです。実務でもクラウド運用でも、まず使いません。

```bash
$ man 6 intro                       # セクション6の概要ページ
INTRO(6)                     Games Manual
```

---

#### 7（その他いろいろなもの）

マクロパッケージや慣習など、上のどれにも入らないものです。
規約や仕様の解説が入っているため、意外と読む価値があります。

```bash
$ man 7 hier                        # ファイルシステム階層（FHS）の解説
HIER(7)                      Linux Programmer's Manual
       hier - description of the filesystem hierarchy

$ man 7 signal                      # シグナルの一覧と意味
SIGNAL(7)                    Linux Programmer's Manual
```

#### 8（システム管理コマンド）

通常は root が使う管理コマンドのマニュアルです。

```bash
$ man 8 crond                       # cron デーモン（管理コマンド）のマニュアル
CROND(8)                     System Administration

$ man 8 mount                       # mount コマンドも管理コマンド
```

`cron` デーモンそのものを調べるなら **8** と、番号で用途が分かれます。

#### 9（カーネルルーチン［非標準］）

カーネル内部のルーチンのマニュアルです。非標準なので、多くのディストリではそもそも存在しません。

### 変数に入れたコマンドの実行

> 証跡 8

**問題**

変数 `DATE` に「`date`」という文字列（現在の日時を表示するコマンド）を格納した。
以下のコマンドの実行結果は次のうちどれか。

```bash
$ echo `$DATE`                      # ← この実行結果を答える
```

（1）`DATE` （2）`date` （3）`$date` （4）現在の日時 （5）`$DATE`

---

**正解** … （4）現在の日時

---

**解説**

「`` ` ``」（バッククォーテーション）はシェルによって特別に解釈されるメタキャラクタの 1 つです。
シェルは「`` ` ``」で囲まれた文字列（**変数の場合は、変数に格納されている値**）をコマンドと見なし、
そのコマンドの実行結果を文字列として使用します。

また、`echo` コマンドは引数に指定された文字列を表示するコマンドです。
「`` ` ``」で囲まれている「`$DATE`」は変数のため、
変数 `DATE` に格納されている「`date`」がコマンドと見なされ、
「`date` コマンドの実行結果」が `echo` コマンドの引数になります。
`date` は現在の日時を表示するコマンドですので、「現在の日時」が実行結果として表示されます。

```bash
$ echo `$DATE`                      # $DATE の中身「date」が実行され、その結果が表示される
2012年 1月 14日 土曜日 15:20:26 MST
```

なお、「`` echo `date` ``」とした場合の実行結果も「現在の日時」です。

**なぜそうなるか（2 段階で評価されている）**

| 順番 | 処理 | 結果 |
|:-:|:--|:--|
| 1 | 変数展開 … `$DATE` を中身に置き換える | `` `date` `` |
| 2 | コマンド置換 … `` ` `` の中身をコマンドとして実行する | `2012年 1月 14日 …` |
| 3 | `echo` がその文字列を表示する | `2012年 1月 14日 …` |

**確認のしかた**

```bash
$ DATE=date                         # 変数に「date」という文字列を入れる
$ echo $DATE                        # クォートなし → 変数の中身がそのまま出る
date

$ echo `$DATE`                      # バッククォートで囲む → 中身がコマンドとして実行される
2026年  8月 27日 木曜日 23:24:40 JST

$ echo $($DATE)                     # $( ) でも同じ（実務ではこちらが推奨）
2026年  8月 27日 木曜日 23:24:40 JST
```

---

**誤答選択肢の解説**

#### date

`date` という**文字列**がそのまま表示されるのは、バッククォートを付けなかった場合です。
設問はバッククォートで囲んでいるので、コマンドとして実行されます。

```bash
$ echo $DATE                        # バッククォートなし → 変数の中身がそのまま出る
date

$ echo "$DATE"                      # ダブルクォートでも変数展開までで止まる
date
```

---

#### $DATE

`$DATE` がそのまま表示されるのは、**シングルクォートで囲んで変数展開を打ち消した**場合です。

```bash
$ echo '$DATE'                      # シングルクォートは $ を打ち消す
$DATE

$ echo \$DATE                       # \ でエスケープしても同じ結果
$DATE
```

---

#### $date

`$date` という表示になることはありません。
変数名は大文字小文字を区別するため、`$date`（小文字）は `$DATE` とは**別の変数**です。
未定義なので、参照しても空文字になります。

```bash
$ echo "[$date]"                    # 小文字の date という変数は定義していない
[]                                  # 空になる

$ echo "[$DATE]"                    # 大文字なら値が入っている
[date]
```

---

#### DATE

`DATE` という表示になることもありません。
`$` を付けずに `echo DATE` と書いた場合だけ、変数名がそのまま文字列として表示されます。

```bash
$ echo DATE                         # $ が無いので、ただの文字列として扱われる
DATE

$ echo $DATE                        # $ を付けると変数の中身になる
date
```

**補足** … この問題は「**変数展開 → コマンド置換**」の 2 段階を追えるかを問うています。
`$` と `` ` `` の**両方**が効いている点が要点です。

| 書き方 | 出力 | 理由 |
|:--|:--|:--|
| `echo DATE` | `DATE` | `$` が無いのでただの文字列 |
| `echo '$DATE'` | `$DATE` | `'` が `$` を打ち消す |
| `echo $DATE` | `date` | 変数展開だけが起きる |
| `` echo `$DATE` `` | 現在の日時 | 変数展開 → コマンド置換の 2 段階 |

### 履歴からの再実行

> 証跡 9

**問題**

以下は `history` コマンドを実行した結果である。

```bash
$ history                           # 現在のコマンド履歴
    1  ls
    2  pwd
    3  cat hoge.txt
    4  cp hoge.txt hoge2.txt
    5  history
```

このうち「`cat hoge.txt`」を再実行するには、どのように入力すればよいか。（2 つ選択）

（1）`!!3` （2）`!3` （3）`#cat` （4）`#3` （5）`!ca`

---

**正解** … （2）`!3` と（5）`!ca`

---

**解説**

`bash` シェルには、過去に入力したコマンドの履歴を記録する機能があります。
`history` コマンドは、このコマンドの履歴を表示します。

**「`!番号`」と入力すると、指定した履歴番号のコマンドを再実行します。**
**「`!文字列`」と入力すると、指定した文字列から始まる直近のコマンドを再実行します。**

設問の実行結果の場合、「`!3`」や「`!ca`」を入力すると「`cat hoge.txt`」を再実行します。

**実行例**

```bash
$ !3                                # 履歴番号3番を再実行
cat hoge.txt                        # 何が実行されるかが表示されてから走る
hello

$ !ca                               # 「ca」で始まる直近のコマンドを再実行
cat hoge.txt
hello
```

**補足** … `!文字列` は「**その文字列で始まる直近**のコマンド」を探します。
履歴に `cat` より後に `cal` を打っていた場合、`!ca` は `cal` を拾ってしまいます。
**確実に狙ったものを実行したいなら `!番号` のほうが安全**です。

```bash
$ cal                               # 別のコマンドを実行して履歴に積む
$ !ca                               # 「ca」で始まる直近は cal になってしまう
cal
```

---

**誤答選択肢の解説**

#### !!3

`!!` は「直前のコマンドを再実行する」という別の書き方です。
そこに `3` が続くと「**直前のコマンドの後ろに `3` を付けて実行する**」という意味になり、
履歴番号 3 番の再実行にはなりません。

```bash
$ history                           # 直前のコマンドは history だったとする
$ !!3                               # 「直前のコマンド + 3」として展開される
history3
bash: history3: command not found
```

**補足** … `!!` 単体は実務で頻繁に使います。特に `sudo` の付け忘れ対応が定番です。

```bash
$ systemctl restart nginx           # 権限不足で失敗する
Failed to restart nginx.service: Access denied

$ sudo !!                           # 直前のコマンドに sudo を付けて再実行
sudo systemctl restart nginx
```

---

#### #cat

`#` は**コメント**の記号です。`#` から行末までは実行されず、無視されます。
履歴を呼び出す機能はありません。

```bash
$ #cat                              # コメント扱いなので何も起きない
$                                   # プロンプトが返るだけ

$ echo hello   # これはコメント     # 行の途中からでもコメントになる
hello
```

**補足** … `#` で始まる行が無視される性質を利用して、
設定ファイルの行を「消さずに無効化する」のが実務の定番です。

```bash
$ grep -n '^#' /etc/crontab | head -3    # 先頭が # の行（コメント行）を確認する
1:SHELL=/bin/bash
```

---

#### #3

これも `#` から始まるためコメント扱いになり、何も実行されません。

```bash
$ #3                                # コメントなので無視される
$                                   # プロンプトが返るだけ
```

**補足** … 「履歴を呼ぶのは `!`、コメントは `#`」と対で覚えます。
`#` を履歴呼び出しだと思い込むと、
**「実行したつもりなのに何も起きない」**という気づきにくいミスにつながります。

| 記号 | 意味 |
|:--|:--|
| `!番号` / `!文字列` | 履歴からの再実行（ヒストリ展開） |
| `#` | コメント。以降は実行されない |

---

## 公式ドキュメントで確認した補足

Ping-t の解説に載っていない範囲で、GNU Bash Manual に明記されている重要なルールです。

---

### 否定は `!` でも `^` でも書ける

Bash マニュアル Pattern Matching には、
「`[` の直後の文字が `!` または `^` の場合、囲まれていない任意の文字にマッチする」と記載されています。

```bash
$ ls [!abc].txt                     # ! による否定
A.txt  x.txt

$ ls [^abc].txt                     # ^ による否定（bash では同じ結果）
A.txt  x.txt
```

ただし **POSIX で規定されているのは `!`** です。試験でも実務でも `!` を使うのが安全です。

---

### 範囲指定 `[a-z]` はロケールに依存する

`[a-z]` の「順序」は `LC_COLLATE` が決めます。
辞書順のロケールでは、`[a-c]` が `aAbBcC` のように**大文字も拾う**ことがあります。

```bash
$ LC_ALL=C ls [a-z].txt             # このコマンドの間だけ C ロケールにして実行
b.txt  x.txt
```

確実に小文字だけを指定するなら、**文字クラス**を使います。

```bash
$ ls [[:lower:]].txt                # ロケールに関係なく「小文字1文字」を指定
b.txt  x.txt
```

| 書き方 | 意味 |
|:--|:--|
| `[[:alpha:]]` | アルファベット 1 文字 |
| `[[:digit:]]` | 数字 1 文字 |
| `[[:alnum:]]` | 英数字 1 文字 |
| `[[:lower:]]` | 小文字 1 文字 |
| `[[:upper:]]` | 大文字 1 文字 |
| `[[:space:]]` | 空白文字 1 文字 |

運用スクリプトでは先頭に `LC_ALL=C` を書いておくと、サーバのロケール差による挙動のブレを防げます。

---

### ブラケット内で記号そのものを指定したいとき

| 指定したい文字 | 書き方 | 理由 |
|:--|:--|:--|
| `]` | `[]abc]` | `[` の直後に置くと文字として扱われる |
| `-` | `[abc-]` または `[-abc]` | 先頭か末尾に置くと範囲記号にならない |

```bash
$ ls [a-]*.txt                      # 「a」か「-」で始まるファイル（- を末尾に置く）
a-z.txt  abc.txt
```

---

### 先頭のドットはワイルドカードにマッチしない

```bash
$ ls -a                             # -a を付けると隠しファイルも表示される
.  ..  .bashrc  b.txt

$ ls *                              # * では .bashrc が出てこない
b.txt

$ ls .*                             # ドット始まりを明示的に指定すると出る
.  ..  .bashrc
```

`rm *` で設定ファイルまで消えないようにするための仕様です。

---

### スラッシュはワイルドカードにマッチしない

```bash
$ ls *.conf                         # カレント直下だけを見る（サブディレクトリは見ない）
$ ls */*.conf                       # 1階層下を見たいなら / を自分で書く
```

再帰的に探すなら `find` を使うか、`shopt -s globstar` を有効にして `**/` を使います。

---

### マッチしないとパターンがそのまま残る

```bash
$ ls *.zip                          # .zip が1つも無い状態で実行してみる
ls: cannot access '*.zip': No such file or directory
```

「`*.zip` というファイルが無い」というエラーに見えますが、実際は
「マッチ 0 件だったので `*.zip` という文字列がそのまま `ls` に渡された」結果です。

| 設定 | マッチ 0 件のときの挙動 |
|:--|:--|
| 既定 | パターン文字列がそのまま渡される |
| `shopt -s nullglob` | その単語ごと消える |
| `shopt -s failglob` | bash がエラーを出し、コマンドを実行しない |

---

### 展開が起きる順番

```
ブレース展開 {a,b}
  → チルダ展開 ~
    → 変数展開・コマンド置換 $VAR $( )
      → 単語分割
        → パス名展開 * ? [ ]
          → クォート除去
```

この順番を知っていると、次の挙動が説明できます。

```bash
$ PAT="*.txt"                       # 変数にワイルドカードの文字列を入れる

$ echo $PAT                         # 変数展開のあとにパス名展開が走る
A.txt a-z.txt abc.txt b.txt x.txt

$ echo "$PAT"                       # クォート内なのでパス名展開されない
*.txt
```

なお **ブレース展開 `{ }` はファイルが存在しなくても展開されます**（単なる文字列生成のため）。

```bash
$ echo {1..5}                       # 存在しない値でも連番の文字列を生成できる
1 2 3 4 5

$ cp nginx.conf{,.bak}              # → cp nginx.conf nginx.conf.bak（バックアップの定番）

$ mkdir -p log/{app,db}/{2025,2026} # 2×2 の組み合わせで4つのディレクトリを一括作成
```

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| `[abc]` が `abc.txt` にマッチしない | `[ ]` は 1 文字のみ | 3 文字なら `???` か `abc` |
| `[abc]` が `A.txt` を拾わない | `[ ]` は大文字小文字を区別する | `[aAbBcC]` か `nocaseglob` |
| `\` が消えてしまう | `\` は直後を打ち消して自身は消える | `\\` と 2 つ重ねる |
| `~` が展開されない | 直後が `/` でない、クォートの中 | `~/` の形にする、クォートを外す |
| `rm: cannot remove '*.log'` | マッチ 0 件でパターンが素通しされた | 先に `ls` で対象の有無を確認 |
| `*` で隠しファイルが対象にならない | 先頭のドットはマッチしない仕様 | `.*` を明示する |
| スペース入りファイル名で失敗 | 変数をクォートしていない | 必ず `"$VAR"` と書く |
| `[a-z]` に大文字が混ざる | ロケール依存 | `[[:lower:]]` か `LC_ALL=C` |
| 行継続の `\` が効かない | `\` の後ろにスペースがある | `cat -A` で行末を確認 |
| `man` で欲しい情報が出ない | セクション番号が違う（コマンドと設定ファイル） | `man -f キーワード` で一覧を確認 |
| `!ca` で違うコマンドが動いた | 「その文字列で始まる**直近**」を拾う | 確実に狙うなら `!番号` |
| `#3` を打っても何も起きない | `#` はコメント。履歴呼び出しは `!` | `!3` と書く |

**危険なコマンドの前は `echo` を付けて展開結果を確認する。** これが最も確実な事故防止策です。

```bash
$ echo rm -rf /var/log/*.gz         # 実行せず、何が削除対象になるかだけ確認
rm -rf /var/log/app.log.1.gz /var/log/app.log.2.gz
```

## クラウド実務メモ

**`aws` コマンドの `--query` はシングルクォートで囲む**

JMESPath 式には `[` `]` `*` `?` が頻出するため、クォートしないとシェルのパス名展開に食われます。

```bash
$ aws ec2 describe-instances --query Reservations[].Instances[].InstanceId
                                    # NG: [] をシェルが解釈してしまう可能性がある

$ aws ec2 describe-instances --query 'Reservations[].Instances[].InstanceId'
                                    # OK: クォートで囲んで aws にそのまま渡す
```

**Windows から持ち込んだパスに注意**

Windows のパス区切り `\` は、Linux では**エスケープ記号**です。
`C:\Users\systemi` をそのまま貼ると `\U` `\s` が消えて別物になります。
シングルクォートで囲むか、`/` に置き換えてから使います。

```bash
$ echo C:\Users\systemi             # \U と \s がエスケープ扱いされて消える
C:Userssystemi

$ echo 'C:\Users\systemi'           # シングルクォートで囲めばそのまま扱われる
C:\Users\systemi
```

**EC2 のユーザーデータは root 権限の非対話シェルで実行される**

`~` の展開先が `/root` になるため、一般ユーザのホームを想定した相対パスは動きません。

**Ansible の `{{ }}` や Terraform の `${}` と混同しない**

それぞれのツールが解釈するもので、シェルの展開とはタイミングが違います。
`ansible -m shell` などシェルを経由する場合は、どちらが先に展開されるかを意識します。
