## 内側から見るか外側から見るか

**同じ「ポートが開いているか」でも、見る位置で分かることが違います。**

```text
   [サーバの中から]  netstat -l / ss -l
        → プロセスが待ち受けているか             （アプリの問題かが分かる）

   [ネットワーク越しに]  nmap / nc
        → 実際に外から届くか                     （経路とファイアウォールが分かる）
```

**この2つが食い違うとき、答えははっきりしています。**

| 中から見ると | 外から見ると | 原因 |
|:--|:--|:--|
| LISTEN している | 届かない | **ファイアウォール / セキュリティグループ / 経路** |
| LISTEN していない | 届かない | **アプリが起動していない、または別のポートで待っている** |
| `127.0.0.1:80` で LISTEN | 届かない | **ループバックにしかバインドしていない** |

3つ目は実務で非常によくあります。**`netstat -ln` の `Local Address` が `127.0.0.1` なのか `0.0.0.0` なのかを必ず見てください。**

## nmap とは

**`nmap` は、対象のポートへ順にパケットを送り、どれが待ち受けているかを一覧するコマンド**です。
構成が分からないネットワークの調査や、セキュリティ検査に使います。

---

## 書式と対象の指定

```text
nmap [スキャンタイプ] [オプション] 対象
```

**対象はホスト1台だけでなく、範囲でも指定できます。**

| 書き方 | 意味 |
|:--|:--|
| `192.168.1.10` | ホスト1台 |
| `example.com` | ホスト名でも指定できる |
| `192.168.1.0/24` | **CIDR 表記でネットワーク全体** |
| `192.168.1.1-254` | **ハイフンで範囲** |
| `192.168.0-255.1-254` | オクテットごとに範囲を書ける |

実測で確かめます。

```bash
$ nmap -sn 127.0.0.1-3 | grep -c "Nmap scan report"   # 3台ぶんスキャンされるか数える
```

```text
3
```

**3 台として解釈されました。**

## 結果画面の見方

```bash
$ nmap 127.0.0.1                            # 既定のスキャンを実行する
```

```text
Starting Nmap 7.94SVN ( https://nmap.org ) at 2026-09-23 15:44 UTC
Nmap scan report for localhost (127.0.0.1)
Host is up (0.0000020s latency).
Not shown: 997 closed tcp ports (reset)
PORT    STATE SERVICE
22/tcp  open  ssh
80/tcp  open  http
443/tcp open  https

Nmap done: 1 IP address (1 host up) scanned in 0.07 seconds
```

| 行 | 意味 |
|:--|:--|
| `Host is up` | **対象が応答した**（latency は往復時間） |
| **`Not shown: 997 closed tcp ports`** | **表示を省いたポートの数と、その状態** |
| `PORT` | **ポート番号 / プロトコル** |
| `STATE` | **`open` / `closed` / `filtered`** |
| `SERVICE` | ポート番号から推定したサービス名（`nmap-services`（`/usr/share/nmap/nmap-services`。**`/etc/services` とは名前が違うことがある**） 由来） |

**`STATE` の3つの違いが最も重要**です。

```text
   open      … 応答があり、待ち受けている          （SYN に SYN+ACK が返った）
   closed    … 応答はあるが、待ち受けていない      （SYN に RST が返った）
   filtered  … 応答そのものが無い                  （途中で落とされている）
```

**`closed` と `filtered` を区別できるのが nmap の価値**です。

```text
   closed   → 相手のホストまでは届いている。アプリが起動していない
   filtered → 途中のファイアウォール / セキュリティグループで落ちている
```

**既定では上位 1000 ポートだけを調べます。** 実測で確かめます。

```bash
$ nmap 127.0.0.1 | grep "Not shown"         # 既定で何ポート調べるか
$ nmap -F 127.0.0.1 | grep "Not shown"      # -F では何ポートか
```

```text
Not shown: 997 closed tcp ports (reset)
Not shown: 97 closed tcp ports (reset)
```

開いていた 3 ポート（22 / 80 / 443）を足すと、**既定は 1000 ポート、`-F` は 100 ポート**です。

## スキャンタイプ

### 既定は実行ユーザで変わる

**スキャンタイプを省略したときの既定は、root かどうかで変わります。** これは見落としやすい点です。

```bash
$ nmap -d 127.0.0.1 -p 80 | grep -i "Initiating.*Scan"   # root で実行した場合
```

```text
Initiating SYN Stealth Scan at 15:44
```

```bash
$ su tu -c 'nmap -d 127.0.0.1 -p 80' | grep -i "Initiating.*Scan"   # 一般ユーザで実行した場合
```

```text
Initiating Ping Scan at 15:44
Initiating Connect Scan at 15:44
```

```text
   root で実行      → SYN スキャン（-sS 相当）。生パケットを作るので root が要る
   一般ユーザで実行 → Connect スキャン（-sT 相当）に自動で落ちる
```

**「既定は SYN スキャン」は root 前提の話**です。
一般ユーザで実行して結果が違うときは、まずここを疑ってください。

### 主なスキャンタイプ

| 指定 | 名前 | 内容 |
|:--|:--|:--|
| **`-sS`** | SYN スキャン | SYN だけ送って応答を見る。**接続を完了させないので速く、ログに残りにくい**。root が必要 |
| **`-sT`** | TCP 接続スキャン | **実際に接続を確立する**。一般ユーザでも使えるが遅く、相手のログに残る |
| **`-sU`** | UDP スキャン | UDP ポートを調べる。**非常に遅い** |
| **`-sn`** | Ping スキャン | **ポートは調べず、ホストが生きているかだけ**を見る（旧 `-sP`） |
| `-sA` | ACK スキャン | ファイアウォールのルールを推定する |

**`-sP` は古い書き方**で、現在は `-sn` です。nmap 7.x では `-sP` も互換のため受け付けます。

```bash
$ nmap -h | grep -- '-sn'                   # ヘルプでの表記を確認する
```

```text
  -sn: Ping Scan - disable port scan
  nmap -v -sn 192.168.0.0/16 10.0.0.0/8
```

（2 行目は EXAMPLES の行が引っかかったものです）

---

### -sS と -sT は何が違うのか パケットで見る

**表で「ハーフオープン」と説明されても分かりにくい**ので、
**同じポートを `-sS` と `-sT` でスキャンして、流れたパケットを並べます。**（実測）

**`-sS`（SYN スキャン）**

```bash
$ sudo nmap -sS -p 80 -Pn 10.10.0.2    # SYNスキャンを実行する
# 別の端末で tcpdump -i veth1 -n 'tcp port 80'
```

```text
① 10.10.0.1.47691 > 10.10.0.2.80: Flags [S],  seq 185906410, win 1024, options [mss 1460]
② 10.10.0.2.80 > 10.10.0.1.47691: Flags [S.], seq 75692308, ack 185906411, win 64240
③ 10.10.0.1.47691 > 10.10.0.2.80: Flags [R],  seq 185906411, win 0
                                         ▲ ACK を返さずに RST で打ち切っている
```

**`-sT`（TCP connect スキャン）**

```bash
$ nmap -sT -p 80 -Pn 10.10.0.2         # connect スキャンを実行する
```

```text
① 10.10.0.1.46124 > 10.10.0.2.80: Flags [S],  seq 3600326287, win 64240
② 10.10.0.2.80 > 10.10.0.1.46124: Flags [S.], seq 2956538613, ack 3600326288, win 65160
③ 10.10.0.1.46124 > 10.10.0.2.80: Flags [.],  ack 1, win 63
                                         ▲ ACK を返して接続を完了させている
④ 10.10.0.1.46124 > 10.10.0.2.80: Flags [R.], seq 1, ack 1, win 63
                                         ▲ そのあと切断している
```

**違いは ③ の 1 パケットだけ**です。

| | **`-sS`** | **`-sT`** |
|:--|:--|:--|
| **3 ウェイハンドシェイク** | **完了させない**（SYN → SYN+ACK → RST） | **完了させる**（SYN → SYN+ACK → ACK） |
| **相手のアプリから見ると** | **接続が来ていない**（カーネルで終わる） | **接続が来て、すぐ切れた**（アプリのログに残る） |
| **必要な権限** | **root**（パケットを自分で組み立てるため） | **一般ユーザで可**（OS の `connect()` を呼ぶだけ） |
| **速さ** | **速い** | やや遅い |
| **別名** | **ステルススキャン / ハーフオープンスキャン** | — |

> **`-sS` が「ステルス」と呼ばれるのは、昔のアプリが
> 「接続が完了しなかったものをログに残さなかった」から**です。
> **いまのファイアウォールや IDS は `-sS` も検知します。**
> **「ばれない」という意味ではありません。**

> **`-Pn` は「事前の生存確認をしない」オプション**です。
> **root で実行したときの生存確認は ICMP だけではありません。**
> **80 番への ACK や 443 番への SYN も使う**ので、
> **ICMP を止めているだけなら `Host is up` と判定されます**（実測）。
> **`-Pn` が要るのは、ICMP も 80 / 443 への探査もすべて遮断されている相手**です。

## ポートを絞る

| オプション | 意味 |
|:--|:--|
| **`-p ポート`** | **調べるポートを指定する**（`-p 80`、`-p 20-25`、`-p 22,80,443`） |
| `-p-` | **全 65535 ポート**を調べる（時間がかかる） |
| **`-F`** | **有名ポート 100 個だけ**を調べる（高速スキャン） |
| `--open` | 開いているポートだけを表示する |

```bash
$ nmap -p 80 127.0.0.1 | sed -n '4,6p'      # 1つのポートだけ調べる
```

```text
PORT   STATE SERVICE
80/tcp open  http
```

```bash
$ nmap -p 20-25 127.0.0.1 | sed -n '4,11p'  # ポートの範囲を調べる
```

```text
PORT   STATE  SERVICE
20/tcp closed ftp-data
21/tcp closed ftp
22/tcp open   ssh
23/tcp closed telnet
24/tcp closed priv-mail
25/tcp closed smtp
```

**書式の注意**

```text
   ○ nmap -p 80 192.168.1.10
   ✗ nmap 192.168.1.10:80      …  Failed to resolve "192.168.1.10:80". で失敗する
   ✗ nmap 192.168.1.10 80      …  80 が 別のホスト として追加スキャンされる
```

**2 つ目は「効かない」だけでは済みません。** 実測します。

```bash
$ nmap -sL 127.0.0.1 80                     # 実際には送信せず対象だけ一覧する
```

```text
Nmap scan report for localhost (127.0.0.1)
Nmap scan report for 80 (0.0.0.80)
Nmap done: 2 IP addresses (0 hosts up) scanned in 0.00 seconds
```

**`80` が `0.0.0.80` というホストとして解釈されました。**
意図しない相手をスキャンしてしまうので、**`-p` は必ず付けてください。**

**TCP ポートを調べるだけなら、スキャンタイプの指定は要りません。**
既定が TCP を使うスキャンだからです。

## nmap のオプション早見表

**`nmap` はオプションが非常に多いので、用途ごとにまとめます。**

### 対象の指定

| 書き方 | 意味 |
|:--|:--|
| **`nmap 10.0.1.5`** | **1 台** |
| **`nmap 10.0.1.0/24`** | **ネットワーク全体**（`nmap` は 256 アドレスすべてを対象にする。`-sL` で確認できる） |
| **`nmap 10.0.1.1-50`** | **範囲指定** |
| **`nmap 10.0.1.5 10.0.1.9`** | **複数を並べる** |
| **`nmap -iL targets.txt`** | **ファイルから読む**（1 行 1 対象） |
| `nmap --exclude 10.0.1.1` | 除外する |

### ポートの指定

| 書き方 | 意味 |
|:--|:--|
| **`-p 22`** | **1 ポート** |
| **`-p 22,80,443`** | **複数** |
| **`-p 1-1024`** | **範囲** |
| **`-p-`** | **全 65535 ポート**（時間がかかる） |
| **`--top-ports 100`** | **よく使われる上位 100 ポート** |
| `-p U:53,T:22` | UDP と TCP を分けて指定。**`-sU` も一緒に指定しないと UDP 側は無視される**（警告が出る） |
| （指定なし） | **よく使われる 1000 ポート**（既定） |

### スキャンの種類

| オプション | 何をするか | 権限 |
|:--|:--|:--|
| **`-sS`** | **SYN スキャン**（既定。前節のとおり） | **root** |
| **`-sT`** | **TCP connect スキャン** | 一般ユーザ可 |
| **`-sU`** | **UDP スキャン**。**非常に遅い** | **root** |
| **`-sn`** | **ポートスキャンをせず、生きているホストだけ探す** | — |
| **`-sV`** | **サービスのバージョンを調べる** | — |
| `-sA` | ACK スキャン（ファイアウォールの有無を調べる） | root |
| `-O` | OS を推定する | **root** |
| `-A` | `-sV` `-O` などをまとめて有効にする | root |

### 速度と挙動

| オプション | 意味 |
|:--|:--|
| **`-Pn`** | **事前の生存確認をしない**。**相手が「落ちている」と誤判定されてスキャンされないのを防ぐ**。ただし全 IP を生きているとみなすので、`/24` などでは遅くなる |
| **`-n`** | **DNS を引かない**（速くなる） |
| **`-T0` 〜 `-T5`** | **速度**。**既定は `-T3`**（`nmap -d` で `max-retries: 10` と確認）。回線が良ければ `-T4` を使うことが多い。`-T0` は極めて遅い |
| **`-v`** / `-vv` | **途中経過を出す** |
| **`-oN ファイル`** | **結果を読みやすい形式で保存** |
| **`-oX ファイル`** | **XML で保存**（ツールに食わせるとき） |
| `-oG ファイル` | grep しやすい形式で保存 |
| `--open` | **開いているポートだけ表示する** |
| `--reason` | **なぜその状態と判断したかを出す** |

**業務でよく打つ形**

```bash
$ sudo nmap -sS -Pn -n -T4 --open -p 1-1024 10.0.1.5     # 下位1024番で開いているものだけ
$ nmap -sT -Pn -n -p 22,80,443 10.0.1.0/24               # 特定ポートをセグメント全体で
$ sudo nmap -sn 10.0.1.0/24                              # 生きているホストの棚卸し
$ sudo nmap -sV -p 443 10.0.1.5                          # 何が動いているか特定する
$ sudo nmap -sS -Pn -oN scan-$(date +%F).txt 10.0.1.5    # 結果をファイルに残す
```

## ポートの状態は6種類ある

**`nmap` が返す `STATE` は `open` / `closed` だけではありません。**
**切り分けではこの区別が決定的に効きます。**

| STATE | 意味 | どう判断されるか |
|:--|:--|:--|
| **`open`** | **待ち受けている** | **SYN に SYN+ACK が返った** |
| **`closed`** | **届いていて、RST が返った** | **SYN に RST が返った** |
| **`filtered`** | **遮られている** | **何も返らない、または ICMP の到達不能が返った** |
| `unfiltered` | ACK は通るが開閉不明 | ACK スキャン（`-sA`）のときだけ |
| `open\|filtered` | 開いているか遮断かが区別できない | UDP スキャンでよく出る |
| `closed\|filtered` | 閉じているか遮断かが区別できない | まれ |

**`closed` と `filtered` の違いが最重要**です。

```text
  closed    RST が返ってきた
                → たいていは アプリ側（待ち受けていない）
                → ただし ファイアウォールが RST で拒否 しても closed になる

  filtered  何も返らない、または ICMP 到達不能が返った
                → 経路側（セキュリティグループ、firewalld、ACL）
```

**同じ `filtered` でも、理由はいくつもあります。**
**`--reason` を付けると判定の根拠が出る**ので、ここで切り分けます。

```bash
$ nmap -sS -Pn --reason -p 80,8001,8002,443 10.10.0.2   # 判定の根拠つきで出す
```

```text
PORT     STATE    SERVICE        REASON
80/tcp   open     http           syn-ack ttl 64
443/tcp  closed   https          reset ttl 64
8001/tcp filtered vcom-tunnel    no-response
8002/tcp filtered teradataordbms admin-prohibited ttl 64
```

**この実測では、相手側をこう設定しています。**

| ポート | 相手側の設定 | REASON |
|:--|:--|:--|
| **80** | **待ち受けている** | **`syn-ack`** |
| **443** | **何もしていない**（閉じている） | **`reset`** |
| **8001** | **`iptables -j DROP`** | **`no-response`** |
| **8002** | **`iptables -j REJECT --reject-with icmp-admin-prohibited`** | **`admin-prohibited`** |

**さらに `REJECT --reject-with tcp-reset` にすると `closed` になります。**（実測）

```text
8003/tcp closed mcreport reset ttl 64
      ▲ ファイアウォールが RST を返しているのに、アプリが閉じているのと区別がつかない
```

> **だから `closed` を見て「アプリ側の問題」と断定できません。**
> **相手にログインできるなら `ss -lnt` で待ち受けの有無を確かめる**のが確実です
> （[ソケットの確認_ss](../08_ネットワーク/ソケットの確認_ss.md)）。
>
> **`REASON` を見る癖を付けてください。**`no-response` なのか `admin-prohibited` なのかで、
> **誰に相談すべきかが変わります。**

**実測**（10.10.0.2 の 22 / 80 / 8080 を開け、443 は閉じた状態）

```bash
$ nmap -sT -p 22,80,443,8080 10.10.0.2     # 4つのポートを調べる
```

```text
PORT     STATE  SERVICE
22/tcp   open   ssh
80/tcp   open   http
443/tcp  closed https
8080/tcp open   http-proxy
```

```bash
$ nmap 10.10.0.2                       # 既定（よく使われる1000ポート）
```

```text
Not shown: 997 closed tcp ports (reset)
PORT     STATE SERVICE
22/tcp   open  ssh
80/tcp   open  http
8080/tcp open  http-proxy
MAC Address: C2:64:A8:1B:BA:14 (Unknown)
```

> **`Not shown: 997 closed tcp ports (reset)`** の `(reset)` が、
> **「RST が返ってきたので closed と判断した」という根拠**です。
> **`--reason` を付けると、各ポートについて同じ根拠が出ます。**
>
> **ここが `filtered` と出た場合は、RST すら返っていない**ということです。

## OS を推定する

**`-O` は、応答パケットの癖から OS の種類を推定**します。

```bash
$ nmap -O 127.0.0.1 | sed -n '3,10p'        # OS の推定を試みる
```

```text
Host is up (0.000062s latency).
Not shown: 997 closed tcp ports (reset)
PORT    STATE SERVICE
22/tcp  open  ssh
80/tcp  open  http
443/tcp open  https
No exact OS matches for host (If you know what OS is running on it, see https://nmap.org/submit/ ).
TCP/IP fingerprint:
OS:SCAN(V=7.94SVN%E=4%D=9/23%OT=22%CT=1%CU=43596%PV=N%DS=0%DC=L%G=Y%TM=6AB3
```

**`No exact OS matches for host` — 必ず特定できるとは限りません。**
開いているポートが少ない、ファイアウォールが挟まっている、といった条件では推定が外れます。
**`-O` の結果は「参考値」として扱ってください。**

`-O` も生パケットを作るため **root 権限が必要**です。

| オプション | 意味 |
|:--|:--|
| `-O` | OS を推定する |
| `-sV` | **サービスのバージョン**を推定する（バナーを読む） |
| `-A` | `-O` と `-sV` などをまとめて有効にする |
| `-n` | 名前解決をしない |
| `-v` / `-vv` | 詳細に表示する |
| `-oN ファイル` | 結果をテキストで保存する |

## nc とは

**`nc`（netcat）は、TCP / UDP で「とりあえず繋いでみる」ためのコマンド**です。
「ネットワークの十徳ナイフ」と呼ばれます。

```text
nc [オプション] ホスト ポート
```

### ポートが開いているか調べる

**`-z`（接続だけ試してデータを送らない）と `-v`（結果を表示）**の組み合わせが定番です。

```bash
$ nc -zv 127.0.0.1 20-25                    # ポート範囲への接続を試す
```

```text
nc: connect to 127.0.0.1 port 20 (tcp) failed: Connection refused
nc: connect to 127.0.0.1 port 21 (tcp) failed: Connection refused
Connection to 127.0.0.1 22 port [tcp/ssh] succeeded!
nc: connect to 127.0.0.1 port 23 (tcp) failed: Connection refused
nc: connect to 127.0.0.1 port 24 (tcp) failed: Connection refused
nc: connect to 127.0.0.1 port 25 (tcp) failed: Connection refused
```

**`succeeded!` が開いているポート**です。**ポートはハイフンで範囲指定できます。**

```text
   Connection refused   … 相手まで届いたが待ち受けていない  （nmap の closed に相当）
   （何も返らず固まる）  … 途中で落とされている              （nmap の filtered に相当）
```

**固まる場合は `-w` でタイムアウトを付けてください。**

```bash
$ nc -zv -w 3 10.0.0.5 3306                 # 3秒で諦める
```

### データを送る

**`-z` を付けなければ、標準入力の内容がそのまま相手へ流れます。**

```bash
$ (nc -l 127.0.0.1 7777 > recv.txt &)       # 受信側を用意する
$ echo "hello from client" | nc -q1 127.0.0.1 7777   # パイプで送る
$ cat recv.txt                              # 受信内容を確認する
```

```text
hello from client
```

**HTTP を手で話すこともできます。**

```bash
$ printf 'GET / HTTP/1.0\r\n\r\n' | nc example.com 80   # HTTP リクエストを直接送る
```

**telnet の代わりに使えます。** telnet が入っていない環境でも `nc` はたいてい使えます。

### 待ち受け側になる

**`-l` を付けると、`nc` 自身が待ち受けになります。**

```bash
$ nc -l 8080                                # 8080 番で待ち受ける
```

**疎通確認の相手役として非常に便利**です。

```text
  [サーバ側]  nc -l 8080            … とりあえず 8080 を開けておく
  [手元から]  nc -zv サーバ 8080    … 経路とファイアウォールだけを試験する
```

**アプリを起動しなくても、経路とファイアウォールだけを切り分けられます。**
セキュリティグループを直したときの確認に、この組み合わせをよく使います。

| オプション | 意味 |
|:--|:--|
| **`-l`** | **待ち受けモード**になる |
| **`-z`** | 接続を試すだけでデータを送らない |
| **`-v`** | 結果を表示する |
| `-w 秒` | 接続のタイムアウト |
| `-u` | **UDP** を使う（既定は TCP） |
| `-p ポート` | 送信元ポートを指定する |
| `-4` / `-6` | IPv4 / IPv6 を明示する |

> **実装差に注意** … `nc` には OpenBSD 版、GNU 版、Nmap 付属の `ncat` があり、
> **オプションが微妙に違います。** 検証環境は OpenBSD 版でした。
> ```text
> $ nc -h
> OpenBSD netcat (Debian patchlevel 1.226-1ubuntu2)
> ```
> `-q` や `-e` は版によって有無が変わるので、**手元で `nc -h` を確認**してください。

## nc のオプション早見表

**`nc` には実装が複数あります**（OpenBSD 版・GNU 版・Nmap の `ncat`）。
**オプションが微妙に違う**ので、まず手元のものを確認してください。

```bash
$ nc -h 2>&1 | head -2                 # どの実装かを確かめる
```

```text
OpenBSD netcat (Debian patchlevel 1.226-1ubuntu2)
usage: nc [-46CDdFhklNnrStUuvZz] [-I length] [-i interval] [-M ttl]
```

**以下は OpenBSD 版（Debian / Ubuntu の既定）で実測したもの**です。

| オプション | 意味 |
|:--|:--|
| **`-z`** | **データを送らず、接続できるかだけ調べる**（スキャンモード） |
| **`-v`** | **結果を表示する**。**失敗は `-v` が無いと何も出ない**ので、`-z` と組で使う |
| **`-l`** | **待ち受け側になる** |
| **`-k`** | **`-l` と併用。1 回接続が切れても待ち受けを続ける** |
| **`-n`** | **名前解決をしない** |
| **`-u`** | **UDP を使う**（既定は TCP） |
| **`-w 秒`** | **タイムアウト**。**これが無いと応答の無い相手で止まる** |
| **`-p ポート`** | **送信元ポートを指定する** |
| `-s アドレス` | 送信元アドレスを指定する |
| `-4` / `-6` | IPv4 / IPv6 に固定する |
| `-U` | UNIX ドメインソケットを使う |

> **RHEL 系では `nmap-ncat` パッケージの `ncat` が入っていることが多い**です。
> **`ncat` では `-z` の動作や出力が OpenBSD 版と異なります。**
> **手順書に書くときは、どちらの実装を前提にしているか明記**してください。

### ポートが開いているか調べる 実測

```bash
$ nc -zv 10.10.0.2 80                  # 80番が開いているか
```

```text
Connection to 10.10.0.2 80 port [tcp/http] succeeded!
```

```bash
$ nc -zv 10.10.0.2 443                 # 443番が開いているか
```

```text
nc: connect to 10.10.0.2 port 443 (tcp) failed: Connection refused
```

**エラーメッセージで原因が分かれます。**

| 出力 | 何が起きているか | 次に見るところ |
|:--|:--|:--|
| **`succeeded!`** | **開いている** | — |
| **`failed: Connection refused`** | **届いたが、そのポートが待ち受けていない**（RST が返った） | **アプリ側**。ただし**ファイアウォールが RST で拒否**しても同じ表示（下記） |
| **`timed out: Operation now in progress`** | **`-w` で指定した秒数まで待って、何も返らなかった** | **経路側**（DROP されている） |
| **`failed: Connection timed out`** | **`-w` を付けず、OS が諦めた**（2 分前後かかる） | 同上 |
| **`failed: No route to host`** | **ICMP の到達不能が返った**（`REJECT --reject-with icmp-admin-prohibited` など） | **経路上のファイアウォール**。`firewalld` の既定の拒否方式がこれ |
| **`failed: Network is unreachable`** | **自サーバに経路が無い** | **自サーバのルーティング**（`ip route`） |
| `Name or service not known` | 名前が引けない | DNS |

**タイムアウトの文言は `-w` の有無で変わります。**（実測）

```text
  nc -zv -w 2 10.10.0.2 8001    →  timed out: Operation now in progress
  nc -zv    10.10.0.2 8001      →  failed: Connection timed out     （2分前後かかる）
```

> **`No route to host` を見て「ルーティングの問題」と決めつけないでください。**
> **ICMP の到達不能（admin-prohibited など）が返ったときにも、この文言になります。**（実測）
> **`Network is unreachable` が自サーバ側の経路の話、
> `No route to host` は相手側か経路上からの拒否**、と区別してください。

### 範囲をまとめて調べる

```bash
$ nc -zv 10.10.0.2 78-82               # 78〜82番をまとめて調べる
```

```text
nc: connect to 10.10.0.2 port 78 (tcp) failed: Connection refused
nc: connect to 10.10.0.2 port 79 (tcp) failed: Connection refused
Connection to 10.10.0.2 80 port [tcp/http] succeeded!
nc: connect to 10.10.0.2 port 81 (tcp) failed: Connection refused
nc: connect to 10.10.0.2 port 82 (tcp) failed: Connection refused
```

**開いているものだけを見たいときは絞り込みます。**

```bash
$ nc -zv 10.10.0.2 1-1024 2>&1 | grep succeeded   # 開いているポートだけ出す
```

> **`nc` の範囲スキャンは `nmap` より遅く、機能も限られます。**
> **`nmap` が入っていない本番サーバで、手早く数ポート見たいとき**に使うのが現実的な用途です。

### -w でタイムアウトを必ず付ける

```bash
$ nc -zv -w 2 10.0.9.9 80              # 2秒で諦める
```

**`-w` が無いと、応答しない相手に対して OS の既定（長いと 2 分以上）まで待ちます。**
**スクリプトに書くときは必ず付けてください。**

### ファイルを送る

**`scp` が使えない環境での緊急手段**です。

```bash
# 受け取る側（先に起動する）
$ nc -l 9100 > received.txt            # 9100番で待ち受けてファイルに書く

# 送る側
$ nc -w 2 10.10.0.2 9100 < send.txt    # ファイルを流し込む
```

**実測では `test-payload-12345` が正しく転送されました。**

> **`nc` の通信は暗号化されません。**
> **認証もありません。** **誰でも、そのポートに繋げば受け取れます。**
> **本番では `scp` / `rsync over ssh` を使い、`nc` は閉じた検証環境に限ってください。**

### サービスが本当に応答するか確かめる

**`-z` は「繋がるか」までしか分かりません。**
**アプリが正しく応答しているかは、実際に喋らせて確かめます。**

```bash
$ printf 'GET / HTTP/1.0\r\n\r\n' | nc -w 3 10.0.1.5 80   # HTTPで喋ってみる
$ nc -w 3 10.0.1.5 25                  # SMTP のバナーを見る
$ nc -zvu 10.0.1.5 53                  # UDP の 53番（DNS）を調べる
```

> **UDP（`-u`）の確認は当てになりません。**
> **UDP には「接続」が無く、応答しないのが正常なサービスも多い**ためです。
> **`nc -zu` が成功と出ても、本当に開いているとは限りません。**

## ネットワーク調査コマンドの整理

**どれも「ネットワークを調べる」ですが、見ているものが違います。**

| コマンド | 何を見るか | 位置 |
|:--|:--|:--|
| **`ping`** | 相手に届くか（ICMP） | 外から |
| **`traceroute`** | どの経路を通るか | 外から |
| **`mtr`** | 経路＋各ホップのロス率と遅延を継続測定 | 外から |
| **`nmap`** | どのポートが開いているか | 外から |
| **`nc`** | 特定のポートに繋がるか、データが流れるか | 外から |
| **`tcpdump`** | 実際に流れているパケット | インタフェース上 |
| **`netstat` / `ss`** | 自ホストの接続・待ち受け・統計 | 中から |
| **`arp`** | IP と MAC の対応（ARP キャッシュ） | 中から |
| **`dig` / `nslookup`** | 名前解決の結果 | DNS へ |

**切り分けの順番**

```text
  1. ping          … そもそも相手に届くか
  2. traceroute    … 届かないなら、どこまで行っているか
  3. nc / nmap     … 届くなら、そのポートが開いているか
  4. tcpdump       … 開いているはずなのに繋がらないなら、パケットを直接見る
  5. netstat / ss  … 相手側にログインできるなら、待ち受けているか確認する
```

## 使ってよい相手とよくない相手

**ポートスキャンは強力なので、扱いには注意が必要です。**

```text
  ○ 自分が管理しているホスト
  ○ 検証環境
  ○ 依頼を受けて実施するセキュリティ検査（書面で合意があるもの）

  ✗ 他人が管理しているホスト
  ✗ クラウド事業者の許可を取っていない大規模スキャン
  ✗ 「気になったから」で外部サイトを試すこと
```

**無断のポートスキャンは攻撃の準備行為とみなされます。**
IDS / IPS に検知され、通報や接続遮断につながることもあります。

**`tcpdump` も同様**です。他人の通信が見えてしまうため、
本番環境で取ったキャプチャの扱い（保存先・共有範囲・保持期間）は事前に決めておいてください。

**実務での安全な進め方**

```text
  1. 対象と範囲を書面で確認する（IP、ポート、実施時間帯）
  2. 関係者へ事前に予告する（監視チームが誤検知で騒がない）
  3. -F や -p で範囲を絞り、-p- のフルスキャンは必要なときだけ
  4. 結果を -oN で保存し、いつ何を実施したか記録に残す
```
