## 特殊パーミッションとは

通常のパーミッションは、**所有者（u）・所有グループ（g）・その他（o）** の 3 者に対して
**読み取り（r）・書き込み（w）・実行（x）** を許可するしくみです。

特殊パーミッションは、この `rwx` とは**別枠**で用意された 3 つのビットで、
「誰の権限で動くか」「新しく作られるファイルがどのグループになるか」といった、
`rwx` だけでは表現できない挙動を制御します。

| ビット | 名前 | ファイルに付けたとき | ディレクトリに付けたとき |
|:--|:--|:--|:--|
| `4000` | SUID（Set User ID） | 実行時、**所有ユーザ**の権限で動く | 効果なし（Linux では無視される） |
| `2000` | SGID（Set Group ID） | 実行時、**所有グループ**の権限で動く | 配下に作られるファイルが**所有グループを継承**する |
| `1000` | スティッキービット | 効果なし（現在の Linux では無視される） | ファイルの所有者・ディレクトリの所有者・root 以外は削除・改名できなくなる |

**このノートで主に扱うのは SGID です。** 実務で使う場面のほとんどは
「ディレクトリに対する SGID」で、チーム共有フォルダのグループを統一する用途です。

## なぜ SGID が必要なのか

Linux では、ファイルに必ず「所有者（ユーザ）」と「所有グループ」が付きます。
**通常は、ファイルを作った人の「そのとき使っているプライマリグループ」が、そのまま所有グループになります。**

このため、複数人が同じ共有フォルダにファイルを置くと、SGID なしではグループがばらばらになります。

```
【SGID なしのフォルダ】
  Aさんが作成 → ファイルのグループ = Aさんのグループ
  Bさんが作成 → ファイルのグループ = Bさんのグループ
  → グループが不統一。他のメンバーが編集権限を持てない事態が起きる
```

SGID を立てたフォルダなら、誰が作っても「フォルダ自身が持つグループ」に統一されます。

```
【SGID ありのフォルダ（グループ = devteam）】
  Aさんが作成 → ファイルのグループ = devteam
  Bさんが作成 → ファイルのグループ = devteam
  → 誰が作っても devteam に統一される
```

**補足** … 「グループが揃う」ことと「メンバーが書き込める」ことは別問題です。
SGID はグループを揃えるだけで、パーミッションのビットは `umask` が決めます。
共有ディレクトリでは `chmod 2775` と `umask 002` をセットで使います。

## SGID の効果

**意味** … 対象がファイルかディレクトリかで、まったく違う意味になります。ここが最大のポイントです。

| 対象 | 効果 |
|:--|:--|
| **実行可能ファイル** | 実行したユーザではなく、**そのファイルの所有グループ**の権限でプログラムが動く |
| **ディレクトリ** | そこに新しく作られたファイル・サブディレクトリが、作成者のプライマリグループではなく**親ディレクトリの所有グループを自動で継承**する |

**例文**

```bash
$ ls -l /usr/bin/chage             # ファイルに付いた SGID の実例
-rwxr-sr-x 1 root shadow 72184  5月 30  2024 /usr/bin/chage

$ ls -ld /var/local                # ディレクトリに付いた SGID の実例
drwxrwsr-x 2 root staff 4096  4月 22  2024 /var/local
```

**補足** … `chage`（パスワード有効期限を変更するコマンド）は、一般ユーザが実行しても
`shadow` グループの権限で動くため、`/etc/shadow` を読めます。
「root 権限を丸ごと渡さずに、必要な範囲だけ権限を貸す」のが SUID / SGID の考え方です。

**補足 … ディレクトリの SGID はサブディレクトリにも伝染する**

SGID ディレクトリの中に作られたサブディレクトリは、グループだけでなく **SGID ビットそのもの**も
引き継ぎます。一度立てておけば、階層を掘っても設定が続きます。

```bash
$ mkdir demo && chgrp devteam demo && chmod g+s demo # 検証用に SGID 付きディレクトリを用意する
$ mkdir demo/sub                   # 配下にサブディレクトリを作る
$ ls -ld demo/sub                  # グループも SGID(s) も引き継がれている
drwxr-sr-x 2 systemi devteam 4096  8月 31 11:22 demo/sub
```

## パーミッション文字列での見え方

**意味** … 特殊パーミッションは独立した列を持たず、`rwx` の **実行権（x）の位置に重ねて**表示されます。

```bash
$ ls -ld test_sgid                 # -d を付けると「中身」ではなく「そのディレクトリ自身」が出る
drwxr-sr-x 2 systemi devteam 4096  8月 31 09:23 test_sgid
```

1 列目の `drwxr-sr-x` を 1 文字ずつ分解すると、次のようになります。

| 位置 | 文字 | 意味 |
|:-:|:-:|:--|
| 1 | `d` | ディレクトリであることを示す |
| 2-4 | `rwx` | 所有者（systemi）の権限：読み・書き・実行すべて可 |
| 5-7 | `r-s` | グループ（devteam）の権限：読み取り可、書き込み不可、**`s` = SGID + 実行権あり** |
| 8-10 | `r-x` | その他のユーザの権限：読み取り・実行可 |

**表示位置の対応**

| ビット | 表示される位置 | 実行権あり | 実行権なし |
|:--|:--|:-:|:-:|
| SUID | 所有者の `x`（4 文字目） | `s` | `S` |
| SGID | グループの `x`（7 文字目） | `s` | `S` |
| スティッキービット | その他の `x`（10 文字目） | `t` | `T` |

**補足 … 大文字が出たら設定ミスを疑う**

小文字（`s` / `t`）は「実行権があり、かつ特殊ビットも立っている」状態、
大文字（`S` / `T`）は「実行権がないのに特殊ビットだけ立っている」状態です。

```bash
$ chmod 2745 noexec                # グループの実行権(x)を落として SGID だけ立てる
$ ls -ld noexec                    # 大文字 S になる＝ほぼ意図しない状態
drwxr-Sr-x 2 systemi devteam 4096  8月 31 11:22 noexec
```

ディレクトリの実行権は「中に入る（`cd` する）権利」なので、
これを落とすとグループのメンバーは共有フォルダに入れません。大文字 `S` はまず設定ミスです。

## 数値で指定する

**意味** … `chmod` の数値表記を **4 桁**にすると、先頭の 1 桁が特殊パーミッションになります。
3 桁で指定したときの扱いは、**対象がディレクトリかファイルかで変わります**（後述）。

| 桁 | 意味 | 値 |
|:-:|:--|:--|
| 1 桁目 | 特殊パーミッション | `4`=SUID / `2`=SGID / `1`=スティッキー（合計値で併用可） |
| 2 桁目 | 所有者 | `r`=4 / `w`=2 / `x`=1 |
| 3 桁目 | 所有グループ | 同上 |
| 4 桁目 | その他 | 同上 |

**例文**

```bash
$ chmod 2775 demo                  # 2=SGID、775=所有者rwx グループrwx その他r-x
$ ls -ld demo                       # 設定後のパーミッションを確認する
drwxrwsr-x 3 systemi devteam 4096  8月 31 11:22 demo

$ stat -c '%a %A' demo             # %a で数値、%A で文字列のパーミッションを表示
2775 drwxrwsr-x
```

**補足 … 3 桁で上書きしたときの挙動はディレクトリとファイルで違う**

GNU coreutils の `chmod` は、**ディレクトリ**の SUID / SGID を数値指定から保護します。
共有ディレクトリの設定をうっかり壊さないための仕様で、`chmod 775` でも `chmod 0775` でも SGID は残ります。
一方、**ファイル**は 3 桁で上書きすると特殊ビットが落ちます。

```bash
$ ls -ld demo                       # 上書き前の状態を確認する
drwxrwsr-x 3 systemi devteam 4096  8月 31 11:22 demo
$ chmod 775 demo                   # ディレクトリは 3桁で上書きしても SGID(s) が残る
$ ls -ld demo                       # SGID の s が残っていることを確認する
drwxrwsr-x 3 systemi devteam 4096  8月 31 11:22 demo

$ ls -l f.sh                        # 上書き前の状態を確認する（s が付いている）
-rwxr-sr-x 1 systemi systemi 0  8月 31 11:26 f.sh
$ chmod 755 f.sh                   # ファイルは 3桁で上書きすると SGID が消える
$ ls -l f.sh                        # s が x に変わっている＝SGID が消えた
-rwxr-xr-x 1 systemi systemi 0  8月 31 11:26 f.sh
```

ディレクトリから SGID を確実に外したいときは、記号指定の `chmod g-s` か、
`=` で全ビットを置き換える `chmod =775` を使います。

```bash
$ chmod g-s demo                   # SGID だけを外す（意図が明確でこちらが安全）
$ chmod =775 demo                  # = は指定したビット以外をすべて落とす
```

## ひとつずつ例文で確認

### SUID

**意味** … 実行ファイルに付けると、**実行したユーザではなくファイルの所有ユーザの権限**で動きます。
「一般ユーザに root しか触れないファイルを、限定された方法で触らせる」ために使います。

**例文**

```bash
$ ls -l /usr/bin/passwd            # 4文字目が s ＝ SUID が立っている
-rwsr-xr-x 1 root root 64152  5月 30  2024 /usr/bin/passwd

$ chmod u+s myprog                 # SUID を付ける
$ chmod u-s myprog                 # SUID を外す
$ chmod 4755 myprog                # 数値なら先頭が 4
```

**補足** … `passwd` は `/etc/shadow`（root しか書けない）を更新する必要があるため SUID が付いています。
一般ユーザが `passwd` を実行している間だけ、プロセスは root の権限を持ちます。
**自作プログラムに安易に SUID を付けるのは危険**で、そのプログラムに脆弱性があれば
そのまま root 権限の奪取につながります。

---

### SGID

**意味** … ファイルに付ければ「所有グループの権限で実行」、
ディレクトリに付ければ「配下に作られるものが所有グループを継承」します。
実務で使うのはほぼ後者です。

**例文**

```bash
$ chmod g+s shared                 # ディレクトリに SGID を付ける
$ chmod g-s shared                 # 外す
$ chmod 2775 shared                # 数値なら先頭が 2

$ ls -l /usr/bin/ssh-agent         # 7文字目が s ＝ ファイルに付いた SGID
-rwxr-sr-x 1 root _ssh 309688  4月 28 09:29 /usr/bin/ssh-agent
```

**補足** … ディレクトリの SGID が効くのは **これから作られるもの**だけです。
すでに置かれているファイルのグループは変わらないため、
途中から SGID を導入したときは `chgrp -R` で既存分を揃えます。

```bash
$ chgrp -R devteam shared          # -R で配下すべてのグループをまとめて変更する
```

### スティッキービット

**意味** … ディレクトリに付けると、**そのディレクトリ内のファイルを削除・改名できるのは、
ファイルの所有者・ディレクトリの所有者・root だけ**になります。
「全員が書き込めるが、他人のファイルは消せない」共有領域を作るための機能です。

**例文**

```bash
$ ls -ld /tmp                      # 末尾が t ＝ スティッキービットが立っている
drwxrwxrwt 10 root root 4096  8月 31 11:21 /tmp

$ chmod +t shared                  # スティッキービットを付ける
$ chmod o+t shared                 # その他ユーザに t を追加する書き方（同じ結果）
$ chmod 1755 shared                # 数値なら先頭が 1（755 に 1000 を足す）
$ chmod 1777 shared                # /tmp と同じにするならこちら
```

**補足** … 通常、ディレクトリに書き込み権（`w`）があると、**中身のファイルの所有者が誰であっても削除できます**。
ファイルの削除は「ファイルへの操作」ではなく「ディレクトリの一覧を書き換える操作」だからです。
`/tmp` のように全員が `rwx` を持つ場所では、これを防ぐためにスティッキービットが必須です。

**補足 … 設定のしかたは 2 通りあります**

| 書き方 | 考え方 |
|:--|:--|
| **`chmod 1755 dir`** | **通常のパーミッションの値に `1000` を加えた値**を設定する |
| **`chmod o+t dir`** | **その他ユーザに `t` という権限を追加**する |

同じ考え方が SUID（`4000` ／ `u+s`）と SGID（`2000` ／ `g+s`）にも当てはまります。

**補足 … root はスティッキービットの制限を受けません**

**root ユーザは、所有者でなくてもファイルを削除できます。**
スティッキービットは**一般ユーザ同士のいたずらや事故を防ぐもの**であって、
root に対する防御ではありません。

## 三つの特殊パーミッションの比較

| | SUID | SGID | スティッキービット |
|:--|:--|:--|:--|
| 記号での指定 | `u+s` | `g+s` | `+t`（`o+t`） |
| 数値 | `4000` | `2000` | `1000` |
| 表示位置 | 所有者の `x` | グループの `x` | その他の `x` |
| 表示文字 | `s` / `S` | `s` / `S` | `t` / `T` |
| **ファイル**に設定 | 実行時に**所有ユーザ**の権限を借りる | 実行時に**所有グループ**の権限を借りる | 効果なし |
| **ディレクトリ**に設定 | 効果なし（Linux では無視） | 配下の新規作成物が**所有グループを継承** | **他人のファイルを削除・改名できない** |
| 代表例 | `/usr/bin/passwd` | `/usr/bin/chage`、共有ディレクトリ | `/tmp`、`/var/tmp` |

**補足 … SUID と SGID を取り違えないための覚え方**

`u` は user（ユーザ）、`g` は group（グループ）です。
**`u+s` なら所有「ユーザ」の権限、`g+s` なら所有「グループ」の権限**を借りる、と記号で覚えると混同しません。
数値は `4`（SUID）→ `2`（SGID）→ `1`（スティッキー）と、`rwx` と同じく上位から並びます。

## 標準で SUID / SGID が付いているコマンド

**一般的な Linux システムにおいて、SUID や SGID が設定されているコマンドは、ごく少数しか存在しません。**
**SUID や SGID が設定されていると、一般ユーザでも root 権限でファイルを実行できる場合があり、
root 権限で不正に操作されるとセキュリティ上問題があるため**です。

**代表的な 4 つ**は、どれも「**一般ユーザにやらせたいが、root しか触れないものが必要**」という共通の事情を持ちます。

| コマンド | 何をするか | なぜ SUID / SGID が要るか |
|:--|:--|:--|
| **`passwd`** | **パスワードを管理する** | **`/etc/passwd`（`rw-r--r--`）と `/etc/shadow`（`rw-------`）を書き換える**必要がある。どちらも root 所有で、通常は一般ユーザが書き込めない |
| **`mount`** | **ファイルシステムをマウントする** | `/etc/fstab` に **`user` または `users`** が設定されていれば、SUID の効果で**一般ユーザも root 権限でマウント**できる |
| **`su`** | **ログインし直さずに他のユーザへ切り替える**（Switch User の略） | **`/etc/shadow` を読んで認証**を行う必要がある |
| **`crontab`** | **cron の設定ファイルを管理する** | **SUID だけでなく SGID が設定される場合**があり、その際は所有グループが特別なグループになっている。特別なディレクトリにアクセスするために必要 |

```bash
$ ls -l /usr/bin/passwd /usr/bin/mount /usr/bin/su /usr/bin/crontab   # 4文字目・7文字目の s を見る
-rwsr-xr-x. 1 root root     64152  2月  1  2026 /usr/bin/passwd
-rwsr-xr-x. 1 root root     59976  2月  1  2026 /usr/bin/mount
-rwsr-xr-x. 1 root root     52880  2月  1  2026 /usr/bin/su
-rwxr-sr-x. 1 root crontab  43352  2月  1  2026 /usr/bin/crontab    ← こちらは SGID
```

> **`/etc/passwd` と `/etc/shadow` の違い**
>
> | ファイル | 中身 | 標準のパーミッション |
> |:--|:--|:--|
> | **`/etc/passwd`** | **ユーザのアカウント情報** | **`rw-r--r--`**（誰でも読めるが、書けるのは root だけ） |
> | **`/etc/shadow`** | **暗号化されたパスワード（シャドウパスワード）とパスワードの有効期限** | **`rw-------`** など（**通常は root のみ読み書き可能**） |

**このリストが問われる理由**

**「SUID / SGID が付いているものを挙げよ」という問いは、裏返すと
「なぜこの 4 つだけ特別扱いなのか」を理解しているかの確認**です。
**数が少ないこと自体が、セキュリティ設計の結果**だと押さえておきます。

## 特殊パーミッションを棚卸しする

**意味** … 意図せず SUID / SGID が立っているファイルは、権限昇格の入口になります。
`find` の `-perm` オプションで定期的に洗い出します。

| 書き方 | 意味 |
|:--|:--|
| `-perm -4000` | SUID が立っているもの（`-` は「指定ビットをすべて含む」） |
| `-perm -2000` | SGID が立っているもの |
| `-perm -1000` | スティッキービットが立っているもの |
| `-perm /6000` | SUID **または** SGID が立っているもの（`/` は「いずれかを含む」） |

**例文**

```bash
$ find /usr/bin -perm -4000 2>/dev/null    # SUID が立っているコマンドを探す
/usr/bin/sudo
/usr/bin/gpasswd
/usr/bin/passwd
/usr/bin/chfn
/usr/bin/umount
/usr/bin/mount
/usr/bin/fusermount3
/usr/bin/newgrp
...

$ find / -perm -2000 -type d 2>/dev/null   # SGID ディレクトリだけに絞る
$ find / -perm /6000 -type f 2>/dev/null   # SUID か SGID のファイルを一括で洗い出す
```

**補足** … `2>/dev/null` は、権限がなくて読めないディレクトリのエラーメッセージを捨てるための指定です。
初回の結果を「正常な状態」として保存しておき、**次回との差分**を見るのが実務的な使い方です。

```bash
$ find / -perm /6000 -type f 2>/dev/null | sort > /var/log/suid_baseline.txt # 初回の一覧を基準として保存する
$ find / -perm /6000 -type f 2>/dev/null | sort | diff /var/log/suid_baseline.txt - # 次回以降は基準との差分を見る
```
