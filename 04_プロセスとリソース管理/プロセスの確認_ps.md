## まずこれだけ

| やりたいこと | コマンド |
|:--|:--|
| **全プロセスを詳しく見る（定番）** | **`ps aux`** |
| 全プロセスを親子つきで見る | `ps -ef` |
| CPU を食っている順に並べる | `ps aux --sort=-%cpu \| head` |
| メモリを食っている順に並べる | `ps aux --sort=-%mem \| head` |
| 特定のプロセスを探す | `ps aux \| grep nginx` |
| 自分の端末のプロセスだけ | `ps`（引数なし） |

**`ps` は「稼働中のプロセスおよび、プロセス毎の CPU やメモリの使用量を表示する」コマンド**です。

**最初に覚えるのは `ps aux` のこの3列**

| 列 | 見るポイント |
|:--|:--|
| **`%CPU`** | **CPU をどれだけ使っているか** |
| **`RSS`** | **実際に使っている物理メモリ（KB）** |
| **`STAT`** | **プロセスの状態**。`Z` があればゾンビ、`D` が続けば I/O 待ち |

## ps とは

**`ps`（process status）は、実行中のプロセスの一覧を表示するコマンド**です。

```bash
$ ps aux                             # すべてのプロセスを詳しく一覧する
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.2  0.0  20036  5312 ?        SLl  14:58   0:01 /sbin/init
root         2  0.0  0.0      0     0 ?        S    14:58   0:00 [kthreadd]
root         3  0.0  0.0      0     0 ?        S    14:58   0:00 [pool_workqueue_release]
```

**「プロセス」とは、いま動いているプログラム 1 つ 1 つ**のことです。
同じプログラムでも、2 回起動すれば 2 つのプロセスになります。

**重要な性質 … `ps` は「その瞬間」しか見せません**

```text
ps    … 写真（スナップショット）。実行した瞬間の状態だけ
top   … 動画。数秒ごとに更新され続ける
```

「いま重い」原因を追うなら `top`、
「この時点で何が動いていたか」を記録に残すなら `ps` という使い分けになります。

## 3種類のオプション書式

`ps` は歴史的な事情で、**書式が 3 系統**あります。ここが最初の関門です。

| 系統 | 書き方 | 例 | 特徴 |
|:--|:--|:--|:--|
| **BSD 形式** | **ハイフンなし** | **`ps aux`** | 最もよく使われる。`%CPU` `%MEM` `RSS` が出る |
| **UNIX（System V）形式** | **ハイフン 1 つ** | **`ps -ef`** | **親プロセス（PPID）** が出る |
| GNU 形式 | ハイフン 2 つ | `ps --sort=-%cpu` | 並べ替えなどの拡張 |

**同じ文字でもハイフンの有無で意味が変わります**

```bash
$ ps a                               # BSD形式の a … 他ユーザのプロセスも表示
$ ps -a                              # UNIX形式の -a … 端末に紐づくプロセスを表示
```

**混同を避ける実用的な結論**

- **`ps aux`** … いつもの一覧。この形で覚える
- **`ps -ef`** … 親子関係（PPID）を見たいときだけ

この 2 つを丸ごと暗記してしまうのが、実務でも試験でも近道です。

## よく使うオプション

### BSD 形式（ハイフンなし）

| オプション | 意味 |
|:--|:--|
| **`a`** | **他のユーザのプロセスも表示**する（自分以外も見る） |
| **`u`** | **ユーザ名や CPU / メモリ使用率を含む詳細形式**で表示する |
| **`x`** | **端末を持たないプロセスも表示**する（デーモンなど） |
| `f` | 親子関係をツリー（アスキーアート）で表示する |
| `w` | 表示を折り返す。`ww` で長いコマンド行も省略せず出す |

**`aux` はこの 3 つを重ねたもの**です。

```text
a … 全ユーザ    ┐
u … 詳細表示    ├─→ 「全ユーザの、端末を持たないものも含めた、詳細一覧」
x … 端末なしも  ┘
```

`x` を付けないと、**`sshd` や `nginx` のようなデーモンが表示されません**。
デーモンは端末（TTY）を持たずに動いているためです。

### UNIX 形式（ハイフンあり）

| オプション | 意味 |
|:--|:--|
| **`-e`** | **すべてのプロセスを表示**する（`-A` と同じ） |
| **`-f`** | **完全形式**で表示する（UID / PID / **PPID** / C / STIME / TTY / TIME / CMD） |
| `-l` | 長い形式で表示する（`PRI` `NI` などが増える） |
| `-u ユーザ名` | 指定ユーザのプロセスだけ表示する |
| `-p PID` | 指定した PID のプロセスだけ表示する |
| `-C コマンド名` | コマンド名で絞り込む（`grep` が要らない） |
| `--forest` | 親子関係をツリー表示する |

```bash
$ ps -ef                             # 全プロセスを完全形式で表示する
$ ps -u nginx                        # nginx ユーザのプロセスだけ
$ ps -C sshd                         # sshd という名前のプロセスだけ
$ ps -p 1234                         # PID 1234 だけ
```

### GNU 形式（ハイフン 2 つ）

| オプション | 意味 |
|:--|:--|
| **`--sort=キー`** | **並べ替える**。先頭に `-` を付けると降順（`-%cpu` = CPU 使用率の高い順） |
| **`-o 列名,...`** | **表示する列を自分で選ぶ** |
| `--forest` | ツリー表示 |
| `--no-headers` | 見出し行を出さない（スクリプト向け） |

```bash
$ ps aux --sort=-%cpu | head -5      # CPU 使用率の高い順に上位5件
$ ps aux --sort=-%mem | head -5      # メモリ使用率の高い順に上位5件
$ ps -eo pid,ppid,user,%cpu,%mem,comm --sort=-%cpu | head   # 列を選んで並べ替える
```

**`-o` で選べる主な列名**

| 列名 | 意味 |
|:--|:--|
| `pid` / `ppid` | プロセス ID / 親プロセス ID |
| `user` | 実行ユーザ |
| `%cpu` / `%mem` | CPU / メモリ使用率 |
| `rss` / `vsz` | 物理メモリ / 仮想メモリ |
| `stat` | 状態 |
| `etime` | 起動してからの経過時間 |
| `comm` | コマンド名だけ（引数なし） |
| `args` / `cmd` | 引数を含むコマンド行 |

## 結果画面の見方

### ps aux の列

```bash
$ ps aux                             # 詳細一覧を表示する
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.2  0.0  20036  5312 ?        SLl  14:58   0:01 /sbin/init
root         2  0.0  0.0      0     0 ?        S    14:58   0:00 [kthreadd]
test2     6167  0.0  0.2   4636  1368 pts/4    Ss   11:33   0:00 -bash
test2    12561 92.5  2.0  67328 10660 pts/4    R+   12:38   0:03 stress --vm 1
```

**11 列すべての意味**

| 列 | 何を表すか | 見るポイント |
|:--|:--|:--|
| **`USER`** | プロセスを実行しているユーザ名 | root で動くべきでないものが root なら要確認 |
| **`PID`** | **プロセス ID**。プロセスを識別する番号 | `kill` するときに使う |
| **`%CPU`** | **CPU 使用率（%）** | **100% を超えることがある**（後述） |
| **`%MEM`** | **物理メモリ全体に対する使用率（%）** | 合計が 100% に近いとメモリ逼迫 |
| **`VSZ`** | **仮想メモリのサイズ（KB）** | 大きくても実害がないことが多い |
| **`RSS`** | **実際に使っている物理メモリ（KB）** | **こちらが実質的なメモリ消費量** |
| **`TTY`** | 紐づいている端末 | **`?` は端末を持たない**＝デーモン |
| **`STAT`** | **プロセスの状態** | `Z`（ゾンビ）や `D`（I/O 待ち）に注目 |
| **`START`** | プロセスが起動した時刻 | 24時間以上前なら日付で表示される |
| **`TIME`** | **CPU を実際に使った累積時間** | 経過時間ではない。ここが伸びるものが CPU を食っている |
| **`COMMAND`** | 実行中のコマンド行 | **`[ ]` で囲まれているものはカーネルスレッド** |

**`%CPU` が 100% を超える理由**

`%CPU` は「**1 コアを 100% として**」計算されます。
4 コアのマシンで 4 コアすべてを使い切るプロセスは **400%** と表示されます。

```text
2コアのサーバで %CPU が 190% → ほぼ全コアを使い切っている
```

**`TIME` の読み方**

`0:03` は「**CPU を 3 秒間使った**」という意味で、「3 秒前に起動した」ではありません。
起動からの経過時間を見たいときは `etime` を使います。

```bash
$ ps -eo pid,etime,time,comm --sort=-time | head -5   # 経過時間とCPU時間を並べて見る
```

**`COMMAND` の `[ ]` は何か**

```bash
root         2  0.0  0.0      0     0 ?        S    14:58   0:00 [kthreadd]
```

角括弧つきの行は **カーネルスレッド**（カーネル自身が動かしている処理）です。
`VSZ` と `RSS` が 0 なのは、**ユーザ空間のメモリを使っていない**ためです。
**これらは `kill` してはいけません。**

### ps -ef の列

```bash
$ ps -ef                             # 完全形式で表示する
UID        PID  PPID  C STIME TTY          TIME CMD
root         1     0  0 14:58 ?        00:00:01 /sbin/init
root         2     0  0 14:58 ?        00:00:00 [kthreadd]
root         3     2  0 14:58 ?        00:00:00 [pool_workqueue_release]
```

| 列 | 何を表すか |
|:--|:--|
| `UID` | 実行ユーザ（`ps aux` の `USER` に相当） |
| `PID` | プロセス ID |
| **`PPID`** | **親プロセス ID**。`ps aux` には無い、この形式最大の利点 |
| `C` | CPU 使用率（整数）。精度が粗いので参考程度 |
| `STIME` | 起動時刻 |
| `TTY` | 端末 |
| `TIME` | CPU 累積時間 |
| `CMD` | コマンド行 |

**`PPID` が役に立つ場面**

「このプロセスは誰に起動されたのか」を辿れます。

```bash
$ ps -ef | grep java                 # 対象のプロセスを見つける
$ ps -p 5678 -o pid,ppid,comm        # その親を確認する
$ ps -p 1234 -o pid,ppid,comm        # さらに親をたどる
```

**`PPID` が `1` なら、親が死んで init（systemd）に引き取られた**という意味です。
デーモン化したプロセスは通常こうなります。

### STAT 欄の読み方

**`STAT` は 1 文字目が「状態」、2 文字目以降が「付加情報」**です。

**1文字目 … プロセスの状態**

| 記号 | 状態 | 意味 |
|:--|:--|:--|
| **`R`** | Running | **実行中、または実行待ち**（CPU を使いたがっている） |
| **`S`** | Sleeping | **待機中**（割り込み可能）。**通常のプロセスの大半はこれ** |
| **`D`** | Uninterruptible sleep | **I/O 待ち**（割り込み不可）。**続くとディスクが遅い兆候** |
| **`Z`** | Zombie | **ゾンビ**。終了したが親が回収していない |
| `T` | Stopped | 停止中（`Ctrl+Z` やデバッガで止められている） |
| `I` | Idle | アイドル状態のカーネルスレッド |

**2文字目以降 … 付加情報**

| 記号 | 意味 |
|:--|:--|
| **`s`** | **セッションリーダ**（そのセッションの親玉） |
| **`+`** | **フォアグラウンドで動いている** |
| `<` | 優先度が高い（nice 値がマイナス） |
| `N` | 優先度が低い（nice 値がプラス） |
| `l` | マルチスレッド |
| `L` | メモリ上にページがロックされている |

**読み方の例**

```text
Ss   … S（待機中）＋ s（セッションリーダ）      → 普通のデーモン
R+   … R（実行中）＋ +（フォアグラウンド）      → いま画面で動いているコマンド
D    … I/O 待ち                                 → ディスク or ネットワークが詰まっている疑い
Z    … ゾンビ                                   → 親プロセスの作りが悪い
SLl  … S ＋ L（メモリロック）＋ l（マルチスレッド）
```

**障害調査でまず探すのは `D` と `Z`**

```bash
$ ps aux | awk '$8 ~ /^D/ {print}'   # I/O 待ちのプロセスを抜き出す
$ ps aux | awk '$8 ~ /^Z/ {print}'   # ゾンビプロセスを抜き出す
```

**ゾンビは `kill` できません。** すでに死んでいるためです。
消すには**親プロセスを終了させる**（親が死ぬと init が回収する）必要があります。

### VSZ と RSS の違い

ここは実務で最も誤解されやすい 2 列です。

| | **VSZ**（Virtual Size） | **RSS**（Resident Set Size） |
|:--|:--|:--|
| 何のサイズか | **確保を「予約」した仮想メモリ全体** | **実際に物理メモリ上にあるサイズ** |
| 実メモリを使っているか | **使っていない分も含む** | **使っている分だけ** |
| 共有ライブラリ | 含む | **含む（複数プロセスで二重に数えられる）** |
| 単位 | KB | KB |
| **障害調査で見るべきなのは** | | **こちら** |

**なぜ VSZ は大きくなるのか**

プログラムは「あとで使うかもしれない領域」をあらかじめ予約します。
Java や Go のランタイムは特に大きく予約するため、
**VSZ が数 GB でも RSS は数百 MB**ということが普通に起きます。

```bash
$ ps -eo pid,vsz,rss,comm --sort=-rss | head -5   # RSS の大きい順に並べる
    PID    VSZ    RSS COMMAND
  12561  67328  10660 stress
```

**「メモリを食っている」の判断は RSS で行います。**

**注意 … RSS を単純に足し算しても実使用量にはなりません**

共有ライブラリは複数のプロセスで共有されていますが、**RSS はそれぞれに計上**されます。
そのため全プロセスの RSS を合計すると、実際の物理メモリより大きくなります。
システム全体のメモリは `free` で見ます（[リソース監視 システム全体](./リソース監視_システム全体.md) 参照）。

## 引数なしで実行した場合

```bash
$ ps                                 # オプションなしで実行する
  PID TTY          TIME CMD
 1604 pts/0    00:00:00 bash
 1610 pts/0    00:00:00 ps
```

**表示されるのは「自分が、いまの端末で動かしているプロセス」だけ**です。
列も 4 つに絞られます。

| 列 | 意味 |
|:--|:--|
| `PID` | プロセス ID |
| `TTY` | 端末 |
| `TIME` | CPU 累積時間 |
| `CMD` | コマンド名 |

**`ps` に自分自身（`ps` コマンド）が写り込んでいる**点にも注目してください。
`ps` を実行した瞬間、`ps` もプロセスとして存在しているためです。

## 実務で使う組み合わせ

### CPU を食っているプロセスを特定する

```bash
$ ps aux --sort=-%cpu | head -6      # CPU 使用率の高い順に上位5件（+見出し1行）
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
test2    12561 92.5  2.0  67328 10660 pts/4    R+   12:38   0:03 stress --vm 1
```

### メモリを食っているプロセスを特定する

```bash
$ ps aux --sort=-%mem | head -6      # メモリ使用率の高い順に上位5件
```

**この 2 つが「サーバが重い」ときの最初のコマンド**です。

### grep で探すときの定番

```bash
$ ps aux | grep nginx                # nginx を含む行を探す
root      1234  0.0  0.1  55000  4000 ?  Ss  09:00  0:00 nginx: master process
root      1250  0.0  0.0  12000  1200 pts/0 S+ 12:00 0:00 grep --color=auto nginx
                                                          ↑ grep 自身が写り込む
```

**`grep` 自身が必ず引っかかります。** 除くには次のどちらかを使います。

```bash
$ ps aux | grep [n]ginx              # 先頭1文字を [] で囲む（grep 自身にマッチしなくなる）
$ pgrep -a nginx                     # そもそも pgrep を使う（こちらが確実）
```

**`[n]ginx` が効く理由** … `grep` のプロセス行には `[n]ginx` という文字列が入りますが、
検索パターン `[n]ginx` は「n という文字 + ginx」を意味するので、
`[n]ginx` という文字列そのものにはマッチしません。

### 特定ユーザ・特定コマンドで絞る

```bash
$ ps -u nginx -o pid,%cpu,%mem,rss,comm    # nginx ユーザのプロセスを列を選んで表示
$ ps -C java -o pid,rss,etime,args         # java プロセスの経過時間とコマンド行
```

### ツリーで親子関係を見る

```bash
$ ps -ef --forest | head -20         # 親子関係をツリー表示する
$ ps auxf | head -20                 # BSD形式でも f でツリーになる
```

「どのプロセスが誰から起動されたか」を追うときに使います。

## 似たコマンドとの使い分け

| コマンド | 何を見るか | 更新 |
|:--|:--|:--|
| **`ps`** | **プロセス一覧のスナップショット** | しない |
| `pgrep` | 条件に合うプロセスの **PID だけ** | しない |
| `pstree` | 親子関係を**ツリー**で | しない |
| **`top`** | プロセス一覧＋全体の状況 | **する** |
| `htop` | `top` の見やすい版 | する |

```bash
$ pgrep -a sshd                      # sshd の PID とコマンド行を出す
$ pgrep -u nginx                     # nginx ユーザのプロセスの PID を列挙する
$ pstree -p                          # 親子関係を PID つきのツリーで見る
```

`top` / `htop` については [リソース監視 プロセス単位](./リソース監視_プロセス単位.md) を参照してください。

## 手を動かして確かめる

**1. 自分の端末のプロセスを見る**

```bash
$ ps                                 # まず引数なしで実行する
  PID TTY          TIME CMD
 1604 pts/0    00:00:00 bash
 1610 pts/0    00:00:00 ps
```

**2. `aux` を付けて全体を見る**

```bash
$ ps aux | head -5                   # 全プロセスの先頭5行を見る
```

**引数なしのときと列が変わったこと**を確認してください。

**3. わざと CPU を使うプロセスを作って観察する**

```bash
$ yes > /dev/null &                  # CPU を使い続けるプロセスを裏で動かす
[1] 2001
$ ps aux --sort=-%cpu | head -3      # CPU 使用率の高い順に見る
USER       PID %CPU %MEM    VSZ   RSS TTY   STAT START   TIME COMMAND
root      2001 99.0  0.0   6892   856 pts/0 R    15:10   0:05 yes
```

`STAT` が **`R`（実行中）** になっていること、`%CPU` がほぼ 100 であることを確認します。

**4. 止めて状態の変化を見る**

```bash
$ kill %1                            # ジョブ番号1のプロセスを終了させる
$ ps aux | grep yes                  # もう存在しない
```

**5. `TIME` と `etime` の違いを確認する**

```bash
$ ps -eo pid,etime,time,comm --sort=-time | head -5   # 経過時間とCPU時間を並べる
    PID     ELAPSED     TIME COMMAND
    476    01:20:15 00:00:27 claude
```

`ELAPSED`（起動からの経過時間）と `TIME`（CPU を使った時間）が
**まったく違う値**であることが分かります。

## つまずきポイント

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| デーモンが一覧に出てこない | `x` を付けていない | `ps aux` のように `x` を含める |
| `%CPU` が 100% を超えている | **1 コアを 100% として計算**するため | コア数で割って解釈する |
| `VSZ` が巨大で驚く | 予約しただけで実使用ではない | **`RSS` を見る** |
| `RSS` を合計したら物理メモリを超えた | 共有ライブラリが二重計上される | 全体は `free` で見る |
| `grep` 自身が結果に出る | `grep` もプロセスだから | `pgrep` を使うか `grep [n]ginx` |
| ゾンビが `kill` できない | すでに終了しているプロセスだから | **親プロセス**を終了させる |
| `TIME` が短いのに重い | `TIME` は CPU 時間で、経過時間ではない | `etime` を併せて見る |
| `[ ]` 付きのプロセスが大量にある | カーネルスレッド | **正常。kill しない** |
| コマンド行が途中で切れる | 端末幅で省略されている | `ps auxww` または `-o args` |

## クラウド実務メモ

**EC2 が「重い」ときの初動 3 コマンド**

```bash
$ uptime                             # ① ロードアベレージで全体の混み具合を見る
$ ps aux --sort=-%cpu | head -6      # ② CPU を食っているプロセスを特定する
$ ps aux --sort=-%mem | head -6      # ③ メモリを食っているプロセスを特定する
```

この 3 つで**「CPU が原因か、メモリが原因か」**の切り分けまで終わります。
そこから先は [リソース監視 システム全体](./リソース監視_システム全体.md) の `vmstat` に進みます。

**`%steal` が高いときは `ps` では分かりません**

`ps` に写るのは「このインスタンスの中の話」だけです。
**ハイパーバイザ側でCPUを奪われている**（`steal`）状況は、
`vmstat` や `sar -u` の `st` 列でしか見えません。
T 系インスタンスの**CPU クレジット枯渇**もここに現れます。

**OOM Killer に殺されたプロセスを追う**

メモリ不足でプロセスが消えたときは、`ps` にはもう写りません。

```bash
$ sudo dmesg | grep -i "killed process"        # OOM で殺された記録を探す
$ sudo journalctl -k | grep -i "out of memory" # systemd 環境ではこちらでも
```

**コンテナの中では PID が別世界になります**

```bash
$ docker exec -it web ps aux         # コンテナ内の PID 名前空間で見える一覧
$ ps aux | grep nginx                # ホスト側から見ると PID が異なる
```

コンテナ内の PID 1 は、ホストから見ると別の番号です。
**ホスト側で `kill` するときは、ホスト側の PID を使う**必要があります。

**監視で拾うべき指標**

| 指標 | 取り方 |
|:--|:--|
| ゾンビプロセス数 | `ps aux \| awk '$8 ~ /^Z/' \| wc -l` |
| 特定プロセスの生存 | `pgrep -c nginx`（0 なら落ちている） |
| プロセスごとのメモリ | CloudWatch エージェントの `procstat` プラグイン |

CloudWatch の標準メトリクスには**プロセス単位の情報がありません**。
必要なら CloudWatch エージェントの `procstat` を設定します。
